定義面拆解 (a)–(n)

(a) 定義本體：函式庫是「被動的程式碼集合」

  • 一堆寫好的函式、類別、常數的打包集合。
  • 沒有自己的生命週期，不會自己啟動。
  • 你不呼叫，它永遠不執行任何一行。
  • 例：Lodash、Day.js、Axios、NumPy、Requests。

(b) 定義本體：框架是「主動的半成品應用程式」

  • 不只給函式，還給整個執行流程與目錄結構。
  • 它自己就是一個能跑起來的殼，你往預留的洞裡塞東西。
  • 你的程式碼是被插入的零件，不是主體。
  • 例：Django、Spring、Angular、Ruby on Rails。

(c) 控制反轉 IoC：定義上最硬的分界線

  • IoC 指「自訂程式碼的控制流由外部來源（框架）接手」。
  • 程序式寫法：你呼叫函式庫處理雜事，控制權從頭到尾在你身上。
  • 用框架：是框架在控制，由框架回頭呼叫你寫的程式碼。
  • 判斷法：有沒有發生控制反轉，就是最可靠的那一刀。

(d) 好萊塢原則 Hollywood Principle

  • 原句：Don't call us, we'll call you（別打給我們，我們會打給你）。
  • 函式庫 = 你打電話給它。
  • 框架 = 你留下電話（註冊 callback、實作介面、寫進指定檔名），它需要時打給你。

(e) 定義測試一：「誰擁有 main 函式」

  • 函式庫情境：main、index.js、if __name__ == "__main__" 在你的檔案裡。
  • 框架情境：進入點是框架的 CLI 或 runtime（django-admin runserver、ng serve），你根本沒寫 main。
  • 最快可驗證的判定法：打開專案，看進入點在誰家。

(f) 定義測試二：「誰決定檔案放哪」

  • 函式庫不管你資料夾怎麼擺，import 進來就好。
  • 框架會規定慣例：Django 的 models.py views.py urls.py、Rails 的 app/controllers。
  • 這叫 convention over configuration（慣例優於設定），是框架獨有的權力。

(g) 擴充點的形狀不同

面向函式庫框架
你如何介入直接呼叫它提供的 API透過預留的 hook、callback、生命週期方法、抽象類別
介入時機你想呼叫就呼叫只能在框架允許的時間點（componentDidMount、middleware）
自由度高被擴充點限制

(h) 框架核心通常不可修改

  • 框架核心邏輯一般固定，只允許擴充、不允許修改框架本身。
  • 函式庫沒有這層約束，理論上 fork 一份改掉也能用。

(i) 涵蓋範圍：單一職責 vs 全流程

  • 函式庫通常解決一個問題：日期格式化、HTTP 請求、數值運算。
  • 框架解決一整條產品線：路由、資料庫存取、樣板渲染、認證、部署慣例全包。
  • 所以框架常常「內含」很多函式庫，反過來不成立。

(j) 一個專案可以有 N 個函式庫，但通常只有 1 個框架

  • 函式庫可疊加：前端專案同時裝 20 個 npm 套件很正常。
  • 框架彼此排斥：因為控制權只有一份。
  • 所以選框架是架構決策，選函式庫只是實作決策。

(k) 抽換成本的量級差異

  • 換函式庫：moment.js 換成 day.js，改幾十處呼叫，通常一天內完成。
  • 換框架：Angular 換 React 等於整個專案重寫，連檔案結構、生命週期、狀態流都不同。
  • 面試講這點，比背定義更能顯示真的理解。

(l) 灰色地帶：同一個東西可能兩者皆是

  • React：官方自稱 library，但它掌管 render 流程並在特定時機呼叫你的 component，實務上已有框架味道；搭配 Next.js 後才是完整框架。
  • Express：app.get() 是你註冊 handler，Express 收到請求時回頭呼叫你 → 典型控制反轉，多數人歸類為輕量框架。
  • 結論：不是二分法，是一條光譜，座標軸就是控制權被讓渡了多少。

(m) 常見誤解澄清

誤解修正
程式碼比較多的就是框架判準是控制權不是體積。Express 很輕卻是框架，TensorFlow 很肥卻是函式庫。
有 CLI 工具就是框架CLI 只是附帶物，判準仍是執行時誰呼叫誰。
框架比函式庫高級兩者是不同層次的工具，框架用自由度換開發速度與一致性。
IoC 就是 DIDI（Dependency Injection，依賴注入）是實現 IoC 的其中一種手法，IoC 範圍更大。

(n) 面試一句話版本

函式庫是我呼叫它，框架是它呼叫我。差別在控制權的方向，這個現象叫控制反轉 IoC，口號是好萊塢原則。實務影響是函式庫可疊加、可低成本抽換，框架一個專案只能有一個、抽換等於重寫。

程式碼範例（同資料夾 框架-vs-函式庫-demo.js）

// A. 函式庫風格：我呼叫它（控制權在我）
const dateLib = { format: (d) => d.toISOString().slice(0, 10) };
console.log(dateLib.format(new Date()));   // 不寫這行，它永遠不跑

// B. 框架風格：它呼叫我（控制權讓渡）
const miniFramework = {
  routes: {},
  get(path, handler) { this.routes[path] = handler; },   // 我只「註冊」
  run() {                                                 // 框架的生命週期
    for (const p of Object.keys(this.routes)) {
      this.routes[p]({ path: p }, { send: (b) => console.log(p, b) });
    }                                                     // ↑ 框架回頭呼叫我
  },
};
miniFramework.get('/hello', (req, res) => res.send('我是被框架呼叫的'));
miniFramework.run();   // 我沒寫任何「執行 handler」的程式碼

實際輸出（已驗證）：

[Library] 我主動呼叫： 2026-08-06
[Framework] 框架啟動，開始接收請求
[Framework] 回應 /hello：我是被框架呼叫的，不是我自己跑的

是非題（自我檢測）

1. 判斷框架或函式庫，主要看程式碼的體積大小。
✗ 錯。判準是控制權方向，不是體積。Express 很輕但是框架，TensorFlow 很肥但是函式庫。對應重點 (m)。
2. 用了框架後，程式的進入點 main 通常不在你自己寫的檔案裡。
✓ 對。框架自帶 runtime／CLI 當進入點，你只提供被呼叫的零件。對應重點 (e)。
3. 一個專案同時使用兩個主要框架，是很常見且合理的做法。
✗ 錯。控制權只有一份，框架彼此排斥。函式庫才可以疊加 N 個。對應重點 (j)。
4. IoC（控制反轉）和 DI（依賴注入）是同一件事的兩種說法。
✗ 錯。DI 是實現 IoC 的其中一種手法，IoC 的範圍更大（還包含樣板方法、事件驅動等）。對應重點 (m)。
5. 好萊塢原則「Don't call us, we'll call you」描述的是框架的行為，不是函式庫的行為。
✓ 對。函式庫是你打給它，框架是它打給你。對應重點 (d)。

申論題（先自己寫，再看參考答案）

Q1. 面試官問：「React 到底是框架還是函式庫？」請說明你的判斷與理由。
參考方向：先給判準再給結論。判準是控制權方向（IoC）。React 官方自稱 library，但 render 流程由 React 掌管、你的 component 是被 React 呼叫的，這已具備控制反轉特徵；然而它不管路由、不管資料層、不規定目錄結構，覆蓋範圍遠小於 Django／Angular。所以最好的答案是：React 在光譜上偏中間，是「掌管 UI 渲染流程的函式庫」，加上 Next.js 才構成完整框架。加分點：指出框架與函式庫不是二分法而是光譜。對應重點 (l)。
Q2. 為什麼說「選框架是架構決策，選函式庫只是實作決策」？請從抽換成本說明。
參考方向：函式庫只被你的程式呼叫，耦合點是呼叫處，抽換時只要改那些呼叫（甚至可用 adapter 包一層讓抽換成本趨近零）。框架則反過來持有你的程式，耦合點是整個專案的結構、生命週期、狀態流，抽換等於重寫，而且無法漸進式進行。因此框架的選擇會鎖死團隊未來數年的技術路徑，屬於架構層級決策；函式庫則可隨時汰換，屬實作細節。對應重點 (j)(k)。
Q3. 用「誰擁有 main」和「誰決定檔案放哪」兩個測試，判斷你手上的專案用的是框架還是函式庫，並寫出你的驗證步驟。
參考方向：步驟①打開 package.json 或啟動指令，看啟動的是自己的 index.js 還是框架 CLI（vite、django-admin、uvicorn）；步驟②看目錄結構是自己決定的，還是被慣例規定的（models.py／routes/／app/controllers）；步驟③看你的核心邏輯是「主動呼叫別人」還是「註冊後等別人呼叫」。三個測試同向指向框架，就可以確定是框架。對應重點 (e)(f)。
