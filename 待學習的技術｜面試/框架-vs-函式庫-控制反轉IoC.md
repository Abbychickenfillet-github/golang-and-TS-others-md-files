# 框架 Framework 與函式庫 Library 的定義差異：控制反轉 IoC

> 本篇重點 (a)–(n)，共 14 個。
> 名詞先攤開：**IoC（Inversion of Control，控制反轉）**、**API（Application Programming Interface，應用程式介面）**、**DI（Dependency Injection，依賴注入）**。

## 一句話定義（先看這張表）

| 項目 | 函式庫 Library | 框架 Framework |
|---|---|---|
| 定義 | 一組可被呼叫的可重用程式碼集合 | 一套已經寫好流程骨架、預留擴充點讓你填空的半成品應用程式 |
| 誰在主導流程 | 你的程式 | 框架本身 |
| 呼叫方向 | 你的程式 → 呼叫 → 函式庫 | 框架 → 呼叫 → 你的程式 |
| 主程式 main 在誰手上 | 你手上 | 框架手上 |
| 心智模型 | 工具箱裡的一把螺絲起子 | 已經蓋好樑柱的房子毛胚屋 |
| 抽換成本 | 低，換掉一個呼叫即可 | 高，等於整間房打掉重蓋 |

判斷關鍵只有一句：**控制權在誰手上**。這就是 [[控制反轉-IoC]] 這個詞被發明出來的理由。

---

## 定義面拆解

### (a) 定義本體：函式庫是「被動的程式碼集合」

- 函式庫是一堆已經寫好的函式、類別、常數的打包集合。
- 它沒有自己的生命週期，不會自己啟動、不會自己跑。
- 你不呼叫它，它就永遠不會執行任何一行程式碼。
- 例：Lodash、Day.js、Axios、NumPy、Requests。

### (b) 定義本體：框架是「主動的半成品應用程式」

- 框架不只給你函式，它給你**整個程式的執行流程**與**目錄結構**。
- 它自己就是一個可以跑起來的殼，你只是往它預留的洞裡塞東西。
- 你的程式碼是「被插入」的零件，不是主體。
- 例：Django、Spring、Angular、Ruby on Rails、Express（路由層面）。

### (c) 控制反轉 IoC：定義上最硬的分界線

- Wikipedia 的定義：IoC 指「自訂程式碼的控制流由外部來源（例如框架）接手」。
- 傳統程序式寫法：你的程式呼叫函式庫處理雜事，**控制權從頭到尾在你身上**。
- 用了框架：**是框架在控制，由框架來呼叫你寫的程式碼**。
- 所以「有沒有發生控制反轉」是定義上判斷框架與函式庫最可靠的一刀。

### (d) 好萊塢原則 Hollywood Principle

- 原句：Don't call us, we'll call you（別打給我們，我們會打給你）。
- 這是 IoC 的口語版本，也是框架的行為特徵。
- 函式庫 = 你打電話給它。
- 框架 = 你留下電話（註冊 callback、實作介面、寫進指定檔名），它需要時打給你。

### (e) 「誰擁有 main 函式」這個定義測試

- 函式庫情境：`main`、`index.js`、`if __name__ == "__main__"` 在**你的**檔案裡。
- 框架情境：進入點是框架的 CLI 或 runtime（例如 `django-admin runserver`、`ng serve`），你根本沒寫 main。
- 這是最快速可驗證的判定法：**打開專案，找進入點在誰家**。

### (f) 「誰決定檔案要放哪」這個定義測試

- 函式庫不管你的資料夾怎麼擺，你 import 進來就好。
- 框架會規定慣例：Django 的 `models.py` `views.py` `urls.py`、Rails 的 `app/controllers`。
- 這叫 **convention over configuration（慣例優於設定）**，是框架獨有的權力。

### (g) 擴充點的形狀不同

| 面向 | 函式庫 | 框架 |
|---|---|---|
| 你如何介入 | 直接呼叫它提供的 API | 透過框架預留的 hook、callback、生命週期方法、抽象類別 |
| 介入時機 | 你想呼叫就呼叫 | 只能在框架允許的時間點（例如 componentDidMount、middleware） |
| 自由度 | 高 | 被框架的擴充點限制 |

### (h) 框架核心通常不可修改

- Wikipedia 的 software framework 條目點出：框架的核心邏輯一般是固定的，只允許擴充、不允許修改框架本身。
- 函式庫則沒有這層約束，理論上你 fork 一份改掉也能用。

### (i) 涵蓋範圍：單一職責 vs 全流程

- 函式庫通常解決**一個問題**：日期格式化、HTTP 請求、數值運算。
- 框架解決**一整條產品線**：路由、資料庫存取、樣板渲染、認證、部署慣例全包。
- 所以框架常常「內含」很多函式庫，反過來不成立。

### (j) 一個專案可以有 N 個函式庫，但通常只有 1 個框架

- 函式庫可以疊加：一個前端專案同時裝 20 個 npm 套件很正常。
- 框架彼此排斥：Django 跟 Rails 不可能同時主導同一個進入點，因為控制權只有一份。
- 這也解釋了為什麼**選框架是架構決策，選函式庫只是實作決策**。

### (k) 抽換成本的量級差異

- 換函式庫：把 `moment.js` 換成 `day.js`，改幾十處呼叫，通常一天內完成。
- 換框架：Angular 換 React，等於整個專案重寫，因為連檔案結構、生命週期、狀態流都不一樣。
- 面試時講這一點，比背定義更能顯示你真的理解差別。

### (l) 灰色地帶：同一個東西可能兩者皆是

- **React**：官方文件自稱 library（函式庫），但它掌管 render 流程並在特定時機呼叫你的 component 函式，實務上已經有框架的味道。搭配 Next.js 後才是完整框架。
- **Express**：`app.get()` 的寫法是你在註冊 handler，然後 Express 收到請求時回頭呼叫你，這是典型的控制反轉，所以多數人歸類為輕量框架。
- 結論：**框架與函式庫不是二分法，是一條光譜，座標軸就是控制權被讓渡了多少**。

### (m) 常見誤解澄清

| 誤解 | 修正 |
|---|---|
| 「程式碼比較多的就是框架」 | 錯，判準是控制權，不是體積。有些框架非常輕（Express），有些函式庫非常肥（TensorFlow）。 |
| 「有 CLI 工具就是框架」 | 錯，CLI 只是附帶物。判準仍是執行時誰呼叫誰。 |
| 「框架比函式庫高級」 | 錯，兩者是不同層次的工具，框架用自由度換開發速度與一致性。 |
| 「IoC 就是 DI」 | 錯，DI（Dependency Injection，依賴注入）是實現 IoC 的其中一種手法，IoC 範圍更大。 |

### (n) 面試一句話版本

> 函式庫是我呼叫它，框架是它呼叫我。差別在控制權的方向，這個現象叫控制反轉 IoC，口號是好萊塢原則 Don't call us, we'll call you。實務影響是函式庫可疊加、可低成本抽換，框架一個專案只能有一個、抽換等於重寫。
