# Day 15｜三個路由，各自複製了一份 email 正規化

> 純 Markdown，可直接貼到 iThome。

昨天（Day14）講過度設計——想太多、抽象搭太早。今天講的是完全相反的極端：**什麼都不設計，需要什麼就複製貼上一份**。

這兩篇是一組對照：過度設計的成本是「人要多讀幾個檔案」，缺乏設計的成本是**更危險的東西——同一段邏輯，在不同地方悄悄長出不一樣的行為**。

---

## 一、重構前

需求：註冊、登入、重設密碼三個 API，都需要把使用者輸入的 email 正規化（去頭尾空白、轉小寫）再拿去查資料庫。

```js
// app/register/route.js
function registerEmailNormalize(email) {
  return email.trim().toLowerCase()
}

// app/login/route.js —— 複製貼上時，覺得「應該用不到 trim」順手拿掉了
function loginEmailNormalize(email) {
  return email.toLowerCase()
}

// app/reset-password/route.js —— 又複製了一次，這次連大小寫都忘記統一
function resetPasswordEmailNormalize(email) {
  return email.trim()
}
```

三段程式碼**各自看起來都合理**，個別測試也都會過。問題出現在**它們被複製了三次，卻沒有人同步維護三份的一致性**。

---

## 二、成本一：同一個輸入，三處給出三種答案

實測同一個原始輸入 `" User@Example.com "`（前後帶空白，這是使用者從信箱複製貼上時很常見的情況）：

| 路由 | 正規化結果 |
|---|---|
| register | `"user@example.com"` |
| login | `" user@example.com "` |
| resetPassword | `"User@Example.com"` |

**三個結果完全不一樣。** 這就是**行為漂移（Behavior Drift）**——同一段邏輯的三份拷貝，隨著各自被修改，慢慢長出不同的行為，而且**沒有任何一份是「錯的」**：每一份單獨看都能通過自己的單元測試。

## 三、成本二：實測一次真實的 bug——註冊成功，登入卻失敗

用一個假資料庫模擬完整流程：

```
註冊結果： { status: 'success', storedKey: 'user@example.com' }
登入結果： { status: 'error', message: '帳號不存在' }
```

**同一個人、同一組帳密**，註冊時用的 key 是 `trim + lowercase` 後的 `user@example.com`，登入時用的 key 卻只做了 `lowercase`（帶著頭尾空白），兩個 key 對不上，資料庫查不到使用者。

這種 bug 最讓人抓狂的地方在於：**你去看 register 的程式碼，邏輯完全正確；去看 login 的程式碼，邏輯也完全正確（單獨看的話）。** 沒有人會第一時間想到「問題出在兩份幾乎一樣的正規化函式，悄悄不一樣了」。

## 四、成本三：規則要改一次，複製貼上版要記得改幾個地方

假設現在要多加一條規則：正規化時要順便把全形空白也清掉。

| | 要改的地方 |
|---|---|
| 複製貼上版 | `registerEmailNormalize`、`loginEmailNormalize`、`resetPasswordEmailNormalize`，**共 3 處**，而且已經證明很容易漏改 |
| 共用函式版 | `normalizeEmail`，**共 1 處**，三個路由自動一起生效 |

---

## 五、重構後

```js
// lib/normalize-email.js
export function normalizeEmail(email) {
  return email.trim().toLowerCase()
}

// 三個路由都改成呼叫它
import { normalizeEmail } from '@/lib/normalize-email'
const key = normalizeEmail(rawEmail)
```

修好之後重跑一樣的情境：

```
修好之後的登入結果： { status: 'success' }
```

行為漂移消失了，因為**只有一份定義，不可能出現「兩份不一樣」的狀態**。

---

## 六、我一開始想錯的兩個地方

### 疑問一：這不就是 DRY 嗎？跟後面要講的 DRY 那篇不會重複嗎？

不一樣，而且是更早、更根本的問題。**DRY（Don't Repeat Yourself）談的是「兩段看起來重複的程式碼，該不該合併」的判斷**——這個判斷本身有陷阱，兩段程式碼長得像，不代表它們代表同一個業務概念，硬合併反而可能製造新的耦合（這是後面 DRY 那篇要細講的）。

今天這篇更前面一步：**這三份 email 正規化，一開始就是同一個概念、同一條業務規則**，不是「看起來像」，是「本來就是同一件事」被複製了三次。這種情況根本不需要猶豫「該不該合併」——一開始就該只寫一次。

**判準是**：如果兩段程式碼代表的是同一個業務規則，複製貼上不是「風格選擇」，是缺陷。DRY 面對的是更曖昧的中間地帶。

### 疑問二：那是不是任何時候複製貼上都不行？

不是。極早期的 prototype、驗證 idea 階段，先求有、不追求設計，是合理的策略——這跟 YAGNI 的精神一致：不確定需求會不會定型，過早抽象反而卡住迭代速度。

**真正變成問題的時間點，是「同一段邏輯第二次被複製」而沒有人停下來想一下。** 第一次複製可以是巧合，第二次通常已經是模式了。

---

## 七、什麼時候複製貼上沒問題

**a. 真的是一次性腳本，不會進 production**
資料遷移用的一次性腳本、debug 用的臨時工具，複製貼上省下的時間比維護成本更划算。

**b. 兩段程式碼現在長得像，但代表完全不同的業務概念**
例如「訂單編號格式化」跟「發票編號格式化」剛好都是「補零到 8 位」，這是巧合相似，不是同一條業務規則——合併它們反而會在未來兩者格式各自演化時製造不必要的耦合。這個判準明天（Day16）會延伸。

**c. 團隊還在探索需求，需求本身還沒定型**
過早抽出共用函式，之後需求分岔時反而要拆開，拆的成本可能比當初沒抽象還高。

---

## 八、今天的判斷標準

看到「這段邏輯我複製一份改一改就好」的念頭時，先問自己：

> **「我複製的這段，代表的是同一條業務規則，還是剛好長得像？」**

| 判斷 | 建議 |
|---|---|
| 同一條業務規則的第 2 次複製 | 抽出共用函式，現在就做 |
| 長得像但代表不同概念 | 可以先不合併，等 Day16／DRY 那篇的判準 |
| 一次性腳本、不進 production | 複製貼上沒問題 |
| 需求還在探索、頻繁變動 | 先不要抽象，等定型 |

## 九、跟前面 Day 串起來

| | Day14 過度設計 | Day15 缺乏設計 |
|---|---|---|
| 極端 | 想太多，先搭好抽象 | 完全不想，複製貼上 |
| 代價 | 人要多讀幾個檔案 | 行為悄悄漂移，同一條規則變出好幾種版本 |
| 共同點 | 兩者都是「沒有隨著需求現況做出對應設計」 | 同左 |

過度設計和缺乏設計，看起來是兩個相反的錯誤，但**共同的病根是一樣的：沒有根據「需求現在實際長什麼樣子」做設計**，一個是設計得比現況多，一個是設計得比現況少。
