🧠 自我測驗

是非題

  1. Captive Portal 為了強制你看到登入頁而做的事，技術上就是中間人攻擊。

    它劫持你的請求、回傳自己的自簽憑證，這正是 MITM 的特徵。所以 SonarLint 才會誤判。

  2. 在咖啡廳遇到憑證警告時，點 Trust 比較省事而且沒什麼風險。

    絕對不要。點下去等於把攔截憑證存進信任庫，之後這條連線對持有私鑰的人就是明文。

  3. 登入 Wi-Fi 之後警告消失，是因為路由器把你的 MAC 加進允許名單、停止劫持了。

    流量直接放行到真正的網際網路，SonarLint 就拿得到正確憑證。

  4. 自簽憑證是由公信的憑證機構 CA 簽發的。

    正好相反，是自己簽自己的，所以瀏覽器與程式預設不信任。

  5. 如果網路完全正常、也沒有 Captive Portal，憑證警告卻一直跳，可以先忽略它。

    這種情況要認真對待。換個網路再試，還是有的話就該查了。

  6. 作業系統本身有偵測 Captive Portal 的機制。

    Windows 的 NCSI、Android 的 connectivitycheck.gstatic.com、Apple 的 captive.apple.com，靠打特定網址看回應對不對來判斷。

填空題

  1. 公共 Wi-Fi 那個「同意條款才能上網」的登入頁，英文叫 Portal。

    中文譯強制網路門戶或強制入口網頁。RFC 8952 定義其架構。

  2. 有人站在你和伺服器中間攔截竄改通訊，縮寫 MITM，全名 Man-In-The-。

    中間人攻擊。

  3. 由自己簽發、非公信 CA 簽發的憑證，叫做 憑證。

    Self-signed Certificate，預設不被信任。

  4. 路由器停止劫持你的流量，是因為把你的 位址加進了允許名單。

    Allowlist。

  5. 判斷法則：警告在完成 Wi-Fi 登入後就消失 → 誤判；網路正常卻持續出現 → 要 。

    這條是整篇最該記住的東西。

申論題

  1. 在咖啡廳寫扣時 IDE 跳出「不可信的伺服器憑證」。請完整說明：這件事的技術成因、為什麼它跟真正的中間人攻擊在技術上難以區分、你會怎麼處理、以及你憑什麼判斷這次是誤判而不是真的被攻擊。

    參考方向：(1) 成因——公共 Wi-Fi 的 Captive Portal 為了強制你看到登入頁，會把尚未認證的裝置所有請求劫持到自家認證頁。IDE 的外掛（如 SonarLint）在背景發 HTTPS 請求時被 AP 攔下，AP 回傳的是自己的自簽憑證（憑發者顯示為該設備廠商，例如 Ruckus Wireless Inc.），而不是外掛預期的伺服器憑證。憑證上的網域跟要連的網域對不上，TLS 驗證失敗，於是跳警告。(2) 為什麼難區分——因為它們做的是同一件事。真正的 MITM 也是插在中間、也是回傳自己的憑證。差別只在動機（一個是要你登入，一個是要偷資料），而動機在技術層面看不出來。這就是為什麼 TLS 的設計是「憑證對不上就一律報錯」，把判斷權交給人。(3) 處理——點 Don't trust 或 Cancel，開瀏覽器把 Wi-Fi 登入流程走完，警告自然消失。絕對不在外部網路點 Trust，那等於把攔截憑證存進信任庫。實務習慣是連上公共 Wi-Fi 後先開瀏覽器完成登入，再開 IDE 或跑 npm install，可以避開一整批莫名其妙的連線錯誤。(4) 判斷依據——關鍵證據是「完成 Wi-Fi 登入後警告就消失」。若是真的攻擊，攻擊者沒有理由在你登入 Captive Portal 之後就收手。另外可以檢查憑證的簽發者是不是該場所的網路設備廠商、以及是否只在這個網路環境發生。反過來說，如果網路已經完全正常、也沒有 Captive Portal，警告卻持續出現，那就要換網路測試並認真調查。(5) 加分：提到唯一該點 Trust 的情境是公司內網做企業級 TLS inspection，那張憑證是公司自己的 CA，而且應該由 IT 事先公告。

SonarLint 憑證警告｜Captive Portal 攔截造成的 MITM 誤判

[!info] 本篇重點 a–l，共 12 個
情境：在咖啡廳（路易莎）用 VS Code 寫扣，SonarLint 突然跳出「發現不可信的伺服器憑證」。這是真的攻擊還是誤會？答案是誤會，但誤會的原因跟真正的中間人攻擊在技術上一模一樣。
關聯筆記：ClickFix社交工程攻擊-假驗證碼誘騙貼上PowerShell與網站被注入的處置 講的是真的攻擊，這篇講的是誤判，兩篇對照著看才能練出「哪種警告該怕」的判斷力；DNS查詢-TCP與TLS握手RTT-邊緣節點與網頁效能 講 TLS 握手在做什麼，這篇是那個握手被第三方插隊時會發生的事。

重點整理

一. 先把名詞定義清楚

(a) MITM（Man-In-The-Middle，中間人攻擊）：有人站在你和伺服器中間，攔截、竄改或偷看雙方的通訊。

(b) Captive Portal（強制網路門戶）：公共 Wi-Fi 那個「同意條款才能上網」的登入頁。中文有時翻成「強制入口網頁」。

(c) 自簽憑證（Self-signed Certificate）：由自己簽發、而非由公信的憑證機構（CA，Certificate Authority）簽發的 SSL/TLS 憑證。瀏覽器與程式預設不信任。

(d) SonarLint：SonarSource 出的 IDE 靜態程式碼檢查外掛，會在背景連回 SonarQube / SonarCloud 伺服器抓規則。

二. 為什麼會跳警告

(e) 關鍵：Captive Portal 為了強制你看到登入畫面，做的事情技術上就是中間人攻擊。

(f) 未登入前的流程：

  1. 你的裝置連上 Wi-Fi，拿到 IP，但 AP（這台是 Ruckus 設備）還沒把你放行。
  2. VS Code 的 SonarLint 在背景發 HTTPS 請求回它自己的伺服器。
  3. Ruckus AP 把這個請求劫持（hijack）下來，回傳自己的自簽憑證（憑發者顯示為 Ruckus Wireless Inc.），想把你導去登入頁。
  4. SonarLint 一看：我要連的是 sonarcloud.io，拿到的憑證卻是 Ruckus 簽的——憑證跟網域對不上，這就是 MITM 的特徵，於是跳警告。

(g) 登入成功後的流程：

  1. 你在瀏覽器完成 Captive Portal 登入。
  2. Ruckus 把你的 MAC 位址加進允許名單（Allowlist）。
  3. 路由器停止劫持，流量直接放行到真正的網際網路。
  4. SonarLint 拿到正確的憑證，警告自然消失。

(h) 所以「登入之後就正常了」不是巧合，而是劫持行為結束了。

三. 該怎麼處理

(i) 正解：點「Don't trust」或「Cancel」，然後去瀏覽器把 Wi-Fi 登入流程走完。登入後警告就不會再出現。

(j) 絕對不要在咖啡廳、機場、飯店這種外部網路點「Trust」。點下去等於把那張攔截憑證存進 SonarLint 的信任庫，之後這條連線上的所有流量對持有那把私鑰的人來說都是明文。

(k) 唯一可以考慮點 Trust 的情境：你在公司內部網路，而且確認公司 IT 政策就是用閘道器做 SSL 檢查（企業 TLS inspection）。這種情況下該憑證是公司自己的 CA。SonarLint 信任庫的預設密碼是 sonarlint。

(l) 通用判斷法則，記這一條就好：

憑證警告 在你完成 Wi-Fi 登入後就消失 → 是 Captive Portal 造成的誤判，安全。
憑證警告 在網路完全正常的情況下還一直出現 → 認真對待，換網路再試，還是有的話就要查了。

[!tip] 補充：Gemini 沒提但值得知道的
現代作業系統其實有偵測 Captive Portal 的機制（Windows 的 NCSI、Android 的 connectivitycheck.gstatic.com、Apple 的 captive.apple.com），它們會去打一個特定的 HTTP 網址看回應對不對，藉此判斷「是否被攔截」，然後自動跳出登入視窗。這也是為什麼手機常常一連上就自動彈登入頁，而 VS Code 這種背景程式沒有這套機制，只能靠憑證錯誤來反應。
另外實用小技巧：連上公共 Wi-Fi 後先開瀏覽器完成登入，再開 IDE 或跑 npm install，可以避開一整批莫名其妙的連線錯誤。

SonarLint SSL 憑證警告解析（2026-08）— https://gemini.google.com/app/25e4d23461e5b89f

使用者：（附上 VS Code 憑證警告的截圖）這什麼問題

Gemini： 這個警告是 SonarQube / SonarLint 擴充功能偵測到網路連線被阻截或攔截（MITM）所跳出的 SSL 憑證信任提示。背景瀏覽器開著 Ruckus 的 Captive Portal（無線網路認證頁面），說明你目前連接的是公共或企業 Wi-Fi。SonarLint 在背景發送 HTTP/HTTPS 請求時，流量被 Ruckus AP 攔截，回傳了 Ruckus 設備本身的自簽憑證（Ruckus Wireless Inc.），導致 SonarLint 認為這是一個「不可信的伺服器憑證」。
解決方法與建議：直接點擊「Don't trust」或「Cancel」（這是最安全的做法，通常在你完成公共 Wi-Fi 的網頁登入後，網路恢復正常，警告就不會再出現）；完成 Wi-Fi 認證；如果連線正常但持續跳出，若你是在公司內部網路且公司確實使用 Ruckus 網關進行 SSL 通訊檢查，點擊 Trust 才會將該憑證存入 SonarLint 的信任庫（預設密碼為 sonarlint）。若在非信任的外部網路，請切勿點擊 Trust。

使用者： 為何登入以後就正常了，但我現在其實在路易莎欸

Gemini： 這是因為公共 Wi-Fi 的 Captive Portal（強制頁面門戶）運作機制。
未登入前的狀態（中間人攔截）：路易莎的 Wi-Fi 路由器（使用 Ruckus 設備）為了強制讓你看到登入畫面，會把你的所有網路請求強制劫持到他們的認證網頁。當 VS Code 的 SonarLint 插件嘗試連回伺服器時，請求被 Ruckus 攔截，Ruckus 回傳了自己的 SSL 憑證，而非 SonarLint 預期的憑證。SonarLint 發現憑證不對勁，以為遇到中間人攻擊，因此跳出警報。
登入成功後的狀態（放行流量）：當你在瀏覽器點擊同意並完成登入後，Ruckus 路由器會將你的 MAC 地址加入「允許名單（Allowlist）」，路由器停止劫持你的流量，直接將請求放行傳到真實的網際網路。SonarLint 終於能順利連到真正的伺服器、拿到正確的 SSL 憑證，警告自然就消失了。
