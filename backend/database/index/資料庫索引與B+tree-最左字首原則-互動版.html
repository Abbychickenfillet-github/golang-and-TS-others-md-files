重點整理

1. 索引是什麼（一句話）

索引（Index）就像書後面的目錄：不用把整本書讀完，靠目錄直接翻到頁碼。資料庫用它以極快速度定位特定資料，不必掃整張表。任何資料表都能建索引，不是只有 junction table 才有。

2. B-tree vs B+tree（為什麼中間層 40、葉子卻到 49）

❓ Q：B+tree 的中間層數字和葉子節點數字為什麼不一樣？

答案：中間層（內部節點）只負責「導航、指路」，數字是用來引導搜尋方向的；真正存放實際資料鍵值的是「葉子節點」。兩者記錄的東西不同，數字不一樣很正常。

  • B+tree 的葉子節點之間用鏈結串起來（linked list），所以範圍查詢超快。
  • 範例 WHERE id BETWEEN 30 AND 70 之所以常被拿來示範，是因為它剛好跨越樹的不同分支：先從根節點定位起點 30，再順著葉子節點的鏈結一路掃到 70，完美展示 B+tree 的範圍查詢效率。

3. 叢集索引 vs 非叢集索引

💡 核心差異在「葉子節點裡放什麼」

- 叢集索引（Clustered）：索引結構和資料本身綁在一起，找到葉子就直接拿到完整資料，而且資料在磁碟上的排序就照這個鍵值排。
- 非叢集索引（Non-clustered）：葉子節點存的是指向資料的「地址」，必須再多一次查詢才能拿到完整資料。

  • MySQL（InnoDB）的資料表本身就是叢集索引（索引組織表），會自動且強制依主鍵（Primary Key）順序實體儲存，所以 MySQL 不支援也不需要 CLUSTER 指令。
  • PostgreSQL 才有 CLUSTER 表名 USING 索引名;，用來依某索引把資料表做一次性的實體重排。

4. 哪些欄位「適合」建索引

  • 高選擇性（High Cardinality）：重複值少、獨特值多，如 email、user_id、phone。
  • 經常出現在 WHERE 篩選條件的欄位（如 status、created_at）。
  • 多表 JOIN 用的外鍵（order_id、customer_id）。
  • 經常 ORDER BY / GROUP BY 的欄位 —— 因為 B-tree 本身就是排好序的，可省去排序動作。

5. 哪些欄位「不適合」建索引

⚠️ 索引不是越多越好

- 資料量極小的表（幾十～幾百筆）：直接全表掃描（Sequential Scan）通常更快。
- 低選擇性欄位：如 gender、is_deleted（true/false），建了 B-tree 也常被查詢器忽略。
- 頻繁被更新的欄位：每次資料變更都要同步改所有相關索引，太多索引嚴重拖慢寫入。
- 超長文字（TEXT/BLOB）：要搜尋請用全文檢索（Full-Text Search）或 Partial Index。

維運健康值：每張表維持 3～5 個核心索引最理想；18 個明顯偏多。

6. 最左字首原則（Leftmost Prefix Rule）

複合索引就像一本依 (姓氏, 名字) 印刷的電話簿：先按姓氏排，姓氏相同才按名字排。

對索引 (member_id, created_at, deleted_at)：

查詢 能用索引嗎 原因
WHERE member_id=5 AND created_at>'2026-01-01' ⭕ 極快 命中最左兩欄（1→2）
WHERE member_id=5 AND deleted_at IS NULL ⚠️ 部分 跳過中間的 created_at，deleted_at 無法在索引精準定位，只能找到 member 後逐筆過濾
WHERE created_at>'2026-01-01' ❌ 失效 跳過最左的 member_id，只能全表掃描
❓ Q：為什麼有了 (member_id, created_at, deleted_at)，舊的 (member_id, deleted_at) 就可以刪？

答案：因為兩者最左欄都是 member_id，當執行 WHERE member_id=5 時兩個索引都能用；大索引已經涵蓋了小索引最左欄的查詢場景，再留小索引只是白白浪費硬碟空間。

7. 軟刪除 deleted_at 出現在多個索引裡，是問題嗎？

✅ 通常不是問題，是軟刪除架構下的「正常現象」

採用 Soft Delete 時，幾乎每句 SELECT 都會加 WHERE deleted_at IS NULL。不同查詢情境（依 user 查 / 依 activity 查）是獨立的，沒辦法靠單一索引兼顧，所以 deleted_at 自然會出現在多組複合索引裡。

代價（B+tree 的隱形成本）：索引變大、寫入變慢——每多一個含 deleted_at 的索引，INSERT/UPDATE 時就多一棵 B+tree 要維護。

💡 PostgreSQL 的終極解法：Partial Index（部分索引）

不把 deleted_at 當索引「欄位」，而是當建立索引的「條件」，只把還活著的資料建進 B+tree：
sql CREATE INDEX idx_user_active_posts ON posts (user_id) WHERE deleted_at IS NULL;
好處：超省空間（樹裡完全沒有已刪除資料）、Key 變乾淨（只需 user_id）、查詢 WHERE user_id=123 AND deleted_at IS NULL 完美命中。

8. 怎麼把所有索引一次撈出來

-- PostgreSQL：用高階視圖 pg_indexes（比 join pg_class/pg_index 更穩、不易出錯）
SELECT schemaname, tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public'
ORDER BY tablename, indexname;

-- MySQL：查單表
SHOW INDEX FROM YourTableName;
-- MySQL：查整個資料庫
SELECT TABLE_SCHEMA, TABLE_NAME, INDEX_NAME, COLUMN_NAME, NON_UNIQUE
FROM information_schema.statistics
WHERE TABLE_SCHEMA = 'your_db'
ORDER BY TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX;
🚨 常見踩雷：跑錯資料庫系統 / 打錯字

- pg_class、pg_index、pg_attribute 是 PostgreSQL 專屬系統目錄，MySQL 看不懂。錯誤訊息出現 corresponds to your MySQL server version 就是「走錯棚」。
- 打錯字：= =ix.indexrelid（多一個 =）、ix.indkey_（尾巴多底線）都會語法錯誤。
- MySQL 不支援 PostgreSQL 的陣列操作符 ANY(...)。

9. HeidiSQL 的 Collation: A 是什麼

❓ Q：HeidiSQL 索引欄位顯示 Collation = A，是英文字母 A 嗎？

答案：不是字母 A，是 Ascending（升冪／由小到大） 的縮寫。代表索引在資料庫內依該欄位由小到大排序儲存；降冪會顯示 D。所以下 ORDER BY ... ASC 時能直接吃排好序的索引，省 CPU。

也要注意：HeidiSQL 看到同一個 Key_name 配不同 Column_name、Seq_in_index 1/2/3，那其實是一個三欄位複合索引，不是三個獨立索引；若整組重複出現兩次，就是 migration 重跑產生的髒資料，刪掉一組。

10. 延伸：購物車「一張訂單多個商品」= 多對多

order 與 product 是多對多（M:N），不能在 order 塞多個 product_id，要用中間表 order_item / order_product：

CREATE TABLE order_product (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_id BIGINT NOT NULL,
  product_id BIGINT NOT NULL,
  buy_price INT NOT NULL,           -- 🌟 歷史購買價快照(不可即時 join product，否則漲價會讓舊訂單金額亂掉)
  quantity INT NOT NULL DEFAULT 1,
  CONSTRAINT fk_op_order FOREIGN KEY (order_id) REFERENCES `order`(id) ON DELETE CASCADE,
  CONSTRAINT fk_op_product FOREIGN KEY (product_id) REFERENCES product(id),
  INDEX idx_op_order_id (order_id),
  INDEX idx_op_product_id (product_id)
);

11. 追加 2026-07-27：為什麼「走索引」是 O(log n)

ℹ️ O(log n) 是什麼

O(n)（全表掃描）：像看小說找情節，要從第一頁翻到最後一頁。
O(log n)（走索引）：像查字典，每次翻開中間那一頁，就能排除掉一半不需要看的內容。

為什麼對欄位下函數會讓索引失效、退化成 O(n)：

-- ❌ 對欄位做函數運算 → 索引失效 → 全表掃描 O(n)
WHERE order_number LIKE CONCAT(REPLACE(order_number, '-', ''), '%')

資料庫必須把每一列的 order_number 都先做一次 REPLACE 運算，才能跟目標字串比對，因此無法使用預先建好的索引。正確做法是把字串正規化（去掉 -）這件事搬到程式碼（Go/Python）先處理好，再丟給 SQL 做「精確匹配」，索引才會生效：

-- ✅ 精確值比對 → 索引生效 → O(log n)
WHERE order_number = 'TKT2026XXXX'

索引背後的資料結構：B+ Tree 把資料由小到大排序並分層管理，每一層節點都像指路標籤，查詢時依大小決定往左還是往右跳（二分查找）。100 萬筆資料的 B+ Tree 通常只需 3～4 次跳轉（I/O 操作）就能找到目標。

原寫法（計算型，對每列做運算）vs 新寫法（精確值，直接查索引樹）對比：

特性 原寫法（計算型） 新寫法（精確值）
行為 對每一筆 row 做運算 直接在索引樹查找
複雜度 O(n) O(log n)
10 萬筆資料 需要檢查 100,000 次 大約只需要 17 次比對
CPU 消耗 高（因為有運算） 極低

對數（Logarithm）最直覺的複習：對數是在問「底數的幾次方會等於這個數字」，例如 2³=8，以 2 為底 8 的對數就是 3（寫作 log₂8=3）。想像玩猜數字遊戲：範圍 1～8，每次只能回答「更大」或「更小」——第一次提問排除一半（剩 4 個）、第二次再排除一半（剩 2 個）、第三次抓到目標。這就是「8 要砍半幾次才變成 1，答案是 3 次」的物理意義。

資料量 (n) 對數次數 (log₂n) 備註
8 3 很快
1,024 10 1K 資料只要 10 次
1,048,576 20 100 萬筆資料只要 20 次
1,000,000,000 30 10 億筆資料也才 30 次

快速記憶法：指數（2ⁿ）像細胞分裂，數量爆炸式增長；對數（log n）像砍半查找，次數極緩慢增加。常用公式（工程師版，預設底數 2）：log(A×B) = logA + logB、log(A/B) = logA − logB、log(Aⁿ) = n·logA（估算複雜度時好用）。

哪些運算算「資料庫運算」、哪些該搬到程式碼：JOIN、子查詢（Subquery）、聚合函式（SUM/AVG/COUNT）都屬於資料庫運算，不是要搬離資料庫的對象。真正的判斷標準不是「這是不是 SQL 語法」，而是「這個計算會不會讓索引失效」：

類型 範例 建議留在 SQL？
篩選 Filter WHERE status = 'paid' 一定要，否則會撈出全表再在程式裡篩
關聯 Join JOIN users ON ... 通常要，資料庫對關聯有高度優化（Index Join）
排序 Sort ORDER BY created_at 通常要，有索引時排序近乎瞬間
對欄位做函數運算 REPLACE(order_number, '-', '') ❌ 不要，索引失效、退化成全表掃描

架構層級補充：單體架構（Monolith）大膽用 JOIN；微服務/分散式架構下可能避免跨資料庫 JOIN，改成程式碼分別呼叫 API 再手動拼接。

與 [[backend/database/SQL-INSERT語法與菜單JSONB選項建模-Alias|SQL-INSERT語法與菜單JSONB選項建模-Alias]] 互相呼應：那篇的「（g）（h）」講的正是同一條「能搬到程式碼算的就不要在資料庫算」黃金準則，本節（11）補上了「為什麼」——因為函數運算會讓 B+Tree 索引失效，複雜度從 O(log n) 退化成 O(n)。

自我測驗

  1. （是非題）MySQL InnoDB 需要手動執行 CLUSTER 來讓資料依主鍵排序。
    答案：✗。InnoDB 本身就是索引組織表，自動依主鍵實體排序，沒有也不能用 CLUSTER（那是 PostgreSQL 的功能）。
  2. （是非題）WHERE created_at > '2026-01-01' 可以命中複合索引 (member_id, created_at)。
    答案：✗。跳過了最左欄 member_id，索引失效，只能全表掃描。
  3. （申論題）說明在大量採用軟刪除（soft delete）的系統，為什麼 PostgreSQL 推薦用 Partial Index 取代「把 deleted_at 塞進每個複合索引」。
    答案：因為傳統做法會讓每個索引都多存一個時間欄位，樹變大、寫入時要維護多棵 B+tree。Partial Index 把 deleted_at IS NULL 當成建索引的條件而非欄位，只索引「還活著」的資料，樹更小更淺、Key 只需要業務欄位，且查詢 WHERE x=? AND deleted_at IS NULL 仍能完美命中，兼顧空間與速度。
  4. （填空題）100 萬筆資料的 B+ Tree 索引，查詢通常只需要約 __ 次跳轉就能定位到目標；10 億筆資料也大約只要 ____ 次。
    答案：20 次；30 次（log₂1,048,576≈20，log₂1,000,000,000≈30）
  5. （是非題）WHERE order_number = REPLACE(input, '-', '') 這種對常數做運算、欄位本身不變的寫法，也會讓索引失效。
    答案：✗。索引失效的關鍵是「對『索引欄位本身』做函數運算」，如 WHERE REPLACE(order_number, '-', '') = input 才會失效；如果只是對輸入的常數／變數做運算，欄位本身維持乾淨的等值比對，索引仍然有效。

🙋 使用者

我還是不太懂叢集和非叢集的差異。

✨ Gemini

最主要的差異在於索引節點裡放的是什麼。叢集索引的索引結構和資料本身綁在一起，找到葉子節點就能直接拿到完整資料，而且資料在磁碟上的排序就是照這個鍵值排的；非叢集索引的葉子節點存放的是指向資料的地址，必須再多一次查詢才能找到完整資料。

🙋 使用者

不同的 key 上出現 deleted_at 是一個問題嗎？

✨ Gemini

通常不是問題，而是配合軟刪除查詢效能的必然結果。因為業務查詢（例如找某使用者的未刪除文章）同時需要過濾特定 key 加上 deleted_at IS NULL，資料庫必須依賴這些含 deleted_at 的索引才能跑得快。代價是索引變大、寫入效能被稍微拖慢。PostgreSQL 的終極解法是部分索引（Partial Index）：把 deleted_at IS NULL 當成建立索引的條件而非欄位，只把還活著的資料建進 B+ 樹，既省空間、Key 又乾淨、查詢還能完美命中。

🙋 使用者

為何在 idx_event_member_created 我加了 member_id, created_at, deleted_at，Index_type 是 BTREE，可是 COLLATION A 代表什麼？這三個 column 有什麼問題嗎？Key_name 一樣可是 column 不同。

✨ Gemini

COLLATION 的 A 是 Ascending（升冪）的縮寫，代表索引依該欄位由小到大排序儲存。Key_name 相同、Seq_in_index 1/2/3、Column 不同，代表這三列共同組成一個三欄位複合索引，不是三個獨立索引。真正的問題是你重複建了兩組一模一樣的複合索引，且和舊的 (member_id, deleted_at) 功能重疊（最左字首原則下被大索引涵蓋），請把重複與被覆蓋的清掉。

Leftmost Prefix Rule 我還是不太確定複合式索引的意思。

✨ Gemini

複合索引就像一本依 (姓氏, 名字) 排序印刷的電話簿，先按姓氏排，姓氏相同才按名字排。最左字首原則：必須從最左欄開始匹配，跳過最左欄索引就失效。找「姓陳」⭕、找「陳小東」⭕、只找「名字=小東」❌（要全表掃描）。套到 (member_id, created_at, deleted_at)：member_id=5 AND created_at>... 極快；member_id=5 AND deleted_at IS NULL 部分有效（跳過 created_at）；只用 created_at>... 完全失效。

我如果要做一個購物車的資料表設計 order, product, member，product 如果要多個商品 order 要怎麼設計？

member→order 是一對多；order 與 product 是多對多，要用中間表 order_item/order_product 解開。四張表：member、product、order（只記總體資訊：誰買的、總金額、狀態），以及中間表 order_product（order_id、product_id、buy_price 歷史購買價快照、quantity）。中間表的 buy_price 一定要存當下價格快照，不能即時 join product，否則商品漲價或打折會讓歷史訂單金額對不起來。並幫外鍵 order_id、product_id 建索引，JOIN 才會快。

走索引直接O(log n)定位到底什麼意思

✨ Gemini

O(log n) 是對數時間複雜度：資料量翻倍，查詢時間只增加一點點。全表掃描是 O(n)，像看小說要逐頁翻；走索引是 O(log n)，像查字典每次翻中間頁排除一半。原本寫法 LIKE CONCAT(REPLACE(order_number,'-',''),'%') 對欄位做函數運算，資料庫要對每列都運算過才能比對，索引失效退化成全表掃描；正確做法是先在程式碼把字串處理好，再用精確值比對，索引才會生效。資料庫索引通常用 B+ Tree，分層管理、每層節點指路，100 萬筆資料通常只需 3～4 次跳轉即可定位。

🙋 使用者

幫我複習一下對數 最簡單的例子

✨ Gemini

對數是在問「底數的幾次方等於這個數字」，如 2³=8 則 log₂8=3。最直覺的例子是猜數字遊戲：範圍 1～8，每次問題只能排除一半，3 次就能鎖定目標，這就是 log₂8=3 的物理意義。對數函數增長極緩慢：100 萬筆資料只要 20 次、10 億筆也才 30 次，這正是工程師愛用 O(log n) 的原因。常用公式：log(A×B)=logA+logB、log(A/B)=logA−logB、log(Aⁿ)=n·logA。

可以在程式碼運算的就不要再資料庫裡面算 🤔 什麼JOIN語法 子查詢算程式碼還是資料庫

✨ Gemini

JOIN、子查詢（Subquery）、聚合函式（SUM/AVG/COUNT）都屬於「資料庫運算」，只要寫在 SQL 或透過 ORM 產生的都是交給資料庫引擎執行。真正該搬到程式碼的，是「會讓索引失效」的計算，例如對欄位做 REPLACE 這類函數運算。權責分工：篩選、JOIN、排序建議留在 SQL；複雜的字串處理、需要複雜 IF/ELSE 邏輯的計算適合搬到 Go/Node 處理。單體架構大膽用 JOIN；微服務/分散式架構可能改為程式碼分別呼叫 API 再拼接資料。
