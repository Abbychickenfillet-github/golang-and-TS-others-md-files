🧠 自我測驗

是非題

  1. 大範圍斷線時，應該對每一台離線設備都發送一則告警，才不會遺漏。

    那會造成告警疲勞（Alert Fatigue），真出事反而沒人看。要做窗口聚合與分級告警。

  2. 只要做了指數退避（Exponential Backoff），就不會發生驚群效應。

    設備同時斷線，退避時間也會同時到期。必須再加隨機抖動（Jitter）。

  3. 斷路器（Circuit Breaker）的作用是在後端過載時主動回 503／429，保護核心資源。

    犧牲部分請求換取整體不崩潰。

  4. 把設備最後在線狀態存在 Redis，是為了節省資料庫的儲存空間。

    目的是避免頻繁查詢主資料庫造成的讀取壓力，是效能考量不是空間考量。

填空題

  1. 數萬台設備在網路恢復瞬間同時重連，形成類 DDoS 的現象，稱為 Herd（驚群效應）。

    解法是指數退避加抖動。

  2. 在接入層與業務處理層之間加入 Kafka 來緩衝瞬間流量，這個手法叫流量 （Load Leveling）。

    不讓突發流量直接打到最貴的資源。

  3. AWS 建議的抖動寫法是 Full Jitter，公式為 sleep = random(0, min(cap, base × 2 的 n 次方))，其中 n 代表 次數。

    attempt 次數，每失敗一次就往上加。

  4. 監控 Kafka／RabbitMQ 積壓與寫入失敗率的告警，簡稱 Monitoring（死信佇列偵測）。

    Dead Letter Queue。

申論題

  1. 面試官問：某地區車輛大範圍斷線，你會如何設計告警與重試？請用 3 分鐘的長度組織你的答案。

    參考方向（分四段講）：一、先釐清問題邊界——問清楚設備規模、心跳頻率、可容忍的偵測延遲，並指出要先能區分「設備真的掉線」與「我們自己的 ingest 服務掛了」，做法是同時監控上行訊息總量：單一地區飆高多半是該地區網路，全網一起飆高先懷疑自家系統。二、告警設計——不對單台設備告警，改用窗口聚合（Flink 或 Redis TimeSeries 依地區開窗），規則是「T 分鐘內離線比例超過 X% 才觸發 Critical」；並做 L1 記錄日誌／L2 通知值班／L3 自動化應變的分級；另外監控 DLQ 積壓與寫入失敗率。三、重試設計——設備端用指數退避加 Full Jitter，避免恢復瞬間的驚群效應；後端加斷路器，過載時主動回 429／503 保護資料庫與認證服務。四、架構配套——Kafka 削峰、Redis 存最後在線狀態、優先級佇列讓行駛中的車輛先進來；並強調所有補傳的狀態更新必須冪等且帶時間戳，避免舊狀態覆蓋新狀態。最後主動說出取捨：這套設計犧牲了偵測即時性（窗口聚合會有延遲）來換取告警品質。

題目

系統監控與異常處理：如果某個地區的車輛突然大範圍斷線（IoT 通訊異常），你會如何設計告警機制與後端重試策略？

(a) 這題考的是三件事：系統穩定性、寫入負載緩衝（Backpressure）、故障自癒（Self-healing）。

重點整理

一、告警機制：從「雜訊」中提取「訊號」

(b) 最忌諱的做法是每一台設備離線都發一則告警，這會造成告警疲勞（Alert Fatigue），真的出事時反而沒人看。

(c) 窗口聚合（Windowed Aggregation）：用 Flink 或 Redis TimeSeries 針對「地區」維度開窗。規則寫成——若該地區在 T 分鐘內離線設備比例超過 X%，才觸發 Critical 告警。

(d) 分級告警（Tiered Alerting）：

等級 觸發條件 動作
L1 Normal 個別設備離線 僅記錄日誌，不打擾人
L2 Warning 單一基站或特定小區離線數異常上升 通知值班
L3 Critical 全地區斷線 觸發自動化應變流程，推播給當地維護團隊

(e) 死信佇列偵測（DLQ Monitoring）：監控 Kafka／RabbitMQ 的積壓情況，寫入失敗率飆升就立即告警。

二、重試策略：防止「驚群效應」

(f) 通訊恢復的瞬間才是真正的危險：數萬台設備同時重連，效果等同一次 DDoS。這叫 Thundering Herd（驚群效應）。

(g) 指數退避（Exponential Backoff）：設備端不要立刻重連，而是等待 2ⁿ 秒後再試（1、2、4、8、16…）。

(h) 隨機抖動（Jitter）：只有指數退避還不夠——所有設備同時斷線，退避時間也會同時到期，還是會撞在一起。所以要在退避時間加隨機因子（2ⁿ + random_ms），把壓力均勻攤到時間軸上。

// 指數退避 + 抖動（Full Jitter）
function backoffDelay(attempt, baseMs = 1000, capMs = 60000) {
  const exp = Math.min(capMs, baseMs * 2 ** attempt);
  return Math.random() * exp;   // Full Jitter：0 ~ exp 之間隨機
}

(i) 斷路器模式（Circuit Breaker）：若後端資料庫或認證服務壓力過大，後端主動「跳閘」，直接回 503 Service Unavailable 或 429 Too Many Requests，保護核心資源不被拖垮。

三、架構優化三招

策略 說明
流量削峰（Load Leveling） 在後端接入層與業務處理層之間加 Kafka，緩衝瞬間湧入的狀態變更訊息
無狀態快取（Stateless Cache） 把設備最後在線狀態存在 Redis，避免頻繁查主資料庫（MySQL／PostgreSQL）
優先級佇列 優先處理「正在行駛中」的車輛連線請求，靜止或充電中的延後處理

(j) 這三招的共同思路都是「不要讓突發流量直接打到最貴的資源」：Kafka 擋在資料庫前面、Redis 擋在資料庫前面、優先級佇列則是在資源不足時決定犧牲誰。

四、面試複習清單

(k) 重點複習：Exponential Backoff with Jitter 的原理，Amazon 與 Google 的面試極常出現。

(l) 作品集強化：若作品集有 IoT 或任何會重試的專案，檢查是否處理了「離線狀態冪等性（Idempotency）」——設備補傳的舊狀態不能覆蓋新狀態。

(m) 延伸題：如何處理大規模數據寫入的資料一致性。

(n) 補充（Gemini 沒講）：判斷「離線」本身需要 Heartbeat（心跳）＋ 超時門檻，而大範圍斷線時要能區分「設備真的掉了」與「是我們自己的 ingest 服務掛了」。做法是同時監控「上行訊息總量」——若某地區離線率飆高但其他地區正常，多半是該地區網路；若全網離線率一起飆高，先懷疑自家系統。這個判斷在面試講出來會很加分。
