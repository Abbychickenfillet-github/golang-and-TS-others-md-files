# 支付系統架構｜數位錢包（載體）與支付處理器（清算）的分工

> 本篇重點 a–j，共 10 個

相關筆記：[[2025-11-19_ticket-purchase-payment-flow]]、[[冪等性Idempotence與冪運算的區別]]、[[ECPay]]
關聯原因：Future Sign 的售票金流就是「前端載體 → 後端處理器」這條鏈的實例；而付款 API 一定要冪等，否則使用者連點兩次就會扣兩次款。

---

## 重點整理

### 一、問題起點：「支付系統」是個歧義詞

(a) <mark style="background: #FFF3A3A6;">「支付系統」對不同角色意味不同的東西</mark>：有人指的是 Apple Pay／Google Pay 這種數位錢包，有人指的是 PayPal／Stripe 這種後端處理系統。<mark style="background: #FF5582A6;">所以設計之前必須先釐清需求談的是哪一層</mark>。

(b) <mark style="background: #BBFABBA6;">一句話記住分工</mark>：<mark style="background: #ADCCFFA6;">Apple Pay 是「載體」，Stripe 是「處理器」</mark>。

---

### 二、兩大角色對照

| 特性 | 數位錢包（Apple／Google Pay） | 支付處理器／網關（Stripe／PayPal） |
|---|---|---|
| 所在層 | Client-side（客戶端） | Server-side（服務端基礎建設） |
| 角色 | 身分驗證與憑證存放 | 資金清算與帳務交換 |
| 主要用戶 | 一般消費者 | 軟體工程師、電商業主 |
| 存放內容 | 虛擬化的信用卡資訊、票卡 | 交易流水帳、客戶收付款記錄 |
| 獲利模式 | 向銀行收手續費、提升生態系黏性 | 每筆交易抽成（如 2.9% + $0.3） |
| 開發重點 | 硬體安全（NFC）、生物辨識（FaceID） | API 穩定性、資安合規（PCI DSS）、防詐騙 |
| 解決的問題 | 「如何方便且安全地支付」 | 「如何收到錢並完成銀行間清算」 |

(c) <mark style="background: #ADCCFFA6;">數位錢包不直接搬錢</mark>：它把實體信用卡資訊換成一組虛擬代碼（<mark style="background: #ADCCFFA6;">Token</mark>），感應手機時只是安全地把這組代碼交給商家，取代掏皮夾刷卡的動作。

(d) <mark style="background: #ADCCFFA6;">支付處理器是商家與銀行之間的橋樑</mark>：商家收到錢包傳來的資訊後發送給 Stripe，由 Stripe 去跟銀行確認額度、做風控，最後把錢從銀行搬到商家戶頭。

---

### 三、一次結帳的四層流程

(e) <mark style="background: #FFF3A3A6;">流程順序</mark>：

1. <mark style="background: #ADCCFFA6;">用戶層</mark>：使用者點「Apple Pay」按鈕（數位錢包）。
2. <mark style="background: #ADCCFFA6;">傳輸層</mark>：Apple Pay 授權，把卡片 Token 傳給網站。
3. <mark style="background: #ADCCFFA6;">處理層</mark>：網站後端呼叫 Stripe API（支付處理器）。
4. <mark style="background: #ADCCFFA6;">清算層</mark>：Stripe 聯繫收單銀行與發卡銀行，完成扣款。

(f) <mark style="background: #BBFABBA6;">開發時的分工判準</mark>：做 App → 整合 Apple Pay 的 SDK；架電商後端 → 對接 Stripe 的 API 與 <mark style="background: #ADCCFFA6;">Webhook</mark>。

(g) <mark style="background: #FFB8EBA6;">兩者是協作而非競爭</mark>，一個完整的支付流程往往需要兩者同時存在。

---

### 四、補充（Gemini 原文沒講但一定要知道）

(h) <mark style="background: #FF5582A6;">Webhook 才是金流的真相來源</mark>。前端跳轉回「付款成功頁」不代表錢真的進來了（使用者可能中途關掉分頁）。<mark style="background: #BBFABBA6;">訂單狀態必須以支付處理器打回來的 Webhook 為準</mark>，而且 Webhook 可能重送，所以處理端必須<mark style="background: #FFF3A3A6;">冪等</mark>，參見 [[冪等性Idempotence與冪運算的區別]]。

(i) <mark style="background: #FF5582A6;">絕對不要讓卡號經過自己的伺服器</mark>。用 Stripe Elements／Checkout 這類前端元件把卡號直接送到 Stripe，自己只拿到 Token，這樣 PCI DSS 的合規範圍才會縮到最小。

(j) <mark style="background: #D2B3FFA6;">台灣情境的差異</mark>：本地案子常見的是綠界 ECPay、藍新 NewebPay、TapPay，而不是 Stripe；台灣的「載體」層還多了 LINE Pay、街口這類第三方支付 App，分類上介於錢包與處理器之間（它們同時做載體也做清算）。這點跟 Gemini 給的美國視角不同。

## 各對話來源（原文）

### 支付系統：前端載體與後端處理（2026-08 前後）— https://gemini.google.com/app/351c10478b1693cd

**使用者：**（引述一段文字）支付系統對不同的人意味著不同的事。有些人認為它像 Apple Pay 或 Google Pay 這樣的數字錢包；而另一些人則認為它是處理支付的後端系統，如 PayPal 或 Stripe。因此，在設計之前，必須先明確需求。這 2 個有什麼不一樣

**Gemini：** 在技術架構上，這兩者分別代表了支付生態系中的「前端交互層」與「後端處理層」。簡單來說，Apple Pay 是「載體」，而 Stripe 是「處理器」。
1. 數位錢包（Digital Wallet）——代表：Apple Pay、Google Pay、Samsung Pay。角色：身分驗證與憑證存放。核心功能：它們並不直接「處理」資金轉移，而是將你的實體信用卡資訊轉換成一組虛擬的「代碼」（Token）。當你感應手機時，它只是安全地把這組代碼傳給商家，代替了你掏出皮夾刷卡的動作。面向對象：終端消費者。
2. 支付處理器／網關（Payment Processor/Gateway）——代表：Stripe、PayPal、Square、Adyen。角色：資金清算與帳務交換。核心功能：它是連接「商家」與「銀行」之間的橋樑。當商家收到 Apple Pay 傳來的資訊後，會把這筆資訊發送給 Stripe，由 Stripe 去跟銀行確認這張卡有沒有錢、防範詐騙，並最終把錢從銀行搬到商家的戶頭裡。面向對象：企業主或開發者。
兩者的關係圖解：用戶層——你點擊「Apple Pay」按鈕（數位錢包）；傳輸層——Apple Pay 授權並將卡片代碼傳給網站；處理層——網站後端調用 Stripe API（支付處理器）；清算層——Stripe 聯繫收單銀行與發卡銀行，完成扣款。
總結差異：主要用戶方面，數位錢包是一般大眾（消費者），支付處理系統是軟體工程師與電商老闆（商家）；存放內容方面，前者是虛擬化的信用卡資訊與票卡，後者是交易流水帳與客戶收付款記錄；獲利模式方面，前者通常向銀行收取手續費或提升生態系黏性，後者從每筆交易中抽成（如 2.9% + $0.3）；開發重點方面，前者是硬體安全（NFC）與生物識別（FaceID），後者是 API 穩定性、資安合規（PCI DSS）與防詐騙系統。
筆記整理：Apple/Google Pay 是 Client-side（客戶端）的工具，解決的是「如何方便且安全地支付」的問題；Stripe/PayPal 是 Server-side（服務端）的基礎建設，解決的是「如何接收資金並完成銀行間清算」的問題。在設計系統時，如果你在開發 App，你需要整合的是 Apple Pay 的 SDK；如果你在架設電商後端，你需要對接的是 Stripe 的 Webhook 與 API。這兩者通常是協作關係而非競爭關係，一個完整的支付流程往往需要兩者同時存在才能完成。
