🧠 自我測驗

是非題

  1. 只要前端用了 HTML5 的 required 屬性，後端就可以省略驗證。

    攻擊者可以用 Postman 或 curl 直接打 API，完全不經過你的前端。

  2. 「這個 Email 是不是已經被註冊過」這種檢查，前端自己做得到。

    前端沒有資料庫，必須由後端查表才知道。

  3. 驗證通過的資料，寫進資料庫時就不必再用參數化查詢了。

    驗證是「該不該收」，參數化查詢與 escaping 是「收下之後怎麼安全地存與顯示」，兩件事都要做。

  4. 用 Zod 或 Pydantic 把規則寫成一份 schema 給前後端共用，可以避免兩邊規則不一致。

    這是實務上防止「前端說可以、後端說不行」的標準做法。

填空題

  1. 表單資料本身有問題時，後端通常回 HTTP Bad Request。

    401 是沒表明身分，403 是有身分但沒權限。

  2. FastAPI 的 Pydantic 對驗證錯誤預設回的狀態碼是 。

    422 Unprocessable Content 表示語法對但語意不合規。

  3. 前端驗證的主要目的是提升 ，後端驗證的主要目的是保障安全。

    即時回饋，減少無效的網路請求。

申論題

  1. 請用「誰 用什麼 做什麼、產物是什麼、再拋給誰」的句型，把一次註冊表單從按下送出到寫入資料庫的完整流程寫出來，並標出驗證失敗時流程在哪裡折返。

重點整理

1. 定義與一句話心法

(a) Server-side form validation（伺服器端表單驗證）：使用者送出表單之後，伺服器端的程式碼再檢查一次這些資料是否符合格式、安全性與業務邏輯。

(b) 心法：前端驗證是為了體驗，後端驗證是為了安全。兩者不是二選一，是分工。

2. 為什麼前端擋不住（核心理由）

(c) 前端驗證可以被繞過，而且門檻極低。攻擊者根本不必用你的網頁，三種常見繞法：

繞法 1：瀏覽器關掉 JavaScript          → 所有 JS 驗證直接不執行
繞法 2：F12 改掉 <input required> 屬性  → HTML5 內建驗證失效
繞法 3：用 Postman / curl 直接打 API    → 從頭到尾沒有經過你的前端

所以後端是<mark style="background: #BBFABBA6;">保護資料庫的第一道，也是最後一道防線</mark>，能擋下 SQL Injection、XSS 這類把惡意字串塞進欄位的攻擊（延伸見 <span class="wikilink" title="Obsidian 連結：javascript-url-XSS-實驗室">javascript-url-XSS-實驗室</span>）。

(d) 資料完整性：確保進資料庫的每一筆都合規——Email 格式對、必填欄位有值、密碼強度夠。

(e) 複雜業務邏輯只有後端做得到，因為必須查資料庫才知道答案：

  • 這個帳號或 Email 是不是已經被別人註冊走了
  • 這個商品的庫存還夠不夠

  • 這個使用者有沒有權限執行這個操作

    前端沒有資料庫，這三題它一題都答不出來。

3. 前端驗證 vs 後端驗證對照

比較項目 Client-side validation（用戶端驗證） Server-side validation（伺服器端驗證）
執行位置 使用者的瀏覽器，用 HTML5 屬性或 JavaScript 後端伺服器，用 Node.js、Python、Java、PHP 等
主要目的 提供即時回饋，提升使用者體驗 保障系統安全，維護資料正確性
安全性 低，極易被繞過或修改 高，使用者無法直接控制後端邏輯
反應速度 極快，不需經過網路傳輸就能提示錯誤 較慢，需要一次 API 請求或網頁重新載入
能不能查資料庫 不能 能

4. 實作流程（誰做什麼、產物丟給誰）

(f) 完整一輪的拋接關係寫成一句話：

使用者 在前端填完表單並按送出
  → 瀏覽器 把欄位資料序列化成 JSON，用 fetch 送到後端 API
    → 後端路由 接到資料，呼叫驗證層（必填檢查 → 正規表示式格式檢查 → 查資料庫比對）
      → 驗證失敗：後端 組出錯誤訊息物件，回 HTTP 400 Bad Request 給前端
          → 前端 收到 400，把訊息渲染到對應欄位下方讓使用者修正
      → 驗證成功：後端 執行業務邏輯（寫入資料庫）
          → 回 HTTP 200／201 與成功結果，前端 導頁或顯示成功

(g) 驗證失敗回 400 Bad Request，代表「你送來的東西本身有問題」。
跟它容易混淆的鄰居：401 Unauthorized 是「你沒表明身分」，403 Forbidden 是「你表明了身分但沒權限」，422 Unprocessable Content 是「語法對但語意不合規」，有些框架（例如 FastAPI 的 Pydantic）預設對驗證錯誤回 422 而不是 400。

5. 最佳實務

(h) 「前後端雙重驗證」是標準答案：前端負責即時提醒（密碼沒填就立刻紅字），減少無效的網路請求；後端負責最後把關，確保就算繞過前端資料也絕對安全。

(i) 不要為了省事只留一邊。只留前端＝門沒鎖；只留後端＝使用者每打錯一個字都要等一次 round trip。

(j) 驗證規則最好只寫一份、兩邊共用。實務上用 schema 函式庫（Zod、Yup、Pydantic）把規則定義成一個 schema 物件，前端 import 它做即時檢查，後端 import 同一份做最終把關，避免兩邊規則不一致導致「前端說可以、後端說不行」的鬼打牆。

(k) 後端驗證跟 escaping 是兩件事：驗證是「這筆資料該不該收」，escaping／參數化查詢是「收下之後怎麼安全地存與顯示」。通過驗證的資料仍然要用參數化查詢寫入資料庫，仍然要在輸出時做 HTML escaping，不能因為驗證過了就省略。

伺服器端表單驗證解析（2026-09）— https://gemini.google.com/app/f1ff251f8f4d9ec7

使用者： 何謂 server-side form validation？

Gemini： Server-side form validation（伺服器端表單驗證）是指當使用者填寫並送出表單後，將資料傳送至伺服器（Server），由伺服器端的程式碼來檢查這些資料是否符合格式、安全性與業務邏輯的過程。

  1. 為何需要伺服器端驗證？安全性（防範惡意攻擊）：用戶端驗證很容易被繞過（例如透過關閉瀏覽器 JS、使用 Postman 等工具直接發送請求，或修改前端程式碼）。伺服器端是保護資料庫與系統安全的第一道，也是最終一道防線，能防止 SQL 注入、跨站腳本攻擊（XSS）等風險。資料完整性與準確性：確保存入資料庫的資料均符合規範。複雜業務邏輯檢查：有些驗證必須查詢伺服器資料庫才能完成，例如檢查註冊的帳號／Email 是否已被其他人使用、檢查商品庫存是否足夠、檢查使用者是否有權限執行該操作。

  2. 與 Client-side Form Validation 的差異：執行位置、主要目的、安全性、反應速度四項對照（見上方表格）。

  3. 常見的實作流程：送出表單 → 後端接收資料後呼叫驗證邏輯 → 若驗證失敗，伺服器回傳錯誤訊息與狀態碼（如 HTTP 400），前端收到後顯示給使用者修正；若驗證成功，伺服器處理業務邏輯並回傳成功結果或進行頁面跳轉。

最佳實務原則：「前後端雙重驗證」是最佳作法。用戶端驗證負責即時提醒，減少無效的網路請求；伺服器端驗證負責最後把關，確保資料就算繞過前端也絕對安全無誤。
