一、延遲 Latency：名詞導覽、正常與慢、怎麼降

對應筆記第一節，是全篇總入口：先把名詞講完，再定義延遲、算帳、給「正常與慢」的標準，最後講怎麼降。後面各節只是把其中一格放大。

(a-0) 先定義「第幾層」

第 1 層是實體層（硬體），第 7 層是應用層（軟體）。OSI 的編號由下往上數：數字越小越靠近電線與電波、越偏硬體；數字越大越靠近使用者與程式、越偏軟體。送出資料時由第 7 層往第 1 層走（封裝），接收時由第 1 層往第 7 層走（解封裝）。

層號名稱偏軟還是偏硬這一層在解決什麼本篇例子
7應用層 Application軟體（程式與函式庫）程式之間用什麼「語言」溝通DNS、HTTP、WebSocket
6展示層 Presentation軟體資料格式、編碼、加密TLS（常被歸在此）
5會談層 Session軟體建立與管理一次對話實務少獨立看待
4傳輸層 Transport作業系統核心（軟體）送到對方機器上的「哪個程式」，並決定可不可靠TCP、UDP
3網路層 Network核心與路由器（軟體為主）跨網路送到「哪一台機器」IP
2資料連結層 Data Link網卡與驅動（軟硬交界）同一段網路上送給下一台設備Wi-Fi、Ethernet、MAC
1實體層 Physical硬體位元如何變成電波或光訊號光纖、無線電波、雙絞線

TCP/IP 四層模型的教材常把「連結、網際網路、傳輸、應用」由下往上標成 1～4（不同教材編法不一）；業界說 L3、L4、L7 一律指 OSI 編號。

stub resolver 有確實解析嗎？

有。它負責「替程式解析」，沒做的只是「追查」。RFC 9499 定義 stub resolver 為「無法自己完成整個解析的 resolver」，RFC 1034 §5.3.1 說這是把解析功能交給支援遞迴查詢的 name server，本機只需一份 name server 位址清單。

stub resolver 的工作做不做說明
提供解析入口給程式（如 getaddrinfo）做程式問「這個名字的 IP」，由它回答
查 hosts 檔與本機快取做命中就直接回，連網路都不出
送查詢給設定好的 recursive resolver做Linux 的位址在 resolv.conf 的 nameserver
處理逾時、重送、換下一台做RFC 1034 §5.3.1：要自己設重送間隔，同時應付掉包與伺服器當機
依 TTL 快取答案做本機實測：清空快取後解析 example.com，TTL 300，3 秒後變 297
追查 root、TLD、authoritative不做這是 recursive resolver 的工作

瀏覽器端：Chrome 有自己的 built-in resolver（Chromium net/dns README），也可呼叫作業系統的 getaddrinfo()，符合條件時擇一。

(a-2) TCP 與 UDP：點一個情境，看該用哪個

兩者是同一層（L4）的兩種取捨，不是新舊或好壞。以 RFC 日期看，UDP（1980）比 TCP（1981）還早一年。

提示點上面的情境。
比較項目TCPUDP
連線先三向握手（約 1 RTT）才能傳資料不需要握手，直接送
可靠性掉了會重傳，保證送達不保證，要不要補由應用層決定
順序保證依序不保證
資料形式連續位元組流，沒有訊息邊界獨立的資料報，有邊界
額外負擔標頭大、要維護連線狀態、有擁塞控制與慢啟動標頭很小（來源埠、目的埠、長度、檢查碼各 16 位元）
延遲特性握手與重傳讓首包慢；掉包時後面要等（隊頭阻塞）首包最快，但掉包不會自動補
規範RFC 793（1981-09），現行 RFC 9293RFC 768（1980-08）

DNS 為什麼預設走 UDP 的 53 埠？兩者一定有關係嗎？

沒有必然關係：UDP 是「怎麼送」（傳輸協定），53 是「送給這台機器上的哪個服務」（埠號），是兩件獨立的事。RFC 1035 §4.2 說 DNS 可用資料報或虛擬電路（TCP），查詢「偏好」資料報是因為額外負擔低、效能好；同一個 53 埠在 UDP 與 TCP 各登記一份（IANA：domain 53 的 TCP 與 UDP）。UDP 與 TCP 的埠號是各自獨立的空間，UDP 53 與 TCP 53 是兩個不同的端點。

DNS 的傳輸方式協定與埠什麼時候用規範
傳統查詢（預設）UDP 53一問一答很小，省掉握手，1 RTT 問完RFC 1035（1987-11）
傳統查詢的 TCP 版TCP 53回應被截斷（TC 位元）、區域傳輸；RFC 7766 要求 DNS 實作必須支援 TCPRFC 1035、RFC 7766（2016-03）
加大 UDP 訊息仍是 UDP 53原始 UDP 訊息上限 512 位元組；EDNS(0) 讓雙方宣告更大的大小，建議從約 4096 起試RFC 6891（2013-04）
DNS over TLS（DoT）TCP 853加密 stub 到 recursive resolver 的查詢RFC 7858（2016-05）
DNS over HTTPS（DoH）走 HTTPS（TCP 之上，慣用 443）把每個 DNS 查詢包成一次 HTTP 請求RFC 8484（2018-10）
DNS over QUIC（DoQ）UDP 853QUIC 之上的加密 DNSRFC 9250（2022-05）

埠號是約定，不是技術限制：IANA 登記表把 domain 53 同時登記給 TCP 與 UDP（受讓人為 DNS 發明者 Paul Mockapetris）；853 則登記給「DNS over TLS（TCP）」與「DNS over DTLS／QUIC（UDP）」。

(a-3) 與延遲有關的量

名詞衡量什麼單位受什麼影響
Latency 延遲一個封包從來源走到目的地的時間ms物理距離、轉接次數、無線段
RTT 往返時間A 到 B 再回 A，延遲最常用的量法ms同上，約為單程兩倍
Bandwidth 頻寬線路單位時間「最多」能送多少Mbps線路規格
Throughput 吞吐量單位時間「實際」送了多少Mbps延遲、擁塞、慢啟動、掉包
TTFB送出請求到收到第一個位元組，已含 DNS、TCP、TLS 與伺服器處理ms各段 RTT 之和加伺服器處理
Jitter 抖動延遲一次比一次不穩的程度ms無線訊號、擁塞
Packet loss 封包遺失率送出的封包掉了幾成%訊號差、壅塞；TCP 重傳使延遲變大

頻寬是水管多粗，latency 是水管多長，水管再粗也縮短不了長度。

(b) 為什麼不能直接把 RTT 相加

原因說明
各段對象不同DNS 是手機到 resolver，TCP、TLS、HTTP 是手機到 web server，RTT 不一樣長
有快取與複用DNS 快取命中為 0；連線複用時 TCP 與 TLS 為 0
不是全部串行瀏覽器同時對多個 hostname 建連線
資料還要傳檔案大小 ÷ 有效頻寬，且慢啟動使大檔要多個 RTT 才加速到全速
伺服器與渲染也要時間後端查資料庫、瀏覽器解析與渲染都不在 RTT 裡

總載入時間 ≈ 連線建立（各段往返數 × 該段 RTT）＋ 伺服器處理 ＋ 傳輸（資料量 ÷ 有效頻寬，含慢啟動）＋ 瀏覽器解析與渲染。下面第三節的試算就是在算「連線建立」那一段。

(b-3) 現代降低延遲的做法（點方向篩選）

降低延遲只有三個方向：縮短距離、減少往返次數、讓等待重疊（提前或平行），每一項都是它們的變形。

四、OSI 七層：點一層看這一層在本篇扮演什麼

提示紅框的三層（7、4、3）是本篇主角。

TLS 在 OSI 沒有明確位置，常被放在 L6；TCP/IP 四層模型把 5～7 層合併為應用層。DNS 在 L7，查出來的 IP 是 L3 位址。

一條 WebSocket 連線，每個名詞在哪一層

WebSocket 在 L7（最上層）；TCP 在 L4 傳輸層，不是 L3；socket 與 fd 不屬於七層，是程式呼叫核心的 API。

TCP 較老、TLS 較新；TLS 疊在 TCP 上，所以 TCP 握手必在前。MDN 說 TLS「five more round trips」是把圖上的 5 條單趟箭頭當成往返；一個 RTT 含去與回兩條箭頭。

六、一條執行緒怎麼顧 N 條連線：event loop 與 epoll

epoll 是作業系統的 API，event loop 是程式的迴圈結構：迴圈每一輪都呼叫 epoll_wait，問核心哪些 fd 就緒了。拖動連線數，比較兩種模型：

一連線一執行緒（阻塞 I/O）

需要執行緒：1000 條
每條執行緒有自己的 stack，大多數時間在 read 上睡著等資料。

I/O 多路複用（event loop）

需要執行緒：1 條　監看 fd：1000 個
執行緒目前狀態：睡眠
  1. 1. 呼叫 epoll_wait 等待（睡眠，不用 CPU）
  2. 2. 核心回報 3 個 fd 就緒（醒來，標紅的連線）
  3. 3. 依序執行這 3 條連線的處理函式（運算中，用 CPU，所以要短）
  4. 4. 回到步驟 1，又睡眠

沒有「I/O 專用執行緒」與「CPU 執行緒」之分：同一條執行緒反覆睡眠、醒來、運算。一條 WebSocket ＝ 一條 TCP 連線 ＝ 一個 socket（fd）。
