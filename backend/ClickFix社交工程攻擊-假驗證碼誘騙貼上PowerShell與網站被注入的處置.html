是非題

  1. 正常的 reCAPTCHA 驗證有時候會需要你複製一段指令到終端機執行。

    絕對不會。任何叫你離開瀏覽器去貼指令的「驗證」一律是攻擊，沒有例外。

  2. 看到 ClickFix 彈窗，就代表你自己的網站被駭了。

    也可能是你造訪了被植入的網站，或自己的瀏覽器擴充被劫持。要先分清楚是受害者還是加害者。

  3. ClickFix 之所以難防，是因為它繞過了技術防線——沒有下載檔案，是使用者自己手動執行的。

    防毒很難擋一個使用者主動輸入的指令。

  4. 如果已經執行了惡意指令，應該立刻在那台電腦上修改所有帳號密碼。

    要在「另一台乾淨的裝置」上改。在已感染的機器上改等於直接送給對方。

  5. 改完密碼就安全了，不需要做其他事。

    InfoStealer 也會偷 session cookie，要另外在各服務後台執行「登出所有裝置」把既有 session 作廢。

  6. CSP 設定 script-src 'self' 時，頁面內嵌的 <script> 也會被擋掉。

    因為沒寫 unsafe-inline。這正是它能防注入的原因，但專案得先清掉 inline script。

  7. 自己的網站被注入時，最常見的入口是自己寫錯程式碼。

    近年最常見的是供應鏈攻擊——你一行沒改，但某個 npm 套件或第三方 script 被接管了。

申論題

  1. 你是 Future Sign 的開發者。使用者回報造訪你的網站時跳出「請按 Win+R 貼上以下指令完成驗證」的視窗。請寫出你從收到回報到收尾的完整處置流程，並說明每一步的理由。

    參考方向：(1) 先分流判斷——不要立刻假設被駭，也不要立刻假設沒事。請回報者提供截圖與網址，自己用乾淨環境（無痕、不同網路、不同裝置）重現。若只有特定使用者遇到，可能是他的瀏覽器擴充被劫持；若人人都遇到，才是自家站被注入。(2) 止血——確認是自家站之後，立刻設維護模式或把 DNS 切到備份頁，避免訪客繼續受騙。同時清 CDN 全站快取，否則被污染的靜態資源會繼續被讀。(3) 找感染源，分三層查：前端（DevTools 檢視原始碼，搜尋 Verification Steps、reCAPTCHA Verification ID、powershell、FromBase64String 這些關鍵字；檢查 index.html 或打包進入點有沒有外連的不可信 script）；依賴（檢查 npm lockfile 有沒有被改、Analytics／客服插件／廣告聯播網的 script 有沒有被串改——這是近年最常見的入口）；後端與資料庫（檢查有沒有 <script> 被寫進資料表，用 git status / git diff 比對伺服器上的檔案異動）。順手開 DevTools 的 Application 分頁比對 cookie 與 localStorage 有沒有自己沒設過的項目。(4) 輪換憑證——重產 SSH 部署金鑰、資料庫密碼、API Keys，檢查伺服器有無異常帳號，審查 CI/CD Secrets。理由是既然對方有注入權限，很可能也拿到了某把金鑰。(5) 強化——上 CSP，先用 Report-Only 收報告確認不誤殺再轉正式；把 inline script 清掉；第三方 script 加 SRI（Subresource Integrity）。(6) 對外——通知已造訪的使用者，明確告知「如果你照做貼上了指令，請斷網、全盤掃描、在另一台裝置改密碼並登出所有裝置」。這一步常被忽略但最重要，因為真正的受害者是他們。(7) 事後——寫 postmortem，加上 dependency 掃描（npm audit、Dependabot）與部署前的靜態檢查，避免再犯。

重點整理

第一部分：ClickFix 攻擊本身

一. 這是什麼

(a) ClickFix（也叫 Fake CAPTCHA、Paste-and-Run）：一種社交工程攻擊。最早的公開回報是 2024 年 3 月，2025 年 3 月 18 日被正式收錄為 MITRE ATT&CK 的 T1204.004（User Execution: Malicious Copy and Paste），已知被 Latrodectus、Lumma Stealer、NetSupport RAT 等惡意程式家族當作主要感染途徑。網頁彈出假的「我不是機器人」或「修復顯示問題」視窗，指示使用者按 Win + R、貼上一段已經在剪貼簿裡的指令、按 Enter。

(b) 為什麼有效：它繞過了所有技術防線。沒有下載檔案、沒有可疑附件、沒有觸發瀏覽器的下載警告——是使用者自己在自己的電腦上手動執行的。防毒軟體很難擋一個「使用者主動輸入的指令」。

(c) 重要澄清：看到這個彈窗，不代表你的網站被駭。你可能只是造訪了一個被植入惡意腳本的網站，也可能是自己的瀏覽器擴充功能被劫持。要分清楚「我是受害者」還是「我的站在害別人」。

二. 那段惡意腳本在做什麼

[!note] 為什麼這裡不貼原始碼
原始的攻擊 payload 是一長串 Base64，本篇刻意不完整收錄，避免以後不小心複製到。原文可回對話連結查看。以下只記錄它的行為特徵，這才是能拿來辨識下一次攻擊的東西。

(d) 多層混淆與加密：同時用 Base64 編碼與 Caesar Cipher（凱撒位移密碼）字母替換來藏住真實內容，目的是規避防毒軟體的靜態特徵比對。

(e) 下載並執行外部檔案：解碼後的腳本會用 WinHttp.WinHttpRequest 這類 COM 物件向遠端伺服器發 HTTP 請求，偷偷把惡意程式抓下來。

(f) 背景隱蔽執行：透過 ProcessStartInfo 啟動處理程序，並把 CreateNoWindow 設為 true、WindowStyle 設為 Hidden，讓你完全看不到有東西在跑。

(g) 竊密：抓下來的通常是 InfoStealer（資訊竊取程式），目標是瀏覽器存的密碼、信用卡號、加密貨幣錢包，並在登錄檔（Registry）留後門讓自己開機自動執行。

(h) 辨識特徵懶人包，看到以下任一組合就是它：

特徵 為什麼可疑
FromBase64String + Invoke-Command / IEX 把編碼過的字串直接當程式執行，正常維運腳本不會這樣寫
[scriptblock]::Create(...) 動態產生程式碼，典型的混淆手法
-WindowStyle Hidden / CreateNoWindow 刻意不讓你看到
-EncodedCommand / -enc 傳一段 Base64 給 PowerShell 直接跑
DownloadString / WinHttpRequest 接著執行 下載即執行
網頁上出現 Verification Steps、Verification ID、powershell 假驗證碼的痕跡

三. 已經貼上去了怎麼辦

(i) 立即斷網：拔網路線或關 Wi-Fi，阻止資料繼續上傳。

(j) 完整病毒掃描：Windows Defender 離線掃描或第三方防毒的全盤掃描。

(k) 在另一台乾淨的裝置上更換所有重要帳號密碼（Email、社群、銀行、GitHub、雲端），並啟用 2FA。重點是「另一台」——在已被感染的機器上改密碼等於直接送給對方。

(l) 補充 Gemini 沒講的：InfoStealer 也會偷 session cookie，所以光改密碼不夠，要在各服務後台執行「登出所有裝置」把既有 session 作廢。另外開發者要特別檢查 .env、~/.aws/credentials、~/.ssh/、瀏覽器存的 GitHub token。

第二部分：身為網站開發者的處置

四. 應急止血

(m) 下架或設維護模式：正式環境先切到維護頁或備份頁，避免訪客持續受騙。

(n) 清 CDN 與前端快取：Cloudflare 或其他 CDN 要清全站快取，否則被污染的靜態資源會繼續被讀。

五. 找感染源

(o) 前端注入點：開 DevTools 檢視原始碼，搜尋 Verification Steps、reCAPTCHA Verification ID、powershell、FromBase64String 這些關鍵字。檢查 index.html 或打包進入點有沒有引入不可信的外連腳本。

(p) 第三方套件與供應鏈攻擊（Supply Chain Attack）：檢查 npm 依賴、Analytics、客服插件、廣告聯播網的 script 有沒有被串改。這是近年最常見的入口——你自己的程式碼一行沒改，但某個小套件被接管了。

(q) 後端與資料庫注入：檢查資料庫（WordPress 的 wp_posts、wp_options 等）有沒有被寫入 <script> 或隱藏 DOM。用 git status / git diff 比對伺服器上的檔案有沒有未授權異動。

(r) 檢查瀏覽器儲存也是排查的一環——被注入的腳本常會塞新的 cookie 或 localStorage 項目來記錄「這個訪客已經看過彈窗」：

這張是自家 TimeLog 專案 localhost:3001 的正常狀態：只有一個 ACCESS_TOKEN（JWT），HttpOnly 打勾、SameSite 為 Lax。排查被注入的站時，就是拿這種「我知道每一項是什麼」的乾淨基準，去比對出多出來的陌生項目。平常就留一張正常狀態的截圖，出事時比對會快很多。

六. 強化

(s) 設定 CSP（Content Security Policy，內容安全政策）：在 HTTP 回應標頭中限制只能載入哪些來源的腳本。

Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com;

逐段拆解：default-src 'self' 是預設規則，所有資源只能來自本站；script-src 單獨覆寫腳本規則，只允許本站與指定的 CDN。注意這份設定沒有寫 'unsafe-inline'，所以頁面內嵌的 <script>...</script> 也會被擋掉——這正是它能防注入的原因，但也代表你的專案得先把 inline script 清乾淨才能上這條規則。建議先用 Content-Security-Policy-Report-Only 跑一陣子收報告，確認不會誤殺再切成正式模式。

(t) 輪換所有憑證：重新產生 SSH 部署金鑰、資料庫密碼、API Keys，檢查伺服器有沒有被建立異常帳號，審查 CI/CD 的 Secrets 有沒有外洩。

第三部分：怎麼判斷一個陌生網址

以 c1ph3r.site 為例（請勿造訪）：

  • 名稱混淆：Cipher（加密）這種技術味的詞常被拿來包裝成看似專業的網站，降低戒心。加上 leetspeak 數字替換（i→1、e→3）本身就是可疑訊號。
  • 頂級域名（TLD）屬性：.site 是低門檻便宜域名，常被用於短期釣魚站。這只是統計上的風險偏高，不是判罪依據，正當網站也會用。
  • 取得管道決定風險：陌生人在社群或交友軟體推薦的投資平台、通訊軟體不明群組的連結、聲稱帳號有問題的郵件——這三種來源的連結一律不點。
  • 驗證工具：用 VirusTotal 或 Trend Micro Site Safety Center 掃網址，不要自己開來看。
  • 若已點開：不要輸入任何資料，關閉並掃描系統。

[!warning] ⚠️ 存疑 / 更正
1. Gemini 說「你的網站並沒有被駭」——這句話下得太快。當時它還不知道使用者是這個站的開發者，也不知道彈窗出現在哪。彈窗可能來自被入侵的自家站、被劫持的瀏覽器擴充、或只是造訪了別人的惡意站，這三種情況的處置完全不同，不能一句話帶過。第二輪回答有修正回來。
2. Gemini 提到的惡意網域與 c1ph3r.site 的風險判斷，是根據當時的社群回饋，不是權威威脅情資。網域的信譽會變動，實際判斷請以 VirusTotal 等即時掃描結果為準，本筆記只保留「判斷方法」不保留「結論」。
3. Gemini 沒有提到 session cookie 也會被偷、光改密碼不夠（見 (l)），也沒有提醒 CSP 應該先用 Report-Only 模式試跑（見 (s)）。這兩點是本篇補上的。
