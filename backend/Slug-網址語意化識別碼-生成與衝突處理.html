Slug—網址語意化識別碼的生成、衝突處理與中文陷阱

🔖 本篇重點索引：a–l，共 12 個。

重點整理

(a) Slug 定義：網址（URL）中用來辨識特定資源、且易於人類閱讀的那一段，通常是 URL 的最後一節。它是標題的變體——大寫轉小寫、用連字號 - 取代空白與特殊符號，目的是讓搜尋引擎（SEO）與使用者都能一眼看懂這頁在講什麼。

(b) ID vs Slug 對照：假設有一篇標題為「如何學習 JavaScript」的文章——

類型 URL 範例 優缺點
用 ID example.com/posts/12345 對機器友善，但對人類不直觀，對 SEO 無助益
用 Slug example.com/posts/how-to-learn-javascript 語意明確、有利搜尋排名，使用者也比較敢點

(c) Slug 的四個特徵：

  • 全小寫：避免大小寫造成的連結混淆（部分伺服器路徑是區分大小寫的）。
  • 連字號分隔：用 - 而不是底線 _ 或空白——空白在 URL 中會被編碼成醜陋的 %20。
  • 唯一性：在同一個路徑下必須唯一，資料庫通常會對這個欄位建唯一索引（Unique Index）。
  • 不可變性：技術上可以改，但隨意改會讓舊連結全部 404，需要搭配 301 永久重導向。

(d) 為什麼 - 比 _ 好：Google 明確表示會把連字號視為分詞符號，底線則會被當成單字的一部分——how_to_learn 會被讀成一個詞，how-to-learn 才會被拆成三個詞。這是 SEO 上的實質差異，不只是慣例。

(e) 後端處理 Slug 的三個階段：

  1. 生成：使用者輸入標題（如 Hello World!），程式轉成 hello-world。
  2. 處理衝突：若資料庫已有 hello-world，自動加後綴變成 hello-world-1。
  3. 查詢：改用 slug 欄位查，而不是主鍵。
// 傳統用 ID 查詢
const post = await db.posts.findOne({ id: 123 });

// 使用 Slug 查詢（記得這欄要有索引，否則會全表掃描）
const post = await db.posts.findOne({ slug: 'how-to-learn-javascript' });

(f) ⚠️ Gemini 給的產生器有中文陷阱：原始版本如下，它宣稱輸出會保留中文，但實際上不會。

// ❌ Gemini 原版：中文會被整段吃掉
function createSlug(text) {
  return text
    .toString()
    .toLowerCase()
    .trim()
    .replace(/\s+/g, '-')      // 空白換成 -
    .replace(/[^\w-]+/g, '')   // 移除所有非字母、數字、連字號的字元
    .replace(/--+/g, '-');     // 避免重複的 --
}

createSlug("Node.js 101: 快速上手指南！");
// Gemini 宣稱輸出："nodejs-101-快速上手指南"
// 實際輸出："nodejs-101-"   ← 中文全被 [^\w-] 刪光了

原因是 JavaScript 的 \w 等價於 [A-Za-z0-9_]，只涵蓋 ASCII，任何中文、日文、重音字母都落在 [^\w-] 裡而被移除。

(g) ✅ 支援中文的正確寫法：改用 Unicode 屬性跳脫 \p{L}（任何語言的字母）與 \p{N}（任何數字），並加上 u 旗標。

function createSlug(text) {
  return String(text)
    .normalize('NFKC')              // 全形轉半形、統一相容字元
    .toLowerCase()
    .trim()
    .replace(/[\s_]+/g, '-')        // 空白與底線 → 連字號
    .replace(/[^\p{L}\p{N}-]+/gu, '') // 只保留任意語言的字母、數字、連字號
    .replace(/-+/g, '-')            // 收斂連續連字號
    .replace(/^-|-$/g, '');         // 去掉頭尾的連字號
}

createSlug("Node.js 101: 快速上手指南！");
// → "nodejs-101-快速上手指南"

(h) 中文 Slug 要不要用？兩派做法：

  • 保留中文：可讀性最好，現代瀏覽器網址列會正常顯示；但實際傳輸時會被百分比編碼（Percent-encoding）成一長串 %E5%BF%AB...，複製貼到純文字環境（如 Email、Slack）就很醜。
  • 轉拼音或改用英文標題：URL 乾淨、跨環境安全；代價是需要額外的轉換套件，且同音字會撞在一起。
  • 實務折衷：/posts/12345-how-to-learn-javascript——前面放 ID 保證唯一與查詢效率，後面放 slug 給人與搜尋引擎看，改標題也不會壞連結（只認前面的 ID）。

(i) 衝突處理不要只加流水號就收工：hello-world-1、hello-world-2 這種做法在高並發下會產生競爭條件（Race Condition）——兩個請求同時查到「沒有 hello-world-1」就都寫入。正確做法是靠資料庫的唯一索引擋下重複，捕捉 unique violation 錯誤後重試，而不是先查再寫。

(j) Slug 改動時務必留下 301：把舊 slug 存進一張 post_slug_history 表，路由查不到現行 slug 時再去歷史表撈，撈到就 301 Moved Permanently 導到新網址。這樣既保住 SEO 權重，也不會讓別人分享出去的舊連結變 404。

(k) 為什麼叫 Slug？這個詞源自新聞編採（Newsroom）。報紙排版時代，編輯會給每篇報導取一個簡短的「工作名稱」方便在排版流程中追蹤，那個短名就叫 slug；後來被引申到網頁開發。（更早則來自鉛字排版時代那塊叫 slug 的鉛條。）

(l) 安全提醒：slug 來自使用者輸入，即使清洗過也不要直接串進 SQL 或檔案路徑。要特別擋掉 ..、純數字（會跟 ID 路由撞車）以及保留字（new、edit、admin），否則 /posts/new 這種路由會被一篇標題叫「New」的文章劫走。

⚠️ 存疑／更正

Gemini 的 createSlug 範例輸出結果標錯了。它宣稱 createSlug("Node.js 101: 快速上手指南！") 會輸出 "nodejs-101-快速上手指南"，但 JavaScript 的 \w 只等於 [A-Za-z0-9_]，因此 [^\w-]+ 會把所有中文字一併刪除，實際輸出是 "nodejs-101-"。可自行在瀏覽器 Console 貼上驗證。本篇重點 (f)(g) 已標示錯誤並給出使用 \p{L}／\p{N} 加 u 旗標的正確版本。

另外 Gemini 未提到衝突處理在並發下的競爭條件（重點 i）、slug 與保留字路由撞車的風險（重點 l），這兩點在實作時比「怎麼生 slug」更容易踩雷。
