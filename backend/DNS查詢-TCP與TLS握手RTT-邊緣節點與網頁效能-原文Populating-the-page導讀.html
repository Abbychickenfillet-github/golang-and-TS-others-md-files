重點整理

一、DNS 查詢（DNS Lookup）

[!info] 一句話 瀏覽器要先把網域名稱翻譯成IP 位址，才有辦法建立連線，這個翻譯動作就是 DNS 查詢。

(a) 前往網頁的第一步，是找出該頁面的靜態資源（Assets）放在哪台伺服器上。Assets 指的是 HTML、CSS、JavaScript、字型、圖片等所有前端資源，不是只有圖片。

(b) 瀏覽器發起 DNS 查詢後，由名稱伺服器（Name Server）接收並回傳 IP 位址。原文的 fielded by a name server 中，field 借自棒球的「接球、處理球」，是「接收並應答」的意思，不是「有名的伺服器」。

(c) 首次查詢完成後，IP 會被快取（Cache）一段時間，後續請求直接讀快取，不必再問名稱伺服器。

(d) 每次載入網頁，每個主機名稱（Hostname）通常只需查一次；但頁面引用了幾個不同主機名稱，就要各查一次。字型、圖片、腳本、廣告、數據統計工具若分屬不同網域，就會產生多次 DNS 查詢。

(e) 原文的 metrics 在 Web 領域指數據統計／分析追蹤工具（如 Google Analytics 追蹤碼），不是法律上的「舉證」。

(f) 行動網路特別吃虧：請求要先到基地台，再到電信公司的中央機房核心網路（Core Network），才送上網際網路，物理距離會明顯拉高延遲。

(g) add significant latency 是「增加顯著的延遲時間」，不是「讓每一個延遲都有顯著差異」。

二、這篇 2015 年前後的老文章現在還成立嗎

[!check] 依然成立的部分 DNS 解析仍是建立連線的必要前置；訊號往返的物理延遲（RTT）在行動裝置上仍是不可忽視的成本。

[!tip] 已被現代技術大幅緩解的部分 (h) Anycast DNS 與邊緣節點：權威 DNS 與 CDN 節點部署在離使用者極近的邊緣機房，縮短往返耗時。 (i) HTTP/2 與 HTTP/3 多路複用：HTTP/1.1 時代為了繞過「單一網域最多 6 條連線」的限制而流行 Domain Sharding（域名分片），反而製造多次 DNS 查詢；HTTP/2 之後最佳實踐反轉成盡量維持單一網域。 (j) Resource Hints：<link rel="dns-prefetch"> 提前解析 DNS，<link rel="preconnect"> 連 TCP 與 TLS 都提前做完。 (k) 5G 與 MEC（多存取邊緣運算）：把處理與快取下放到基地台旁，降低前往中央機房的延遲。

三、邊緣節點（Edge Nodes）的物理實體

(l) 邊緣節點確實是分布在世界各地城市的實體機房，術語叫 PoP（Point of Presence），一個 PoP 可能有幾台到幾百台機架式伺服器，比起佔地數十萬平方公尺的 Hyper-scale Data Center 精簡許多。

(m) 光在光纖玻璃介質中的速度約 2×10⁸ m/s（真空中約 3×10⁸ m/s）。台灣到美西來回約 20,000 公里，光單純在光纖裡飛一趟的硬性物理極限就要約 100 毫秒，加上沿路數十個路由器轉接，實際 RTT 常達 150～200 毫秒。走邊緣節點則傳輸距離從 10,000 公里降到 10 公里，實體傳輸時間從 100 ms 降到 1～5 ms。

架構 使用者到伺服器距離 純光纖傳輸時間 實際 RTT 量級
集中式源站（美國俄勒岡） 約 10,000 km 約 50 ms 單程 150～200 ms
邊緣節點 PoP（台北） 約 10 km 可忽略 1～5 ms

(n) Populating the page 指把資料填入頁面：先拿到空骨架 HTML（如 <div id="app"></div>）→ 透過 API 取得資料 → 把資料塞進 DOM 並繪製上畫面。First Contentful Paint 通常發生在頁面被「完全填滿」之前。

四、跨網域載入資源的成本

(o) <img src="https://other.com/a.jpg"> 這種跨域圖片在效能上的代價是：多一次 DNS 查詢、多一次 TCP＋TLS 握手、且無法共享既有的 HTTP/2 連線。

(p) 但在安全性（同源政策 SOP）上是預設允許的：瀏覽器允許 <img src>、<script src>、<link rel="stylesheet"> 嵌入跨域資源。風險在於對方刪圖或掛掉會連累你（Hotlinking 外連）。

(q) <a href="https://other.com"> 這種點擊才跳轉的超連結完全沒有效能成本，因為使用者按下去之前瀏覽器根本不會去連 other.com。

[!example] 「無法共享 HTTP/2 多路複用」白話版（公路比喻） 建立連線＝在你的電腦與某台伺服器之間蓋一條專屬公路（TCP 連線＋TLS 加密通道），蓋起來很花時間。 HTTP/1.1＝一條車道一次跑一輛車，只好同時蓋 6 條公路。 HTTP/2 多路複用＝同一條公路切成無數個微型通道，CSS、JS、圖片同時併發傳送。 但公路是建立在特定兩端之間的：通往 mywebsite.com 的公路 A 根本通不到 other.com，所以跨域圖片必須另外蓋公路 B。

你的電腦 (瀏覽器)
├──【公路 A (HTTP/2 通道)】────> mywebsite.com   (CSS, JS, HTML 共享同一條管道)
└──【公路 B (全新獨立通道)】───> other.com       (圖片 a.jpg，需重做 DNS + TCP + TLS)
五、TCP 三向握手、TLS 握手各需幾個 RTT，以及握完手之後的慢啟動

[!info] 什麼是 RTT RTT（Round Trip Time，往返時間）＝封包從瀏覽器發出、到達伺服器、再傳回瀏覽器的一整趟來回時間。

(r) TCP 三向握手固定 1 個 RTT（SYN → SYN-ACK → ACK），與 TLS 版本無關。

Client (瀏覽器)                                Server (伺服器)
   |─────── SYN ───────────────────────────────>|
   |<────── SYN + ACK ──────────────────────────|   ──> 累計 1 RTT
   |─────── ACK ───────────────────────────────>|   TCP 通道建立完成

(s) TLS 握手依版本而異：

階段與協定 所需 RTT 首次連線總計 備註
TCP 三向握手 1 RTT — 所有 TCP 連線的基本開銷
TLS 1.2 握手 2 RTT 3 RTT 傳統標準，需兩次完整往返
TLS 1.3 握手 1 RTT 2 RTT 現代主流，把演算法協商與金鑰交換合併
TLS 1.3 0-RTT Resumption 0 RTT 1 RTT 已有歷史 Session Key 時，可在 TCP 的 ACK 夾帶 Early Data

[!warning] 跨域為什麼慢 即使用 TLS 1.3，載入跨域資源仍要重付 2 個 RTT（TCP 1＋TLS 1）。跨國傳輸若 1 RTT＝150 ms，光是連線建立就白白浪費 300 ms。

五之一之補、SYN、ACK 這些縮寫到底是什麼意思（2026-09-22 補充）

上面那張圖寫了 SYN → SYN-ACK → ACK，但那三個字其實是三個旗標位元（flag bits），不是三種特別的封包。

先認字
縮寫 全名 中文 這一位元設成 1 代表
SYN Synchronize 同步 「我要建立連線，並且同步序號」
ACK Acknowledge 確認 「我確認收到你到某個序號為止的資料」
FIN Finish 結束 「我沒有資料要再傳了」（正常關閉用）
RST Reset 重設 「這個連線有問題，立刻砍掉」（異常中斷用）
PSH Push 推送 「別再等緩衝區裝滿了，馬上交給應用程式」

所以「SYN-ACK」不是一種新的封包類型，它是同一個封包裡把 SYN 和 ACK 兩個位元同時設成 1。它在一次傳輸裡同時說了兩句話：「我同意建立連線」＋「我確認收到你剛剛那個」。

三個步驟各自在說什麼
  Client                                        Server
    |                                             |
    |──── ① SYN, seq=x ─────────────────────────>|
    |     「我要連線，我這邊的序號從 x 開始」            |
    |                                             |
    |<─── ② SYN + ACK, seq=y, ack=x+1 ───────────|
    |     「我同意。我的序號從 y 開始，                 |
    |       而且我確認收到你的 x，下一個請給我 x+1」     |
    |                                             |
    |──── ③ ACK, ack=y+1 ───────────────────────>|
    |     「我確認收到你的 y，下一個請給我 y+1」         |
    |                                             |
    |════ 連線建立，開始傳資料 ═══════════════════>|

白話講 seq 與 ack 這兩個數字：

  • seq（Sequence Number，序號）：我送出的這批資料，第一個位元組的編號是幾號。

  • ack（Acknowledgment Number，確認號）：我已經收到你到某個編號為止的資料，下一個請從這個號碼開始給我。

這兩個數字就是 TCP 能「可靠傳輸」的關鍵——有了編號，封包就算亂序抵達也能重新排好，掉了哪一段也算得出來，該重傳哪一段一目了然。這也是為什麼前面說封包會被切開、順序可能錯亂，但你的 HTML 最後還是完整的。

為什麼非要三次？兩次不行嗎

這是經典面試題，關鍵在「雙向都要確認對方收得到」。

步驟 完成後，誰確定了什麼
① SYN Server 知道：Client 能發送，而且想連線
② SYN-ACK Client 知道：Server 收到了我的請求，而且 Server 也能發送
③ ACK Server 才知道：Client 收到了我的回應

少了第三步，Server 永遠不知道自己那個 SYN-ACK 有沒有送到。它會處於「我以為連線建立了，但對方可能根本沒收到」的狀態——如果 SYN-ACK 在路上掉了，Server 會傻等一個永遠不會來的請求，而 Client 完全不知道有連線存在。

（延伸：TCP 關閉連線需要四次（FIN → ACK → FIN → ACK），因為兩個方向要分別關閉，一邊說完了另一邊可能還有資料要傳。）

順便協商了什麼：MSS 就是在這裡決定的

握手不只是打招呼，雙方會在 SYN 與 SYN-ACK 的選項欄位（TCP Options）裡交換參數：

協商的參數 全名 作用
MSS Maximum Segment Size 一個封包最多能裝多少資料，雙方各報一個，取小的那個
Window Scale 窗口縮放因子 讓接收窗口能超過 65535 bytes 的上限，高頻寬連線必要
SACK Permitted Selective Acknowledgment 支援「選擇性確認」，掉包時只重傳缺的那段而不是全部重來
Timestamps 時間戳 用來量測 RTT 與判斷封包新舊

這一格解答了一個之前留著的問題：「MSS 約 1460 bytes」這個數字從哪來的？

答案是：它不是寫死的常數，是每次連線在三向握手時協商出來的結果。

流程是這樣：

  • a. 雙方各自算出自己這邊能接受的 MSS（通常是 本地 MTU − 40，以太網路就是 1500 − 20（IP 標頭）− 20（TCP 標頭）= 1460）
  • b. 在 SYN／SYN-ACK 裡互相告知
  • c. 實際採用兩者中較小的那個

所以如果中間經過 VPN 或某些隧道（它們會加自己的標頭，壓縮可用空間），MSS 就會小於 1460，你的 HTML 會被切成更多包。這也是為什麼「1460」要講成「典型值」而不是定值。

[!tip] 想親眼看到這三個封包 Chrome DevTools 的 Network 面板看不到這一層，它最細只到「一個 HTTP 請求」。 要看到 SYN／SYN-ACK／ACK 三個實際封包、以及 Options 欄位裡協商的 MSS 數字，工具是 Wireshark（封包分析器）。抓一次連線，在過濾欄打 tcp.flags.syn == 1 就只會留下握手的封包。

五之二、握完手還不會全速：TCP Slow Start（慢啟動）

(u) TCP Slow Start（慢啟動）是一套避免網路擁塞的發送速率控制機制 　　它解決的問題是：連線剛建立時，伺服器並不知道中間這條路徑能吃多少資料量 　　　　若一開始就全速送，中途的路由器來不及處理就會丟封包（Packet Loss），反而更慢 　　所以它的哲學是「先用小流量試水溫，再指數級加速」

(v) 誰用什麼控制什麼：發送端（伺服器）維護一個叫「擁塞視窗」（CWND，Congestion Window）的計數器 → CWND 決定「還沒收到 ACK 之前，最多能在路上放幾個封包」 → 每收到接收端回來的 ACK 就把 CWND 放大 → 放大到門檻或丟包為止

項目 全名與中文 這個值在做什麼 典型數值
CWND Congestion Window，擁塞視窗 發送端自己算出來的「路上最多能放幾個封包」 初始 10 個 MSS（約 14 KB）
RWND Receive Window，接收視窗 接收端告訴發送端「我的緩衝區還吃得下多少」 由接收端在 TCP 標頭回報
ssthresh Slow Start Threshold，慢啟動門檻 指數成長的煞車點，超過就換成線性成長 動態調整，丟包時被下修
MSS Maximum Segment Size，最大區段大小 一個 TCP 區段能裝的最大位元組數 乙太網路典型 1460 bytes

[!note] 實際送出量＝min(CWND, RWND) 發送端每一輪能送的量取兩個視窗的最小值：CWND 是「怕塞車」（網路狀況），RWND 是「怕爆倉」（接收端處理能力）。慢啟動只管 CWND 這一邊。

(w) 成長節奏：每經過 1 個 RTT，CWND 大致加倍（指數成長）

第 1 輪 RTT：送 10 個封包  ──收到 ACK──>
第 2 輪 RTT：送 20 個封包  ──收到 ACK──>
第 3 輪 RTT：送 40 個封包  ──收到 ACK──>
第 4 輪 RTT：送 80 個封包 ……

名字叫「Slow」是指「起步點很低」，不是指「成長很慢」——它其實是 2 的次方在飆。

(x) 兩種結束方式，對應兩種後果：

結束原因 發生了什麼 CWND 接下來怎麼走
CWND 達到 ssthresh 指數成長踩煞車 進入擁塞避免（Congestion Avoidance），改成每 RTT 只加 1 個 MSS 的線性成長
偵測到封包遺失 路由器塞車、封包被丟 下修 ssthresh，並大幅縮減 CWND 重新試探（詳見下方存疑欄的 Reno 行為）

[!warning] 這件事怎麼咬到網頁效能 (1) 小檔案吃不到你家的大頻寬：幾 KB 的 CSS／JS 可能在 CWND 還沒長大前就傳完了，頻寬根本沒用到。 (2) 每加速一級都要等 1 個 RTT，所以跨國高延遲線路上，慢啟動的代價會被 RTT 放大——這正好接回上面 (r)(s) 的 RTT 計算。 (3) 現代的解法是不要一直重開新連線：HTTP Keep-Alive／HTTP/2 多路複用讓同一條已經「暖起來」（CWND 已長大）的連線繼續用；HTTP/3（QUIC）則用 0-RTT 恢復與連線遷移，減少重來一次的次數。

六、封包（Packet）與 Socket 的差別

(t) 兩者不是同一個東西：封包是網路上流動的「資料包裹」，Socket 是作業系統開給程式的「通訊端點／API」。

比較項目 封包（Packet） Socket（套接字）
真實身分 網路傳輸層級的資料單元 作業系統開給軟體的程式介面 API
生活比喻 郵差在路上送的實體信件 你家門口的郵筒／電話機
存在位置 在纜線、路由器、Wi-Fi 訊號中流動 在電腦記憶體與作業系統核心中
包含內容 Header（來源 IP、目標 IP、Port）＋ Payload IP＋Port＋協定，在 Linux 中對應一個 File Descriptor
程式員怎麼碰 通常不直接處理，由 OS 自動切碎與組裝 直接呼叫 socket.connect()、socket.write()、socket.recv()

Socket 的中文正式譯名是「套接字」，意譯可作「通訊端點」，但實務上工程師多半直接講英文 Socket。

[ 你的應用程式 ]  ── socket.write("Hello World") ──▶
[ Socket (OS 核心介面) ]  ── OS 加上 TCP/IP 標頭，切成封包 ──▶
[ 封包 Packets ]  ── 經光纖／基地台飛越網路 ──▶
[ 伺服器 OS ]  ── 拆標頭、重組、放進 Socket buffer ──▶
[ 伺服器應用程式 ]  ── socket.read() 讀出 "Hello World"
七、TLS 是什麼

TLS（Transport Layer Security，傳輸層安全性協定）是網路上用來防偷看、防竄改、防假冒的加密通訊標準。HTTP ＋ TLS ＝ HTTPS。

  • 機密性（Encryption）：把明文變密文，公用 Wi-Fi 被監聽也看不懂。
  • 完整性（Integrity）：透過雜湊與 MAC 確保途中沒被竄改。
  • 身分驗證（Authentication）：靠 CA（憑證頒發機構）簽發的憑證，確認連到的是真網站而非釣魚站。

TLS 與 SSL 是新舊代關係：SSL 由 Netscape 於 1990 年代開發（1.0／2.0／3.0），因嚴重漏洞已全部廢棄；TLS 1.0 其實就是 SSL 3.1。現在網路上跑的全是 TLS 1.2 與 1.3，大家口中的「SSL 憑證」正式名稱其實是「TLS 憑證」。

| 應用層 (HTTP, WebSocket, SMTP)     |  <-- 業務資料
+------------------------------------+

八、觀念釐清：「你的電腦」是誰的電腦

[!question] Abby 的疑問 「我已經部署上去了，為什麼還說是『我的電腦』和伺服器之間搭公路？不就只剩伺服器嗎？」

這裡的「你的電腦」指的是訪問網站的人（Client）的電腦，不是你寫程式、部署網站的那台開發機。

  • Server：24 小時開機、有固定 IP 的遠端主機，靜靜等待連線。
  • Client：任何打開瀏覽器輸入你網址的人，包括你自己用手機測試的時候。
  • 公路不是預先蓋好的：每一位訪客按下 Enter 的那一刻，才會與你的伺服器動態建立一條專屬於該次存取的加密通道。

TCP Slow Start 慢啟動（2026-09-21 擷取）— https://gemini.google.com/app/d3170a12b286f9b1

使用者：用中文解釋（承接前一則關於 TCP Slow Start 的英文說明）

Gemini：TCP Slow Start（慢啟動）是一種為了防止網路擁塞而採取的資料傳輸機制，核心哲學是在不確定網路狀況時，先從小流量開始測試，再快速提升傳輸速度。

  1. 為什麼需要：客戶端與伺服器剛建立 TCP 連線時，伺服器並不知道中間的網路路徑能承受多少資料量。如果一開始就以最大頻寬全力發送，很容易造成網路路由器來不及處理而丟包（Packet Loss），導致嚴重的網路卡頓。

  2. 運作原理：伺服器會維護一個稱為「擁塞視窗」（Congestion Window, CWND）的數值，代表一次可以發送的資料包數量。早期規範 CWND 從 1 個封包開始，現今標準（如 RFC 6928）大多從 10 個封包（約 14 KB）開始。伺服器每收到一輪客戶端回傳的確認訊號（ACK），就會將 CWND 的大小加倍：第 1 輪 RTT 發送 10 個封包、第 2 輪 20 個、第 3 輪 40 個、第 4 輪 80 個。名字雖然叫 Slow，指的是起步時流量很小，但實際上傳輸速度是以 2 的次方呈指數級快速飆升。

  3. 何時結束 Slow Start：(a) 達到慢啟動門檻 ssthresh 時，切換到擁塞避免（Congestion Avoidance）階段，不再以 2 倍暴增，改成每輪只增加 1 個封包的線性平緩增長；(b) 發生封包遺失時，伺服器會重新調整門檻（ssthresh），並大幅縮減 CWND，重新調整發送節奏。

  4. 對網頁載入速度的影響：小檔案無法發揮全速，許多容量小的網頁元件（如幾 KB 的 CSS 或 JS 檔）可能在 Slow Start 還沒升到最大速度前就已經傳送完畢；由於每增加一次流量都需要等待一個往返時間（RTT），在高延遲的網路上（如跨國連線）連線建立初期會感覺較慢；現代 HTTP 協定採用 Keep-Alive（連線複用），或是基於 UDP 的 QUIC／HTTP/3，盡量減少重複建立 TCP 連線與重新經歷 Slow Start 的次數。

[!warning] ⚠️ 存疑／提醒 (1) Gemini 說「TLS 1.2 需要 2 個 RTT」是標準完整握手的情況；實務上 TLS 1.2 若使用 False Start 或 Session Resumption，可縮短到 1 個 RTT，這點對話中沒有提到。 (2) 對話中提到的 IP 位址 93.184.216.34 是 example.com 的舊 IP，該網域已於 2025 年更換 IP 與託管方式，僅供理解範例，不要當現況引用。 (3) 「1 RTT＝150 ms」是台美跨國的典型量級，實際值依線路與時段變動很大，不是固定常數。 (4) Gemini 說「每收到一輪 ACK 就把 CWND 加倍」是簡化說法。RFC 5681 的實際規則是每收到一個 ACK，CWND 就增加 1 個 MSS；因為一個 RTT 內會收到「整個視窗份量」的 ACK，加總起來的效果才近似於每 RTT 加倍。面試若被追問「為什麼是指數成長」，要答得出這個逐 ACK 累加的機制，而不是只背「加倍」。 (5) Gemini 說「丟包就大幅縮減 CWND」沒有分清楚兩種丟包。以 TCP Reno 為例：偵測到重複 ACK（Fast Retransmit）時，ssthresh 降為目前 CWND 的一半、CWND 進入快速恢復；但若是逾時（RTO Timeout），CWND 會直接打回 1 個 MSS 重新慢啟動，代價大得多。另外現代 Linux 預設用的 CUBIC、Google 的 BBR 對丟包的反應都跟 Reno 不同，BBR 甚至不把丟包當成擁塞訊號。 (6) QUIC／HTTP-3 並沒有取消慢啟動：RFC 9002 明定 QUIC 也有 Slow Start 與 Congestion Avoidance。QUIC 真正省掉的是 TCP 與 TLS 分開握手的 RTT，以及靠 0-RTT 恢復與連線遷移減少「從頭再暖一次」的次數。
