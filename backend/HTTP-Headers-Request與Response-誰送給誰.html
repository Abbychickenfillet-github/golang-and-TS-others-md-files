  2. 同一個頁面裡，CSS 請求與 API 請求各自帶著自己那一包 Request Headers。

    每一個網路請求都是獨立的一次 HTTP 交換，headers 各自產生。

    UTF-8 是字元編碼，壓縮是 Content-Encoding: gzip 在管的。

    bundle 會被下載到使用者電腦，按 F12 就能讀到字串，金鑰必須留在後端。

    OAuth 彈窗登入需要靠 window.opener 把結果回傳給母視窗。

申論題

  1. 請完整說明：一個使用者在你的網站按下按鈕呼叫第三方 AI API，從前端到第三方之間，金鑰經過了哪些 header、由誰產生、為什麼不能少掉中間那一層後端。

    參考方向：(1) 前端只打自家後端，這一段的 Request Headers 不含第三方金鑰，可能只帶自家的 Cookie 或 Authorization。(2) 後端路由收到請求，從伺服器上的環境變數讀出金鑰，組出 x-goog-api-key 與 Content-Type: application/json，再對第三方發一次全新的請求。(3) 第三方回 Response Headers 與 body 給後端，後端只把需要的資料轉給前端。(4) 少掉後端這層，金鑰就會出現在瀏覽器可讀的位置，任何人 F12 就能盜用，帳單算在你頭上。

HTTP Headers — Request 與 Response 各自由誰產生、送給誰、用完丟掉

⚠️ 這篇的來源對話在 Gemini 側欄被自動命名為「常見 4xx 用戶端錯誤狀態碼」，但整段對話的實際內容是 HTTP Headers 的方向性與 API 金鑰該放在哪個 header，跟 4xx 狀態碼無關。標題以實際內容為準。

重點整理

1. 一次請求裡有兩包 header，方向剛好相反

(a) Request Headers（請求標頭）：瀏覽器（client）產生，往伺服器（server）送。
內容是「我是誰、我想要什麼、我接受什麼格式」，例如 User-Agent、Cookie、Accept、Authorization。

(b) Response Headers（回應標頭）：伺服器產生，往瀏覽器送。
內容是「我回給你的東西長怎樣、你要怎麼處理」，例如 Content-Type、Content-Encoding、Cross-Origin-Opener-Policy。

(c) Abby 當時講反了，這裡是修正點：瀏覽器收到 Response Headers 之後，只拿來處理「這一次」的回應內容，不會再把 Response Headers 原封不動回傳給公司的伺服器。
所以「大型應用有幾百萬使用者，是不是每次都要把 response headers 傳回去」這個擔心不存在——response headers 是單向、用完即丟。

(d) 真正每次都會往上送的是 Request Headers：每一個網路請求（HTML、CSS、JS、圖片、XHR/fetch）都各自帶自己的一包 Request Headers，所以在 DevTools Network 面板裡每一列都能點開看到各自不同的 headers。

2. 逐條看這次對話出現的 header

Header 方向 誰產生 做什麼
User-Agent Request 瀏覽器 一段文字，告訴伺服器「我是哪個瀏覽器、哪個作業系統、哪種裝置」，讓伺服器回傳合適的內容
Cookie Request 瀏覽器 把先前 Set-Cookie 存下來的值帶回同源伺服器
Content-Type 兩邊都有 送出方 宣告 body 的媒體型別與字元編碼，例如 text/css; charset=UTF-8、application/json
Content-Encoding Response 伺服器 宣告 body 用哪種壓縮演算法壓過，例如 gzip，瀏覽器據此解壓，目的是縮小傳輸體積
Cross-Origin-Opener-Policy（COOP） Response 伺服器 控制這份文件跟它用 window.open() 開出來的新分頁，要不要放在同一個 browsing context group
x-goog-api-key / Authorization Request 呼叫方程式 攜帶 API 金鑰做身分驗證

(e) Content-Type 的兩段式寫法：text/css 是媒體型別（MIME type），charset=UTF-8 是字元編碼。
要分清楚：UTF-8 是字元編碼，不是壓縮演算法；壓縮是 Content-Encoding: gzip 那一條在管的。對話裡這兩個詞曾混在一起講，這裡拆開。

(f) COOP 的 same-origin-allow-popups：這份文件自己被隔離在獨立的 browsing context group，但它主動開出來的 popup 仍然保留 window.opener 參照，代價是拿不到 cross-origin isolation。
典型用途是 OAuth 彈窗登入：授權頁在 popup 開啟，結果要靠 window.opener 回傳給母視窗，所以不能把參照切斷（延伸見 OAuth與RESTful-Firebase登入-彈窗vs重定向）。

3. API 金鑰放在哪裡

(g) API 金鑰是「夾在 Request Headers 裡」送出去的，不是另外一個神秘的地方。
在 DevTools Network 面板點開該筆請求 → Request Headers，就會看到金鑰那一行，同一包裡通常還有 Content-Type: application/json。

(h) curl 用 -H 參數加上這個標頭，例如：

curl "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent" \
  -H "x-goog-api-key: $GEMINI_API_KEY" \
  -H "Content-Type: application/json" \
  -X POST \
  -d '{"contents":[{"parts":[{"text":"Hello"}]}]}'

(i) 金鑰一定要寫在後端路由裡，不要寫在前端程式。
原因很直白：前端 bundle 會被下載到使用者電腦上，任何人按 F12 就能讀到字串。正確做法是前端打自家後端 → 後端拿伺服器上的環境變數組出 x-goog-api-key → 後端再打第三方 API → 把結果回給前端。

(j) 金鑰本身的新舊制差異另開一篇：Gemini-API-Auth-Keys-授權金鑰-與標準API-Key差異。

4. 怎麼自己驗證（Abby 可以馬上動手）

(k) 打開任一網站 → F12 → Network → 重新整理 → 點任一列 → Headers 分頁。
上半 General（method、status code、remote address），中段 Response Headers，下段 Request Headers。同一頁的 CSS 請求跟 API 請求，Request Headers 內容會不一樣，這就是 (d) 說的「每個請求各自一包」。

(l) 在 Console 打 navigator.userAgent，會印出這個瀏覽器送出去的 User-Agent 字串本體，跟 Network 面板裡看到的那一行對得起來。
