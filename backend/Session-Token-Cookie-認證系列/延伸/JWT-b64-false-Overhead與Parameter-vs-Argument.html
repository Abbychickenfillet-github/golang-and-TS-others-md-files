JWT b64:false、Overhead 與 Parameter vs Argument

geminijwtrfc7797術語更新 2026-11-03

RFC 7797 為 JWS 新增 b64 header parameter，可讓 payload 不經 Base64url 編碼。順便釐清兩個容易混淆的術語。相關：[[Session與JWT-有狀態與無狀態驗證-過期機制與Base64url]]（Base64url 的來龍去脈）。

重點整理

本篇重點 a–j，共 10 個　 （點一下重點可隱藏／顯示，自己考自己）

(a)b64 是 JWS Header 裡的布林值 parameter，預設 true（payload 必須 Base64url 編碼）。設 "b64": false 時，規範允許 payload 保持原樣（Unencoded）直接簽章與傳送。所以「可不編碼」就是因為它是可選的 true／false 旗標。
(b)Overhead（開銷）：為完成任務而額外消耗、但不是核心資料本身的資源（時間、記憶體、頻寬）。比喻：寄 200 公克的書，紙箱與氣泡紙就是 overhead。
(c)Base64 的 overhead 有兩種：資料體積（每 3 bytes 變 4 字元，約膨脹 33%，3 MB 變 4 MB）與CPU 運算（發送端編碼、接收端解碼）。b64:false 就是為了省掉這兩者。
(d)Overhead 一詞來自會計：工廠只要「屋頂（overhead）還在」就必須付的固定費用（租金、電費、行政薪水），相對於直接成本（原料、產線人力）。後來借用到電腦科學。
(e)Parameter（參數）是規格或函式宣告中的欄位名稱（function add(a,b) 的 a、b）。Argument（引數）是呼叫時實際傳入的值（add(3,5) 的 3、5）。
(f)RFC 7515（JWS）與 RFC 7519（JWT）把 header 的 key（alg、typ、crit、b64）統稱 Header Parameter，因為規範是在「定義欄位結構」而不是「呼叫函式」。實際填入的 false、"HS256" 才是值。
(g)常見 JWT 用 JWS Compact Serialization：Header、Payload、Signature 三段都經 Base64url 編碼，再用 . 串接。Header 與 Payload 是 JSON 先以 UTF-8 轉 bytes 再 Base64url；Signature 是對「編碼後 Header + . + 編碼後 Payload」簽章後再 Base64url。
(h)Base64url 是編碼不是加密：任何人解碼都能讀 Payload，不能放密碼與個資。例外 b64:false 是更明文，不是更安全。
(i)編碼：公開、可逆、不需金鑰，為跨系統傳輸（Base64、URL encoding）。加密：演算法加金鑰保護隱私。編碼是公開的翻譯，加密是加上密碼的鎖。
(j)UTF-8 是可變長度編碼：ASCII 1 byte，常見中文字 3 bytes，罕見字與 emoji 可到 4 bytes。JWT 含中文時須先 UTF-8 再 Base64url。
