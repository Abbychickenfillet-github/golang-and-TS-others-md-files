# AES-256-GCM 的 256 是金鑰的位元數，和 SHA-256 的摘要長度是兩回事

本篇重點 a–e，共 5 個。相關：[[4-jwt-signing-algorithms-and-access-refresh-flow]]、[[15-憑證-簽章-權限三詞辨析]]

## a. 兩個 256 各自量什麼

| 名稱 | 256 指的是 | 輸入 | 輸出 |
| --- | --- | --- | --- |
| SHA-256 | 輸出（摘要 digest）固定 256 位元，即 32 位元組 | 任意長度資料 | 32 位元組 |
| AES-256 | 金鑰（key）長度 256 位元，即 32 位元組 | 128 位元的區塊＋32 位元組金鑰 | 128 位元的區塊 |

AES 的區塊（block）不論 128、192、256 都固定是 128 位元；變的只有金鑰長度。GCM 是運作模式，常見的隨機數 nonce 為 96 位元、驗證標籤 tag 為 128 位元，這兩個數字和 256 無關。

## b. 金鑰不是文字，是 32 個位元組

AES 演算法吃的是 32 個位元組的二進位資料，位元組可以是 0 到 255 的任意值，大多數不是可印出的字元。所以「金鑰長度 256 位元」的意思是「這串位元組有 32 個」，不是「文字有 32 個字」。

## c. 你問的「金鑰用 UTF-8 編碼後的長度」對了一半

把文字當金鑰用，函式庫最後仍要拿到 32 個位元組，常見做法是把文字用 UTF-8 編成位元組，所以只有在文字剛好編出 32 位元組時才合法。

| 寫法 | 長度怎麼算 | 問題 |
| --- | --- | --- |
| 32 個英數字的字串，直接 UTF-8 | 英數字每個字 1 位元組，共 32 位元組 = 256 位元 | 長度對了，但每個字元只有約 6 位元的亂度，實際強度遠低於 256 位元 |
| 含中文的字串 | 中文每個字 3 位元組，11 個字就 33 位元組 | 「字數」不等於「位元組數」，容易長度不符而報錯 |
| 32 位元組隨機資料再存成 hex | 文字長 64 字 | 文字是 64 字，但金鑰仍是 256 位元 |
| 32 位元組隨機資料再存成 Base64 | 文字長 44 字（含 `=` 補位） | 同上，用的時候要先解碼回 32 位元組 |

所以文字長度、位元組長度、強度（亂度）是三件事：「長度」看位元組數，「強度」看這串位元組有多不可預測。

## d. 人記得住的密碼要怎麼變成 256 位元金鑰

不能直接把密碼當金鑰，要經過金鑰衍生函式（KDF，Key Derivation Function）拉成 32 位元組。

| 來源 | 建議做法 |
| --- | --- |
| 使用者輸入的密碼 | 用 Argon2、scrypt 或 PBKDF2 這類刻意慢的 KDF，加隨機 salt |
| 另一把高亂度的主金鑰 | 用 HKDF 衍生出不同用途的子金鑰 |
| 直接要一把新金鑰 | 用密碼學安全的亂數產生器取 32 位元組，例如 Node 的 `crypto.randomBytes(32)` |

把密碼丟進 SHA-256 取 32 位元組雖然長度剛好，但雜湊很快、攻擊者能每秒猜上億次，不建議當成標準做法。這也是兩個 256 的交會點：SHA-256 的輸出剛好能當 AES-256 的金鑰長度，但「長度合適」不代表「適合拿來衍生金鑰」。

## e. 對應到 JWT 的 A256GCM

JWE 的 `enc: 'A256GCM'` 要求內容加密金鑰（CEK）剛好 256 位元。用 `alg: 'dir'` 時，你提供的對稱金鑰就是 CEK，所以必須正好 32 位元組；少一個位元組函式庫就會拒絕，不會自己補。
