JWT b64:false、Overhead 與 Parameter vs Argument

RFC 7797 為 JWS 新增 b64 header parameter，可讓 payload 不經 Base64url 編碼。順便釐清兩個容易混淆的術語。相關：[[3-Session與JWT-有狀態與無狀態驗證-過期機制與Base64url]]（Base64url 的來龍去脈）。

重點整理

本篇重點 a–j，共 10 個

(a) b64 是 JWS Header 裡的布林值 parameter，預設 true（payload 必須 Base64url 編碼）。設 "b64": false 時，規範允許 payload 保持原樣（Unencoded）直接簽章與傳送。所以「可不編碼」就是因為它是可選的 true／false 旗標。

(b) Overhead（開銷）：為完成任務而額外消耗、但不是核心資料本身的資源（時間、記憶體、頻寬）。比喻：寄 200 公克的書，紙箱與氣泡紙就是 overhead。

(c) Base64 的 overhead 有兩種：資料體積（每 3 bytes 變 4 字元，約膨脹 33%，3 MB 變 4 MB）與CPU 運算（發送端編碼、接收端解碼）。b64:false 就是為了省掉這兩者。

(d) Overhead 一詞來自會計：工廠只要「屋頂（overhead）還在」就必須付的固定費用（租金、電費、行政薪水），相對於直接成本（原料、產線人力）。後來借用到電腦科學。

(e) Parameter（參數）是規格或函式宣告中的欄位名稱（function add(a,b) 的 a、b）。Argument（引數）是呼叫時實際傳入的值（add(3,5) 的 3、5）。

(f) RFC 7515（JWS）與 RFC 7519（JWT）把 header 的 key（alg、typ、crit、b64）統稱 Header Parameter，因為規範是在「定義欄位結構」而不是「呼叫函式」。實際填入的 false、"HS256" 才是值。

⚠️ 存疑/更正：b64:false 使用時 RFC 7797 要求 header 的 crit 也要列出 b64，且 unencoded payload 不能含 . 等會破壞 compact serialization 的字元，Gemini 本次回答沒提到，Abby 若要實作請讀 RFC 7797 第 5 節。（此為我依 RFC 內容補充，未重新抓取全文，請核對。）

追加 2026-11-05

(g) 常見 JWT 用的是 JWS Compact Serialization：Header、Payload、Signature 三段都經過 Base64url 編碼，再用 . 串接。Header 與 Payload 是 JSON 先以 UTF-8 轉成 bytes 再 Base64url；Signature 是對「編碼後的 Header + . + 編碼後的 Payload」做簽章後再 Base64url。

(h) Base64url 是編碼（Encoding）不是加密（Encryption）：任何人解碼就能讀 Payload，所以不能把密碼、個資放進 Payload。唯一例外是 (a) 的 b64:false 讓 Payload 不編碼，但那是更明文，不是更安全。

(i) 編碼與加密的差別：編碼是公開、可逆的轉換規則，目的是跨系統正確傳輸，不需要金鑰（Base64、URL encoding）。加密是用演算法加金鑰保護隱私，沒金鑰就無法輕易還原。口訣：編碼是公開的翻譯，加密是加上密碼的鎖。

(j) UTF-8 是支援中文的可變長度字元編碼（Unicode 的實作方式）：ASCII 英數 1 byte，常見中文字 3 bytes，罕見字與 emoji 可到 4 bytes。所以 JWT 內含中文時，必須先 UTF-8 轉 bytes 再 Base64url。

追加 2026-11-09：JWS 與 JWT 的層級、為何 b64:false 還要放進 crit

(追加 a) JWT（RFC 7519）是上層容器規範，定義 Claims 的格式。簽章的 JWT 本質上就是一個 JWS（RFC 7515），JWS 規定「頭部、載荷（Payload）、簽章」如何組合與保護。

(追加 b) 啟用 RFC 7797 未編碼載荷時，Protected Header 長這樣：{"alg":"HS256","b64":false,"crit":["b64"]}。

(追加 c) b64:false 是「載荷不做 Base64URL 編碼」，crit:["b64"] 是「接收方不認得 b64 就必須拒絕」。 　沒有 crit 時，舊版驗證端會忽略不認識的 b64，照舊把載荷當 Base64URL 解碼，結果驗簽失敗或解出亂碼。 　所以 RFC 7797 規定用 b64:false 就必須把 b64 列進 crit。
