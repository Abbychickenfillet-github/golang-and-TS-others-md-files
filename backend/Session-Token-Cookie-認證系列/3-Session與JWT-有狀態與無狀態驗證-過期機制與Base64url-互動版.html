1. JWT 和 JWS 的關係：JWS 是「整個簽過章的物件」的通用格式，JWT 是拿 JWS 當外殼來裝 claims（userId、exp…）的一種用法，所以 JWT 欄的「防竄改」和 JWS 欄相同。
　　RFC 7797 規定 JWT 不得使用 b64:false，這個選項只有一般 JWS 能用。詳見第 4 篇 相關公式一覽。
2. iron-session 的效果接近 JWE：兩者都是「藏起來＋防竄改」，差別在 JWE 是 RFC 標準、可以交給別的系統讀；iron-session 適合自己發、自己讀。三種格式的並排圖見第 4 篇 第 5 節。

重點整理

a. HTTP 是無狀態（Stateless）協定：它沒有內建機制把前後兩個獨立請求關聯起來。所以網站要記住「這個人已登入」就得額外做 Session 管理。

b. Session 驗證流程：
1. 使用者登入送出 credentials。
2. 伺服器 authenticate 是否 valid。
3. 伺服器建立 Session，把 Session ID 存進 session store。
4. 伺服器把 Session ID 用 Set-Cookie 發給瀏覽器。
5. 之後每個請求瀏覽器自動夾帶這個 Cookie ，伺服器拿 ID 查表確認身分。

c. OWASP 的建議：架構允許時優先選集中式 Session，Session ID 放 Cookie 並設 Secure 與 HttpOnly ，搭配 SameSite（Lax 或 Strict）擋 CSRF ，並使用成熟框架而不是自己實作。

d. 兩種攻擊與防禦：
1. Session 劫持（Hijacking）：攻擊者用 MITM 或 XSS 偷走 Session ID。防禦是全站 HTTPS 加 HttpOnly。
2. Session 固定（Fixation）：攻擊者預先指定 Session ID 騙使用者登入。防禦是 每次登入都重新產生新的 Session ID 並作廢舊的。

e. Session 過期有兩層，缺一不可：
1. Cookie 層：省略 Expires 與 Max-Age 就是 Session Cookie ，關瀏覽器即刪（OWASP 預設建議）。設了就變 Persistent Cookie ，例如「記住我 30 天」。
2. 伺服器層：只靠前端清 Cookie 不算登出 ，伺服器沒刪 Session 就等於沒收回權限。

f. 伺服器端三種逾期機制：閒置逾期（Idle ，例如 20 分鐘沒請求）、絕對逾期（Absolute ，例如登入後 8 小時）、更新逾期（Renewal ，定期換發新 ID 並作廢舊 ID ）。

g. 有狀態的優點：隨時可控（刪一筆就踢人）、機敏資料留在伺服器、請求只帶短 ID 。缺點：流量大時要共用 store ，伺服器負擔重。

h. 無狀態的 JWT 把狀態打包成「伺服器簽章過的物件」交給客戶端，資源伺服器驗得出簽章就不必回頭查發行端，適合分散式微服務。缺點是體積較大與難以即時作廢。

i. 補救 JWT 難作廢的做法：Access Token（短效期）加 Refresh Token（長效期），由 Refresh Endpoint 集中決定要不要繼續發新 Access Token 。

j. JWT 被改過 exp 無法登入：JWT 由 Header、Payload、Signature 三段組成，Signature 是伺服器用密鑰對前兩段運算出來的。你可以輕易解碼並修改 Payload（它只是 Base64url 編碼，不是加密），但改完後簽章與內容對不上；你沒有密鑰就無法重新產生正確簽章，後端驗證失敗回 401 Unauthorized 。

k. 後端驗證 JWT 的步驟：後端用自己的密鑰，對收到的 Header 與 Payload 重新做簽章運算，算出結果與第三段比對，不一致就拒絕。

l. ⚠️ 補充（Gemini 沒講）：JWT 的 Payload 「可被任何人讀」，所以不要放密碼等機敏資料。簽章保證的是「沒被改」，不是「看不到」。

簽章怎麼保護 payload：整個 token 的保護力，來自別人無法複製出正確的 signature。
　　signature 是伺服器用 secret 對 header 與 payload 算出來的。secret 本身不在 signature 裡，也無法從 signature 反推回 secret。
payload 其實是裸的：只做 Base64url 編碼，任何人都看得到內容，只是改了就會被發現。

m. URL-safe 的意思：資料編碼後只含不會破壞 URL 結構的字元。標準 URL 的保留字元（? & / =）與不安全字元（空格 + # < >）若混在資料裡，會被誤判為網址結構。

n. Base64url 與標準 Base64 的差異：
1. 把 + 換成 - 。
2. 把 / 換成 _ 。
3. 通常省略結尾補齊用的 = 。
這是 JWT 被稱為「compact, URL-safe」的原因（RFC 7519）。

1. btoa 的名字是 binary to ASCII：把 bytes 轉成 ASCII 可見字元，用的方法就是 Base64，所以輸出的 64 個字元全部落在 ASCII 範圍內。
2. 只編碼 {" 兩個 bytes 時，第 3 個字元是 I，結尾補一個 =。後面接上更多內容，例如 btoa('{"alg"')，第 3 個字元才會變成 J，得到 JWT 常見的 eyJ 開頭。
3. btoa 輸出的是標準 Base64（含 + / =）。要得到 Base64url，Node 可用 Buffer.from(字串).toString('base64url')。

o. JWT 確實會出現在網址中（Email 驗證連結、密碼重設連結、OAuth／OIDC 轉址、臨時下載連結），但即使它主要放在 Authorization Header ，採用 Base64url 也讓同一套編碼能同時用在 Header 與 URL 。

o-1. 什麼時候會用到 Base64url：token 為什麼會放進網址

1. Base64url 是為了網址傳輸設計的：token 有時要夾在網址參數裡傳遞，用 Base64url 編碼可以確保它在路由或解析時不會因為特殊字元而壞掉。
　　Base64url 是換一套字母表，而不是轉義：把 + 換成 -、/ 換成 _、拿掉結尾的 =，編碼出來的字元全部屬於網址可以直接出現的字元，所以放進網址時根本不需要再做百分比編碼（percent-encoding）。

2. 為什麼 token 要放在網址：因為有些情境下網址是唯一能帶資料的地方。

  • Email 驗證連結、重設密碼連結：信件只能給一個連結。使用者點下去時，可能已經不在原本的登入狀態，或是換了瀏覽器，沒有 cookie 可以帶，所以要把 token 放進網址，讓伺服器直接完成一次性的身分確認。
  • OAuth／OIDC 登入跳轉：瀏覽器從 LINE、Google 跳回來時只能透過網址帶資料，不能附加自訂 header（例如 ?code=…&state=…）。
  • WebSocket、EventSource：瀏覽器原生 API 不能設定 Authorization header，常改放 ?token=。
  • 臨時下載連結：例如 AWS S3 presigned URL，簽章直接寫在網址裡。

3. 重設密碼連結能放 token，靠的是「能收到這封信」，而不是「本來就有密碼」：使用者忘記密碼時，手上並沒有可用的憑證。
　　伺服器信任這個連結，是因為只有能登入那個信箱的人才拿得到它，token 證明的是「你控制這個 email」。
　　也因為網址會留在瀏覽器紀錄、伺服器 log 與 Referer 標頭裡，這類 token 一定要做到三件事：隨機且夠長、只能用一次、很快過期（常見 15 分鐘到 1 小時）。很多系統用的是存在資料庫的隨機字串，不一定是 JWT。

4. Instagram 分享連結：貼文網址 /p/短碼/ 的短碼，用的字元集是 A-Z a-z 0-9 - _，跟 Base64url 相同，一般認為它是把貼文的數字 ID 換算成這套 64 進位字元，讓網址變短又不需要轉義。
　　分享時另外帶的 igsh= 參數是分享識別碼，Instagram 沒有公開它的編碼方式，「它記錄了分享人」屬於推測，未經官方證實。

p. ⚠️ 存疑／更正：Gemini 把「JWT 放在 URL query」講得像常態做法，沒有提到風險。Token 放在網址會進入瀏覽器歷史、伺服器 access log 與 Referer 標頭而外洩，一般建議 Access Token 放 Header 或 HttpOnly Cookie ，網址上只適合「單次、短效期」的連結。另外 OIDC 的 implicit flow（把 id_token 放在 # fragment 回傳）已不被建議，現行建議用 Authorization Code Flow 加 PKCE 。

q. create session 譯成「建立工作階段」或「建立會話」，不要譯成「創造一個對話」。session 在後端指伺服器與客戶端之間的一段互動期間，不是 ChatGPT 那種聊天 Chat。情境對照：一般網路架構譯「建立工作階段」，登入認證譯「建立登入狀態」，資料庫或網路連線譯「建立連線」。

r. 純 JWT 不含傳統的 Session ID。伺服器不在資料庫存狀態（Stateless），使用者身分、權限、過期時間都打包在 Header.Payload.Signature 裡，伺服器用密鑰驗簽章就能信任內容。常見混合用法：在 Payload 放 jti（JWT ID，token 識別碼）做黑名單，或搭配存在資料庫的 Refresh Token，此時 Refresh Token 的運作就很像 Session。

s. 簽 JWT 用 EdDSA 時，header 正確寫法是 { alg: 'EdDSA' }，沒有 EdDSA256 這個名稱。ES256、ES384、ES512 帶數字，是因為 ECDSA 可搭 P-256、P-384、P-521 多種曲線；EdDSA 在 RFC 8037 預設搭 Ed25519 曲線，演算法名稱就叫 EdDSA。

t. 非對稱金鑰不是字串，也不是像 HS256 那樣直接傳 'my-secret-key'。流程是：PEM 文字（DER 二進位經 Base64 編碼、再加 -----BEGIN ...----- 頭尾）→ 用 jose 的 importPKCS8（私鑰）或 importSPKI（公鑰）轉成金鑰物件 → 交給 .sign() 或 jwtVerify()。私鑰常見格式是 PKCS#8，公鑰是 SPKI；舊版 RSA 私鑰標頭是 BEGIN RSA PRIVATE KEY（PKCS#1）。多行 PEM 放進 .env 時，換行要寫成 \n 或用引號包住多行。

import { generateKeyPair, SignJWT, jwtVerify } from 'jose'

// 1. 在記憶體產生 Ed25519（EdDSA）公私鑰對
const { privateKey, publicKey } = await generateKeyPair('EdDSA', { crv: 'Ed25519' })

// 2. 用私鑰簽發 JWT（protected header 的 alg 寫 'EdDSA'）
const jwt = await new SignJWT({ userId: 'user_123', role: 'engineer' })
  .setProtectedHeader({ alg: 'EdDSA' })
  .setIssuedAt()
  .setExpirationTime('2h')
  .sign(privateKey)

// 3. 用公鑰驗證，並限定只接受 EdDSA
const { payload } = await jwtVerify(jwt, publicKey, { algorithms: ['EdDSA'] })

u. ⚠️ 存疑／更正：(1) Gemini 說 KeyLike 可以是 JWK 物件，但 JWK 通常要先用 importJWK 轉成金鑰物件，且 jose 新版（v6）已移除 KeyLike 型別，改用 CryptoKey、KeyObject、Uint8Array 表示，實際型別請以你安裝版本的官方文件為準（本次未重新抓取）。(2) Gemini 示範的 PEM 內容（如 MC4CAQAwBQYDK2VwBCIEIJ...）是示意字串，不是可用金鑰，不能直接拿去驗證。

追加 2026-11-16：JWS 兩種序列化格式與 kid

v. JWS Compact Serialization（緊湊序列化）：三段以點隔開的 URL-safe 字串 BASE64URL(Protected Header).BASE64URL(Payload).BASE64URL(Signature)，只能單一簽章，整個 Header 都是 Protected Header，常用於 Authorization: Bearer 與 JWT。

w. JWS JSON Serialization：JSON 物件，成員 protected／header／payload／signature(s)，支援多重簽章與 Unprotected Header。protected 與 header 差在是否被簽章涵蓋：protected 放 alg 等不可竄改參數；header 是明文，放 kid 這類提示，不可放安全關鍵資訊。

x. kid（Key ID）：告訴驗證方用哪把公鑰驗章。金鑰會輪替（Key Rotation），有 kid 可直接從 JWK Set 取對應公鑰，沒有就得逐把試。（出處：RFC 7515）
