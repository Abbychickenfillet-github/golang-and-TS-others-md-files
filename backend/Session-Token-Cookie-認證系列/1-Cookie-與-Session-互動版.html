1. 為什麼需要 Cookie / Session

HTTP 協定本身是無狀態的(Stateless):伺服器把每個請求都當成獨立事件,沒有內建機制把「同一個客戶端的前後兩個請求」關聯起來(這比「伺服器不記得你是誰」精確)。

所以任何要「跨請求記住狀態」的功能——登入、購物車、偏好設定、多步驟表單——都需要額外的狀態管理,Cookie 就是 RFC 2109 為此設計的機制。

一句話分層:Cookie 是「傳遞機制」(RFC 定義的兩個 header),Session 是蓋在它上面的「有狀態的一段期間」,兩者不同層,不是同類並列。

小圖示:HTTP 請求與回應 →(create)→ stateful session

2. Cookie vs Session(資料存哪裡)

Cookie(客戶端儲存)

  • 一小段文字,伺服器發送、存在使用者瀏覽器。
  • 瀏覽器後續每次請求自動把 Cookie 帶回(放請求標頭)。
  • 容易被竄改或竊取,不適合放敏感資料。

Session(伺服器端儲存)

  • 資料存在伺服器(記憶體/DB)。
  • 給使用者一張「身分證」session_id,透過 cookie 傳給瀏覽器。
  • 安全性較高:使用者只看到 id、看不到內容。

白話:cookie 是「瀏覽器自動帶回」的小紙條;session 是把真資料留伺服器、紙條上只寫一個 id。

3. acme 購物流程逐步(RFC 2109 經典例子)

RFC 2109 用「買火箭發射器」示範:伺服器一路用 Set-Cookie 存狀態,瀏覽器一路用 Cookie 帶回、累加。

# 步驟 1  瀏覽器→伺服器:登入(送表單)
POST /acme/login HTTP/1.1

# 步驟 2  伺服器→瀏覽器:登入成功,發 cookie 記住身分
HTTP/1.1 200 OK
Set-Cookie: Customer="WILE_E_COYOTE"; Version="1"; Path="/acme"

# 步驟 3  瀏覽器→伺服器:加入購物車(自動帶上剛拿到的 cookie)
POST /acme/pickitem HTTP/1.1
Cookie: $Version="1"; Customer="WILE_E_COYOTE"; $Path="/acme"

# 步驟 4  伺服器→瀏覽器:再發一顆 cookie 記住商品
Set-Cookie: Part_Number="Rocket_Launcher_0001"; Version="1"; Path="/acme"

# 步驟 5+ 之後每次請求,瀏覽器把累加的 cookie 全帶回…

白話:每一步「伺服器發 Set-Cookie → 瀏覽器下次用 Cookie 帶回」。注意 這是 RFC 2109 的老示範:它把「商品、運送方式」等實際資料直接塞進 cookie。

⚠️ 實作時別學這點:現代做法是 cookie 只放 session_id,購物車/商品資料存在伺服器 DB(用 id 查回)。把 Part_Number 塞 cookie 是過時的。

4. Set-Cookie 與 Cookie 的對齊(互動)

你發現「Set-Cookie 發出去的 名=值,瀏覽器會原封帶回」——沒錯。把滑鼠移到任一段,上下對應的那段會同時亮(磚紅色):

伺服器→瀏覽器Set-Cookie: Customer="WILE_E_COYOTE"; Version="1"; Path="/acme"
瀏覽器→伺服器Cookie:　　 $Version="1"; Customer="WILE_E_COYOTE"; $Path="/acme"

對應關係:Customer=… ↔ Customer=…、Version="1" ↔ $Version="1"、Path="/acme" ↔ $Path="/acme"。

  • Customer="WILE_E_COYOTE" 兩邊一模一樣——瀏覽器把拿到的 名=值 原封帶回。
  • Version、Path 帶回時多了 $——下一節解釋。

5. 造訪 ≠ 登入;Set-Cookie 就是建立最小 session

  • 造訪網站就是一個「請求」,不一定要登入。HTTP 永遠「先請求、才有回應」,所以步驟 1(請求)不是 optional,是必做。
  • 你的 curl -I https://github.com 就是步驟 1(造訪)＋步驟 2(回 Set-Cookie),只是步驟 1 是「造訪首頁」不是「登入」。
  • 沒錯——步驟 2 伺服器回 Set-Cookie 的那一刻,就已經建立了一個「最小的 cookie-based session」。GitHub 連登入都不用、光造訪就發 _gh_sess(匿名 session),印證 session ≠ 登入。

呼應 RFC 2109:session 是「有狀態的一段期間」,跟有沒有登入無關。

6. session-based vs JWT-based 的路徑(連 ByteByteGo)

不管哪種「X-based」,整體形狀都一樣:登入 → 拿到憑證 → 之後每次請求帶憑證。差別在「帶什麼、走哪個標頭」:

Session-basedJWT-based
憑證是什麼session_id(短、要查 server)JWT(自帶資料、驗簽不查 server)
走哪個標頭Cookie(瀏覽器自動帶)常走 Authorization: Bearer(手動);也可放 cookie
acme 這個流程✅ 就是它❌ 不一定走 Set-Cookie/Cookie

白話:你貼的 acme 流程 ＝ session-based(走 Cookie) 那一條。JWT 若用 Authorization: Bearer,就不是走 acme 的 Set-Cookie/Cookie 路徑了。詳見 [[3-Session與JWT-有狀態與無狀態驗證-過期機制與Base64url]]。

7. 為何帶回去要加 $($Version、$Path)

  • $ 是 RFC 2109／2965 的「保留屬性標記」:帶 $ 的不是 cookie 本身,是關於 cookie 的 metadata(屬性),用 $ 跟真正的 名=值 區分。
  • $Version ＝ 用哪版 cookie 規格;$Path ＝ 這顆 cookie 的作用路徑(Path 就是 cookie 的生效範圍)。
  • 重點:這個 $ 語法早就淘汰了。現行 RFC 6265 的 Cookie 標頭沒有 $,就是 Cookie: name1=value1; name2=value2。你 curl 抓到的現代 cookie 也沒有 $——它只在這份老 RFC 看得到。

8. 登入會拿到自己的 cookie(step 3)+ 演算法時機

問:登入 GitHub 會得到自己的 cookie 嗎?

會。造訪時先拿到匿名 cookie(_gh_sess、logged_in=no);按下登入、帳密驗證成功後,那個回應會再 Set-Cookie 一顆代表「你是誰」的已驗證 cookie(如 user_session),並把 logged_in 改成 yes。等於把匿名 session 升級成已驗證 session。

問:演算法在 Set-Cookie 的時候就執行完畢了嗎?

對。加密／簽章是伺服器「送出 Set-Cookie 之前」就跑完的,Set-Cookie 帶的值已經是加密/簽好的成品。瀏覽器只負責存,不跑任何加密。所以你看到 Set-Cookie 時,演算法早在 server 端做完了(例如 GitHub 的 _gh_sess 是 Rails 用 AES-256-GCM 封好才送出,見 [[4-jwt-signing-algorithms-and-access-refresh-flow]] 的 GCM 動畫)。

9. F12 觀察重點:Set-Cookie 在哪、為什麼有時看不到

  • 口訣:Set-Cookie 是伺服器設定給我(response header)、Cookie 是我帶回去(request header)。
  • 坑:F12 複製「Response」看不到 Set-Cookie,因為你複製到回應主體(body),而 Set-Cookie 是標頭。要看:點請求 → Headers 分頁 → Response Headers。
  • 就算看 Headers 也可能沒有:Set-Cookie 只在「發新/更新 cookie」時出現(登入、登出、換 session);平常載入只是你帶 Cookie 上去。
📂 點開:我自己 curl -I https://github.com 的實測(2026-11-10) 
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Strict-Transport-Security: max-age=31536000; includeSubdomains; preload
X-Frame-Options: deny
Content-Security-Policy: default-src 'none'; ...(超長,略)...
Server: github.com
Set-Cookie: _gh_sess=CEyDhjWFL%2B...(加密亂碼)...%3D%3D; path=/; HttpOnly; secure; SameSite=Lax
Set-Cookie: _octo=GH1.1.1000111298.1794301386; expires=...2027...; domain=.github.com; path=/; secure; SameSite=Lax
Set-Cookie: logged_in=no; expires=...2027...; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax

三顆 Set-Cookie,都在「還沒登入」就發了:

  • _gh_sess:加密 session cookie(值用 -- 分三段 ＝ 密文/IV/驗證標籤,Rails 的 AES-256-GCM 格式);裝防 CSRF token、要跳回哪頁這種暫時狀態。
  • _octo:訪客識別碼(名字來自吉祥物 Octocat),做流量分析,跟登入無關,效期約一年。
  • logged_in=no:標記還沒登入;登入成功後改成 yes 並另發 user_session。

10. Cookie 安全旗標

  • HttpOnly:JS 讀不到(防 XSS 偷 cookie)。
  • Secure:只走 HTTPS。
  • SameSite(Lax/Strict/None):防 CSRF,搭配 [[9-CSRF-與-Antiforgery-Cookie]]。
  • Expires／Max-Age:決定關瀏覽器後是否還在(沒設 ＝ session cookie,關了就消失)。

白話:登入 cookie 三件套 HttpOnly ＋ Secure ＋ SameSite 一起上。查法:F12 → Application → Cookies。

11. 如果要自己用資料表存 session_id(有狀態 store)

// Prisma(next-one 用)
model Session {
  id           String    @id            // session_id（建議存雜湊值）
  userId       Int
  user         User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  data         Json?
  createdAt    DateTime  @default(now())
  expiresAt    DateTime
  revoked      Boolean   @default(false) // 強制登出用
  @@index([userId])
}
  • id:session_id 當主鍵,建議存雜湊(SHA-256)後的值(DB 外洩也不能直接冒用)。
  • revoked 或直接刪列 ＝ 強制登出——有狀態 session 勝過 JWT 的地方(能即時踢人)。

注意:你 next-one 現在用的 iron-session 是加密 cookie 派(stateless、沒這張表);只有想「即時撤銷、server 端查表」才需要建它。

12. 名詞定義 / RFC 是什麼

  • user agent(使用者代理):發 HTTP 請求的客戶端程式,最常見是瀏覽器,也含 App 的 HTTP client、curl、爬蟲。RFC 用這詞是不假設一定是瀏覽器。
  • origin server(原始伺服器):真正持有資源、產生權威回應那台(資源源頭),對照 CDN/快取/proxy。來源:RFC 9110。

RFC ＝ Request for Comments(名字是歷史遺留)

  • 1969 ARPANET 時真的是「徵求評論」的草稿,名字沿用至今;不是每個 RFC 都是標準(看狀態:Standards Track / BCP / Informational…)。
  • 標準會被取代:cookie 的 RFC 2109(1997)→ 2965 → 現行 6265,前兩個是 Historic。
  • 歷史:RFC 2109(1997-02)比 Ajax(2005 命名)早八年;當時主流瀏覽器是 Netscape Navigator(cookie 是 Netscape 1994 發明的)。
  • ECMAScript 跟 RFC 無直接關係:它由 Ecma International(TC39)維護(ECMA-262),跟 IETF 不同組織;但 JSON 同時被 ECMA-404 與 RFC 8259 定義、保持相容。

13. 自我測驗

  1. (是非)造訪網站一定要登入,伺服器才會發 Set-Cookie。

    光造訪(匿名)伺服器也會發 cookie,例如 GitHub 的 _gh_sess。session ≠ 登入。

  2. (填空)口訣:Set-Cookie 在 標頭,Cookie 在 標頭。

    Set-Cookie 是伺服器設定給你(response)、Cookie 是你帶回去(request)。

  3. (是非)現代 RFC 6265 的 Cookie 標頭還要寫 $Version、$Path。

    $ 語法是 RFC 2109/2965 的老東西,已淘汰。現行只寫 name=value。

  4. (申論)同樣是「登入→拿憑證→每次帶憑證」,session-based 和 JWT-based 差在哪?

    憑證不同:session_id(短、要查 server)vs JWT(自帶資料、驗簽不查 server);傳輸不同:session 走 Cookie 自動帶,JWT 常走 Authorization: Bearer 手動帶(也可放 cookie)。
