🧠 自我測驗

是非題

  1. 只要 Token 還沒過期，就可以判定使用者目前在線上。

    錯。Token 只能證明通過身分驗證，證明不了人現在在不在、視窗開著還是已經斷線。

  2. 使用者拔掉網路線時，前端會送一個下線通知給伺服器。

    錯。異常斷線不會有任何通知，只能靠伺服器端的心跳逾時判定。

  3. 手動設定的「請勿打擾」應該壓過自動偵測的結果。

    對。手動狀態優先權最高，否則使用者一動滑鼠就被改回 online。

  4. 線上狀態應該直接寫進主資料庫以確保一致性。

    錯。狀態變動非常頻繁，會把主 DB 打爆，實務上用 Redis 承接並用 Pub/Sub 廣播。

    再用 Key 的 TTL 或背景 Task 判斷是否逾時。

  3. Redis 做跨伺服器狀態廣播時用的機制叫 。

    發布訂閱，讓多台伺服器都能收到狀態變更。

申論題

  1. 請設計一個「好友上線狀態」功能，說明前端與後端各自負責什麼。

    參考方向：(1) 先把問題拆兩層——連線層決定 online/offline，行為層決定 idle/away/busy。(2) 連線層：登入後建立 WebSocket 長連線，連上就把 Redis 中該 user 標為 online 並廣播給好友；正常登出時前端主動通知（用 navigator.sendBeacon 較可靠）；異常斷線靠伺服器端 Ping-Pong 心跳逾時自動判定 offline。即時性要求不高時可退成每 30～60 秒的輪詢，用 last_active_time 加 TTL。(3) 行為層（純前端）：用 Page Visibility API 監聽 visibilitychange 決定 away；用 mousemove/keydown/scroll/click 重置 Timer，5～10 分鐘無動作切 idle；手動的「請勿打擾」存 DB 且優先權最高。(4) 後端只負責儲存與廣播，用 Redis Key-Value 存當前狀態、Pub/Sub 做跨機器廣播，避免高頻寫入主資料庫。(5) 補一句取捨：逾時秒數是產品決策不是規範，要看對「延遲多久算離線」的容忍度。

(4) Cookie-與-Session 講的是「身分怎麼被記住」，本篇講的是「狀態怎麼被即時同步」，兩件不同的事常被混為一談。

重點整理

一、為什麼不能只看 Token（a–b）

(a) 實務上絕對不會單靠 Token 判斷線上狀態。JWT 這類 Token 只能證明「使用者通過了身分驗證」，它無法反映使用者當下在不在、視窗開著還是縮小、或是已經斷線。

(b) 正確作法是把問題拆成兩層：「連線層」決定 online／offline（WebSocket 或輪詢），「行為層」決定 idle／away／busy（瀏覽器事件）。面試被問到這題，先講這個拆分再講細節，會比直接背 API 好很多。

二、線上／離線：兩種作法（c–e）

(c) 作法 A：WebSocket／Socket.io 長連線（主流，即時性高）

事件 發生什麼
上線 登入後建立 WebSocket 長連線；連線成功即把 Redis／DB 中該 user 狀態改為 online，並廣播給好友
正常下線 使用者點登出或關分頁，前端主動送斷線通知
異常斷線 伺服器在時限內收不到 Heartbeat／Ping-Pong 封包，自動觸發 disconnect 事件改為 offline

(d) 作法 B：Heartbeat／Polling 輪詢（即時性要求不高時）。前端每 30 秒到 1 分鐘打一次 Ping API，伺服器收到就更新 Redis 裡的 last_active_time；若超過 2～3 分鐘沒更新就判定離線，靠 Redis Key 的 TTL 或背景 Task 掃描。

(e) 兩種作法的差別只在「誰主動」：WebSocket 是伺服器發現連線斷掉，輪詢是伺服器發現時間戳過期。但兩者都需要逾時判定，因為「使用者拔網路線」不會有任何通知送到伺服器。

三、閒置／離開／忙碌：純前端偵測（f–h）

(f) Page Visibility API 負責「切分頁／視窗縮小」：

document.addEventListener('visibilitychange', () => {
  if (document.hidden) {
    // 切走了 → 送出「離開 (Away)」
  } else {
    // 回來了 → 送出「線上 (Online)」
  }
});

(g) Idle Detection 靠自己起一個 Timer：監聽 mousemove、keydown、scroll、click，有動作就重置計時器；5～10 分鐘沒動作就切成「閒置 (Idle)」。

(h) 手動狀態的優先權最高。像 Slack、Discord 的「請勿打擾 (Do Not Disturb)」是使用者自己選的，存進資料庫後必須壓過所有自動偵測結果，否則使用者一動滑鼠就被系統改回 online，體驗會很糟。

四、業界常見組合（i–j）

(i) 前端負責「判斷」，後端負責「儲存與廣播」：前端用 Page Visibility ＋ 滑鼠鍵盤 idle 事件決定當下狀態，透過 WebSocket 把狀態變更事件送出。

(j) 後端用 Redis 而不是主資料庫。狀態變動非常頻繁，寫進主 DB 會把它打爆；Redis 的 Key-Value 讀寫快，還能用 Pub/Sub 做跨伺服器廣播。這也是為什麼 presence 幾乎是 Redis 的教科書級使用情境。

⚠️ 存疑／需要留意

項目 對話中的說法 需要留意的地方
正常下線 「關閉分頁，前端發送斷線通知」 關分頁時送請求並不可靠。beforeunload 裡的一般 fetch 常來不及送出，要用 navigator.sendBeacon()；即使如此仍應以伺服器端心跳逾時為最終依據
逾時秒數 2～3 分鐘、5～10 分鐘 這是慣例值不是規範，實際要依產品對「延遲多久算離線」的容忍度調整
