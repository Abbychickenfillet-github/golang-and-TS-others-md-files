重點整理

一、渲染（Rendering）到底在做什麼

c. 渲染（Rendering）是瀏覽器把 HTML、CSS、JavaScript 這些靜態程式碼，轉換成螢幕上看得見、可互動的動態畫面的整個過程。方向是「靜態原始碼 → 動態畫面」，不是反過來。

d. 這個過程內部依序包含：Style（樣式計算）→ Layout（版面配置）→ Paint（繪製）→ Composite（合成）。

二、Reflow 與 Repaint 的分界（面試常考）

e. Repaint（重繪）：元素的外觀改變，但大小與位置沒變時，瀏覽器只需要重新畫這個元素。例如改 color、background-color、visibility。

f. Reflow／Layout（重排）：元素的尺寸或位置改變，瀏覽器必須重新計算版面。例如改 width、height、margin、top。

g. 成本關係：Reflow 一定會連帶觸發 Repaint，反過來不會。所以 Reflow 比 Repaint 貴，優化時優先消滅 Reflow。

h. 正解做法：做動畫時改用 transform 與 opacity。這兩個屬性可以直接交給合成線程（Compositor Thread）處理，跳過主線程的 Layout 與 Paint，主線程就不會被卡死。用 left／top 做位移則每一幀都要 Reflow。

三、面板上怎麼看

i. 在 Performance 面板錄製 Trace 之後，看主線程（Main Thread）那條火焰圖：紫色區塊代表 Layout 與 Style 計算，綠色區塊代表 Paint／Repaint 活動。

j. Long Task（長任務）：單一任務佔用主線程超過 50 毫秒就被歸類為 Long Task，這段期間頁面無法回應輸入，使用者感受到的就是掉幀（Jank）。面板會在該區塊右上角標紅色三角形。

k. 錄製結果可以存成 .json.gz 的 Trace 檔（勾選 include resource content 會一併帶上資源內容），之後匯入面板重新分析——適合把「當下重現的卡頓」留存下來慢慢查。

四、怎麼把這個技能講給別人聽

l. 對面試官（講底層邏輯）：「我會用 Chrome DevTools Performance 錄製 Trace，切分主線程的 Tasks，觀察點擊事件觸發後產生了多少次 Style 與 Layout（紫色區塊）。如果發現不必要的 Repaint（綠色區塊），我會檢查是哪個 CSS 屬性造成的，改用 transform／opacity 讓瀏覽器走合成線程，避免主線程卡死。我可以精準定位是哪一個 JS 函式讓主線程超過 50ms。」

m. 對主管（講商業價值）：「過去複雜頁面滑起來會頓，我們只能猜。現在我可以錄製 Performance，直接找出掉幀的根本原因，指出是哪一行 JS 阻塞、或哪裡 DOM 節點太多。遇到效能瓶頸不用盲目改 code。」

n. 兩段話的差別：對工程師講機制與名詞，對主管講問題被解決了、而且不用亂猜。同一個技能包裝成兩種語言，這件事本身就是面試加分項。
