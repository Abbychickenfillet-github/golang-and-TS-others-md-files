🧠 自我測驗

是非題

  1. 在 pgAdmin 4 裡，資料庫的大小要看 Properties 分頁。

    Properties 是設定（Owner、Encoding、Tablespace），Statistics 分頁才有 Size。這場對話就是卡在這個分別。

  2. pg_size_pretty 會把位元組數字轉成 kB / MB / GB / TB 的字串。

    它是純粹的格式化工具，本身不查任何東西。

  3. ORDER BY pg_size_pretty(pg_database_size(datname)) DESC 可以正確排出最大的資料庫。

    pg_size_pretty 回傳的是字串，排序會變成字典序，出現「9 MB 比 10 GB 大」的笑話。排序要用原始 bigint。

  4. pg_total_relation_size 等於 pg_table_size 加 pg_indexes_size。

    官方文件明講。一張表的總佔用 = 表本身 + 所有索引。

  5. DELETE 掉大量資料之後，pg_database_size 查到的數字會立刻變小。

    因為 MVCC，DELETE 只把 tuple 標成 dead，autovacuum 回收成可再用空間但不還給作業系統。要縮檔案得 VACUUM FULL 或 pg_repack。

  6. pg_database_size 的結果包含 WAL（預寫式日誌）的體積。

    不含。它只算資料庫的資料檔。C 槽爆掉時 WAL 堆積往往才是主因。

  7. 要用 pg_database_size 查某個資料庫，你必須對它有 CONNECT 權限。

    不過 CONNECT 預設就是授予的。

填空題

  1. 查單一資料庫總磁碟佔用的內建函式是 pg_database_。

    吃資料庫名稱或 OID，回傳 bigint。

  2. pgAdmin 4 裡真正顯示 Size 的分頁叫 。

    Properties 只有設定，沒有大小。

  3. 存放所有資料庫一列一筆的系統目錄表叫 pg_。

    欄位 datname 是名稱，datistemplate 標記是否為範本庫。

  4. 只算某張表所有索引總和的函式是 pg_ _size。

    很多時候索引比資料本身還大。

  5. PostgreSQL 讓刪除的資料不立刻消失的並行控制機制縮寫是 MVCC，全名 Multi-Version Concurrency 。

    這就是「刪了大小卻沒變小」的原因。

  6. 要真正把檔案縮小、把空間還給作業系統，可以跑 VACUUM （會鎖表）。

    或用不鎖表的 pg_repack 擴充套件。

申論題

  1. 你的 C 槽快滿了，懷疑是跑在 Docker 裡的 PostgreSQL。請完整說明你的排查步驟：怎麼在 pgAdmin 界面看、怎麼下 SQL 一次看出哪個庫哪張表最肥（並說明排序時最容易犯的錯）、以及為什麼「刪了一堆資料但大小沒變」、還有為什麼 pg_database_size 的數字跟 Docker volume 的實際佔用經常對不起來。

    參考方向：(1) 界面路徑——pgAdmin 4 左側 Object Explorer 點資料庫節點，主面板切 Statistics 分頁看 Size。注意選 Server 節點看到的是連線與交易統計，選 Database 才有 Size；Properties 分頁沒有大小。(2) SQL——單庫用 SELECT pg_size_pretty(pg_database_size('庫名'))；全庫排行用 SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database WHERE datistemplate = false ORDER BY pg_database_size(datname) DESC；找肥表用 pg_total_relation_size 搭配 pg_statio_user_tables，並分開列 pg_relation_size（資料）與 pg_indexes_size（索引）。(3) 排序陷阱——ORDER BY 一定要用原始 bigint，不能用 pg_size_pretty 的結果，否則是字串字典序，9 MB 會排在 10 GB 前面。(4) 刪了不變小——MVCC 的關係，DELETE 只把 tuple 標成 dead tuple，autovacuum 把它回收成「檔案內部可再用的空間」但不歸還作業系統。要真的縮檔案得 VACUUM FULL（鎖表、需要等量額外磁碟）或 pg_repack。(5) 數字對不起來——pg_database_size 只算該資料庫的資料檔，不含 WAL（Write-Ahead Log）、不含其他資料庫、不含 Docker 映像層與容器可寫層。可用 docker system df -v 對照 volume 實際佔用；C 槽爆掉時 WAL 堆積（例如 replication slot 卡住不推進）往往才是真兇。

PostgreSQL 資料庫大小怎麼看

[!info] 本篇重點 a–n 共 14 個
兩條路：點界面（pgAdmin 4 的 Statistics 分頁） 與 下 SQL（pg_database_size 家族）。後者才是能寫進監控腳本的那一種。

[!info] 與其他筆記的關聯（附理由）
a. 呼應 SQL-Join-Inner-Left-Right-主表判定與資料保留：同一個 SQL 資料夾底下的姊妹篇，那篇談查詢語意，本篇談維運面的「這個庫到底多肥」。
b. 呼應 PostgreSQL-Checkpoint與SIGTERM-Docker停止機制（在 Abby-notes 根目錄）：那篇講 PostgreSQL 什麼時候把資料真正寫到磁碟，本篇量的正是那些落地檔案的體積，兩篇是同一件事的因與果。
c. 呼應 C槽空間清理SOP 與 Docker問題prune+壓縮vhdx(虛擬磁碟)解決硬碟爆掉：C 槽爆掉時，跑在 Docker 裡的 PostgreSQL 常常是隱形兇手之一，本篇的查詢就是用來抓它的，可以接在那份 SOP 的排查清單後面。
d. pg_indexes_size 會告訴你索引佔了多少，很多時候索引比資料本身還大，這條線可以接回同層的 SQL-Join-Inner-Left-Right-主表判定與資料保留——JOIN 效能好不好，跟索引有沒有建對、建了多少直接相關。

重點整理

一、用 pgAdmin 4 點出來（e–g）

e. 最快的路徑：左側 Object Explorer 點選你的資料庫 → 主面板切到「Statistics」分頁。裡面會有一列 Size。

f. 「Properties」分頁看不到大小。Properties 是「這個物件的設定」（擁有者、編碼、Tablespace、權限），Statistics 才是「這個物件目前的統計數據」。這場對話裡 Gemini 兩邊講來講去，就是卡在這個分別。

pgAdmin 分頁 顯示什麼
Properties 物件的定義與設定（Owner、Encoding、Collation、Tablespace）
Statistics 物件的即時統計數據，資料庫層級包含 Size
SQL 這個物件對應的 DDL
Dependencies / Dependents 相依關係

g. 小提醒：Statistics 顯示的統計資料會依「你選的是哪種物件」而不同。選 Server 看到的是連線與交易統計，選 Database 才有 Size，選 Table 則會有 tuple 數、seq scan 次數這些。

二、下 SQL 才是正解（h–l）

界面只能點一個看一個，要排序、要寫進監控、要一眼看出誰最肥，就得下 SQL。

h. 單一資料庫：

SELECT pg_size_pretty(pg_database_size('future_sign_prod'));
片段 意思
pg_database_size(name) 內建函式。吃資料庫的名稱或 OID，回傳它佔用的總磁碟位元組數（bigint）。需要對該資料庫有 CONNECT 權限，預設是有的
pg_size_pretty(bigint) 把一坨位元組數字格式化成人看得懂的 kB / MB / GB / TB 字串

i. 所有資料庫排行榜（維運最常用的一句）：

SELECT datname AS 資料庫,
       pg_size_pretty(pg_database_size(datname)) AS 大小
FROM pg_database
WHERE datistemplate = false
ORDER BY pg_database_size(datname) DESC;
片段 意思
pg_database 系統目錄（system catalog）表，一列一個資料庫
datname 資料庫名稱欄位（dat 是 database 的縮寫慣例）
datistemplate = false 濾掉 template0 / template1 這兩個建庫用的範本
ORDER BY pg_database_size(datname) DESC 排序要用原始 bigint，不能用 pg_size_pretty 的結果——那是字串，排出來會變成「9 MB 比 10 GB 大」的字典序笑話

j. 揪出最肥的表（含索引）：

SELECT schemaname || '.' || relname AS 資料表,
       pg_size_pretty(pg_total_relation_size(relid)) AS 總大小,
       pg_size_pretty(pg_relation_size(relid))       AS 資料,
       pg_size_pretty(pg_indexes_size(relid))        AS 索引
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 20;

k. 各函式的分工（這張表是本篇最該記的）：

函式 量的是什麼
pg_database_size 整個資料庫佔用的總磁碟空間
pg_total_relation_size 一張表 + 它所有的索引 + TOAST。等於 pg_table_size + pg_indexes_size
pg_table_size 只有表本身（含 TOAST、free space map、visibility map），不含索引
pg_relation_size 單一 fork 的大小，預設是主資料檔，不含 TOAST 也不含索引
pg_indexes_size 這張表所有索引的總和
pg_column_size 單一欄位值的儲存大小（含壓縮後）
pg_size_pretty 純粹的格式化工具，把 bytes 轉成人話

l. 為什麼「刪了資料大小卻沒變小」：PostgreSQL 用 MVCC（Multi-Version Concurrency Control，多版本並行控制），DELETE 只是把 tuple 標成死掉（dead tuple），空間仍留在檔案裡等 autovacuum 回收成可再用空間，但不會還給作業系統。要真正縮檔案得跑 VACUUM FULL（會鎖表、需要等量的額外磁碟空間）或用 pg_repack。

三、Docker 裡的 PostgreSQL 另外量（m–n）

m. 如果 PostgreSQL 跑在容器裡，除了問資料庫本身，也要問 Docker：

# 進容器下 SQL
docker exec -it <容器名> psql -U postgres -c "SELECT pg_size_pretty(pg_database_size(current_database()));"

# 看 volume 實際佔多少
docker system df -v

n. 兩個數字通常對不起來，這是正常的：pg_database_size 只算資料庫的資料檔，不含 WAL（Write-Ahead Log，預寫式日誌）、不含其他資料庫、也不含容器的映像層。C 槽爆掉時，WAL 堆積往往才是主因。
