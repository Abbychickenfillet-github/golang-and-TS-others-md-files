零、這段程式碼在 MDN 的哪裡

var a = {};
Object.defineProperties(a, {
    'name': { value:'fillano', writable:false, enumerable:false, configurable:false },

誠實的答案：這段程式碼本身不在 MDN 上

fillano 是作者自己的名字，這是 fillano 的 ES5 介紹文（約 2011 年）裡自己寫的範例。 但它示範的語法在 MDN 上有明確對應的章節。

原文在講的事MDN 對應章節
Object.defineProperties(obj, {...}) 這個方法 Object.defineProperties()
四個欄位的意思與預設值 Object.defineProperty() → Description
Data 與 Accessor descriptor 互斥 Object.defineProperty() → Description
原文下一段那種 get／set 寫法 Working with objects → Defining getters and setters
哪些操作看得到不可列舉屬性 Enumerability and ownership of properties
"A data descriptor is a property with a value that may or may not be writable. An accessor descriptor is a property described by a getter-setter pair of functions. A descriptor must be one of these two flavors; it cannot be both."
—— MDN, Object.defineProperty() → Description

一、這算 getter 跟 setter 嗎

不算。你貼的這一段完全沒有 getter 跟 setter。

  1. 你貼的這段用的是 value 跟 writable → 這叫 ？？？，屬性背後就是一格死的值。
  2. 原文下一段才用 get 跟 set → 那個才叫 ？？？，屬性背後是一對函式。
  3. 一個 property 只能是其中一種。

所以分類方向是對的（這確實是物件相關的筆記），但精確地說： 主題是 property descriptor，getter/setter 只是它的其中一種形態。

二、最重要的澄清：writable 不是「能不能寫」的總開關

我原本的疑問

「writable: true 代表可以覆寫，拿掉是寫成 writable: false 還是完全不寫？ 拿掉也很奇怪啊，你要可以寫才能 get 或 set 吧？」

答案：完全不寫。而且「不寫」不等於「寫成 false」。

a. writable 只存在於 data descriptor 上，accessor descriptor 根本沒有這一格

不是「預設 false」，是這個欄位不存在。實測印出來只有四個欄位：

const e = {}; let _v = 'fillano';
Object.defineProperty(e, 'name', {
  get() { return _v; }, set(x) { _v = x; },
  enumerable: true, configurable: true
});

Object.getOwnPropertyDescriptor(e, 'name')
// { get: [Function], set: [Function], enumerable: true, configurable: true }
//   ↑ 沒有 value，也沒有 writable

b. 有沒有 set 函式，才是 accessor 屬性「能不能寫」的答案

e.name = '改成功了';
e.name    // '改成功了'   ← 沒有 writable 照樣寫得進去

c. 只有 get 沒有 set 才是真正的唯讀

const f = {};
Object.defineProperty(f, 'ro', { get() { return 1; }, enumerable: true });
f.ro = 999;  f.ro     // 1   ← 非嚴格模式，靜靜失敗
(function(){ 'use strict'; f.ro = 999; })()
// TypeError: Cannot set property ro of #<Object> which has only a getter

一句話記住兩組欄位的分工

你想表達的意思data descriptor 用accessor descriptor 用
這個屬性存什麼valueget 函式的回傳值
能不能被寫writable: true / false有沒有給 set 函式

所以「你要可以寫才能 get 或 set」這個推論，是把兩套機制混在一起了。 writable 管的是 data 屬性的賦值，set 管的是 accessor 屬性的賦值， 它們是兩條平行的路，不是一個在管另一個。

五、enumerable 的可見性對照

「enumerable: false 代表 for...in、Object.keys()、JSON.stringify() 對它沒有作用」—— 方向對，但措辭要修：不是那些方法對它沒作用，而是那些方法根本看不到它。 它還在物件上好端端地，只是不參與列舉。

Object.values(a)[30]Object.hasOwn(a,'name')true
Object.entries(a)[['age',30]]Object.getOwnPropertyNames(a)['name','age']

所以 enumerable: false 是「隱藏」不是「保護」。 真正的機密不該進到這個物件裡。

for...in 跟 Object.keys 的關鍵差異：原型鏈

function Parent(){}
Parent.prototype.inherited = 1;
const c = new Parent();  c.own = 2;

for (const k in c) ...   // ['own', 'inherited']   ← 走上原型鏈了
Object.keys(c)           // ['own']                ← 只看 own

這也解釋了為什麼老教科書會叫你在 for...in 裡加 ？？？。

六、「own」到底是什麼意思

own property（自有屬性）＝這一格是刻在這個物件身上的，不是從 ？？？繼承來的。

const proto = { fromProto: 'A' };
const d = Object.create(proto);   // d 的原型是 proto
d.normal = 'B';

d.fromProto                       // 'A'    ← 讀得到
Object.hasOwn(d, 'fromProto')     // false  ← 但不是 d 的 own property
Object.hasOwn(d, 'normal')        // true

三個條件一起擋掉誰的實測：

const proto = { fromProto: 'A' };
const d = Object.create(proto);                                        // ① 不是 own
d.normal = 'B';                                                        // 全部通過
Object.defineProperty(d, 'hidden', { value:'C', enumerable:false });   // ② 不可列舉
d[Symbol('sym')] = 'D';                                                // ③ 不是字串鍵

JSON.stringify(d)    // {"normal":"B"}   ← 只剩一個活下來

為什麼 payload 要寫成 {"__proto__": {"hacked": 1}}

hacked 這個名字沒有意義，它只是一個記號，用來檢查污染有沒有成功 —— 檢查方式是去問一個全新的空物件有沒有長出這個屬性。

  1. JSON.parse 之後 → ({}).hacked 是 undefined，沒被污染。
  2. p.__proto__ = { hacked: 1 } 之後 → 只有 p 自己的原型被換掉，({}).hacked 還是 undefined。
  3. 把 parse 結果丟進用賦值寫的遞迴 merge 之後 → ({}).hacked === 1、[].hacked === 1， ？？？。這才是災難。

十、跟其他筆記的關聯

  • 嚴格模式-PropertyDescriptor-與JSON的關係｜這篇是它的物件分支。那篇處理 descriptor → JSON 的方向，這篇處理 descriptor 本身的結構。
  • JavaScript資料型別總覽-原始型別與物件｜那篇說「物件是一組 key-value」，這篇補上每一個 value 其實是一份六欄位的說明書，不是一個裸值。
  • JSON｜enumerable 那一格是 JSON.stringify 的第二道篩選閘門。
  • JavaScript-Map-與-Object｜Map 的項目不是 property，所以完全不受 descriptor 系統管轄，JSON.stringify(new Map(...)) 才會得到 {}。
  • Day1-型別辨別-自動轉換-與immutable的四個層次｜那篇的第一層就是 writable:false，第二層 Object.freeze 等於把所有屬性的 writable 與 configurable 一起關掉。
