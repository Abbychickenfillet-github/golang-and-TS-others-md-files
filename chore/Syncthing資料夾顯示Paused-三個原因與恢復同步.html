🧠 自我測驗

是非題

  1. 資料夾顯示 Paused 代表同步發生錯誤。

    錯。Paused 是暫停狀態不是錯誤，通常是手動暫停或運行條件未滿足。

  2. 只要有一端暫停，兩邊的資料就會停在原地不同步。

    對，所以也要檢查 Devices 分頁看遠端裝置狀態。

  3. Syncthing 有開 File Versioning 之後，就算我在本機自己誤刪檔案也救得回來。

    錯。File Versioning 只對「從其他裝置同步過來的變更」生效，本機自己刪的舊版本 Syncthing 不會歸檔。

  4. 中了勒索軟體時，Syncthing 會把被加密的檔案同步到其他裝置。

    對。雙向同步不分好壞，刪除與加密都會被忠實傳播，所以它不是備份。

  5. Git 可以保護專案裡所有檔案，包含 .gitignore 掉的 .env 與本機資料庫。

    錯。Git 只保護「已 commit 且已 push」的內容，未追蹤檔案硬碟壞掉就沒了。

填空題

  1. Android 版 Syncthing 的省電與網路限制設定在 Settings → Conditions。

    常見的是「僅在 Wi-Fi 下同步」與「僅在充電時同步」。

  2. 備份的業界檢查表是 原則：3 份副本、2 種媒體、1 份異地。

    CISA 也以此作為小型組織的基準建議。

  3. Syncthing 把被覆蓋或刪除的舊檔放在資料夾內的 目錄。

    這是 File Versioning 的預設存放位置。

  4. 評估「多久救得回來」的指標縮寫是 （Recovery Time Objective，復原時間目標）。

    資料沒丟不等於沒影響，重灌與重新同步的時間也是成本。

申論題

  1. 為什麼 Paused 沒被發現會很麻煩？

    參考方向：兩端會各自累積修改，之後再恢復同步就要處理衝突檔（sync-conflict）。對筆記 vault 特別痛，因為同一篇 .md 兩邊都改過時 Syncthing 只會保留兩份，得手動合併。所以看到 Paused 要當成待辦立刻處理，而不是等下次再說。

  2. Abby 目前是「本機 + 手機 Syncthing + GitHub」，請說明這個組合合不合格，缺了什麼。

    參考方向：以 3-2-1 來看，份數（3）、媒體種類（本機碟／手機／雲端，2 種以上）、異地（GitHub）都勉強湊得出來，結構上算合格。真正缺的是「不會即時同步的那一份」——因為 Syncthing 是雙向即時，誤刪或中毒會同時毀掉本機與手機；GitHub 雖有歷史，但只涵蓋有 commit 且 push 的內容，涵蓋不到 .env、AppData 設定、SSH 私鑰與本機資料庫。補法是加一份冷備份（平常拔掉的外接硬碟或每週手動封存上雲），並列一張「換新電腦要重建什麼」的清單以縮短 RTO。

重點整理

(a) 資料夾右側出現紫色 Paused 標籤，代表該資料夾處於手動暫停或設定造成的暫停狀態，不是錯誤。

(b) 原因一：手動暫停過。點該資料夾展開詳細選單，找 Resume（恢復） 按鈕點下去即可。大多數情況是這個。

(c) 原因二：行動裝置的運行條件沒滿足。Android 版（尤其 Syncthing-Fork）有省電與網路限制，常見的是「僅在 Wi-Fi 下同步」與「僅在充電時同步」，條件不符就自動轉 Paused。到 App 的 Settings → Run Conditions 檢查勾選項。

(d) 原因三：遠端裝置那頭暫停了。切到 Devices（裝置） 分頁，確認對方裝置顯示為已連線且非 Paused。兩端只要有一端暫停，資料就停在原地。

追加 2026-09-07｜「我有 Git 又有 Syncthing，硬碟壞掉是不是就沒差？」（e–m）

起因對話：〈電腦啟動自動開啟網頁設定〉（標題是 Gemini 亂命名的，內容其實在問備份策略）— https://gemini.google.com/app/c4cf33faea9066d9

(e) 先講結論：Git ＋ Syncthing 這個組合可以擋「硬碟壞掉」，但擋不了「誤刪」與「中毒」。兩者都不是備份工具，只是剛好有備份的副作用。

(f) Git 備的是「內容的歷史」。它保存每一次 commit 的完整快照，所以你可以回到任何一個過去的版本。但它只保護「已經 commit 而且 push 出去」的東西——未追蹤的檔案（.gitignore 掉的 .env、node_modules、資料庫檔）、以及只在本地 commit 還沒 push 的內容，硬碟壞掉就一起走了。

(g) Syncthing 備的是「當下的狀態」。它做的是雙向即時同步（two-way sync）：A 裝置的檔案長什麼樣，B 裝置就跟著長什麼樣。

(h) 這正是它最危險的地方：刪除也會被同步。你在電腦上手滑刪掉整個資料夾、或中了勒索軟體把檔案全加密，Syncthing 會盡責地把「刪除」與「加密後的檔案」推到手機與另一台電腦，幾秒之內所有副本一起陣亡。Syncthing 官方 FAQ 自己就寫得很直白：它不是一個好的備份程式，因為所有變更都會傳播到所有裝置。

(i) 緩解方式一：打開 Syncthing 的 File Versioning（檔案版本控制）。它會把被覆蓋或刪除的舊檔丟進資料夾內的 .stversions/。但有一個關鍵限制：versioning 只對「從別台裝置同步過來的變更」生效——如果是你在本機自己改壞或刪掉檔案，Syncthing 不會、也沒辦法幫你歸檔舊版本。所以它是安全網，不是備份。

(j) 緩解方式二：補一份「冷備份」（cold backup），也就是不常時連線、不會即時跟著變動的離線副本，例如平常拔掉的外接硬碟、或每週手動壓縮上傳的雲端封存。冷備份的價值就在「它不同步」——災難傳不過去。

(k) 業界慣用的檢查表是 3-2-1 原則：3 份副本、放在 2 種不同媒體、其中 1 份異地（offsite）。對照 Abby 現況：Abby-notes 有「本機 + 手機（Syncthing）+ GitHub（Git）」大致湊得出 3 份、2 種媒體、1 份異地，結構上其實是合格的；缺的是「有一份不會即時同步」的那一環。

(l) RTO（Recovery Time Objective，復原時間目標）是備份策略裡另一個常被忽略的維度：資料沒丟不等於沒影響。硬碟壞掉後，重灌系統、git clone、重裝相依套件、等 Syncthing 把幾十 GB 重新同步回來，這段時間你是不能工作的。評估備份時要同時問「救不救得回」與「多久救得回」。

(m) 最容易漏掉的是「不在任何備份範圍內的檔案」：瀏覽器設定檔、各種工具的 AppData 設定、SSH 私鑰、.env、本機資料庫。建議做法是列一張「換新電腦要重建什麼」的清單（vault 裡已有 ../系統維護-C槽清理/本機應用程式用途清單 可以延伸），比事後才想起來好得多。

[!warning] ⚠️ 存疑／更正
Gemini 在這則對話裡把 Syncthing 描述成「備份」的一種，這個定位是錯的——Syncthing 官方文件明確說明自己不是備份程式。本篇 h、i 兩節已依官方 FAQ 與 File Versioning 文件更正。另外 Gemini 提到 versioning 可以救誤刪，也沒有說明「本機自己刪的救不到」這個關鍵限制，已於 (i) 補上。
