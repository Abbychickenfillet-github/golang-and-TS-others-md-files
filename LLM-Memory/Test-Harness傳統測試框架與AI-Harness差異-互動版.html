Test Harness 傳統測試框架與 AI Harness 差異

本篇重點 a–n，共 14 個

重點整理

a. Test Harness（測試框架/測試底層環境）定義：在單元測試或整合測試中，用來自動化執行測試、準備環境、注入依賴與模擬（Mock）輸入輸出的底層環境；在外部層級（API/服務整合測試/微服務）架設，目的是把被測系統（SUT）當黑盒，完全從外圍模擬真實相依服務。

b. 外層 Harness 核心架構：Test Runner 透過 HTTP/RPC 呼叫 SUT，SUT 對外的呼叫則導向 Mock/WireMock/LocalStack/Testcontainers 等模擬服務層，讓 SUT 收到的外部回應完全可控可預測。

c. 架設步驟：① 隔離外部依賴——REST API 用 WireMock/MSW 搭 Stub Server，資料庫/MQ/Redis 用 Testcontainers 或 Docker Compose 拉起乾淨隔離實例；② 設計 Harness 模組三個生命週期 setup()(啟動模擬容器)、reset()(每筆測試前清理狀態)、teardown()(釋放資源)；③ 測試案例透過統一 Harness 介面（beforeAll/afterEach/afterAll）專注在測試邏輯與斷言。

d. 最佳實踐：環境變數注入（SUT 需支援用環境變數覆寫外部服務 URL，否則 Harness 無法導流到 Mock）、共享容器策略降低重建成本（每次測試前 TRUNCATE 或 reset 狀態）、Deterministic State（測試間絕不互相干擾，所有外部回應與資料庫狀態每次測試開頭重新設定）。

e. AI Harness 定義：包在 LLM 外層的一套控制與評測系統。因為 LLM 本質上是黑盒且具隨機性（non-deterministic），AI Harness 負責輸入處理（Prompt 模板/RAG/Guardrails）、流程控制與 Tool Call、輸出結構化與校正（JSON Schema 驗證/修復）、評估與監控（回答品質評分/Token 消耗/延遲）。

f. AI Harness 架構：使用者輸入先經 Input Guardrails（安全檢查/防注入）與 Context/RAG Builder，進入 Harness Engine 與 LLM 模型（Gemini/Claude）往返，再經 Tool Call Manager（執行工具/重試）與 Output Parser（校正 JSON/Schema）、最後由 Evaluator & Logger 記錄品質與 Token，才輸出最終結構化結果。

g. AI Harness 三大類型：① Agent Runtime Harness——控管 Agent 行動邏輯，限制思考輪數避免死迴圈、捕捉 tool_call 去執行實際 API/DB、JSON 格式錯誤時自動請 AI 修正；② Evaluation Harness（如 lm-evaluation-harness）——丟入 MMLU/GSM8K 等 Benchmark 題集自動計分，統計正確率與幻覺率；③ Guardrails & Governance Harness——輸入過濾（Prompt Injection/PII）、輸出過濾（違規內容/JSON Schema 合規）。

h. 傳統 Test Harness vs AI Harness 對照：主要對象「傳統程式碼/微服務(SUT)」vs「LLM/AI Agent」；核心挑戰「控制外部服務依賴與模擬環境」vs「控制不確定性(non-determinism)與幻覺」；主要任務「Setup DB、Mock API、執行 Assertion」vs「Guardrails、Prompt 注入、Tool 執行、格式校正、Eval 評分」。

i. 正解：不需要為 AI 系統寫兩套業務邏輯——核心業務邏輯（結帳流程/計算折扣/抓資料庫）只寫在應用程式（Backend/API）裡；AI 負責思考、理解語言、決策與調用工具；AI Harness 是 AI 與原本系統之間的「守門員與接線生」，不是把 AI 思考邏輯重寫一遍。比喻：LLM 像能力強但偶爾犯錯的高薪顧問，AI Harness 像資深秘書——整理資料交給顧問（RAG/Context）、提醒顧問照公司格式講話（Output Validation）、顧問要做事時秘書幫忙操作內部系統（Tool Call）；業務系統才是公司真正的核心系統。

j. Harness 程式碼實際在寫什麼（通常只有幾百行，或直接調用 LangChain/LlamaIndex/Vercel AI SDK）：① 結構化約束（Schema Enforcement，JSON 格式不符自動加警語重送）；② 安全防護門（Guardrails，攔截敏感詞/Prompt Injection 不送給 AI）；③ 工具橋接器（Tool Executor，AI 要呼叫某函式時 Harness 代為呼叫後端 Service，結果轉文字餵回 AI）。

k. 業界常見 AI Harness 工具：評測類——EleutherAI/lm-evaluation-harness（git clone + pip install -e .，Hugging Face 排行榜背後的評測底層）、Promptfoo（npx promptfoo@latest init，CI/CD 用的 Prompt/RAG 測試工具）；Agent 控制類——LangChain/LangGraph（npm install langchain @langchain/core 或 pip install langchain）、Letta（前身 MemGPT，pip install letta，長期記憶 Agent 控制框架）；防護類——Guardrails AI（pip install guardrails-ai）。AI Harness 不是單一叫這個名字的下載軟體，而是一種軟體設計架構/工具套件的統稱，沒有單一官網下載頁。

l. Harness 沒有、也不可能達到 100% 準確率，原因：① LLM 底層是機率預測下一個 token，非確定性邏輯，即使 Temperature=0 仍可能在複雜語境產生幻覺或邏輯謬誤；② Prompt Injection 是無限博弈，攻擊者持續發明新越獄語法，Guardrail 規則不可能預測所有未知攻擊模式；③ 人類語言本身有歧義，語意不明時 Harness 難以 100% 判斷 AI 回答是否真正符合使用者意圖。

m. 加上良好 Harness 後的量化改善（相對「無 Harness 純 LLM 直連」）：JSON 格式合法率從約 70~85% 提升到約 99.9%（自動重試修復）；幻覺控制（RAG 情境）從容易憑空捏造降至約 2~5% 以下（限定只依參考資料回答）；工具調用成功率提升到 95% 以上（型別檢查+Fallback 重試）；Prompt 攻擊防禦率可達 90~98% 以上。

n. 業界因應「無法 100% 準確」的策略：Human-in-the-loop（高風險操作如轉帳/發正式信/改權限，Harness 只輸出「待確認動作」由人工點擊確認）、Graceful Degrade（重試 3 次仍失敗或低信心度時，直接切回傳統固定程式碼或回覆「系統繁忙」，不把壞答案丟給使用者）、持續監控與評測（用 Promptfoo/LangSmith 等每天跑幾千個邊界案例，確保更新 Prompt 或模型後準確率不下滑）。
