是非題

  1. pre / post 鉤子只對 start、test、stop、restart 這幾個保留字有效。

    對任意 script 名稱都有效。你自己取的 deploy、lint、report 一樣會找 predeploy、postdeploy。

  2. npm run build -- --mode staging 的 --mode staging 也會傳給 prebuild。

    官方文件明講：參數只傳給你指定的那支 script，不傳給 pre 或 post。

  3. build 失敗（非 0 退出碼）時，postbuild 不會執行。

    post 鉤子只在主 script 成功結束後才跑。

  4. 不管你在哪個子資料夾打 npm run，script 執行時的工作目錄都是 package.json 所在那一層。

    所以 script 裡可以放心用相對路徑。

  5. 環境變數 npm_lifecycle_event 會告訴你目前跑到哪一個階段。

    可以只寫一支腳本、內部依階段分支。

  6. postinstall 在資安上沒什麼風險，因為它只是安裝後的清理工作。

    它是供應鏈攻擊最愛的落腳點——npm install 一個被投毒的套件就會自動執行任意程式碼。新版 npm 已加入 npm-approve-scripts 這類審核機制。

  7. scripts 裡能直接寫 vite build 而不用寫完整路徑，是因為 npm 執行前會把 node_modules/.bin 塞進 PATH。

    這也是 npx 的第一順位查找位置。

填空題

  1. npm 的 pre/post 規則寫在官方文件的 using-npm/ 章節。

    網址是 docs.npmjs.com/cli/v11/using-npm/scripts/。

  2. 告訴你目前跑到哪個生命週期階段的環境變數是 npm_lifecycle_。

    值就是 prebuild、build、postbuild 這類字串。

  3. husky 這類 git hook 工具通常掛在 npm 的 這個安裝期腳本上。

    它在 npm install 後、npm publish 前，以及安裝 git 依賴時觸發。

  4. shell 慣例裡代表「參數結束、後面原封不動往下傳」的標記是兩個減號 。

    npm run build -- --mode staging 就是靠它。

  5. 跨平台版本的 rm -rf，常被寫在 prebuild 裡清理輸出資料夾的套件叫 。

    因為 Windows 沒有 rm -rf。

申論題

  1. 你接手一個專案，package.json 裡有 prebuild、build、postbuild、predeploy、deploy 五個 script。請完整說明 npm 的 pre/post 生命週期規則、它跟安裝期生命週期腳本（preinstall/install/postinstall/prepare）的差別、有哪三個實務上最容易踩的細節、以及為什麼 postinstall 是供應鏈資安的高風險點。

    參考方向：(1) 規則——對任意 script 名稱 X，npm run X 會依序找並執行 preX → X → postX。這不限保留字，自訂名字一樣吃這套。所以打 npm run deploy 實際上會先跑 predeploy（通常裡面寫 npm run build），再跑 deploy。(2) 與安裝期腳本的差別——preinstall / install / postinstall / prepare 是 npm install 時自動觸發的，跟 npm run 無關；prepare 在 npm install 不帶參數後、npm publish 前，以及安裝 git 依賴時跑，husky 就掛在這裡。(3) 三個易踩細節——(甲) npm run X -- --flag 的參數只傳給 X，pre/post 收不到；(乙) 主 script 失敗（非 0 退出碼）時 post 不會執行，所以不能把「一定要做的清理」放 post；(丙) 工作目錄永遠是 package.json 那一層，不是你打指令的地方，所以相對路徑要以套件根目錄為準。另可提 npm_lifecycle_event 讓一支腳本共用於多階段。(4) postinstall 的風險——它會在依賴安裝完成時自動執行，使用者通常不會看內容。一個被投毒的套件（或它的間接依賴）只要在 postinstall 放一行下載執行的指令，npm install 就等於任意程式碼執行。防禦面可提 npm 的 --ignore-scripts、lockfile 鎖版本、npm-approve-scripts 審核機制、以及 CI 用 npm ci 而非 npm install。

npm scripts 的 pre / post 生命週期鉤子

[!info] 本篇重點 a–l 共 12 個
起因是一個很單純的疑問：「npm run build 會自動先跑 prebuild、再跑 postbuild，這條規則到底寫在哪？」答案是 npm 官方文件的 Scripts 章節。

[!info] 與其他筆記的關聯（附理由）
a. 直接承接 npm-run-script-mechanism：那篇回答「npm run dev 的 run 是誰加的」以及 start / test / stop / restart 這幾個可省略 run 的保留字。本篇是它的下一層——run 找到 script 之後，npm 在它前後還偷偷做了什麼。兩篇合起來才是 npm script 的完整執行流程。
b. 呼應 前端專案建立與打包選型-Vite與createVue與NextJS與npm鎖版本：那篇處理 package.json 的版本語意，本篇處理 package.json 的 scripts 欄位語意，是同一個檔案的兩個面向。
c. 呼應 前端開發工具-打包編譯Lint與Parser：pre / post 鉤子最典型的用途就是「build 前先 lint、build 後先跑 type check」，那篇說明這些工具各自負責什麼。

重點整理

一、規則本身（d–f）

d. 規則寫在 npm 官方文件的 using-npm/scripts 章節，不是社群慣例、也不是某個套件的功能，是 npm CLI 本身的行為。

e. 規則一句話：對任意 script 名稱 X，執行 npm run X 時，npm 會依序尋找並執行 preX → X → postX。

npm run build   →   prebuild  →  build  →  postbuild
npm run test    →   pretest   →  test   →  posttest
npm run 隨便取   →   pre隨便取  →  隨便取  →  post隨便取

f. 這不限於保留字。你自己取的任何名字都吃這套規則：

{
  "scripts": {
    "prebuild": "rimraf dist",
    "build": "vite build",
    "postbuild": "node scripts/report-size.js",

    "predeploy": "npm run build",
    "deploy": "gh-pages -d dist"
  }
}
片段 意思
"scripts" package.json 裡的欄位，值是一個物件。key 是你取的 script 名字，value 是要丟給系統 shell 執行的字串
"prebuild": "rimraf dist" 因為名字是 pre + build，npm 在跑 build 之前會自動先跑這行。rimraf 是跨平台的 rm -rf
"postbuild" build 成功結束後自動跑。build 失敗（非 0 退出碼）的話 postbuild 不會執行
"predeploy": "npm run build" 很常見的組合技：部署前自動打包，不用記得手動先 build

二、幾個容易踩的細節（g–j）

g. 參數不會傳給 pre / post。官方文件明講：npm run 後面接的參數只會傳給你指定的那支 script，不會傳給 pre 或 post。

npm run build -- --mode staging
# --mode staging 只會進到 build,prebuild 與 postbuild 收不到

（-- 是 shell 慣例的「參數結束標記」，後面的東西原封不動往下傳。）

h. script 的工作目錄永遠是套件根目錄。不管你在哪個子資料夾打 npm run，script 執行時的 cwd 都是 package.json 所在的那一層。所以 script 裡可以放心用相對路徑。

i. 環境變數 npm_lifecycle_event 會告訴你「現在跑到哪一階段」。這讓你可以只寫一支腳本、內部依階段分支：

// scripts/hook.js
switch (process.env.npm_lifecycle_event) {
  case 'prebuild':  /* 清理 */ break;
  case 'postbuild': /* 產報表 */ break;
}

j. 除了你自己取的名字，npm 還有一組安裝期的生命週期腳本，是 npm install 時自動觸發的，跟 npm run 無關：

階段 觸發時機
preinstall 套件被安裝前
install / postinstall 套件安裝後（原生模組編譯常掛在這裡）
prepare npm install（不帶參數）後、npm publish 前，以及安裝 git 依賴時。husky 就是掛在這裡

資安提醒：postinstall 是供應鏈攻擊最愛的落腳點——只要 npm install 一個被投毒的套件就會自動執行任意程式碼。新版 npm 已加入 npm-approve-scripts 這類機制讓你先審核再放行。

三、對話裡沒答完的那半題（k–l）

k. 對話最後問到「npx es link 嗎？」，Gemini 的回覆被截斷成「好的，這是 npm —」就沒了。推測原意是 npm link 與 npx，補充如下：

指令 做什麼
npm link 在本機建立套件的符號連結（symlink），讓你在 A 專案改的套件原始碼，B 專案立刻吃得到，不用每次發版重裝
npx <套件> 執行套件的 CLI。本機 node_modules/.bin 有就用本機的，沒有就臨時下載執行完丟掉

l. 兩者跟本篇的關係：scripts 裡的指令能直接打套件名（例如 "build": "vite build"）而不用寫完整路徑，是因為 npm 執行 script 前會把 node_modules/.bin 塞進 PATH。這也是 npx 的第一順位查找位置。

練習題（延伸）

npm 生命週期是工具鏈知識，LeetCode 與 NeetCode 沒有對應題目。想驗證有沒有懂，做這個小實驗比刷題有效：

  1. 建一個空資料夾，npm init -y
  2. 在 scripts 加三行："prehello": "echo A"、"hello": "echo B"、"posthello": "echo C"
  3. 打 npm run hello，確認輸出順序是 A B C
  4. 把 "hello" 改成 "exit 1"，再跑一次——確認 posthello 這次不會執行
