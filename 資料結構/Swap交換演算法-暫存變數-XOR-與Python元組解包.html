先回答問題

(a) Swap 是一個「基本操作」的概念，不是 Python 的內建方法。Python 沒有 swap() 這個函式，也沒有這個方法。

(b) Swap 的定義：把兩個變數所持有的值（或參考）互相對調。它本身談不上是「演算法」等級的東西，比較精確的說法是它是排序、反轉、分割這類演算法內部反覆用到的原子操作。

三種實作路線

(c) 路線一：暫存變數（Temporary Variable）

最基礎、任何語言都通用的寫法。

temp = a
a = b
b = temp

空間複雜度 O(1)、時間複雜度 O(1)，多用一格記憶體換取「絕對不會出錯」。

(d) 路線二：XOR 位元交換（XOR Swap）

不需要額外變數。

a = a ^ b
b = b ^ a
a = a ^ b

原理是 XOR 的自反性：x ^ y ^ y == x。

(e) XOR swap 有一個致命陷阱：當 a 與 b 指向同一個記憶體位置（例如 swap(arr[i], arr[i])）時，結果會直接變成 0。而且它只適用於整數型別，浮點數與物件不能這樣做。

(f) 實務上不要用 XOR swap。現代編譯器對「暫存變數版」的最佳化已經比 XOR 版好，XOR 版還會破壞指令層級的平行性。它的價值只剩「面試時展示你懂位元運算」。

(g) 路線三：Python 的元組解包（Tuple Unpacking）

a, b = b, a

這是 Python 的語法糖，也是在 Python 裡唯一該用的寫法：不用暫存變數、不用擔心型別、一行講完意圖。

⚠️ 存疑／更正：a, b = b, a 到底有沒有建立元組？

(h) 原始對話中 Gemini 說：「右側的 b, a 會先在記憶體中建立一個隱式的元組 (b, a)，接著解包並分別賦予給左側」。

(i) 這個說法在「兩個變數」的情況下是不正確的。CPython 的窺孔最佳化器（peephole optimizer）會檢查右側序列長度：

右側元素數 實際產生的位元組碼 有沒有建立元組
2 個 ROT_TWO（3.10 以前）／SWAP 2（3.11 起） 沒有
3 個 ROT_THREE + ROT_TWO 沒有
4 個以上 BUILD_TUPLE + UNPACK_SEQUENCE 有

(j) 也就是說，a, b = b, a 只是把直譯器堆疊（stack）上最頂端的兩個參考換位置，沒有任何記憶體配置。Gemini 講的「比傳統變數對調更快」結論是對的，但它給的理由（建立元組再解包）跟真正的原因剛好相反——正是因為「沒有建立元組」才快。

(k) 想自己驗證，用內建的 dis 模組看位元組碼即可：

import dis
dis.dis(compile("a, b = b, a", "<s>", "exec"))
# 會看到 LOAD_NAME b / LOAD_NAME a / SWAP 2（或 ROT_TWO）/ STORE_NAME ...
# 全程不會出現 BUILD_TUPLE

dis.dis(compile("a, b, c, d = d, c, b, a", "<s>", "exec"))
# 這時候才會看到 BUILD_TUPLE 4 與 UNPACK_SEQUENCE 4

關聯筆記與關聯原因

  • 冒泡排序法-range參數與時間複雜度：冒泡排序的內層迴圈每一次比較後做的就是這個 swap。這篇是那篇裡「交換」那一行的放大版。
  • 快慢指標-讀取指標i與寫入指標k-原地刪除：原地（in-place）演算法之所以能做到 O(1) 額外空間，靠的就是 swap 這種不配置新記憶體的操作。兩篇共用「原地」這個核心概念。

申論題面試官問：「為什麼現在不建議用 XOR swap？」請完整回答。
三個理由：
(1) 正確性風險：當兩個運算元是同一個記憶體位置時結果會歸零，而且只能用在整數型別。
(2) 效能已經輸了：現代編譯器對暫存變數版的最佳化更好，XOR 版的三個相依指令會破壞指令層級平行性（ILP），反而更慢。
(3) 可讀性差：省下的一格記憶體在任何現實情境都不值得換取這個維護成本。
