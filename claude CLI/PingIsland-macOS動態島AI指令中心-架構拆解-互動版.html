重點整理

這是什麼

(a) Ping Island 是一款 macOS 專用的「動態島（Dynamic Island）」風格指令中心，用來集中管理與監控多個 AI 程式設計助理（Claude Code、GitHub Copilot、Gemini CLI、Cursor 等十幾種）。

(b) 核心價值 — 減少視窗切換：當 AI 需要你批准（執行指令、讀取檔案）或等待回覆時，它會從螢幕頂部展開，讓你直接在動態島介面點同意／拒絕／輸入文字，不必中斷思緒切回終端機或 IDE。

(c) 另外兩項功能：集中狀態監控（在瀏海／選單列精簡顯示各代理狀態）與一鍵跳轉（點擊直接帶回正在跑該任務的 iTerm2／Terminal／tmux 或編輯器視窗），不同 AI 工具還有專屬吉祥物圖示以便區分。

(d) Windows 不能用：系統需求明訂 macOS 14.0 以上，介面與功能高度依賴 Mac 原生系統 API。Abby 是 Windows 使用者，所以這款只能當架構參考，不能實際安裝。

為什麼是 .swift

(e) .swift 是 Apple 官方語言 Swift 的原始碼副檔名（專案中如 Package.swift、PingIslandUITests.swift）。選用 Swift 的三個理由：

  • 原生 macOS 開發：能直接調用 SwiftUI 與 AppKit 打造懸浮介面與動畫
  • 底層系統 API 介接：需要 macOS 的 Accessibility API（輔助使用 API）做視窗跳轉、呼叫 sysctl 監控背景 AI 進程，Swift 才拿得到最完整的原生權限
  • 高效能低耗：Swift 是編譯型語言，常駐選單列時不會吃掉太多記憶體與 CPU

(f) 頂部懸浮 UI 怎麼做到的：用 SwiftUI + AppKit 的 NSPanel / NSWindow 建立懸浮視窗，把視窗層級（window level）設為浮動層級，貼附於螢幕頂部選單列或瀏海區域，達成動態島效果。

最值得學的一段：統一 Session 資料結構

(g) 問題：要同時支援十幾種 AI 工具，但它們的狀態輸出格式完全不同——

工具 輸出形式
工具 A JSON，例如 {"status": "waiting_permission"}
工具 B 終端機純文字，例如 Do you want to run this command? (Y/n)
工具 C 只能從背景 Process 狀態判斷忙碌中

(h) 不標準化的後果：動態島介面必須為每一種 AI 工具各寫一套渲染與判斷邏輯，程式碼混亂且難以維護，每多支援一個工具就要動到 UI 層。

(i) 解法 — 抽象化（Abstraction）：在 Models 模組定義一個通用的 struct Session，把所有 AI 工具的回傳狀態都轉成一致的欄位（ID／PID、狀態、訊息內容、所屬視窗等）。各工具各寫一個「轉接器」負責把自家格式翻譯成 Session，UI 層只認得 Session 一種型別。

(j) 面試可用的一句話總結：這是典型的轉接器模式（Adapter Pattern）＋ 反腐層（Anti-Corruption Layer）思路——把「外部系統的雜亂格式」擋在邊界外，內部只流通自己定義的乾淨資料模型。新增第 15 種 AI 工具時只要多寫一個轉接器，UI 一行都不用改。

(k) ⚠️ 存疑備註：Gemini 對 Models、UI 目錄與 struct Session 欄位的描述是從目錄結構與 commit 紀錄推論的，未逐行讀原始碼。實際欄位名稱請以官方 repo 為準再核對，本篇的架構解讀當概念參考即可。
