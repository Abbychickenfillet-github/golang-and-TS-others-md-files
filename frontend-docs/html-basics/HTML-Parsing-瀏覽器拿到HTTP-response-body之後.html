1. 主軸圖：四步流水線 ＋ 原型繼承鏈

左圖是時間軸（一份 HTML 從網路到 DOM 走過的四步）；右圖是身份鏈（步驟 4 產出的那個物件，為什麼有能力可設寬高、可掛事件）。
兩張圖要合起來看：左圖的第 4 步，產出的就是右圖最上面那個框。

一句話把兩張圖串起來： 「<div> 這 5 個字元」在圖 A 的第 3 步只是一個 start tag token（資料），到第 4 步才被 new 成物件並接上圖 B 那條鏈，於是它同時擁有了 style（HTMLElement 給的）、 classList（Element 給的）、 appendChild（Node 給的）、 addEventListener（EventTarget 給的）。 （點粉紅色方塊看答案）

先講清楚：extends 到底是誰繼承誰

class 子 extends 父　—— extends 左邊是子類，右邊是父類。「子繼承父」，方向永遠是這樣。
所以 class HTMLDivElement extends HTMLElement 讀作「HTMLDivElement 繼承 HTMLElement」：Div 是子，HTMLElement 是父。
寫法誰是子（繼承者）誰是父（被繼承者）白話
HTMLDivElement extends HTMLElementHTMLDivElementHTMLElementdiv 是一種 HTML 元素
HTMLElement extends ElementHTMLElementElementHTML 元素是一種元素（SVG 元素也是）
Element extends NodeElementNode元素是一種節點（文字節點、註解節點也是）
Node extends EventTargetNodeEventTarget節點是一種「可以接收事件的東西」（window、XHR 也是）
三個記法，挑一個記住就好：
  1. 「is-a」造句法：A extends B 讀成「A is a B」。「div is a HTMLElement」通順 ✅；反過來「HTMLElement is a div」不通 ❌ —— 通的那個方向就是對的。
  2. 範圍大小法：父的範圍一定比子大。EventTarget（所有能收事件的東西）＞ Node（所有節點）＞ Element（只有元素）＞ HTMLElement（只有 HTML 元素）＞ HTMLDivElement（只有 div）。越往父走，成員越多、能力越通用。
  3. 查找方向法：JS 找屬性時是從子往父一層層往上找。你在 div 上呼叫 addEventListener，引擎先找 HTMLDivElement.prototype（沒有）→ HTMLElement.prototype（沒有）→ Element.prototype（沒有）→ Node.prototype（沒有）→ EventTarget.prototype（找到了）。圖 B 的箭頭方向就是這個查找方向。
// 用程式碼證明方向：只有「子 instanceof 父」會是 true
const d = document.createElement('div');

d instanceof HTMLDivElement;   // true
d instanceof HTMLElement;      // true  ← 子也算是父
d instanceof Element;          // true
d instanceof Node;             // true
d instanceof EventTarget;      // true  ← 一路都算

// 反過來就不成立：父的實例不算是子
document.createTextNode('hi') instanceof Node;     // true
document.createTextNode('hi') instanceof Element;  // false ← 文字節點不是 Element

// 誰是誰的父，直接問
Object.getPrototypeOf(HTMLDivElement) === HTMLElement;  // true ← Div 的父是 HTMLElement
Object.getPrototypeOf(HTMLElement)    === Element;      // true
Object.getPrototypeOf(Element)        === Node;         // true
Object.getPrototypeOf(Node)           === EventTarget;  // true
⚠️ 注意：瀏覽器不是真的用 class ... extends ... 這段 JS 寫出來的（見第 6 節，它們是 C++ 物件）。
規範用的是 WebIDL 的 interface HTMLDivElement : HTMLElement 語法，冒號左邊是子、右邊是父，跟 extends 同義。
我們用 extends 來描述，是因為它在 JS 這一側表現得完全一樣，比較好懂。

自己動手驗證這條鏈

let p = Object.getPrototypeOf(d), chain = [];
while (p) { chain.push(p.constructor.name); p = Object.getPrototypeOf(p); }

// HTMLDivElement → HTMLElement → Element → Node → EventTarget → Object

// 驗證 addEventListener 到底掛在哪一層

// ['constructor', 'addEventListener', 'dispatchEvent', 'removeEventListener']

// 驗證 style 掛在哪一層
console.log('style' in HTMLElement.prototype);  // true
console.log('style' in Element.prototype);      // false ← Element 沒有 style

2. 步驟 1 — bytes：網路上流的到底是什麼

bytes 是什麼

byte（位元組）＝ 8 個 bit ＝ 8 個 0 或 1。 網路上、磁碟上，所有東西一律是 bytes，沒有例外。「文字」不是儲存格式，而是解碼之後才存在的概念。

所以「HTML 是純文字檔」這句話要這樣理解：

說法正確嗎精確講法
HTML 是純文字格式✅ 對指它的內容語意是給人讀的文字，相對於 JPG／MP4 那種二進位格式
HTML 在網路上傳的時候不是 bytes❌ 錯一定是 bytes。純文字格式只是說「這些 bytes 用某個編碼表解出來會是有意義的字」
拿到 response body 就是字串了❌ 錯拿到的是 byte stream，還要經過圖 A 的第 2 步才有「字元」

同一句 <!DOCTYPE html> 在網路上的樣子：

字元：  <   !   D   O   C   T   Y   P   E  (空白) h   t   m   l   >
bytes： 3C  21  44  4F  43  54  59  50  45  20  68  74  6D  6C  3E   ← 十六進位
bits：  00111100 00100001 01000100 …                                ← 真正在線上跑的
F12 實測（F12 → Network → 點那個 HTML 檔）：
  1. Headers 分頁：Content-Type: text/html; charset=utf-8 ← 這裡宣告了「用哪張表解碼」
  2. Headers 分頁：Content-Length: 1834 ← 這個 1834 的單位就是 bytes，不是字數。中文一個字在 UTF-8 佔 3 bytes，所以中文網頁的 bytes 數會遠大於字數
  3. Response 分頁：看到的是已經幫你解碼過的文字。DevTools 貼心，但那不是原始資料

3. 步驟 2 — decoding：bytes 怎麼變成字元，以及那個雞生蛋問題

3-1. 產物叫 input stream，內容是 code points

規範裡這個東西不叫「字串」，叫 input stream，裡面裝的是 code point（碼點，一個 Unicode 字元的編號）。

比較項字串 String流 Stream
長度有 .length，一開始就知道不知道，可能還在下載
存取方式可隨機索引 s[5]，可以回頭讀只能依序消耗，讀過就過去了
中途可以變長嗎不行（字串不可變）可以：網路 chunk 陸續進來，document.write() 也會插隊塞進來
存在哪完整存在記憶體邊來邊處理，不必等到齊
這個差別為什麼重要：因為它就是「HTML 可以邊下載邊顯示」的原理。如果規範定義成「字串」，就必須等整份下載完才能開始 parse，首屏會慢非常多。 串流式 SSR（React 18 的 renderToPipeableStream）能分段送 HTML，靠的也是這個「流」的性質。

3-2. 雞生蛋問題：charset 寫在 bytes 裡面

你問「<meta charset> 應該是指 HTML 的標籤了吧」—— 是的，而這正是矛盾點：

要讀 <meta charset> 這個標籤，得先解碼；要解碼，得先知道 charset。
→ 規範用 encoding sniffing algorithm（編碼嗅探演算法） 解決，優先序如下。
順序依據說明
1BOM（Byte Order Mark）檔案開頭的特殊 bytes（UTF-8 是 EF BB BF）。有就直接採信，信心值 certain
2使用者手動指定瀏覽器選單裡強制指定編碼
3HTTP headerContent-Type: text/html; charset=utf-8。比 meta 優先
4prescan 前 1024 bytes先粗掃開頭 1024 bytes 找 <meta charset>。這就是為什麼 charset 必須放在 head 最前面
5父文件iframe 且同源時，繼承父頁的編碼
6歷史紀錄之前造訪過這頁時偵測到的編碼
7自動偵測用統計特徵猜（規範不鼓勵）
8語系預設值猜錯就是亂碼（mojibake），例如「中文」變成 ä¸­æ–‡
這一段跟同資料夾的 HTML文件結構-DOCTYPE與骨架.md 的 Q9「為何 <meta charset> 要放 head 最前面」 是同一件事的兩個切面：
那篇回答「要放哪裡」，這篇回答「在整條流水線的第幾步、為什麼一定要有這一步」。
「中」這個字在 UTF-8 是 3 個 bytes：E4 B8 AD。
如果瀏覽器誤以為是 Latin-1（每個 byte 就是一個字元），它會把這 3 個 bytes 各自當成一個字：E4→ä、B8→¸、AD→­，於是「中」變成「ä¸­」。
bytes 完全沒錯，錯的是解碼用的那張表。這就是圖 A 第 2 步存在的意義。

4. 步驟 3 — tokenization：HTML 也有 tokenizer

直接回答你的疑問：不是偷換成 JS。HTML、JS、CSS 各自有一套完全獨立的 tokenizer。 「tokenization」是編譯原理的通用術語，任何要被機器讀懂的語言都有這一步，不是 JS 的專利。
語言誰執行 tokenizetoken 長什麼樣下一步產出
HTMLBlink（渲染引擎）start tag / end tag / character / comment / DOCTYPE / EOF，共 6 種DOM 樹
CSSBlink 的 CSS parserident / hash / string / dimension / delim …CSSOM 樹
JavaScriptV8（JS 引擎）keyword / identifier / operator / literal / punctuator …AST → bytecode
⚠️ 最容易搞混的一點：HTML 永遠不會進 V8，也永遠不會變成 AST 或 bytecode。 三條線都在同一條主執行緒上用 CPU，但是三個不同元件。 （這點與 ../web-platform/script載入方式+前因後果.md 的 (q) 節一致。）

HTML tokenizer 眼中的 <div id="root">Hi</div>

輸入（碼點流）： < d i v   i d = " r o o t " > H i < / d i v >

輸出（token 序列，只有 3 個）：
  ① StartTagToken  { name: "div", attributes: { id: "root" }, selfClosing: false }
  ② CharacterToken { data: "H" }
  ③ CharacterToken { data: "i" }
  ④ EndTagToken    { name: "div" }

⚠️ 注意：token 還是「資料」，是一筆記錄，不是物件。
   它沒有 .style、沒有 .addEventListener，還接不上圖 B 那條鏈。

tokenizer 自己也是一台狀態機，狀態約 80 個，例如 data state（一般文字）、tag open state（剛讀到 <）、attribute name state（正在讀屬性名）。這些狀態只管切字元，完全不管樹長什麼樣。

4-b. 反過來問：轉譯之後才能做 HTML Parsing 嗎？

不是。兩者沒有任何依賴關係。 轉譯處理的是「你寫的 JS 長得不標準」；HTML Parsing 處理的是「文字要變成物件」。 對象不同、機器不同、時間不同。

會有這個錯覺，是因為建置流程圖通常由上往下畫，看起來像「① 轉譯 → ② 打包 → ③ 純文字 → ④ HTML Parsing」一條線。但那張圖跨了兩台機器、兩個時間點，中間是斷開的：

【機器 A：你的筆電 / CI】          build-time，做一次
  .tsx → 轉譯 → bundle → 產出靜態檔
                    │
                    ▼
              ✂️ 部署，斷開 ✂️
              （中間可能隔了三天）
                    │
                    ▼
【機器 B：使用者的瀏覽器】          run-time，每人各做一次
  收到 bytes → decode → tokenize → tree construction → DOM

兩個直接反證

  1. 純手寫的 .html 完全沒有轉譯，瀏覽器照樣 parse。 你隨手存一個 test.html 雙擊打開 —— 沒有 build、沒有 Babel、沒有 bundler，本篇的四步照樣跑完。
  2. PHP、WordPress、Rails 前端根本沒有轉譯步驟。 HTML 是後端 template 引擎吐出來的字串，直接進瀏覽器解析。

→ 所以轉譯不是 HTML Parsing 的前置條件。

1. HTML Parsing 開始（步驟 3、4 進行中）
        ↓
2. 讀到 <script src="main.abc.js">    ← 這個 tag 是 build 時被注入的
        ↓
3. HTML Parsing 停住（無屬性）或繼續（defer）
        ↓
4. V8 執行那支 JS —— 它「早就」轉譯完了，在三天前的 CI 上
        ↓

⚠️ 在使用者的機器上，轉譯這件事早就結束了，不參與任何順序。

唯一的關聯是間接的

轉譯 → bundle → 產出 main.abc123.js → build tool 把 <script src="main.abc123.js"> 注入到 index.html 的文字裡。

所以轉譯影響的是「HTML 裡那個 src 字串寫什麼」，不是「HTML 能不能被 parse」。就算 src 指向一個不存在的檔案，HTML Parsing 照樣跑完，只是那支 script 404 而已。

唯一一條「JSX 的 div 最後真的被 HTML parse」的路徑：SSR

轉譯（build-time）
   → 部署
   → 使用者請求
   → Node 上執行 renderToString()    ← ★ 執行，不是轉譯
   → 產出 HTML 字串 "<div class="a">Hi</div>"
   → HTTP 傳輸
   → 瀏覽器 HTML Parsing（本篇步驟 2、3、4）

注意中間那一步是「執行」不是「轉譯」。轉譯早在 build 就做完了，SSR 是在 run-time（伺服器端的 run-time）跑那份已經轉譯好的 JS。

一句話總結：轉譯是 build-time 的翻譯工作，HTML Parsing 是 run-time 的建構工作，兩者沒有先後依賴。

5. 步驟 4 — tree construction：in head 那些字串是什麼

直接回答："initial"、"before html"、"in head"、"in body" 叫做 insertion mode（插入模式）。
① 它不是 HTML 標籤。
② 它不是 任何程式語言的語法或工具。
③ 它是 WHATWG 規範文件裡的英文術語——樹建構狀態機的狀態名稱。瀏覽器實作時通常變成 C++ 的 enum，例如 Blink 裡叫 kInHeadMode。

規範裡的 21 個 insertion mode（完整清單）

initial            before html        before head        in head
in head noscript   after head         in body            text
in table           in table text      in caption         in column group
in table body      in row             in cell            in template
after body         in frameset        after frameset     after after body
after after frameset

解析一份最小 HTML 時，狀態怎麼跑

<!DOCTYPE html><html><head><title>A</title></head><body><div></div></body></html>

收到 token              目前 insertion mode      做了什麼
─────────────────────────────────────────────────────────────────
(開始)                  initial                  等 DOCTYPE
DOCTYPE token       →   initial → before html    建 DocumentType 節點
<html>              →   before html → before head 建 HTMLHtmlElement
<head>              →   before head → in head    建 HTMLHeadElement
<title>             →   in head → text           title 內容當純文字讀
</title>            →   text → in head           回來
</head>             →   in head → after head     head 收工
<body>              →   after head → in body     建 HTMLBodyElement
<div>               →   in body（不變）           ★ new 一個 HTMLDivElement 掛上去
</div>              →   in body（不變）           從 open elements stack 彈出
</body>             →   in body → after body
</html>             →   after body → after after body
為什麼要分這麼多狀態？因為同一個 token 在不同位置意義不同。
例如一個 <td> token：在 in row 是合法的儲存格；在 in body 就是錯放，規範會直接忽略它。
HTML 之所以「寫錯也不會白屏」，就是因為每個 insertion mode 都明文寫了「遇到不該出現的 token 要怎麼補救」。這是與 XML 最大的差別——XML 錯一個字就整份不解析。

回答你的判斷題

你問「我看到 d 點是 DOM 結構的生成了，那 HTML Parsing 是指 a b c 三個步驟嗎」——你判斷對了。
規範第 13.2 章「Parsing HTML documents」涵蓋的正是 decoding ＋ tokenization ＋ tree construction（本篇的步驟 2、3、4）。
DOM 是第 4 步的產物，不是第 5 個步驟——它是名詞，不是動詞。

6. DOM 節點是「真正的 JS 物件」嗎 ★★★★★

你說：「DOM 節點就是真正的 JS 物件，難怪都要變成 DOM 才能讓 JS 去抓他」——方向完全正確，但有兩個地方要修正。

修正一：它是「宿主物件」，不是用 JS 寫出來的物件

層次真相
你在 JS 裡拿到的 document.body✅ 確實是一個 JS 物件，有原型鏈、可以 . 取屬性、可以傳來傳去
它的資料實際住在哪❌ 不在 JS 堆積裡。真正的節點是瀏覽器引擎的 C++ 物件（Chrome 是 Blink）
那 JS 拿到的是什麼一個透過 WebIDL binding 產生的包裝物件（wrapper / platform object），也叫宿主物件（host object）

三行驗證

// (1) 它自己身上一個屬性都沒有
console.log(Object.keys(document.body));            // []
console.log(document.body.hasOwnProperty('tagName')); // false

// (2) tagName 其實是 prototype 上的 getter，背後轉呼叫 C++
console.log(Object.getOwnPropertyDescriptor(Element.prototype, 'tagName'));
// { get: ƒ, set: undefined, enumerable: true, configurable: true }

// (3) 一般 JS 物件對照組
const plain = { tagName: 'DIV' };
console.log(Object.keys(plain));                     // ['tagName']  ← 有
這件事的實務價值（也是五星的原因）：
每次讀寫 DOM 屬性，都是一次 JS ↔ C++ 的跨界呼叫，比操作純 JS 物件貴得多。
→ 這就是虛擬 DOM 存在的理由：React 先在便宜的純 JS 物件上算差異，最後才一次跨界改真 DOM。
→ 也是為什麼「在迴圈裡讀 offsetHeight」會造成強制同步排版（layout thrashing）。

修正二：「都要變成 DOM 才能讓 JS 抓他」要加一個限定詞

精確講法是：要用 DOM API 抓，就必須先有 DOM。 JS 其實也能直接處理 HTML 字串，只是那不叫「抓 DOM」：

const html = '<div id="root">Hi</div>';

html.includes('root');                    // true   ← 純字串操作，不需要 DOM
html.match(/id="(\w+)"/)[1];              // "root" ← 正則，不需要 DOM

// 但這些就一定要有 DOM：
document.getElementById('root');          // 需要 DOM
el.addEventListener('click', fn);         // 需要 DOM（而且是 EventTarget 那層）
el.getBoundingClientRect();               // 需要 DOM ＋ 已完成 Layout

// 想在不上畫面的情況下把字串變成 DOM，用這個：
const doc = new DOMParser().parseFromString(html, 'text/html');
console.log(doc.getElementById('root').tagName);  // "DIV"
// ↑ 這行等於手動觸發了圖 A 的第 3、4 步

7. CSR / SSR / SSG / PHP / WordPress / Rails 在這條線上有差嗎

圖 A 那四步，這幾種一模一樣，零差別。因為那是 HTML 標準規定的，跟誰產生 HTML 無關。
差別只在三個變數：① 誰產生 HTML 字串　② 什麼時候產生　③ 第一個 response 裡面有沒有內容。
模式HTML 字串誰產生何時產生首個 response 有內容嗎圖 A 四步第 4 步結束後還要做什麼
純靜態 HTML人手寫寫程式時✅ 有完全相同沒事了，直接 paint
SSG（Astro、Hugo、Jekyll、next export）建置工具build time，全站算一次✅ 有完全相同若有互動，需 hydration
SSR（Next.js、Nuxt、Remix）Node 伺服器跑 renderToString每次 request✅ 有完全相同hydration 掛事件
PHP / WordPressPHP 直譯器每次 request✅ 有完全相同沒事了（除非另有 JS）
Rails / Django / Laravel後端 template 引擎（ERB、Jinja、Blade）每次 request✅ 有完全相同同上
CSR（Vite ＋ React SPA）瀏覽器裡的 JSHTML 解析完、JS 執行時❌ #root 是空的完全相同還要跑一整套 JS 才有內容
Streaming SSR（React 18 renderToPipeableStream）Node 伺服器，分段吐每次 request，邊算邊送✅ 有（陸續到）完全相同，但吃滿了「流」的性質分段 hydration

真正的分歧點在時間軸的後半段

【有內容的那幾種：靜態 / SSG / SSR / PHP / Rails】
  bytes → decode → tokenize → tree construction → DOM 有內容 → paint 🎉
                                                  ↑ 使用者這裡就看得到東西了

【CSR】
  bytes → decode → tokenize → tree construction → DOM 只有一個空 div → 白畫面 😐
                                                       ↓
                                        下載 JS → V8 parse → 執行
                                                       ↓
                              React createElement / appendChild（又一輪建 DOM）
                                                       ↓
                                                  paint 🎉
所以你原本筆記那句「這邊不是 CSR、SSR、SSG⋯⋯的專屬，他們全一樣，無例外」是對的，但可以再精確一點：
「HTML Parsing 這四步無例外，但四步結束後畫面上有沒有東西，就完全不一樣了。」

一分鐘驗證法

  1. Ctrl＋U（View Source）→ 這是伺服器丟過來的原始字串，JS 一行都還沒跑
  2. F12 → Elements → 這是現在這一刻的 DOM 樹，JS 已經改造過
  3. 兩者差很多、#root 在 View Source 裡是空的 → CSR
  4. 兩者幾乎一樣 → SSR / SSG / PHP / Rails（再看有沒有 hydration 用的 JS 才能細分）

所以同一個問題的兩個答案都成立，端看你問的是哪一層：

8. Markdown → DOM 的兩條路（其中一條不經過 HTML Parsing）

你問「Markdown 渲染為 DOM 也是要先轉換成 HTML 字串才有戲，這邊乾脆把流水線講完，還要被 HTML Parsing 吧」——你說的是路徑 A，那條確實要再走一次 HTML Parsing。但還有一條路徑 B 不用。

路徑 A：marked／markdown-it ＋ innerHTML（最常見）

.md 檔（bytes）
   ↓ 1. decode
Markdown 字串
   ↓ 2. Markdown 自己的 tokenizer（跟 HTML 的不同一套）
Markdown token 序列 → AST（mdast）
   ↓ 3. renderer 把 AST 印成字串
★ HTML 字串 ★   ← 例如 "<h1>標題</h1><p>內文</p>"
   ↓ 4. el.innerHTML = htmlString
★ 觸發 fragment parsing algorithm ★  ← 這就是圖 A 的第 3、4 步（片段版）
   ↓
DOM

所以路徑 A 一共 tokenize 了兩次：一次 Markdown 的、一次 HTML 的。你的直覺完全正確。

路徑 B：react-markdown（remark ＋ rehype-react）——不經過 HTML 字串

.md 檔（bytes）
   ↓ decode
Markdown 字串
   ↓ remark 解析
mdast（Markdown AST）
   ↓ remark-rehype 轉換
hast（HTML AST，但仍是 JS 物件，不是字串）
   ↓ rehype-react
React element（純 JS 物件）
   ↓ React 呼叫 document.createElement / appendChild
DOM

❌ 全程沒有出現過 HTML 字串
❌ 因此也完全沒有觸發 HTML Parsing
⚠️ 這是要回頭修正 ../web-platform/Markdown-渲染為DOM的過程.md 的地方：
「Markdown 不能直接被渲染成 DOM，一定要先轉成 HTML 字串」——這句話對路徑 A 成立，對路徑 B 不成立。
路徑 B 是繞過 HTML 字串直接建 DOM 的，而且這正是 react-markdown 比 dangerouslySetInnerHTML 安全的原因：沒有字串可以被注入。
比較路徑 A（marked ＋ innerHTML）路徑 B（react-markdown）
中間有沒有 HTML 字串有沒有
有沒有跑 HTML Parsing有（fragment parsing）沒有
tokenize 幾次2 次（Markdown ＋ HTML）1 次（只有 Markdown）
XSS 風險高，要另外接 DOMPurify低，天生擋掉大部分注入
建 DOM 的人Blink 的 HTML parserReact 呼叫 document.createElement

9. 自我測驗

9-1. 填空（點方塊看答案）

a. 網路上傳輸的一切都是 bytes（位元組），「文字」是 解碼之後 才存在的概念。

b. 圖 A 第 2 步的產物在規範裡叫 input stream，裡面裝的是 code points（碼點），不是字串。

c. HTML tokenizer 只吐 6 種 token：DOCTYPE、start tag、end tag、comment、character、EOF。

d. 樹建構那台狀態機的狀態叫 insertion mode（插入模式），規範共 21 種。

e. addEventListener 定義在原型鏈的 EventTarget 這一層；style 定義在 HTMLElement 這一層。

f. 執行 HTML tokenize 的是 Blink（渲染引擎），不是 V8。

g. charset 的判定順序是 BOM ＞ 使用者指定 ＞ HTTP header ＞ prescan 前 1024 bytes 找 meta。

h. DOM 節點在 JS 裡是 包裝物件 / 宿主物件，真正的資料住在瀏覽器引擎的 C++ 物件 裡。

9-2. 是非題

① HTML 是純文字格式，所以它在 HTTP response body 裡不是 bytes。
錯。「純文字格式」講的是內容語意，不是儲存或傳輸形式。網路上一律是 bytes，沒有例外——包含 HTML、JSON、CSS、JS 全部。
② 講到 tokenization 一定是在講 JavaScript，HTML 沒有這個階段。
錯。HTML、CSS、JS 各有一套獨立的 tokenizer。HTML 的由 Blink 執行、JS 的由 V8 執行，兩者互不相干，HTML 也永遠不會變成 AST 或 bytecode。
③ "in head"、"in body" 是規範裡樹建構狀態機的狀態名稱，不是 HTML 標籤。
對。它們叫 insertion mode，是 WHATWG 規範的術語，共 21 個。瀏覽器實作時會變成 enum，例如 Blink 的 kInHeadMode。
④ CSR 的 HTML 解析流程跟 SSR、PHP 不一樣，因為它要等 JS。
錯。解析流程完全一樣（圖 A 四步）。不一樣的是「四步結束後畫面上有沒有東西」：CSR 的 #root 是空的，還要跑 JS；其他幾種解析完就能 paint。
⑤ DOM 節點是用 JavaScript 實作的普通 JS 物件。
錯（這題很細）。它在 JS 裡表現得像 JS 物件，有原型鏈可以操作，但實體是瀏覽器引擎的 C++ 物件，JS 拿到的是透過 WebIDL binding 產生的包裝物件。Object.keys(document.body) 回傳 [] 就是證據。這也是虛擬 DOM 存在的理由。
⑥ Markdown 要變成 DOM，一定得先轉成 HTML 字串。
錯（有例外）。marked／markdown-it ＋ innerHTML 這條路要；但 react-markdown（remark ＋ rehype-react）是 mdast → hast → React element → document.createElement，全程沒有 HTML 字串，也沒有 HTML Parsing。
⑦ <meta charset> 要放 <head> 最前面，是因為瀏覽器只 prescan 前 1024 bytes。
對。而且要注意 HTTP header 的 charset 優先於 meta，所以伺服器設定錯的時候，改 meta 是沒用的。
⑧ 要先做完轉譯（transpile），瀏覽器才能開始做 HTML Parsing。
錯。兩者沒有依賴：轉譯在 build-time、開發者機器上，處理的是 JS/TS/JSX；HTML Parsing 在 run-time、使用者瀏覽器上，處理的是 HTML 字串。純手寫 .html 與 PHP 完全沒有轉譯，照樣 parse。JSX 的 <div> 會被轉成 _jsx("div", {...})，永遠不會經過 HTML parser。見第 4-b 節。

9-3. 申論題

Q1. 面試官說：「請描述在網址列按下 Enter 之後，瀏覽器怎麼把伺服器回來的東西變成畫面上可以點的按鈕。」請把 bytes、input stream、token、insertion mode、DOM、EventTarget 這六個詞都用上。

伺服器回來的 response body 是一串 bytes，還不是文字。瀏覽器先用 encoding sniffing 決定編碼（BOM ＞ HTTP header ＞ 前 1024 bytes 的 meta），把 bytes 解碼成 input stream，內容是 code points；它是「流」不是字串，所以可以邊下載邊解析。

接著 tokenizer 這台狀態機把碼點切成 token，只有 DOCTYPE、start tag、end tag、comment、character、EOF 六種，此時仍是資料。

token 進入樹建構，狀態機依當下的 insertion mode（initial、before html、in head、in body⋯⋯共 21 種）決定怎麼處理。讀到 <button> 的 start tag token 時，在 in body 模式下 new 出一個 HTMLButtonElement 掛到樹上，這棵樹就是 DOM。

這個物件的原型鏈是 HTMLButtonElement → HTMLElement → Element → Node → EventTarget，最底層的 EventTarget 提供 addEventListener，所以 JS 才能替它掛 click 事件。字串形態的 <button> 沒有這條鏈，所以什麼都做不了。

最後 DOM 與 CSSOM 合成 Render Tree，經 Layout、Paint、Composite 才真的出現在螢幕上。

Q2. 同事說「CSR 慢是因為它的 HTML 解析比較慢」。請指出他錯在哪，並說明真正的原因。

他錯在把「解析慢」跟「首屏慢」混為一談。

CSR 的 HTML 解析反而更快，因為它的 HTML 極短（通常就一個空的 <div id="root"></div>），token 少、要建的節點也少。圖 A 那四步 CSR 跑得比 SSR 快。

真正的原因是：四步跑完之後，畫面上什麼都沒有。使用者要等的是後面那一整段——下載 JS bundle、V8 tokenize ＋ parse ＋ 產 bytecode、執行 React、呼叫 createElement 再建一次 DOM，最後才 paint。

所以 CSR 的 FCP（First Contentful Paint）差，瓶頸在 JS 的下載與執行，不在 HTML Parsing。對應的優化手段也因此是 code splitting、preload、SSR/SSG，而不是「把 HTML 寫短一點」。

Q3. 為什麼虛擬 DOM 會比較快？請從「DOM 節點到底是什麼物件」這件事回答。

因為 DOM 節點不是純 JS 物件。它的實體是瀏覽器引擎的 C++ 物件，JS 拿到的只是透過 WebIDL binding 產生的包裝物件；每次讀寫它的屬性，都是一次跨越 JS ↔ C++ 邊界的呼叫，成本遠高於操作純 JS 物件。

虛擬 DOM 的做法是：先在便宜的純 JS 物件上做完所有比對與計算，算出最小差異集合，最後才一次性跨界去改真 DOM。省的不是「計算」，而是跨界次數。

⚠️ 誠實補充：虛擬 DOM 不一定比「手寫最佳化的直接 DOM 操作」快，它換來的是可維護性——你可以用宣告式寫法，而不必自己手動追蹤該改哪幾個節點。Svelte 就選了另一條路：在 build time 編譯出精準的 DOM 操作，完全不用虛擬 DOM。
