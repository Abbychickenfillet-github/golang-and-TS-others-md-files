Next.js：ISR／SSR／Streaming 與 Parsing 先後

本篇重點 a–i，共 9 個

重點整理

  • (a) getStaticProps 只在 build time 跑一次，除非回傳物件加上 revalidate: 秒數，才變成 ISR（Incremental Static Regeneration，增量式靜態再生）。
  • (b) ISR 流程：伺服器先把「舊的靜態 HTML」立刻回傳給請求者（stale-while-revalidate）→ 同時在背景重新執行 getStaticProps 向資料庫要新資料 → 重新 render 出新 HTML 並替換快取 → 下一位使用者拿到新版。
  • 資料庫被使用者 CRUD 改變，靠的是這個背景再生，不是重新打包 source code。
export async function getStaticProps() {
  const data = await fetchFromDatabase()
  return { props: { data }, revalidate: 60 } // 60 秒內最多觸發一次背景更新
}
  • (c) Rendering（伺服器把元件＋資料組成 HTML 字串）與 Parsing（瀏覽器的 HTML Parser 把收到的 byte stream 解碼成字元、再逐標籤建出 DOM 節點）是兩個不同階段，先後是接力關係。
  • 順序：伺服器 render 出 HTML 字串 → 打成 byte stream 經網路傳送 → 瀏覽器解碼 → HTML Parser 邊收邊 parse → 長出 DOM → Paint。
  • (d) CSR（純客戶端渲染）傳來的是空的 <div id="root"></div>，Parser 解析完畫面是空白，要等 JS 下載並執行才補內容。SSG／SSR 傳來的 HTML 已含內容，Parser 不用等 JS 就能畫出畫面，所以 FCP 與 SEO 較好。
  • (e) 傳統 getServerSideProps（Pages Router）是 blocking SSR：資料全部抓完、整頁 render 完，才一次把完整 HTML 傳給瀏覽器，TTFB（Time To First Byte）較長。
  • (f) Streaming SSR（App Router＋React Suspense）才是邊算邊傳：先送不需等資料的骨架（導覽列、版型）→ 資料就緒後再以 chunk 補送，瀏覽器動態補進畫面。
  • (g) 「沒有依賴 URL data 的部分」＝不隨網址參數（路徑 id／slug／?page=2）改變的共用區塊，例如 Navbar、Sidebar、Footer。
  • (h) Shell（外殼）＝上述共用骨架。用途：client navigation 時當作預設 prefetch payload 先下載，點擊後瞬間顯示，動態內容未到前也可拿來當 loading 畫面。
  • (i) ⚠️ 存疑／更正：Gemini 對「快取內容在 stale time ≥ 5 分鐘時才被包進 shell」的白話解釋偏推測，原文出自 Next.js 較新的 Glossary（與 Cache Components／PPR 相關），請以官方原文為準再核對。
