一、兩個 Hook 各自讀 URL 的哪一段

(a) usePathname() 是 Next.js App Router 提供的 client hook。它讀取的受詞是 URL 的路徑（Path），回傳型態是 字串 string，回答的問題是「使用者現在站在哪一頁」。

(b) useSearchParams() 讀取的受詞是 URL 問號後面的查詢字串（Query String），回傳型態是唯讀物件 ReadonlyURLSearchParams，要再用 .get('key') 把值取出來。回答的問題是「使用者這一頁帶了什麼篩選條件」。

(c) 以網址 https://example.com/dashboard/products?category=shoes&sort=asc 為例，兩者切開的位置是這樣：

比較項目usePathname()useSearchParams()
讀到的內容/dashboard/productscategory=shoes&sort=asc
回傳型態字串 string唯讀物件 ReadonlyURLSearchParams
取值寫法直接當字串用要再呼叫 .get('category')
典型用途導覽列高亮目前頁面搜尋關鍵字、商品篩選、分頁切換
靜態預渲染可以直接用必須包在 Suspense 裡，否則 build 失敗
口訣想知道「走到哪一頁」想知道「帶了什麼條件」

(d) usePathname 的實作範例，用途是把目前頁面的連結標成紅色：

'use client'

import { usePathname } from 'next/navigation'
import Link from 'next/link'

export default function Navigation() {
  const pathname = usePathname()          // 例如回傳 "/dashboard"

  return (
    <nav>
      <Link
        href="/dashboard"
        style={{ color: pathname === '/dashboard' ? 'red' : 'black' }}
      >
        Dashboard
      </Link>
    </nav>
  )
}

(e) useSearchParams 的實作範例，用途是把 ?category=shoes 的 shoes 取出來顯示：

'use client'

import { useSearchParams } from 'next/navigation'

export default function SearchResult() {
  const searchParams = useSearchParams()
  const category = searchParams.get('category')   // ?category=shoes 時回傳 'shoes'

  return <p>當前分類：{category}</p>
}

二、Bailout 是怎麼發生的（對照主軸圖的右半邊）

(f) Bailout（跳船）指的是 Next.js 在建置期放棄把某一棵元件樹預渲染成 HTML，把它降級成使用者端渲染（CSR）。「跳船」是比喻：靜態預渲染這條船開不下去了，這棵樹自己跳下去用瀏覽器游過去。

(g) 為什麼只有 useSearchParams 會觸發它，關鍵在建置期知不知道這個值。路徑 /dashboard/products 在 npm run build 的當下是寫死在檔案系統裡的，Node.js 算得出來；查詢字串 ?search=react 代表未來某一個使用者的請求，建置期的伺服器根本還沒收到任何請求，不可能知道。

(h) 所以只要元件直接呼叫了 useSearchParams() 又沒有 <Suspense> 接住，next build 會直接拋出這一行錯誤：

Error: Missing Suspense boundary with useSearchParams
(i) 災情大小取決於呼叫點的位置有多上層 整條 client 元件樹都會被一起拖下水。實測案例：Abby 的 next-one-main 專案，LoaderProvider 寫在 root layout 裡並且呼叫了 useSearchParams，結果整站每一頁的 client 樹全部 bailout 成 CSR，FCP 被拖到 5.24 秒。原始碼層級的完整驗證寫在 FCP-5.24秒-Next.js效能診斷實錄-從指令到根因.md 的 Step 7。

三、三種解法，由輕到重

(j) 解法一：改用 usePathname（最輕量，優先考慮） 判斷標準是：這個元件只是想知道「現在在哪一條路由」來切換樣式或決定要不要顯示嗎？如果是，直接換成 usePathname 就好，完全不影響靜態預渲染。Abby 的 LoaderProvider 正是這一種情況。
(k) 解法二：用 <Suspense> 把呼叫點包起來 如果真的必須讀 Query String（搜尋欄、篩選器），就把呼叫 useSearchParams 的那個 client component 用 <Suspense> 包住。這麼做並不會讓 bailout 消失，而是把損失關在 Suspense 邊界裡：外層頁面 shell 照常靜態預渲染，只有內部那一小塊在瀏覽器補上。 
import { Suspense } from 'react'
import SearchBar from './search-bar'

export default function Page() {
  return (
    <main>
      {/* 外層保持靜態，只有 SearchBar 這一塊動態載入 */}
      <Suspense fallback={<div>Loading...</div>}>
        <SearchBar />
      </Suspense>
    </main>
  )
}
(k-2) 先把三個渲染時機的名詞定死（2026-09-17 補入） 靜態渲染與動態渲染都是「伺服器端」的處理方式，差別只在算的時間點是建置期還是請求期，不要把「動態渲染」跟「CSR」混為一談。
名詞誰在什麼時候產出 HTML拿到的資料是什麼時候的
靜態渲染 Static RenderingNext.js 在 next build 建置時就先生成 HTML，之後每個請求都直接送這份快取建置當下的資料
動態渲染 Dynamic Rendering伺服器在每一個請求進來時才即時生成 HTML該次請求當下的最新資料
使用者端渲染 CSR伺服器只送空殼，瀏覽器下載 JS 後才把畫面畫出來瀏覽器執行時的資料
(k-3) 加不加 <Suspense>，決定的是「損失範圍」而不是「有沒有損失」 兩者不是互相排斥的「二選一」，而是你在決定「希望哪一部分先在伺服器做完」。useSearchParams 的本質是：在元件中呼叫這個 hook 會通知 Next.js「必須等到參數確認後才能完整呈現」，所以才需要在懸吊邊界（Suspense boundary）處把它隔離起來。
做法頁面外層讀 Query String 的那一塊代價
用 <Suspense> 包住呼叫點維持 static／SSR，伺服器先把骨架與靜態 HTML 渲染出來只有這一小塊在瀏覽器補上使用者會先看到 fallback 再看到內容
不包 <Suspense>整頁被降級成全動態渲染（Dynamic Rendering）跟著整頁一起動態伺服器每收到一次 Request 都要重算整頁，完全享受不到靜態快取
(l) 解法三：改在 Server Component 用 searchParams prop 如果讀取點就在 page.tsx，根本不需要動用 client hook。App Router 的 Page 元件原生就會收到一個 searchParams prop，直接在伺服器端拿到參數，連 client boundary 都不用開。 
// app/products/page.tsx —— 這是 Server Component，不要加 'use client'
export default async function Page({
  searchParams,
}: {
  searchParams: Promise<{ category?: string }>
}) {
  const { category } = await searchParams
  return <p>當前分類：{category}</p>
}
⚠️ 版本差異 Next.js 15 起 searchParams 改成 Promise，必須 await 才拿得到值；Next.js 14 及以前是同步物件，可以直接 searchParams.category。詳見 官方 Page 的 searchParams 說明。

四、判斷順序（遇到 bailout 時照這個順序問自己）

(m) 這是一條有先後的檢查流程，所以用數字而不是字母：

  1. 這個元件真的需要 Query String 嗎？不需要就改 usePathname（解法一）
  2. 需要，但讀取點在 page.tsx 嗎？是的話改用 searchParams prop（解法三）
  3. 需要，而且一定要在 client component 裡讀嗎？才用 <Suspense> 包（解法二）
  4. 包完之後，確認 <Suspense> 的位置越低越好，不要包在 layout 這種每頁都吃到的地方

(n) 延伸備註：bailout 這個詞在 Next.js 文件裡不只一種用法。本篇講的是預渲染 bailout（prerender bailout），發生在建置期；另外還有 React 自己的 render bailout（state 沒變就跳過 re-render），那是執行期的事情，兩者不要混在一起。

申論題

Q1. 用「誰 用什麼 做什麼、產物是什麼、再拋給誰」的句型，完整描述 next build 遇到一個沒有被 Suspense 包住的 useSearchParams() 時發生了什麼事。
Next.js 用 Node.js 在建置期把 /dashboard 的元件樹執行一遍，產物本來應該是一份寫進 .next/server/app/dashboard.html 的完整 HTML 字串。執行到 useSearchParams() 時，這個 hook 偵測到自己正在「靜態預渲染」而不是在瀏覽器裡，而它要讀的 Query String 在這個時間點不存在，於是它 throw 出一個 bailout 例外。這個例外往上冒泡，本來應該被最近的 <Suspense> 邊界接住並把該子樹標記成「交給瀏覽器渲染」；但因為沒有任何 Suspense，例外一路冒到頂端沒人接，Next.js 就把整個 build 判定為失敗，拋給終端機的訊息是 Missing Suspense boundary with useSearchParams。
Q2. 為什麼 usePathname 不會 bailout，useSearchParams 卻會？請用「建置期能不能算出這個值」當主軸回答，並說明這跟 FCP 有什麼關係。
差別在於值的來源。路徑是由檔案系統的資料夾結構決定的，app/dashboard/page.tsx 這個檔案擺在那裡，建置期就知道它的路徑是 /dashboard，所以 Node.js 算得出來、可以安心預渲染。查詢字串則是由未來某一個使用者在網址列打出來的，建置的當下還沒有任何請求進來，這個值在邏輯上不存在，不是「還沒算」而是「無法算」。

跟 FCP 的關係是：bailout 之後伺服器吐給瀏覽器的 HTML 裡沒有真正的文字，只剩空殼。瀏覽器必須先下載 JS、執行 React、再發 API 請求，才畫得出第一個字，FCP 因此被拉長好幾秒。這也是為什麼 bundle 很小（gzip 才 177 KB）FCP 卻還是 5.24 秒——問題不在體積，在 HTML 裡沒東西。

useSearchParams 與 usePathname 都用於獲取當前頁面的 URL 資訊，但專注的位置與用途完全不同。usePathname 讀取 URL 的路徑（Path），主要用於判斷使用者「現在在哪個頁面」；useSearchParams 讀取 URL 的查詢參數（Query String），主要用於取得網址問號後面的資料篩選、分頁或搜尋條件。接著給出對照表（讀取範圍、傳回型態、常見情境、伺服器預渲染需求）與兩段程式碼範例：usePathname 用來設定選單高亮，useSearchParams 需搭配 .get() 獲取特定參數。簡單口訣是「想知道走到哪一頁用 usePathname，想知道帶了什麼條件用 useSearchParams」。

Gemini
useSearchParams 造成 Prerender Bailout（靜態渲染失效）是 Next.js App Router 社群中非常經典且常見的陷阱。在生產環境構建或靜態預渲染時，伺服器會嘗試將頁面事先打包成 HTML；usePathname 的路徑在構建時是固定且可預測的，因此可以安心預渲染；useSearchParams 的查詢參數代表動態的使用者請求資料，在伺服器靜態打包的當下不可能知道使用者未來會帶什麼 Query String 進來。因此一旦元件直接使用了 useSearchParams()，Next.js 會認定這個元件無法在靜態打包時完成渲染，將包含該元件的整條 Client 元件樹跳出靜態渲染，轉為用戶端渲染。如果沒有用 <Suspense> 包覆，在 next build 時會直接拋出 Missing Suspense boundary with useSearchParams。常見解決方案有三個：替換為 usePathname、加上 <Suspense> 包覆、改用 Server Component 的 searchParams prop。
