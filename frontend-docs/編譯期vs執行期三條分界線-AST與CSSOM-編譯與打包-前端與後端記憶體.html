🧠 自我測驗

是非題

  1. PostCSS 產生的 AST 和瀏覽器產生的 CSSOM 是同一棵樹的不同名字。

    AST 在建構期由 Node.js 工具產生用來改程式碼；CSSOM 在執行期由瀏覽器產生用來畫畫面，兩者從不相遇。

  2. Vite 或 Webpack 本身認得 .vue 檔的語法。

    建置工具只是排程器，是外掛（@vitejs/plugin-vue / vue-loader）裡的 @vue/compiler-sfc 才認得。

  3. HTML5 原生的 <style scoped> 屬性目前仍是主流瀏覽器支援的標準。

    因渲染效能與 Reflow 開銷過大被廢棄，改由 Shadow DOM 或編譯期方案（Vue Scoped CSS、CSS Modules）取代。

  4. 單向綁定中的「Model」指的是後端資料庫的資料表。

    Model 指前端 JS 記憶體裡的 state 變數，跟 API 與資料庫完全無關。

  5. 前端記憶體與後端記憶體可以直接互相讀寫變數。

    兩者實體隔絕，唯一通道是網路（HTTP／WebSocket）。

  6. 後端記憶體是所有使用者共享同一個進程，前端記憶體則是每個使用者獨享。

    這也是後端寫全域變數要特別小心的原因。

  7. 用 textContent 賦值時，字串裡的 <img onerror=...> 會被瀏覽器執行。

    textContent 會強制轉義成純文字，這正是它比 innerHTML 安全的地方。

填空題

  1. AST 的全名是 Abstract Tree，中文叫抽象語法樹，產生於建構期。

    由 PostCSS／Babel／ESLint 這類工具產生，目的是修改程式碼。

  2. CSSOM 的全名是 CSS Model，產生於執行期，會與 DOM 樹合併成 Render Tree。

    CSS 物件模型，由瀏覽器渲染引擎建立。

  3. 把 <template> 轉成 JS 渲染函式屬於「」這道工序；把數百個檔案依 import 關係合併成 index.js 屬於「打包」。

    Compilation／Transpilation 是碼轉碼，Bundling 是多檔合併。

  4. Vue 外掛的核心編譯器叫 @vue/compiler-，負責把 .vue 拆成 template／script／style 三塊。

    Single File Component 單檔案元件編譯器。

  5. Vue Scoped CSS 的做法是在編譯期產生一個 hash，把選擇器改寫成 .title[data-v-] 這種形式。

    實際值是隨機 hash，重點是「用屬性選擇器把作用域鎖住」。

  6. 原生 <style scoped> 被廢棄後，執行期的替代方案是 DOM，編譯期的替代方案是 Vue Scoped CSS 與 CSS Modules。

    Shadow DOM 提供瀏覽器原生的樣式隔離。

  7. 單向綁定的精確定義是： 的變動不會自動同步回 JS 的 Model 變數。

    所以 React 必須顯式寫 onChange 去 setState。

申論題

  1. 面試官問：「CSS 到底是變成 AST 還是 CSSOM？」請完整回答。

    參考方向：(1) 兩個都會發生，但分屬不同階段。(2) 建構期：PostCSS／Babel 這類 Node.js 工具把 CSS 文字解析成 AST（抽象語法樹），目的是用程式去尋找並改寫程式碼，例如替 .title 補上 [data-v-xxxx]，處理完再 Stringify 回一份新的 .css 檔。(3) 執行期：瀏覽器下載到那份「已經被改寫完的最終 CSS」，才把它解析成 CSSOM，與 DOM 樹合併成 Render Tree，最後 Paint 出像素。(4) 關鍵是瀏覽器完全不知道 PostCSS 存在，它拿到的就只是普通 CSS。(5) 一句話收尾：AST 是為了改程式碼而生的樹，CSSOM 是為了畫畫面而生的樹。

  2. 請說明 Vite/Webpack 是怎麼「知道」一個 .vue 檔該怎麼處理的，並用這個例子說明前端工具鏈的分層設計。

    參考方向：(1) 建置工具本身不認識 Vue，它只是任務排程器，靠副檔名觸發設定好的外掛。(2) 讀到 .vue 時觸發 @vitejs/plugin-vue 或 vue-loader，外掛核心是 @vue/compiler-sfc。(3) 這支編譯器做 SFC Block Parsing，把檔案拆成 template（轉 JS Render Function）、script、style scoped（產生唯一 hash）。(4) 再把 CSS 與 hash 一起交給 PostCSS，由 PostCSS 的插件把選擇器改寫成 .title[data-v-7ba5bd90]。(5) 分層設計的精神：核心保持通用，語言與框架知識全部下放到外掛；每一層只認識自己那一小塊——PostCSS 也不知道 Vue 是什麼，它只收到「一段 CSS 加一個 hash 字串」。

  3. 用「修改使用者名字」這個情境，說明資料從前端記憶體一路到資料庫的完整流程，並指出最常見的觀念誤區。

    參考方向：(1) 前端記憶體：使用者在 input 打字，透過 onChange 呼叫 setName，name 從 'Abby' 變成 'Alex'。注意如果只綁 value 不寫 onChange，變數根本不會變（單向綁定）。(2) 網路傳輸：按下儲存按鈕，前端 JSON.stringify 後發 HTTP POST /api/user。(3) 後端記憶體：Node.js／FastAPI／Go 進程收到 request，解析成 req.body.name 這個伺服器記憶體裡的變數。(4) 永久儲存：後端執行 UPDATE users SET name = 'Alex' 寫入硬碟上的資料庫。(5) 最常見誤區：以為 setState 就等於存好了。前端記憶體非常短命，重新整理就清空；沒有發 API 的話，後端與資料庫根本不知道這件事發生過。(6) 可補充兩塊記憶體的隔離性差異：前端每個使用者獨享，後端所有使用者共享同一進程。

編譯期 vs 執行期的三條分界線

[!info]- 📍 這篇在整條學習線的哪裡
承接：00-前端建構到執行全景地圖 把整條路畫成一張圖，這篇專門攻其中最容易混淆的三個交界處——每一個都是「名字很像、實際上分屬兩個世界」。
延伸：Scoped CSS 的 Vue 實作細節見 Vue-SFC實務-styles資料夾與scoped編譯原理-lang與src屬性-CSS預處理器-JSX支援；瀏覽器端的 CSSOM → Render Tree 見 Critical-Rendering-Path-關鍵渲染路徑-重排vs重繪。

本篇重點 (a)–(p)，共 16 個。三條分界線：一、AST／CSSOM　二、編譯／打包　三、前端記憶體／後端記憶體。

分界線一：AST 與 CSSOM——同樣是「把 CSS 變成樹」，卻是兩個世界

[!question]+ 原本的疑問
「PostCSS 的工作是把 CSS 解析成語法樹（AST）」——CSS 不是應該轉成 CSSOM 嗎，怎麼會是 AST？

a. 兩個都對，只是發生的時間與地點完全不同，它們從來不會在同一個場景相遇。

AST（抽象語法樹） CSSOM（CSS 物件模型）
全名 Abstract Syntax Tree CSS Object Model
發生時間 建構期／編譯期（Build Time） 執行期（Runtime）
發生地點 你的電腦或 CI 上的 Node.js 環境 使用者瀏覽器的渲染引擎（Blink、Gecko）
誰在用 PostCSS、Babel、ESLint 這些程式碼處理工具 瀏覽器渲染引擎
目的 為了修改與重寫程式碼 為了計算樣式並畫出畫面
產物 一份新的 .css 文字檔 與 DOM 樹合併成 Render Tree，然後 Paint 出像素

b. AST：PostCSS 把 .title { color: red; } 這串純文字解析成 JS 物件結構，這樣程式才有辦法「找到 .title 這個選擇器，然後在它後面補上 [data-v-xxxx]」。處理完再字串化（Stringify）還原成新的 CSS 檔。

c. CSSOM：瀏覽器下載到「最終那份已經被改寫完的 CSS」之後，才把它解析成 CSSOM 樹。瀏覽器從頭到尾不知道有 PostCSS 這回事——它拿到的就只是一份普通 CSS。

d. 一句話記法：AST 是「為了改程式碼」而生的樹，CSSOM 是「為了畫畫面」而生的樹。前者活在你的硬碟上，後者活在使用者的瀏覽器裡。

分界線二：編譯與打包——.vue 檔到底經歷了什麼

[!question]+ 原本的疑問
.vue 檔經過 Webpack 或 Vite，叫做編譯還是打包？如果 <style scoped> 要在打包階段把樣式丟給 PostCSS 改寫屬性，那這個編譯器怎麼知道它是 Vue？

e. 答案是兩件事同時在發生，但是不同工序：

工序 定義 在 .vue 上具體做了什麼
編譯（Compilation／Transpilation） 把某種程式碼轉換成另一種程式碼 把 <template> 轉成 JS 渲染函式；把 <style scoped> 交給 PostCSS 轉成帶 hash 屬性的 CSS
打包（Bundling） 把多個獨立模組整理合併成少數幾個產出檔 把數百個 .js／.vue／.css 依 import 依賴關係圖拼接、壓縮成 index.js 與 index.css

f. 建置工具本身完全不認識 Vue。Vite 與 Webpack 只是任務排程器，它們靠外掛機制（Plugins／Loaders）來識別檔案類型。整條鏈是這樣接的：

Vite / Webpack 讀到副檔名 .vue
        │  觸發設定好的外掛
        ▼
@vitejs/plugin-vue  或  vue-loader
        │  外掛的核心是這支編譯器
        ▼
@vue/compiler-sfc（Vue 單檔案元件編譯器）
        │  做 SFC Block Parsing，把 .vue 拆三塊
        ├── <template> ──► JS Render Function
        ├── <script>   ──► JS 模組
        └── <style scoped>
                │  產生唯一 hash，例如 data-v-7ba5bd90
                ▼
            呼叫 PostCSS，把 CSS 與 hash 一起丟過去
                │
                ▼
            選擇器被改寫成 .title[data-v-7ba5bd90]

g. 所以「編譯器知道它是 Vue 嗎」的正確答案是：通用的建置工具不知道，是外掛裡的專用編譯器 @vue/compiler-sfc 知道。這是前端工具鏈一貫的分層設計——核心保持通用，語言／框架知識全部下放到外掛。

h. 同理可推：PostCSS 也不知道 Vue 是什麼。它只是收到「一段 CSS ＋ 一個 hash 字串」，然後照插件的規則做字串層級的選擇器改寫。每一層都只認識自己那一小塊。

<style scoped> 的身世：一個被廢棄的 HTML5 提案

i. 在標準 HTML 裡，CSS 預設是全域生效的。頁面任何地方寫了 p { color: red; }，全頁所有 <p> 都會變紅。

j. HTML5 曾有一個原生的 <style scoped> 提案：<style> 若帶上 scoped 屬性，它的作用範圍就被限制在它的父元素及其內部子元素，不會外洩到全域 DOM。

<!-- 全域環境 -->
<p>我是黑色的字（不受影響）</p>

<div class="card">
  <!-- 這段樣式原本只該對 <div class="card"> 及其內部生效 -->
  <style scoped>
    p { color: red; }
  </style>
  <p>我是紅色的字</p>
</div>

k. 為什麼被廢棄：要瀏覽器在動態解析 DOM 樹的當下即時計算並切斷樣式作用域，對渲染引擎的效能開銷極大，且容易觸發重複排版（Reflow）。主流瀏覽器最終放棄原生實作。

l. 現在的替代方案分兩派：執行期派是 Shadow DOM（瀏覽器原生隔離）；編譯期派是 Vue Scoped CSS（建置階段改寫選擇器）與 CSS Modules（建置階段改寫 class 名）。社群主流走編譯期派，因為把成本挪到建置階段，執行期零開銷——這又回到了分界線一與分界線二。

分界線三：前端記憶體與後端記憶體——「Model」到底指哪裡

[!question]+ 原本的疑問
「單向綁定時使用者 input 不會直接寫入 Model」——這個 Model 是指不會直接打 API，還是不會直接寫到資料表？

m. 都不是。這裡的 Model 指的是 JavaScript 記憶體裡存的資料狀態（State／變數），跟後端 API 與資料庫完全無關。前端 MVVM／MVC 的分層是：

層 是什麼
View 畫面上的 DOM 元素（<input>、<div>）
Model 前端 JS 記憶體裡的變數（React 的 useState、Vue 的 ref、或普通 JS 物件）
API／資料庫 後端伺服器與資料儲存層，是完全另外一回事

n. 所以單向綁定（Unidirectional Data Binding）的精確意思是：View 的變動不會自動同步回 JS 的 Model 變數。使用者在輸入框打字時，畫面上會顯示（那是瀏覽器的原生行為），但變數完全沒變。

const [name, setName] = useState('Abby');

// ❌ 只綁 value：Model 永遠停在 'Abby'，畫面甚至可能卡住不給你打字
<input value={name} />

// ✅ 必須顯式監聽事件，Model 才會被改
<input value={name} onChange={(e) => setName(e.target.value)} />

o. 前端記憶體與後端記憶體在邏輯上獨立、在實體上也完全隔絕：

特性 前端記憶體（Client-side） 後端記憶體（Server-side）
存在位置 使用者裝置上的瀏覽器進程內（例如 Chrome 的 V8） 遠端伺服器（機房、AWS／GCP、Docker 容器內）
儲存內容 React／Vue 的 state、DOM 樹、當前分頁的 JS 變數 伺服器進程變數、快取（Redis／node-cache）、資料庫連線池
生命週期 非常短命：重新整理或關閉分頁就立刻清空 長期運行：伺服器沒重啟就一直保留
隔離性 每個使用者獨享，互不干擾 所有使用者共享同一個進程

p. 兩塊記憶體無法直接存取對方的變數，唯一通道是網路：

[1. 前端記憶體 Browser RAM]  使用者打字，name 從 "Abby" 變成 "Alex"
        ▼
[2. 網路傳輸]  按下「儲存」→ JSON.stringify → HTTP POST /api/user
        ▼
[3. 後端記憶體 Server RAM]  Node.js / FastAPI / Go 收到 request，解析成 req.body.name
        ▼
[4. 永久儲存 Database Disk]  UPDATE users SET name = 'Alex'

[!danger]+ 最常見的觀念誤區
setName('Alex') 只影響使用者自己電腦瀏覽器裡的記憶體。如果沒有透過 fetch／axios 把資料送給後端，重新整理頁面後前端記憶體被清空，資料就消失了——因為後端記憶體與資料庫根本不知道發生過這件事。

附帶收穫：字串渲染 vs DOM 節點渲染的資安差異

同一段對話最後追問了程式碼範例，Gemini 用 Google Maps API 的新舊寫法示範，這其實是 textContent-innerText-innerHTML差異 的實戰版：

// ❌ 舊版 API：直接吃 HTML 字串 → XSS 漏洞
const userInput = '<img src="x" onerror="alert(1)">';
new google.maps.InfoWindow({
  content: `<div>使用者暱稱：${userInput}</div>`   // 💥 onerror 會被執行
});

// ✅ 現代 API：先建 DOM 節點，用 textContent 賦值
const markerContent = document.createElement('div');
const titleNode = document.createElement('p');
titleNode.textContent = `使用者暱稱：${userInput}`;   // 標籤被強制轉義成純文字
markerContent.appendChild(titleNode);
new google.maps.marker.AdvancedMarkerElement({
  map: mapInstance,
  position: { lat: 25.0330, lng: 121.5654 },
  content: markerContent                              // 傳的是 DOM 物件，不是字串
});
比較項目 舊版字串渲染 現代 DOM 架構
資料載入方式 拼接 HTML 字串（innerHTML） 建立 DOM 物件並賦值（textContent）
XSS 防禦 要開發者手動 sanitize，漏掉就出事 原生層級轉義，標籤一律當純文字
CSS 與腳本隔離 與全域樣式互相干擾 可搭配 Shadow DOM 建立隔離壁壘
