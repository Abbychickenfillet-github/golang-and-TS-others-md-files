a定義：高併發 = 同一時間有很多請求在系統內「進行中」

先講全名與意思，再用縮寫。表格內不放 wikilink（避免 pipe 拆表），關聯筆記集中在最後一節。

名詞全名與意思面試白話
併發 concurrency多個獨立任務在時間上交錯推進，結構上能同時處理（Go 官方部落格引述 Rob Pike：獨立執行程序的組合）一個人輪流照顧多個鍋子
並行 parallelism多個計算在同一個瞬間真的同時執行（需要多核心）多個人各炒一個鍋
QPSQueries Per Second，每秒查詢數，常指伺服器每秒收到的請求數入口流量
RPSRequests Per Second，每秒請求數，與 QPS 在 HTTP 情境常通用同上
TPSTransactions Per Second，每秒完成的交易數（一筆交易可含多個請求）業務完成量
吞吐量 throughput單位時間內系統成功處理的工作量出口產能
P95 與 P99 延遲Percentile，95% 或 99% 的請求不慢於此時間，用來看長尾平均值會騙人，要看 P99
同時在線人數Concurrent Users，同一時間連著系統的使用者，不等於同時發請求在線不等於在打 API
一句話定義：高併發沒有固定門檻數字，是「同時在處理的請求數」逼近或超過系統某一層的容量（連線池、執行緒、資料庫連線、頻寬）。所以說高併發一定要指出瓶頸在哪一層。

Little's law 計算機：同時在飛的請求數 L = λ × W

L 是系統內平均同時存在的請求數，λ（lambda）是平均到達率（QPS），W 是每個請求平均停留時間。來源：Wikipedia Little's law（頁面最後編輯 2026-08-20 UTC）。

QPS 平均延遲 ms 單台可同時處理

e底層觀念如何對應到每個手段

底層觀念一句話對應手段
event loop（2026-04-06）JS 單執行緒，每個 job 跑到完才換下一個（run-to-completion）長任務會卡住點擊與捲動，所以要切片或丟 Web Worker
microtask 與 macrotask（2026-09-22）Promise 的 then 是 microtask，在下一個 task 前清空。setTimeout 是 task併發池 worker 迴圈用 await 讓出，debounce 靠 setTimeout 延後
同源連線數上限HTTP/1.x 同網域常見 6 條，多的請求在瀏覽器排隊減少請求數、合併、併發池控制在上限內
HTTP/2 多工單一連線可同時跑多個請求，不需要網域分片請求量仍要控制，因為伺服器與資料庫沒有變多
HTTP 快取（2026-08-14）max-age 內的回應直接重用，不打來源靜態資源 hash 檔名加長快取，API 看資料新舊度
ISR（Next.js 文件 2026-10-15）先回快取頁，過期後背景重新產生大量讀取的頁面不進 API 與資料庫
Web Worker（2026-08-27）在背景執行緒跑運算，不卡主執行緒大量資料排序與統計

f面試怎麼說：先破題再分層再 STAR

破題（先講這句）：「前端不直接扛高併發，扛的是後端。前端能做的是讓進到後端的請求變少、變慢進來、變重複少，以及流量失敗時優雅降級。」
層次手段一句話
1 少發debounce、throttle、合併請求、快取、CDN、Service Worker最快的請求是不發的請求
2 發得聰明去重、AbortController 取消、併發池、SSR 與 SSG 與 ISR同一件事只做一次，過期的丟掉
3 失敗得漂亮重試加退避、降級、骨架屏、樂觀更新不要讓使用者看到白畫面
4 看得見RUM（Real User Monitoring）、Web Vitals用真實使用者數據證明有改善
展開：可直接背的 STAR 口語稿（引用的數字都來自我的專案程式碼與 commit）
S 情境
「我做了一個 Next.js 的時間紀錄網站 timelog。儀表板一進來要載入時間紀錄、已分享清單和 AI 分析，而且免費與付費使用者有不同的 API 額度，所以我很在意重複與無效的請求。」
T 任務
「目標是流量變大時，不讓無效請求打到資料庫，同時讓首屏夠快。」
A 行動
「後端我在 lib/rate-limit.js 用記憶體 Map 做滑動視窗，依 userId 與類型限額，免費用戶每小時 50 次，超過回 429。前端收到 429 才用動態 import 載入 SweetAlert2，不佔首包。AI 分析區塊用 React.lazy 加 Suspense 延後載入。檢查額度的 API 我改讀 current_log_count 欄位，避免每次 COUNT 查詢。另外我把中文字體子集化，讓 LCP 從 2.4 秒降到 0.81 秒。」
R 結果
「LCP 降到 0.81 秒（commit 敘述）。我也自己檢查出缺口：儀表板的 fetch 還沒有 AbortController，已分享清單是等時間紀錄回來後才依序請求，這兩點是我下一步會用取消舊請求與並行請求補上的。」
面試加分點：主動講缺口與下一步，比誇大成果可信。不要說「我撐過幾萬 QPS」，除非真的壓測過。

g你的專案實證（已實際讀過程式碼）

位置事實對應面試說法
lib/rate-limit.js:7 與 :50模組層級 Map 存每個 userId:type 的時間戳陣列，checkRateLimit 過濾視窗內紀錄，滿額回 allowed false滑動視窗限流，保護後端
lib/rate-limit.js:34免費 api 每小時 50、db 每天 120。付費 api 120、db 520，可用環境變數覆寫分級額度
lib/rate-limit.js:25setInterval 每小時清過期紀錄避免記憶體無限成長
lib/rate-limit.js:93rateLimitMiddleware 是 Express 風格 (req, res, next)，專案內實際只有 checkRateLimit 被 route 呼叫如實說：中介層版本目前沒用
app/dashboard/page.js:823收到 429 且 errorType 是 rate_limit，才 await import('@/lib/swal-rate-limit')降級提示與 code splitting
app/dashboard/page.js:24AvatarUpload 與 AIAnalysisSection 用 React.lazy非首屏功能延後載入
app/dashboard/page.js:811 與 :857fetchTimeLogs 成功後才 await fetchSharedLogIds，兩個請求串行。fetch 沒有帶 signal缺口：可改 Promise.all 並加 AbortController
app/(api)/api/timelogs/route.jstimeLog.findMany 沒有 take 或分頁，並 include steps缺口：資料變多要分頁或游標
stores/useTimeLogStore.js:248 與 app/(api)/api/timelog/route.js:67儲存流程先 GET check-limit 再 POST timelog，兩支 route 都呼叫 checkRateLimit，一次儲存吃兩次 api 額度可合併成一次請求
app/api/timelog/check-limit/route.js註解寫明用 current_log_count 欄位避免 COUNT 查詢用冗餘欄位換資料庫負載
services/rest-client/use-fetcher.js使用 SWR 的 useSWR。SWR 同 key 並行請求會去重（SWR 文件）請求去重來源
專案全文搜尋找不到 AbortController、debounce、throttle 的使用如實說還沒做
推論（非程式碼事實）：rate-limit 的 Map 存在單一程序記憶體，若部署成多個實例，每個實例各算各的。Next.js 文件對 ISR 檔案快取也有同樣的「每個實例各自一份」警告。
