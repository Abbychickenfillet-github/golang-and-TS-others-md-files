## A. 渲染流程／HTML Parsing／主執行緒

**Q1. 從伺服器把 HTML 丟給瀏覽器，到畫面出現，中間發生什麼？**
<details><summary>▶ 參考答案</summary>

伺服器送來的是**一長串純文字**；瀏覽器的 **HTML 解析器（Blink，不是 V8）**在**主執行緒**上把字串 Parse 成 **DOM 樹**（`<div>` 文字 → `HTMLDivElement` 物件），CSS 解析成 CSSOM，合成 render tree → 排版（layout）→ 繪製（paint）。JS 由 V8 另一條線處理。
**決勝點**：純文字→Parse→DOM、Blink 做解析、主執行緒、DOM/CSSOM/render tree。
</details>

**Q2. HTML Parsing 是誰做的？跟 V8 有關嗎？**
<details><summary>▶ 參考答案</summary>

**瀏覽器渲染引擎（Chrome＝Blink）的 HTML 解析器**做的，**跟 V8 無關**。V8 是 JavaScript 引擎、只處理 JS（JS→AST→bytecode→機器碼）。HTML 永遠不會變成 AST/bytecode。
**決勝點**：Blink 解析 HTML、V8 只管 JS、兩條平行線。
</details>

**Q3. 為什麼一段 JS 執行會「卡住畫面」？**
<details><summary>▶ 參考答案</summary>

因為 **HTML 解析、DOM 建構、樣式計算、渲染、JS 執行共用同一條主執行緒（Main Thread）**，同一時間只能做一件事。JS 執行時會搶走主執行緒，解析/渲染就得暫停 → 畫面凍住。
**決勝點**：主執行緒唯一、JS 與渲染互斥、長任務會 block。
</details>

## B. `<script>` 載入策略

**Q4. `async` 與 `defer` 差在哪？各自何時用？**
<details><summary>▶ 參考答案</summary>

兩者都**背景平行下載、不中斷解析**。差別在執行：**`async` 一抓完就立刻插隊執行、不保證多支順序**（適合 GA/廣告等獨立腳本）；**`defer` 等整份 HTML 解析完才依序執行、保證順序**（適合要操作 DOM 的主程式）。
**決勝點**：下載都不擋、async 不保證順序/defer 保證、defer 等 DOM 蓋完。
</details>

**Q5. `<script type="module">` 跟 defer 有什麼關係？**
<details><summary>▶ 參考答案</summary>

**module 預設就是 defer 行為**（不中斷解析、等解析完才執行），還會依 `import` 遞迴載相依、自帶模組作用域。所以現代前端寫 `type="module"` 就不用再加 `defer`。
**決勝點**：module 預設 defer、有模組作用域、Vite 預設。
</details>

**Q6. `async`/`defer` 加在 inline script（沒有 src）上有效嗎？**
<details><summary>▶ 參考答案</summary>

**無效**。`async`/`defer` 只對「有 `src` 的外部 script」有意義（因為它們講的是「那支要下載的檔何時下載/執行」）；inline script 沒東西要下載，屬性被忽略、立刻執行。
**決勝點**：只對外部 src 有效、inline 忽略。
</details>

## C. 打包（build pipeline）

**Q7. 為什麼前端要「打包（build）」？**
<details><summary>▶ 參考答案</summary>

瀏覽器不認得 JSX/TS、也不想在使用者端逐支載幾百個模組。build-time 先**轉譯**（JSX/TS→JS）、**bundle**（合併成少數幾支）、**tree-shake/minify**（縮小）、**hash 注入**，產出 `dist/`（index.html + 幾支帶 hash 的 .js/.css），提升相容性與載入效能。
**決勝點**：相容性（轉譯）＋效能（合併/縮小/快取）＋瀏覽器只認 JS。
</details>

**Q8. transpile 跟 compile / bundle 差在哪？**
<details><summary>▶ 參考答案</summary>

**transpile（轉譯）＝原始碼→原始碼**（高階→高階，如 JSX/TS→JS），產物仍是純文字 JS。**bundle＝把多個模組合併成 chunk**。真正「編譯成 bytecode/機器碼」是 **V8 在 runtime** 做的（Ignition→bytecode、TurboFan→機器碼）。前端 build 不產生機器碼。
**決勝點**：transpile 源碼對源碼、bundle 合併、機器碼在 V8 runtime。
</details>

**Q9. 什麼是 tree-shaking？靠什麼運作？**
<details><summary>▶ 參考答案</summary>

**砍掉「沒被 import 用到的 export」（死碼）**，讓產物更小。靠 **ES module 的靜態 import/export**（編譯期就能分析誰用到誰）；CommonJS 的動態 `require` 不易分析。副作用檔要靠 `package.json` 的 `sideEffects` 保護、別被亂砍。
**決勝點**：移除死碼、靠 ESM 靜態分析、sideEffects。
</details>

**Q10. code splitting 跟 lazy loading 差在哪？（陷阱題）**
<details><summary>▶ 參考答案</summary>

**主詞與時間點不同**：**code splitting 在 build-time**——bundler 把 `import()`/`React.lazy` **切成獨立 chunk 檔**；**lazy loading 在 runtime**——**瀏覽器**在使用者走到那頁時才**下載**那支 chunk。build 切好、runtime 才按需載。
**決勝點**：build 切 vs runtime 載、主詞（bundler／瀏覽器）。
</details>

**Q11. Webpack 跟 Vite 差在哪？**
<details><summary>▶ 參考答案</summary>

**Webpack** 全程 bundle（含開發），啟動較慢；**Vite** 開發用**瀏覽器原生 ES Module + esbuild 預轉譯**（幾乎不 bundle，啟動快），**生產才用 Rollup（Vite 8 起 Rolldown）bundle**。2026 Vite 是新專案預設、CRA 已棄用。
**決勝點**：Vite dev 用原生 ESM 不 bundle、prod 用 Rollup、Webpack 全程 bundle。
</details>

## D. CSR／SSR／SPA／hydration

**Q12. CSR 跟 SSR 差在哪？各優缺？什麼時候選 SSR？**
<details><summary>▶ 參考答案</summary>

**CSR**：伺服器發空殼 HTML，**瀏覽器端 JS 渲染**；伺服器輕、首屏慢、SEO 差。**SSR**：**伺服器每請求跑 React 產好內容 HTML**（`renderToString` 出字串），首屏快、SEO 好，但吃伺服器資源。**要 SEO / 首屏速度 / 社群預覽**時選 SSR。
**決勝點**：誰渲染首屏、首屏速度、SEO、伺服器負載。
</details>

**Q13. SPA 就是 CSR 嗎？**
<details><summary>▶ 參考答案</summary>

**不是。** 「SPA/MPA」是**路由模型**（換頁重不重載）；「CSR/SSR」是**首屏渲染在哪**，兩個獨立的軸。可組合：**SPA+CSR**（CRA/Vite SPA）、**SPA+SSR**（Next.js/Nuxt）。Next.js 就是 **SSR+SPA**：首屏伺服器渲染、hydration 後換頁走前端路由不重載。
**決勝點**：兩個獨立軸、Next.js＝SSR+SPA。
</details>

**Q14. 什麼是 hydration（水合）？**
<details><summary>▶ 參考答案</summary>

SSR 送來的是**已有內容但「沒事件」的靜態 HTML**；hydration ＝瀏覽器端 React **把事件監聽器、狀態掛回這些既有 DOM**，讓它變可互動。像「菜已煮好，加熱＝掛上互動」。
**決勝點**：把互動掛回既有 DOM、SSR 之後、讓靜態變可互動。
</details>

**Q15. SSR 是不是「每次 re-render 都在伺服器」？**
<details><summary>▶ 參考答案</summary>

**不是。** 只有**首屏那一次**在伺服器產 HTML 字串；hydration 之後，互動造成的 re-render 回到**瀏覽器端**，跟 CSR 一樣。
**決勝點**：只有首屏在伺服器、互動 re-render 在 client。
</details>

## E. 進階／陷阱

**Q16. Web Worker 解決什麼問題？有什麼限制？**
<details><summary>▶ 參考答案</summary>

把重的 JS 放到**另一條背景執行緒**跑、**不佔主執行緒**，避免卡畫面。限制：**不能直接碰 DOM**（DOM 只屬主執行緒），要靠 `postMessage` 跟主執行緒溝通。
**決勝點**：背景執行緒、釋放主執行緒、不能碰 DOM、postMessage。
</details>

**Q17. 「前端 build 完就變機器碼了」對嗎？**
<details><summary>▶ 參考答案</summary>

**錯。** build 產物是**純文字 JS/HTML**。變 bytecode/機器碼是 **V8 在使用者瀏覽器 runtime** 做的（Ignition→bytecode、TurboFan JIT→機器碼）。
**決勝點**：build 產純文字、機器碼在 runtime 的 V8。
</details>
