Web Worker、網路執行緒、ESM 原生載入與 Ajax 現況

重點整理

一、Web Worker（對話 Web Worker 環境限制）

(a) Web Worker 跑在獨立於 window 的背景執行緒，所以沒有 window 也沒有 document，不能直接操作 DOM。
(b) Worker 與主執行緒的溝通流程：主執行緒呼叫 worker.postMessage(data) 把資料交給 Worker → Worker 在背景計算（也可以用 fetch() 抓資料）→ Worker 呼叫 postMessage(result) 把結果傳回 → 主執行緒收到後自己更新 document。
(c) 為什麼需要：瀏覽器的 JS 預設單執行緒，主執行緒同時負責渲染與使用者互動，若一項運算花 3 秒，畫面會凍結。Worker 就是把重運算搬去背景的「工讀生」。
(d) 適用情境：大數據運算、大型圖片壓縮或影片轉檔、Excel 解析、AI 推論與加解密、背景輪詢與 WebSocket。
(e) XMLHttpRequest 出現在 MDN 的 Worker 文件，是因為 Worker 規格比 fetch 早出現，現在 Worker 內已可使用 fetch()。

二、網路執行緒與 Web API（對話 JS 標籤阻塞問題）

(f) DevTools 網路瀑布圖：綠色 = 等待伺服器回應（TTFB，首位元組時間），藍色 = 下載內容的傳輸時間。timing 分頁可看各階段耗時。
(g) 瀑布圖上的「1.48s」是從開始錄製算起的第 1.48 秒，不是時鐘的 1 點 18 分。
(h) 當瀏覽器 parse HTML 遇到 <script src="app.js">，主執行緒把下載任務交給網路執行緒（Network Thread），由它負責 HTTP 請求、TCP/IP 與 SSL 握手，主執行緒不必空等。
(i) Web API 是瀏覽器提供給 JS 呼叫的介面（fetch、setTimeout、DOM、localStorage）。兩者關係：網路執行緒是底層的「運輸部門」，Web API 是 JS 用來聯絡各部門的「窗口」。fetch() 觸發後，底層請網路執行緒發送請求，抓完再把結果丟回事件佇列。

三、ES Module 與 Ajax（對話 結束對話）

(j) ES Modules 讓腳本在瀏覽器原生運行：Safari 10.1（2017-03）、Chrome 61（2017-09）先後支援 <script type="module">，不再需要 Webpack、Browserify、RequireJS 把檔案打包。
⚠️ 存疑／更正：Gemini 說 Firefox 60 在「2018 年初」支援，Firefox 60 實際約 2018 年 5 月釋出，請以 MDN 相容表為準。
(k) ESM 與進程的關係：沒有新增進程類型。type="module" 預設 defer（不阻塞渲染）→ 網路進程對每個 import 發獨立請求 → 渲染進程的 V8 因 import/export 是靜態的，能在執行前先建好依賴樹。模組預設嚴格模式，且跨網域載入受 CORS 限制。
(l) Ajax 還有人用：AJAX（Asynchronous JavaScript and XML）的概念（不重新整理就向伺服器要資料並局部更新）已是標準，但 XML 已被 JSON 取代，寫法改用 fetch、Axios、TanStack Query、SWR。
