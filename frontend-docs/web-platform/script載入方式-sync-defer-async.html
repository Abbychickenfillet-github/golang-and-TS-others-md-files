網路執行緒那一行同時畫 JS 與 CSS 的下載（上下兩道，因為下載可以同時進行；HTML、圖片、fetch 也走同一個網路，圖中沒畫）。主執行緒只有一行：上道是解析 HTML、空等、執行 JS；下道是同一條主緒上「穿插」的工作，包含建 CSSOM（Blink 的 CSS parser 在主執行緒）以及 V8 的 BC、直譯（它們是「執行 JS」那一格的內部拆解）。一條執行緒同一刻只能做一件事，所以實際上建 CSSOM 會和解析 HTML 輪流使用主緒；圖為了不改動時間刻度，把它畫在下道。主執行緒上粉紅斜線「等 CSSOM」＝JS 已經下載好，卻因為 CSSOM 還沒建好不能執行。網路執行緒是瀏覽器內部的元件，你寫不了它；你能自己開的背景執行緒是 Web Worker，兩者不同。

JIT 編譯的時機點（六種模式共通，位置跟著「執行 JS」走）
  1. 不是 script 一到就編。JS 下載完（inline 則是讀到）後，V8 先 parse 成 AST、產生 bytecode（Ignition，圖中 BC），然後直譯執行並收集型別回饋。JIT 在這之後才可能發生。
  2. 熱了才編。執行時累積「額度」（呼叫次數、迴圈次數），用完才送去編譯；層級由低到高是 Sparkplug、Maglev、TurboFan，越高階門檻越高。短小的 script 可能整段都沒觸發 JIT，所以圖中 JIT 與「換上」畫虛線。細節見 04 V8 引擎管線。
  3. 在哪條執行緒。優化編譯多半在背景執行緒做，主執行緒繼續直譯，編好才換上，所以 JIT 本身不擋解析 HTML；但有些步驟仍在主緒，不是全部都在背景。Sparkplug 另有「背景編譯」的 Chromium 旗標（V8ConcurrentSparkplug），是否預設啟用我沒有查證。
  4. 和六種模式的關係。模式只決定「執行 JS」那一格出現在哪個時間點，JIT 整組跟著往後移，位置關係六種都相同。defer、module 的 JIT 也要等解析完才開始，JIT 補不了「晚執行」。
  5. 圖沒畫的兩件事。① 下載期間 V8 可能已在背景，把「已經收到的那一段原始碼」先 parse 並編成 bytecode（script streaming）：輸入是原始碼，輸出才是 bytecode，主緒只做最後收尾；② 型別假設被打破時 Deoptimization 退回直譯。
來源：V8 官方部落格 Maglev（Ignition、Sparkplug、Maglev、TurboFan 四層；Maglev 隨 Chrome M117 上線）、Background compilation（背景 parse／編譯）；「優化編譯多半在背景」另參考 Intel 工程部落格（二手資料，非 V8 官方文件）。門檻、各層確切觸發條件與各層在哪條執行緒，本頁沒有逐一查證，位置與長度為示意。
CSS 在這張圖的角色（六種模式共通，不隨按鈕變；各模式專屬的 CSS 影響看上方「CSS 在這個模式的角色」）
  1. 平行下載、獨立建 CSSOM，不擋解析 HTML。CSS 的「下載」走網路，和主執行緒的解析 HTML 同時進行，DOM 照蓋。「建 CSSOM」本身多半仍占用主執行緒（各引擎不同），只是很短；「建 CSSOM」那一行是邏輯上的流程，不是獨立的執行緒。
  2. 擋「畫」。CSSOM 沒建好就不畫第一個像素（避免先閃出沒樣式的畫面，FOUC）。所以 CSS 越慢，白畫面越久，和你用哪種 script 載入無關。
  3. 擋「後面的同步 script 執行」。script 可能讀樣式，要等前面 <link> 的 CSSOM 好了才跑。上圖 CSS 比 JS 早好所以看不出來；若 CSS 比 JS 慢，一般 script 的「執行 JS」會被往後推。
DOM ＋ CSSOM → Render Tree → Layout → Paint
CSS → CSSOM：什麼時候開始、怎麼建
  1. 下載起點：CSS 不是從時間 0 就開始。要等瀏覽器讀到 <link rel="stylesheet">（或被 preload scanner 掃到）才去下載。
  2. 建 CSSOM：下載完才由 CSS parser 解析建 CSSOM。<link> 寫在 <head> 所以起點很靠左但不是 0；寫在 <body> 後面就更晚才抓。
  3. CSS 裡的資源：@import、字型、背景圖要等 CSS 解析後才被發現（preload scanner 看不到 CSS 檔內部），所以會一層一層串成瀑布。
  4. preload scanner：它會在主解析器還沒走到之前，先往後掃 HTML 提早抓 CSS 和 JS。圖中的下載起點（包含 JS 的「解析到 <script> 才開始」）都是簡化成「解析到那個標籤」。
三個常見疑問
  1. JS 會改變 HTML Parsing 的結果嗎？會，靠 document.write()：它把字元直接插進解析器「還沒讀到的輸入流」，後面要解析的內容就被改了，所以同步 script 一定要先停下來。一般的 appendChild、innerHTML 是改「已經建好的 DOM」，不會改解析器的輸入。
  2. HTML parser 和 CSS parser 是同一個執行緒嗎？2026-10-28 查到的資料：Blink（Chrome）的 HTML 與 CSS 解析都在主執行緒（背景 HTML parser 已移除，CSS 為同步解析）；WebKit（Safari）的 HTML 解析在主執行緒（2014 年已移除 threaded parser），CSS 未能查證；Gecko（Firefox）不同，HTML 在背景 parser 執行緒，樣式表丟 thread pool 解析。「各自建」只代表兩套互不相依的演算法，真正平行的是網路下載。這是從官方原始碼目錄與討論推得，沒有現行的官方執行緒架構文件，也沒有實測。完整表格與來源見 瀏覽器解析執行緒。
  3. preload scanner 是什麼？不是完整的 parser，是「預載掃描器」：主解析器被 script 擋住時，往後讀 HTML 原始碼，找出 <script src>、<link href>、<img src> 的網址提早發請求。MDN 詞彙表的條目叫 Speculative parsing（推測式解析），該頁沒有出現 "preload scanner" 一詞，描述的是 Firefox 的做法：parser 自己往後解析、推測式建樹並提早載入。Blink 的 HTMLPreloadScanner 是獨立元件，在主執行緒、只掃 body 的第一個 chunk。限制：看不到外部 CSS 檔裡的 @import、url()。
記法：下載是平行的，被擋住的是「畫」與「執行」，不是「建 DOM」。細節見 css-兩種卡頓-render-blocking與執行期jank。

面試用 一般 <script>（無 defer/async）中斷 HTML Parsing「幾秒」？

沒有固定秒數。中斷時間＝兩段相加，而且會隨裝置與網路放大——這正是面試講「為何要 defer/async/code-splitting、為何要顧低階裝置」的切入點。

中斷時間 ≈（外部 src 才有）下載時間 ＋ V8 的 parse＋compile＋execute
  1. ① 下載時間（只有外部 <script src> 才有）＝ 檔案大小 ÷ 網速 ＋ 連線延遲(RTT)。
    網速單位＝bps（bits per second）＝Kbps／Mbps／Gbps。bit ≠ byte：檔案大小用 byte（KB/MB），1 byte＝8 bit，算下載要先 ×8。例：100 KB＝800 Kb，在 10 Mbps ≈ 0.08s（再加 RTT）。
    inline <script>（直接寫在 HTML 裡）沒有這段——字元已在 HTML，不用再發請求下載。
  2. ② parse＋compile＋execute 是 CPU-bound（滑鼠移上去看說明）：V8 把這段 JS 解析、編譯、跑完，吃的是主執行緒的 CPU，跟程式量＋實際做多少事＋裝置 CPU 有關。主場見 04 V8 引擎管線；CPU 本身見 01 CPU 五大單元。
同一支 script，不同裝置／網路差很多：
💻 桌機＋快 WiFi下載 ~50–150ms、執行 ~數十–200ms → 合計約 0.1s
📱 中階手機＋4G下載 ~0.5–1s、執行更久（CPU 較弱）→ 合計約 1–2s
📱 低階手機＋弱 3G下載可能好幾秒、執行也拖 → 合計 卡好幾秒

不同瀏覽器下載時間會不同嗎？下載的 bytes 本身主要由網路頻寬／延遲／伺服器決定，各瀏覽器差不多；但各家的 preload scanner、HTTP/2‧3、連線數、快取策略會影響「多早開始抓、要不要重抓」。真正差較多的是 parse/execute——引擎不同（Chrome/Edge 的 V8、Firefox 的 SpiderMonkey、Safari 的 JavaScriptCore）速度本就有差。

🎯 面試收尾：中斷時間＝下載＋CPU 執行、且隨裝置與網路放大，所以用 defer/async/type="module" 把它挪開、用 code-splitting 讓 bundle 變小，並以低階裝置為基準做效能預算。要精準量：DevTools → Performance 看那支 script 的 Evaluate Script 時間＋Network 的下載時間。

自我測驗 考考自己

Q1. 是非題：瀏覽器收到 index.html 時，<div> 已經是一個可以 .addEventListener() 的物件了。
錯。收到的是純文字字串，<div> 只是 5 個字元。要等 HTML Parsing 把它 new 成 HTMLDivElement、掛上 DOM 樹之後，才有 .addEventListener() 這些方法。（重點 a）
Q2. 哪一種載入方式「下載不中斷解析、且保證多支 script 按順序執行、最適合當操作 DOM 的主程式」？
defer。背景平行下載（不中斷解析），等整份 HTML 解析完、DOM 蓋好後，依 HTML 出現順序執行。async 是「抓完立刻插隊、不保證順序」，適合 GA 這種獨立腳本。（重點 e、f）
Q3. 是非題：「伺服器把 index.html 丟給瀏覽器」代表這一定是 SSR。
錯。CSR/SPA 也會丟 index.html，只是那是靜態檔案伺服器發的空殼（<div id="root"></div>），內容由瀏覽器端 JS 補。SSR 是活著的 Node 程式每請求現場渲染、HTML 裡已經有內容。差在「誰渲染／HTML 裡有沒有內容」。（重點 o、p）
Q4. 申論：為什麼 <script type="module"> 不用另外加 defer？
因為 ES Module 預設就是 defer 行為：不中斷解析、等解析完才依相依圖與順序執行。這是 Vite／原生 ES Module 的預設，所以現代前端寫 type="module" 就已經延後執行了。（重點 h）
