# `<script>` 三種載入方式：同步（預設）／`defer`／`async`

> 從 [[作用域-scope-global-function-block]] 「考點二」延伸出來的獨立筆記：專講瀏覽器解析 HTML 遇到 `<script>` 時的三種行為、以及彼此的差異與適用時機。

## ⚠️ 標籤命名的坑：不要用「同步JS」

一開始想把「沒加 `async`/`defer` 的 `<script>`」標成 `#同步JS`，但這個詞**容易跟另一個完全不同的主題撞名**，所以這篇改用 `#阻塞解析`／`#parser-blocking`／`#script-loading` 這幾個標籤，原因：

- **這篇講的是**：瀏覽器**什麼時候去抓、什麼時候去執行**一份 `.js` 檔案，跟 HTML 解析的**時間順序**有關——是「載入策略」層次的東西。
- **「同步 JS／非同步 JS」這組詞，在 JS 圈更常被拿去指另一件事**：JS **程式碼本身**的執行模型（callback、Promise、`async`/`await`、Event Loop、微任務/巨任務），也就是 [[JavaScript-事件循環與閉包-面試核心]]、[[事件循環-Event-Loop-微任務與巨任務]] 那兩篇在講的主題。
- 這兩個「async」講的是**不同層次的東西**：一個是「瀏覽器抓/跑 `<script>` 檔案的時機」，一個是「JS 程式碼內部處理非同步操作的機制」。如果標籤都叫「同步JS／非同步JS」，之後回頭找筆記會分不清楚是要找哪一篇。

**結論：這篇固定用 `#阻塞解析`(parser-blocking) 稱呼「沒加 async/defer 的預設載入方式」，不用「同步JS」這個詞，避免跟 Event Loop 那組筆記的關鍵字撞在一起。**

## 三種載入方式對照

| 方式 | 抓取(fetch)時機 | Parse／執行時機 | 會不會暫停 HTML 解析 | 多個同類 script 的執行順序 |
|---|---|---|---|---|
| 預設（無 `async`/`defer`） | 解析到當下才開始抓 | 抓完立刻 Parse+執行 | **會**，整個暫停到執行完 | 按 HTML 裡出現的順序（因為本來就是逐一暫停處理） |
| `defer` | 跟 HTML 解析**同時**抓取（不暫停） | **延後到整份 HTML 解析完（DOM 蓋好）之後**才 Parse／執行 | 不會 | **保證**按 HTML 裡出現的順序執行 |
| `async` | 跟 HTML 解析**同時**抓取（不暫停） | **一抓到就立刻插隊**執行（可能打斷 HTML 解析到一半） | 會（但只在它插隊執行的那一刻短暫暫停） | **不保證**順序，誰先抓完誰先跑 |

## 為什麼「多個 `async` 之間不保證順序」——具體例子

**前提：這是指「同一份 HTML 檔案裡，寫了兩個以上 `<script async>` 標籤」這個情境**，例如：

```html
<script async src="a.js"></script>
<script async src="b.js"></script>
```

雖然 `a.js` 寫在 `b.js` 前面，但 `async` 的規則是「**誰先從網路上抓完，誰就先插隊 Parse＋執行**」，完全不管你在 HTML 裡寫的先後順序。如果 `b.js` 檔案比較小、伺服器比較快、剛好網路壅塞狀況對它有利，`b.js` 完全可能比 `a.js` 早抓完，於是執行順序就變成 **b 先、a 後**——結果會依網路狀況浮動，同一份程式碼，這次測試跟下次測試順序可能不一樣。**這就是「不保證順序」的意思：不是每次都固定同一個順序，而是「順序取決於下載完成的先後，本質上是不確定的」。**

> 如果你的兩支 script 之間有依賴關係（例如 `b.js` 要用到 `a.js` 定義的東西），用 `async` 就會有炸掉的風險；這種情況要嘛用 `defer`（保證順序），要嘛把它們合併成一支檔案。

## 這跟「使用者 doubleClick／hover／呼叫 API」是不是同一件事？——不是，是完全不同的兩個階段

你問得很準，這裡要切開兩個完全不同的執行階段：

1. **本篇講的（script 載入排序問題）**：發生在**頁面第一次載入**的過程中，瀏覽器解析 HTML → 抓取/執行 `<script>` 的階段，**使用者根本還沒開始跟頁面互動**，純粹是「瀏覽器自己在跑開機流程」。
2. **doubleClick／hover／呼叫 API**：這些屬於**事件驅動（event-driven）的後續行為**，是頁面**載入完成、開始互動之後**才會發生的事，由 **Event Loop** 排程處理（click/hover 這類使用者互動進 macrotask 佇列，Promise/fetch API 回來的 callback 進 microtask 佇列），細節見 [[JavaScript-事件循環與閉包-面試核心]]。

**兩者的關聯只在於：`<script>` 標籤的載入方式，會決定「事件監聽器（例如 `button.addEventListener('click', ...)`）什麼時候被註冊好」**——如果你把註冊監聽器的程式碼寫在一支還沒執行完的 `<script>` 裡，使用者在那之前點按鈕是不會有反應的（監聽器還沒掛上去）。但「script 怎麼載入」跟「載入完之後使用者怎麼跟頁面互動」，是接續的兩個階段，不是同一套排序規則在管。

## 「瀏覽器把控制權交給 JS 引擎」具體是什麼意思

不是比喻，是**真的執行緒層級**的事：瀏覽器的 **HTML 解析、DOM 建構、畫面渲染、JS 執行，這幾件事全部共用同一條「主執行緒（Main Thread）」**，同一時間只能有一件事在跑。

所以「解析到 `<script>` 時，瀏覽器把控制權交給 JS 引擎」實際發生的事是：

1. HTML 解析器（跑在主執行緒上）解析到 `<script>` 標籤，**自己暫停**（不繼續往下讀 HTML 文字）。
2. 主執行緒現在轉交給 **JS 引擎**（V8 等）繼續用，JS 引擎把這段程式碼 Parse 成 AST → 編譯成 bytecode → 執行完。
3. JS 引擎執行完，**把主執行緒的控制權還給 HTML 解析器**，HTML 解析器才從剛剛暫停的地方繼續往下讀。

`defer`／`async` 之所以能「不暫停 HTML 解析」，靠的是**抓取（fetch，網路 I/O）本來就不占用主執行緒**（瀏覽器有獨立的網路執行緒去抓檔案），真正會佔用主執行緒的是「Parse＋執行」這一段——`defer`/`async` 差別只在於「Parse＋執行」這段**什麼時候**才去搶主執行緒，而不是「要不要」搶。
