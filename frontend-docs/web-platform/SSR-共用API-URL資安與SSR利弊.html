重點整理

本篇重點 a–h，共 8 個　 （點一下重點可隱藏／顯示，自己考自己）

(a)共用同一個對外 API URL 本身不是致命風險：只要是會被前端呼叫的 API，就必須假設會被使用者在 F12 或 Postman 看見並探測。
(b)資安核心是防禦而不是路徑隱蔽（Security through obscurity 不可靠）：Authentication／Authorization（Token、Cookie、Session 驗證）、Rate Limiting、Input Validation（防 SQL injection、XSS）、CORS 設定。
(c)常見模式：SSR 伺服器內部呼叫微服務時用內部網路 URL（例 http://internal-api-service/...），與對外公開 URL 分開。Next.js 的 Route Handlers 或 BFF 也是共用邏輯的標準做法。
(d)SSR 兩大優勢：效能（省去客戶端二次請求資料、FCP 首屏更快）與可訪問性（SEO 與社群縮圖抓取）。
(e)SSR 六個難題：存量 CSR 程式碼要同構（window／document、生命週期、第三方庫、狀態共用）。服務穩定性與高併發要求。配套設施（本地開發、發布流程）重建。Node 伺服器維護成本。Hydration 效能損耗（低階裝置不可互動時間）。資料請求與業務元件耦合需剝離。
(f)適用場景：偏靜態、內容密集（商品詳情、攻略、文章）。不適合互動密集頁面。
(g)CSR 的兩次請求：第一次拿空殼 HTML 與 JS bundle，第二次 JS 執行後以 fetch／AJAX 向 API 要資料再渲染，所以首屏慢。
(h)Next.js App Router：預設走 Server Component，用 async/await 與 fetch() 在伺服器取資料，直接避開 CSR 二次請求。Next.js 15 起 fetch 預設不再自動快取，快取要用設定或 use cache 指令啟用。Client Component 取資料可用 React use() 或 SWR／React Query。

自我測驗

共用 API URL 的安全關鍵是什麼？
後端的驗證授權、限流、輸入驗證與 CORS，而非把 URL 藏起來。
SSR 的 Hydration 是什麼代價？
客戶端收到 HTML 後仍要執行 JS 綁定事件，低階裝置會出現看得到但點不動的時間。
