一、先把最容易講錯的一句話講對

結論：return () => clearInterval(id) 這一行執行時，clearInterval 一次都沒有被呼叫。 它只是建立了一個函式物件並交還給 React。clearInterval(id) 要等到 React 決定該清理時、 真的去呼叫那個函式，才會被執行。

判斷「某個函式有沒有被執行」，看的是它後面有沒有一組緊貼著的呼叫括號：

return () => clearInterval(id)
//     └┬┘    └─────┬──────┘
//      │           └── 這個括號在「箭頭函式的本體裡」，屬於未來才會跑的程式碼
//      └── 這個括號是「參數列表」，代表這個箭頭函式不收任何參數

三種寫法，差一個箭頭天差地遠

寫法發生什麼事
return clearInterval(id) 立刻執行，回傳 undefined。計時器在 setup 當下就被關掉，而且 React 以為你沒有清理邏輯
return () => clearInterval(id) 正解。只造一個函式交出去，等 React 之後決定何時呼叫
return () => { clearInterval(id) } 跟上一列等價，只是寫成區塊本體。上一列是「簡潔本體」，隱含一個 return
用詞校正：return 是回傳／交還，不是「丟出」。 JS 裡「丟出／拋出」專指 throw（丟例外）。面試時講「丟出」會被聽成 throw。

二、填空：把口述版補完整（點擊虛線看答案）

「useEffect 的第一個參數是 點我。 我在它裡面開了一個 setInterval，它回傳一個 點我存進 id。 最後我用 return 把一個新建立的、不收參數的 點我交還給 React——注意這裡只是把函式交出去， clearInterval 點我。 這個函式因為引用了 id，形成 點我，id 被保留在 點我。 React 會把這個函式存進 effect 的 點我， 等到該清理的時機再呼叫它，那時候 clearInterval(id) 才真的執行。」

規律：setup① → cleanup① → setup② → cleanup② … 永遠成對且交錯，不會有兩個 setup 同時活著。
StrictMode（僅開發模式）在 t1 之後會多插一輪 setup① → cleanup① → setup①'， 故意檢查你的 cleanup 有沒有寫對。元件在 StrictMode 下行為異常（計時器變兩倍快、請求送兩次）， 通常代表 cleanup 漏寫了。

四、id 為什麼還在？——閉包把它從 Stack 搬到 Heap

沒有被內層函式引用

變數留在快速的 Stack／CPU 暫存器。 函式一 return，Stack Frame 彈掉，記憶體立刻釋放。

被內層函式引用（本篇的情況）

引擎在 Parse 階段的 Scope Analysis 就判定它會逃逸，改配置在 Heap 上的 Context 物件。setup 的 Execution Context 拆掉之後， id 依然活著，直到沒人引用才被 GC 回收。

一句話：清理函式能關掉「當初那一個」計時器，靠的不是 React 記得， 而是 JS 閉包把 id 從 Stack 搬到了 Heap。

五、React 內部的證據（可以直接背）

React 原始碼 packages/react-reconciler/src/ReactFiberHooks.js：

type Effect = {
  tag: HookFlags,
  inst: EffectInstance,
  create: () => (() => void) | void,   // ← setup 函式：回傳「一個函式」或「什麼都不回傳」
  deps: Array<mixed> | void | null,
  next: Effect,
};

type EffectInstance = {
  destroy: void | (() => void),        // ← 你 return 的那個清理函式，被存在這裡
};

create 的型別簽章 () => (() => void) | void 白紙黑字寫著： 它只能回傳「一個不收參數也不回傳值的函式」，或者什麼都不回傳。這直接解釋了兩個常見錯誤：

  1. useEffect(async () => {...}) → async 函式回傳 Promise，不是函式，型別對不上，React 會警告
  2. return clearInterval(id) → 回傳 undefined，React 以為你沒有清理邏輯

六、是非題

1. return () => clearInterval(id) 這一行會立刻呼叫 clearInterval。
錯。這一行只建立一個函式物件並回傳。clearInterval(id) 的括號在箭頭函式的本體裡，屬於未來才會跑的程式碼；整個箭頭函式後面也沒有再接一組 ()，所以它自己也沒有被呼叫。
2. 清理函式能關掉「當初那一個」計時器，是因為 id 被閉包捕獲後配置在 Heap 上。
對。引擎在 Scope Analysis 就判定 id 會逃逸，把它放進 Heap 上的 Context 物件，所以 setup 函式的 Stack Frame 彈掉之後它依然存活。
3. 依賴陣列寫 [] 的意思是「我希望這個 effect 只跑一次」。
錯。依賴陣列不是「我希望它跑幾次」的開關，是「這個 effect 讀了哪些外部值」的誠實申報。明明讀了 count 卻寫 []，就會產生 stale closure。
4. setup 與 cleanup 永遠成對交錯執行，不會有兩個 setup 同時活著。
對。順序永遠是 setup① → cleanup① → setup② → cleanup② …。依賴變動時 React 一定先跑舊的 cleanup、再跑新的 setup。
5. useEffect(async () => {...}) 是合法寫法，因為 async 函式也是函式。
錯。問題不在 setup 本身是不是函式，而在它回傳什麼。async 函式一定回傳 Promise，而 create 的型別要求回傳「函式或 undefined」，所以 React 會警告。正解是在裡面另外定義一個 async 函式再呼叫它。
6. cleanup 讀到的是「它那一次 render 的值」，這是正確行為，不是 bug。
對。cleanup① 的任務就是收拾 setup① 建立的東西，它當然要用 setup① 當時的那組值。

七、申論題（先自己寫，再看參考答案）

Q1. 請用「面試四段式」解釋 useEffect 的清理函式。
  1. 是什麼：useEffect 的 setup 函式可以選擇性地回傳一個函式，React 官方稱它 cleanup function，存在該 effect 的 inst.destroy 欄位。
  2. 為什麼需要：effect 常會建立「持續存在的東西」——計時器、事件監聽器、WebSocket 連線、訂閱。這些不會隨元件消失而自動消失，必須主動關掉，否則就是記憶體洩漏。
  3. 什麼時候被呼叫：卸載前、每次重跑 setup 之前、以及 StrictMode 開發模式下掛載後多跑的那一輪。順序永遠成對交錯。
  4. 底層原理：cleanup 靠閉包抓住 setup 當次的區域變數。這些變數因為被捕獲而配置在 Heap 的 Context 物件而非 Stack，所以 setup return 之後依然活著，直到 cleanup 被呼叫、effect 卸載、沒人引用，才被 GC 回收。
Q2. 開頭那段計時器為什麼永遠印出 0？請從「每次 render 是一次函式呼叫」推導。
  1. 第一次 render：React 呼叫 Counter()，Creation Phase 建立一組綁定，其中 count 的值是 0。
  2. 依賴陣列是 []，所以 setup 只在第一次 render 的舞台上被執行一次。
  3. setInterval 的回呼抓住了第一次 render 的 count 綁定。因為被抓住，這個綁定被搬到 Heap 上活著。
  4. 第二、三次 render 時 React 確實再呼叫了 Counter()，也建立了全新的 count 綁定，但計時器回呼抓的是第一組，跟新的沒有任何關係。
  5. 所以它每秒忠實印出它抓著的那塊記憶體裡的值：0。而 setCount(count + 1) 永遠是 setCount(0 + 1)。這個現象叫 stale closure（過期閉包），是 JS 閉包語意的必然結果，不是 React 的 bug。
Q3. 三種修法各自的代價是什麼？什麼情況下該選哪一種？
  1. updater function setCount(c => c + 1)：不從閉包讀值，讓 React 把最新值餵進來。代價是只適用於「新值只依賴舊值」；要讀其他 state 或 prop 就救不了。
  2. 誠實申報依賴 }, [count])：count 一變就先跑 cleanup 關掉舊計時器，再用新舞台建一個。代價是計時器每秒被銷毀重建，時間精度會漂移。
  3. useRef 長壽盒子：useRef 回傳的物件在整個元件生命週期都是同一個參考，閉包抓的是盒子而非值，所以每次讀 .current 都最新。代價是 ref 變動不會觸發重渲染，不能拿來驅動畫面。
Q4. 為什麼說「for 迴圈的 var 陷阱」跟本篇的 stale closure 是同構問題？

兩者的共同結構是：一個非同步回呼抓住了某個綁定，等它真的執行時，外面的世界已經前進了。

  1. for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)) 印出三個 3，因為 var 整個迴圈只有一個綁定，三個回呼抓的是同一塊記憶體，而同步迴圈早就跑完把它變成 3。
  2. 本篇的 setInterval 印出 0，因為 [] 讓 setup 只跑一次，回呼抓的是第一次 render 的那組綁定，而 React 後來又建立了新的好幾組。
  3. 差別只在一個是「迴圈的每一輪」、一個是「React 的每一次 render」。let 的修法（每一輪新綁定）在概念上對應 React 這邊「誠實申報依賴，每次 render 重建 effect」。
