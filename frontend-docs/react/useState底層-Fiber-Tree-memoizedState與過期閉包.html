🧠 自我測驗

是非題

  1. useState 的值是存在函式元件內部的區域變數裡。

    存在 React Fiber 節點的 memoizedState 鏈表中，區域變數每次 re-render 就被重置。

  2. 第二次渲染時，原始碼會自動變成 useState(1)。

    原始碼永遠是 useState(0)，是 useState 內部去 Fiber 讀最新值後回傳 1。

  3. () => setCount(count + 1) 是一個 IIFE。

    它只是回呼函式，尾巴沒有立刻呼叫的 ()，點擊時才執行。

  4. Fiber Tree 存在瀏覽器 JavaScript 引擎的 Heap Memory 中。

    它就是一堆互相引用的普通 JS 物件，被 HostRoot 長期引用所以不會被 GC。

  5. 元件重新渲染時，舊的 setTimeout 回呼會自動拿到新的 count。

    這正是過期閉包（Stale Closure），舊閉包鎖住的是當次渲染那一組變數。

  6. 若元件完全沒有呼叫任何 Hook，fiberNode.memoizedState 會是 null。

    沒有 Hook 就沒有鏈表節點可掛。

  7. React 官方原始碼是用物件文字量 {} 直接建立 Fiber 節點的。

    官方用建構函式 FiberNode 搭配 new 實例化，物件文字量只是教學示意。

  8. Function Component 的 FiberNode，它的 stateNode 屬性存的是該元件的實例（Instance）。

    Function Component 沒有實例，stateNode 永遠是 null；有實例的是 Class Component。

  9. React 之所以把 children 陣列改成 child／sibling／return 鏈表，主要動機是讓走訪可以隨時中斷再恢復。

    遞迴走訪無法中途讓出主執行緒，改成 while 迴圈後只要記住 workInProgress 指標就能暫停與續跑。

  10. 某個 Fiber 節點的 childLanes 為 0，代表這棵子樹沒有待處理任務，React 可以整棵跳過。

    這是 Lanes 位元遮罩最主要的剪枝用途。

  11. 列表項目的 key 從 id 換成另一個值時，React 只會更新 props，不會重置內部 state。

    key 改變會判定為不同元件，舊的完整 Unmount（跑 cleanup）、新的重新 Mount，所有 useState 歸零。

填空題

  1. Fiber 節點上存放 Hook 鏈表頭的屬性叫 。

    Hook 結構內部也有同名屬性，那層才存實際數值。

  2. React 同時維持 Current Tree 與 WorkInProgress Tree，這個機制叫 （中文四個字）。

    英文是 Double Buffering，算完把指標一指就完成切換。

  3. setTimeout 回呼讀到舊 state 的現象叫「 閉包」。

    英文 Stale Closure。

  4. Fiber 節點上指向你所寫元件函式本身的屬性是 。

    因為函式也是物件，React 重新渲染時直接執行 fiberNode.type()。

  5. 讓 Render 階段可以中斷、暫停、丟棄重來的模式叫 Mode。

    靠的正是 Fiber 這個可拆成小工作單元的鏈表結構。

  6. FiberNode 上指向「真實 DOM 元素或 Class 實例」的屬性叫做 。

    HostComponent 指向 DOM 物件，ClassComponent 指向實例，FunctionComponent 是 null。

  7. React 的獨立排程套件 Scheduler，內部使用 這種資料結構管理 Task，確保最急的先執行。

    Min-Heap，依 expirationTime 排序。

  8. 想要在 userId 改變時把整個表單的 state 全部重置，最乾淨的做法是傳入 這個特殊 prop。

申論題

  1. 用你自己的話解釋：為什麼「函式元件本身是無狀態的，真正有狀態的是 Fiber Tree」？請把區域變數的生命週期一起講進去。

    參考方向：元件只是一個每次渲染都被重新執行一遍的普通函式，函式內的區域變數建立在 Stack 或短暫的 Heap，執行完若沒有被閉包引用就會被 GC 回收，所以它無法跨渲染保存資料。React 另外在 Heap 中維護一棵被 HostRoot 長期引用的 Fiber Tree，每個元件對應一個 FiberNode，Hook 的值掛在 memoizedState 鏈表上。useState 只是一個介面：執行時去問 Fiber 這個節點存不存在，存在就忽略初始值直接回傳鏈表中的最新值。所以狀態的「所有權」在 Fiber，不在你的函式。

  2. 面試官問：「過期閉包要怎麼解決？」請至少給出兩種方向並說明各自的取捨。

    參考方向：(1) 函式式更新 setCount(prev => prev + 1)——讓 React 把「怎麼算」而不是「算好的值」排進佇列，不依賴閉包裡的舊值，成本最低、最推薦。(2) 用 useRef 存一份可變的最新值，在非同步回呼裡讀 ref.current——能拿到最新值但改 ref 不會觸發 re-render，適合只讀不渲染的場景。(3) 把變數放進 useEffect 的依賴陣列讓回呼重新建立——語意最正確但會頻繁重建訂閱與計時器。取捨核心：函式式更新解決「基於舊值算新值」，useRef 解決「非同步時需要當下最新值」，依賴陣列解決「訂閱要跟著變」，三者情境不同不可互相取代。

  3. 面試官問：「為什麼 React 要把樹狀結構改寫成鏈表？直接用陣列不是更直覺嗎？」請用『遞迴 vs 迴圈』『可中斷性』『GC 壓力』三個角度回答。

    要點：(1) 傳統 Stack Reconciler 用遞迴走訪，Call Stack 一路疊到底，開始了就無法讓出主執行緒；(2) Fiber 用 child/sibling/return 把樹攤平成鏈表，整棵樹用一個 while 迴圈 workLoop 就能走完，目前位置只是一個指標變數 workInProgress，可以隨時記住位置、釋放執行緒、之後接著跑，這才是 Concurrent Mode 的基礎；(3) 陣列需要連續記憶體、頻繁重建會增加 GC 壓力，鏈表沒有這個問題。補一句：childLanes 讓 React 能整棵子樹跳過，進一步剪枝。

  4. 用 index 當 key 除了效能問題之外，還會造成什麼「不會報錯但資料錯亂」的 bug？請舉一個具體情境。

    要點：列表項目內含 <input> 或內部 useState 時，刪掉第一筆後第二筆的 index 會遞補為 0，React 看到 key="0" 依然存在就保留舊 DOM 與舊 state、只替換 props，結果畫面上殘留你輸入給第一筆的內容。這種 bug 不會拋錯，只會讓資料看起來莫名其妙錯亂，比效能問題嚴重得多。

useState 底層 — Fiber Tree、memoizedState 鏈表與過期閉包

本篇重點 a–z，共 26 個（u–z 為 2026-08-31 追加）。

重點整理

一、先釐清：函式怎麼把值交給外面

(a) 副作用（Side Effect） 指的是函式去改動了自己作用域以外的東西。Vue 官方文件那段 let A2 先在外層宣告、再由 update() 去寫入，並不是因為「只有這樣外面才拿得到」，而是為了示範響應式系統如何追蹤一個已存在的狀態。

let A0 = 1
let A1 = 2
let A2                 // 外層宣告的共享狀態
function update() {
  A2 = A0 + A1         // 有副作用：直接改寫外層變數
}

(b) 要把值交給外部，最乾淨的方式就是 return，完全不需要事先在外層 let 一個變數。

function add(a, b) { return a + b }   // 純函式（Pure Function），無副作用
const result = add(1, 2)              // 外部直接接住，資料流一目瞭然

(c) 兩種寫法的定位對照：改寫外層變數 ≈ Vue 的 watchEffect／DOM 渲染（重點在「依賴變了就自動去做某件事」）；return 回傳值 ≈ Vue 的 computed（重點在「算完給你一個值」）。

二、React 的「私有記憶體」到底在哪

(d) Fiber Tree（Fiber 樹）是 React 內部維護的資料結構，完整存在於瀏覽器 JavaScript 引擎（例如 Chrome 的 V8）的 Heap Memory（堆積記憶體）裡。它不是什麼特殊硬體結構，本質就是一堆互相用指標引用的普通 JavaScript 物件。

(e) 每個元件對應一個 FiberNode，關鍵欄位如下：

const fiberNode = {
  type: Counter,          // 指向你寫的元件函式本身（函式也是物件）
  memoizedState: {...},   // Hook 鏈表的頭，存 useState / useEffect 的資料
  updateQueue: null,      // 待處理的 setState 佇列
  child: childFiber,      // 第一個子節點
  sibling: siblingFiber,  // 下一個兄弟節點
  return: parentFiber,    // 父節點（名字叫 return 但意思是「往上回去」）
  alternate: null,        // 指向另一棵樹上的對應節點（雙重緩衝用）
}

(f) type: Counter 的 Counter 就是你 export default function Counter() 的那個元件函式。因為在 JavaScript 裡函式也是一種可被呼叫的物件（Callable Object），所以可以直接把它塞進 type 欄位；React 要重新渲染時就去執行 fiberNode.type()。

(g) 為什麼 Fiber 節點不會被垃圾回收（Garbage Collection）掉？因為 React 初始化時建立了一個長久存活的根物件 HostRoot，整棵樹一直被 React 內部核心引用著。反觀元件函式裡的區域變數，函式一跑完沒人引用就會被 GC 清掉。

(h) 雙重緩衝（Double Buffering）：記憶體裡同時存在 Current Tree（畫面上正在顯示的）與 WorkInProgress Tree（背景正在算的新狀態樹）。算完只要把指標一指就完成切換，舊樹交給 GC。

三、memoizedState 是一條單向鏈表

(i) 有幾個 Hook 就有幾個節點，useState、useEffect、useRef 都算。容易搞混的是「同一個名字用在兩層」：

  • 外層的 fiberNode.memoizedState 是 Fiber 節點上的屬性名稱，指向第一個 Hook 結構。
  • 每個 Hook 結構內部也有一個叫 memoizedState 的屬性，那個才是存實際數值的地方。
// 元件裡寫了兩個 Hook：useState(0) 與 useState('Alice')
fiberNode = {
  type: Counter,
  memoizedState: {          // 第一個 Hook（count）
    memoizedState: 1,       // count 當前的值
    next: {                 // 指向下一個 Hook
      memoizedState: 'Alice',
      next: null,
    },
  },
}

(j) 若元件完全沒呼叫任何 Hook，fiberNode.memoizedState 就是 null。

(k) 常見誤解：第二次渲染時程式碼會變成 useState(1)。不會。原始碼永遠寫死 useState(0)，每次 re-render 都照樣執行到這一行、照樣把 0 傳進去。差別在於 useState 內部會問 Fiber：「這個節點已經存在了嗎」，存在就忽略你傳的初始值，直接回傳鏈表裡的最新值。所以 0 只在第一次掛載（Mount）時有意義。

(l) 一句話收尾：你的函式元件本身是無狀態的，真正有狀態的是背後的 Fiber Tree；useState 只是向 Fiber 借取與更新資料的介面。

四、過期閉包（Stale Closure）

(m) React 完全遵守 JavaScript 的 Lexical Scope（詞法作用域）與閉包（Closure），這正是經典陷阱的來源。

function Counter() {
  const [count, setCount] = useState(0)

  const handleDelayLog = () => {
    setTimeout(() => {
      console.log('3 秒後印出的 count：', count)   // 抓的是「當次渲染」的 count
    }, 3000)
  }

  return (
    <div>
      <h2>當前 Count: {count}</h2>
      <button onClick={() => setCount(count + 1)}>加 1</button>
      <button onClick={handleDelayLog}>點擊後等待 3 秒印出</button>
    </div>
  )
}

(n) 時間軸拆解：

  1. 第 0 秒點「延遲印出」，setTimeout 收下的回呼函式此刻對 count = 0 拍了一張快照（Snapshot）。
  2. 第 1–2 秒連按三次「加 1」，React 重新執行元件三次，每次都產生全新的 count 變數（1、2、3）與全新的作用域，畫面顯示 3。
  3. 第 3 秒計時到，執行的是當初那個回呼，它讀的是第 0 秒鎖住的作用域，所以 console 印出 0 而不是 3。

(o) 關鍵理解：舊作用域裡的函式不會自動拿到新作用域裡的變數。每次 re-render 都是一組新變數，舊閉包鎖住的是舊的那一組。

(p) setTimeout(fn, 3000) 的語意是「3 秒後才執行 fn」，但參數是在呼叫當下就綁定完成的，這兩件事分開想就不會混淆。

五、順手釐清的兩個小坑

(q) () => setCount(count + 1) 不是 IIFE。IIFE（Immediately Invoked Function Expression，立即調用函式表達式）的定義是「定義完當下就立刻呼叫」，語法尾巴一定有一對呼叫用的 ()：

;(() => { console.log('我被定義完就立刻執行了') })()   // 這才是 IIFE

(r) onClick={() => setCount(count + 1)} 只是建立一個匿名箭頭函式當回呼（Callback），交給按鈕的 onClick 保管；使用者真的點下去才會被呼叫。如果寫成 onClick={setCount(count + 1)}（少了 () =>），渲染到那一行就會立刻執行 setCount，觸發 re-render，再執行，再 re-render，陷入無限迴圈。

(s) Concurrent Mode（並行模式）之所以能在 Render 階段中斷、暫停、丟棄重來，靠的就是 Fiber Tree 這個可拆解成一個個小工作單元的鏈表結構。傳統遞迴的 Stack Reconciler 一旦開始就無法中斷，Fiber 把它改寫成可中斷的迴圈，這是 React 16 之後架構重寫的核心動機。

(t) 次要備註：Gemini 用 { type: ..., memoizedState: ... } 這種物件文字量（Object Literal）畫的示意圖是簡化模型，方便看清楚記憶體裡的指向關係。React 官方原始碼（packages/react-reconciler/src/ReactFiber.js）實際上是用建構函式 function FiberNode(tag, pendingProps, key, mode) 搭配 new FiberNode(...) 實例化的。但兩者在 Heap 裡產生的實體都是 JavaScript 物件，本質完全一樣，這就是為什麼你用 Python 的 class Node: def __init__(self, val, next) 也能表達同一個鏈表結構。

六、追加 2026-08-31：FiberNode 的完整屬性、鏈表為何比陣列快、以及 key 的真正作用

(u) FiberNode 的屬性可以分成六大類，把這張表背起來，Fiber 的整套設計動機就串起來了：

分類 屬性 作用
1. 樹狀結構指標 child / sibling / return 第一個子節點／右邊的兄弟節點／父節點。React 用這三個指標把樹「攤平成鏈表」
2. 類型與身分 tag / key / elementType / type tag 是數字列舉（FunctionComponent=0、ClassComponent=1、HostComponent=5…）；type 指向元件函式或 DOM 標籤字串
3. 狀態與屬性 pendingProps / memoizedProps / memoizedState / updateQueue 本次要進來的新 props／上次用過的舊 props／Hook 鏈表頭（Class 則是 this.state）／待處理的更新佇列
4. 真實 DOM 連結 stateNode 指向對應的「實體」，見 (w)
5. 優先級與排程 lanes / childLanes 位元遮罩（Bitmask），見 (x)
6. 雙重緩衝 alternate 指向另一棵樹上的對應節點

(v) 為什麼用單向鏈表取代 children: [] 陣列？關鍵不是「陣列很慢」，而是遞迴無法中斷、迴圈可以：

  • 傳統 Stack Reconciler 用遞迴走訪樹，一旦開始，Call Stack 就一路疊到底，中途沒辦法讓出主執行緒去處理使用者輸入。
  • Fiber 把樹改寫成 child → sibling → return 的走訪規則，整棵樹用一個 while 迴圈（也就是原始碼裡的 workLoop）就能遍歷完：先往下走 child，沒有子節點就往右走 sibling，沒有兄弟就往上 return。
  • 因為「目前走到哪」只是一個指標變數 workInProgress，React 隨時可以把它記下來、釋放主執行緒，等瀏覽器空閒再從那個指標接著跑，完全不必維護遞迴堆疊。
  • 附帶好處：陣列需要連續記憶體、頻繁重建會增加 GC 壓力，鏈表沒有這個問題。

(w) stateNode 存的是「實體（Instance）」，三種情況三種值：

元件種類 stateNode 內容
HostComponent（div、button 等原生標籤） 真實的 DOM 元素物件
ClassComponent new MyClassComponent(props) 產生的實例，裡面有 this.props、this.state、this.setState 與你定義的方法
FunctionComponent 永遠是 null，因為 React 只是執行 Counter(props) 拿回 JSX，沒有 new、也沒有 this 
// Class Component 對應的 FiberNode（簡化）
fiberNode = {
  tag: 1,                    // 1 代表 ClassComponent
  type: MyClassComponent,    // 類別本身
  stateNode: {               // 真正的 Class 實例
    props: { count: 0 },
    state: { name: 'Alice' },
    render() { /* ... */ },
  },
}

(x) 排程（Scheduling）分成兩層，很多人只記得其中一層：

  1. FiberNode 上的標記：lanes 記錄「這個節點自己」有哪些優先級的待處理任務，childLanes 記錄「整棵子樹」有哪些。兩者都是位元遮罩。childLanes === 0 就代表整棵子樹沒事做，React 直接跳過（Skip），不必往下走。這就是 (v) 那個 while 迴圈能大幅剪枝的原因。
  2. 獨立的 scheduler 套件：React 會向它註冊一個 Task，Task 內含 expirationTime（越急的過期時間越短）、callback（實際的渲染工作）、priorityLevel。scheduler 內部用最小堆積（Min-Heap）管理這些 Task，永遠讓最急的先執行。
  3. Lanes 的比喻是「賽道」：使用者點擊（Sync Lane）優先級極高，動畫或 startTransition（Transition Lane）優先級較低。

(y) 列表的 key 要用資料的 id，不要用陣列索引 index，理由有兩個層級：

  • 效能層級：['A','B'] 前面插入 'NEW' 之後，用 index 當 key 會讓 React 認為 key="0" 從 'A' 變成 'NEW'、key="1" 從 'B' 變成 'A'，於是三個 DOM 全部被改寫；用 id 當 key 則只會單純插入一個新節點。
  • 正確性層級（更嚴重）：如果列表項目裡有 <input> 或內部 state，刪掉第一筆之後第二筆的 index 會遞補成 0，React 看到 key="0" 還在就保留舊 DOM 與舊 state、只換 props，結果畫面上留下的是「你原本輸入給第一筆的內容」。這種 bug 不會報錯，只會讓資料看起來錯亂。
  • 只有在「純顯示、絕不重排、不會增刪、且沒有內部 state」的列表，用 index 才勉強安全。

(z) key 一改變，React 就會 Unmount 舊元件再 Mount 新元件。判定規則是：同層級 ＋ 同元件類型 ＋ 同 key → 視為同一個實體，只更新 props；key 不同 → 舊的完整卸載（銷毀 DOM、跑 useEffect 的 cleanup），新的重新掛載（所有 useState 重置）。這個特性可以反過來當作「重置元件狀態」的乾淨手法：

變數宣告與 Return 的差異（2026-08-28）— https://gemini.google.com/app/92bd0f70e642fe50

使用者： 前面的例子在講宣告式跟命令式的不同，但除此之外，又講到原生的 JavaScript 必須要把外部變數定義好，然後再讓函式內部使用。是否是因為這樣子，才能給外部作用域使用？還是說其實我外部不用 let 宣告一個變數，但我內部宣告的變數或是參數寫了 return，一樣可以給外部使用呢？

Gemini： 核心答案是你的理解非常準確，不需要在外部先用 let 宣告變數，只要函式內部有 return，外部就可以接收並使用這個結果。Vue 官方文件那個範例先宣告 let A2 的原因不是「唯有這樣外部才能用」，而是為了演示副作用與狀態變更——update() 沒有返回值，它的目的就是去改變外部狀態 A2，Vue 的響應式系統核心就在於追蹤狀態變化並自動觸發更新。使用 return 則是純函式：資料流明確、無副作用、方便重複呼叫。對照表：外部宣告變數對應 watchEffect 或 DOM 渲染，使用 return 對應 computed。

使用者： 是否對 React 的 useState hook 來說，這個都是在函式元件內部的變數，所以它完全沒有所謂的 lexical scope 的外部變數？

Gemini： 不完全是這樣。useState 雖然在函式元件內部呼叫並宣告狀態，但它之所以能運作，背後完全依賴 JavaScript 的 Lexical Scope 與閉包機制。元件本質上只是一個每次渲染都會重新執行的普通函式，如果 state 單純只是區域變數，每次重新執行就會被重置。useState 能在多次渲染之間記住舊值，是因為 React 在元件外部（React 內部的 Fiber 節點／記憶體）維護了一個狀態鏈表。接著 Gemini 舉了 setTimeout 印出舊 count 的過期閉包範例。

使用者： 1. react 有一個自己私有的記憶體嗎 2. 幫我去我今天的行事曆寫上我需要實作過期閉包 3. 我還沒有真正了解剛剛延遲印出 count 是 0 這件事，我應該直接貼到我的專案中測試嗎？setTimeout() 應該是點擊的 3 秒後才觸發函式的意思嗎？

Gemini： 是的，React 內部有 Fiber Tree，狀態存在 Fiber 節點記憶體而非你的函式內部。行事曆部分回覆「已為你在今天的 Google Calendar 上新增這個研讀事項，標題：實作過期閉包原因：尚未真正了解延遲印出 count 為 0」。並強烈建議直接貼到專案中實作測試，附上 ClosureTest 元件範例。最後拆解時間軸：第 0 秒拍照、第 1–2 秒連點加 1、第 3 秒印出當初那張照片所以是 0。

使用者： 資料結構稱為 Fiber Tree（Fiber 樹）。是在記憶體嗎

Gemini： 是的，完全存在於瀏覽器的 JavaScript 堆積記憶體（Heap Memory）中。它本質上是一堆互相引用的普通 JavaScript 物件，透過指標彼此連結，駐留在 V8 分配的 Heap 中。之所以能在元件執行完後繼續存活，是因為 React 初始化時建立了一個長久存活的根物件 HostRoot。另外 React 在記憶體中同時維持 Current Tree 與 WorkInProgress Tree 兩棵樹，這就是雙重緩衝機制。

使用者： () => setCount(count + 1) 為啥要這樣寫算 IIFE?

Gemini： 它絕對不是 IIFE，只是一個普通的箭頭函式／回呼函式。IIFE 的核心定義是函式定義出來的當下就立刻執行，語法尾巴有一對 ()。而 onClick={() => setCount(count + 1)} 在 React 渲染時只是建立了一個匿名函式交給 onClick，使用者真的點擊才會被呼叫。如果少了 () => 直接寫 onClick={setCount(count + 1)}，渲染到這一行就會立刻觸發，導致無限迴圈崩潰。

使用者： 所以他上次紀錄的值是放在 react fiber tree 裡面嗎？

Gemini： 是的。每個元件對應一個 FiberNode，節點物件內部有一個屬性叫 memoizedState，React 會在上面建立一個單向鏈表。第一次渲染時放入第一個節點值為 0；呼叫 setCount(1) 時 React 把更新請求掛到該節點的更新佇列並排定重新渲染；第二次渲染時 useState 檢查節點是否已存在，存在就忽略初始值 0，直接回傳 memoizedState 計算後的最新值 1。

使用者： 我不太懂我的元件寫在 type: Counter 是什麼意思，這邊的 Counter 是模仿 export default function 的元件名稱嗎？所以是有幾個 useState 就會有幾個 memoizedState 嗎？所有的 memoizedState 都會由一個 memoizedState 屬性包裹？第二次渲染不是已經到 useState(1) 了嗎？函式元件本身是無狀態的，你說在區域變數是一般的記憶體裡面嗎？

Gemini： 逐點回覆——(1) Counter 就是你定義的函式元件，函式也是物件，React 把它的引用存在 Fiber 的 type 屬性。(2) 每一個 Hook 對應鏈表中的一個節點，外層 fiberNode.memoizedState 是屬性名稱指向第一個 Hook，Hook 結構內部也有同名屬性存實際數值；沒有任何 Hook 時外層為 null。(3) 第二次渲染仍走到 useState(0) 是因為原始碼沒有改變，1 是 Fiber 查鏈表後回傳的。(4) 不管第幾次渲染都會檢查 Fiber 節點是否存在。(5) 區域變數存在 Stack 或短暫的 Heap，函式執行完若沒被閉包引用就會被 GC 銷毀；Fiber Tree 則長期駐留。

使用者： 我要介紹 useState 是要怎麼運作的，他是透過 fiberNode。你畫的是一個物件的結構，我也可以寫成 class Node: def __init__(self, val, next)。為什麼要寫成類別，有的又是寫成物件的方式？在 JS 中函式也是一種物件，那在 REACT 中函式也是一種物件嗎？

Gemini： 無論用 Class 還是 Plain Object，在記憶體中建立出來的本質都是物件，差別在抽象層級與設計習慣。Class 適合當藍圖、可封裝方法、支援強型別檢查；Plain Object 語法簡潔、適合純資料結構。至於函式，JavaScript 中函式是一等公民且本身就是可呼叫物件，React 是用 JavaScript 寫的所以完全適用，Fiber 的 type 存的就是 Counter 這個函式物件本身。

使用者： 所以你只是用一個物件去表現 FiberNode，並非 react 官方真的就是這樣寫的嗎？

Gemini： 是的，我寫的是極度簡化的示意模型。React 官方原始碼（packages/react-reconciler/src/ReactFiber.js）確實定義了一個 function FiberNode(tag, pendingProps, key, mode) 建構函式，裡面設定 tag、key、elementType、type、return、child、sibling、memoizedState、updateQueue、alternate 等欄位，運作時透過 new FiberNode(...) 實例化。不管寫成 class 還是物件文字量，在 Heap 裡產生的實體都是 JavaScript 物件。
