🎒 Heap 上的 Context：閉包的「背包」

一般區域變數住在 Stack 的罐頭裡，罐頭彈出就消失。若內層函式還會用到它，引擎就把它裝進 Heap 上的 Context（背包），函式物件再背著這個背包走。
以 <ChatRoom /> 的 useEffect 為例，顏色對應：藍 = Context ①（ChatRoom 那一次 render 的背包） 紫 = Context ②（setup() 那一次呼叫的背包）

📜 程式碼（顏色對應背包）

function ChatRoom({ roomId }) {
  const [serverUrl, setServerUrl] = useState(url)

  useEffect(() => {              // 🔌 setup 函式（閉包 A）
    const connection =
      createConnection(serverUrl, roomId)
    connection.connect()
    return () => {               // 🧹 cleanup 函式（閉包 B）
      connection.disconnect()
    }
  }, [serverUrl, roomId])
}
為什麼是這幾個變數？
setup 函式用到 roomId、serverUrl，所以它們被抓進 Context ①。cleanup 函式用到 connection，所以它被抓進 Context ②。setServerUrl 沒人用，留在 Stack 罐頭裡，罐頭彈出就消失。

📚 Stack（暫時的罐頭）

① render：ChatRoom() 被呼叫進入函式時，引擎為「被內層抓住的變數」建立 Context ①roomId ➜ 🎒①serverUrl ➜ 🎒①setServerUrl 留在罐頭render 結束，罐頭彈出，Context ① 因為 setup 函式還背著它而活下來
② commit：setup() 被呼叫進入函式時建立 Context ②，它的 previous 指向 ①connection ➜ 🎒②setup() 回傳，罐頭彈出，Context ② 因為 cleanup 函式背著它而活下來
③ 之後：cleanup() 被呼叫去 Context ② 讀 connection 呼叫 disconnect()。罐頭彈出，之後沒人引用，背包才被回收

🔍 讀變數＝從自己的背包開始，沿 previous 往外找

誰在讀讀什麼從哪個背包開始在第幾層找到
setup 函式serverUrl、roomIdContext ①第 0 層，直接命中
cleanup 函式connectionContext ②第 0 層，直接命中
cleanup 函式（假設也讀 roomId）roomIdContext ②② 沒有，沿 previous 到 ①，第 1 層，讀到的是「那一次 render」的值

♻️ 背包什麼時候被回收

下一次 render建立全新的 Context ①'（新 roomId），舊的 ① 與 ② 不會被改動
舊 cleanup 還沒被呼叫inst.destroy 還指著它，所以 ① ② 都不能回收
cleanup 被呼叫之後React 把 inst.destroy 設回 undefined，沒人引用，GC 才回收 ① ②
V8 的說法JSFunction 是 (context, code) 的組合。Context 有 scope_info、previous、extension 三個固定欄位，後面才是變數
