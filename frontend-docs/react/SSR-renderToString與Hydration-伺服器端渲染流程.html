🧠 自我測驗

是非題

  1. SSR 的 HTML 是在 build time 就預先產生好的。

    那是 SSG。SSR 是 per-request——每個請求進來才在伺服器現算一份 HTML，所以才能顯示購物車這類即時資料。

  2. CSR 在 build time 不會產生任何有內容的 HTML。

    打包器只吐出 JS bundle 和一個含 <div id="root"></div> 的空 index.html。

  3. SSR 的 build time 會產出兩份 bundle。

    伺服器端 bundle 給 Node.js 跑 renderToString，客戶端 bundle 給瀏覽器做 Hydration。

  4. 伺服器端執行 renderToString 時會建立 DOM Tree。

    Node.js 沒有 window 和 document，產出的只是字串；DOM Tree 是瀏覽器 Parse 之後自己建的。

  5. 同一個 React 元件在 SSR 架構下會執行兩次。

    伺服器一次、客戶端 Hydration 一次——這也是 hydration mismatch 的根本成因。

  6. Hydration 發生在 Layout（Reflow）與 Paint 之後。

    所以 SSR 才有「看得到但還不能點」的空窗期。

填空題

  1. React 把元件樹轉成 HTML 字串的伺服器端函式叫 render__()。

    串流版本是 renderToPipeableStream。

  2. React 在客戶端認領既有 DOM、掛上事件監聽的函式叫 __Root()。

    對照純 CSR 用的 createRoot()。

  3. HTML 在 build time 就產生好的架構叫 __（三個英文字母）。

    Static Site Generation，靜態網站生成。

  4. Next.js 中「先給靜態頁、過期後背景重產」的折衷方案叫 __（三個英文字母）。

    Incremental Static Regeneration，用 revalidate 設定秒數。

  5. 在元件本體直接呼叫 Date.now() 或 Math.__() 會導致 hydration mismatch。

    兩次執行結果必然不同，要改放進 useEffect。

申論題

  1. 面試官問「CSR、SSR、SSG 差在哪」。請用「HTML 在哪一刻、由誰產生」這條主軸回答，並各給一個適合的產品情境。

    參考方向：(1) 先立主軸——三者的 build time 做的事幾乎一樣（編譯＋打包），差別全在 HTML 是誰、在哪一刻拼出來的。(2) CSR：瀏覽器在 runtime 執行 JS 動態建 DOM；首屏最慢、SEO 最差，但伺服器成本最低。適合登入後的後台儀表板（不需要 SEO、使用者願意等一次）。(3) SSR：伺服器在每個請求當下抓資料並 renderToString；首屏快、SEO 好、資料最新，代價是每個請求都吃伺服器 CPU。適合電商商品頁、社群動態這類「內容要即時又要被 Google 收錄」的頁面。(4) SSG：建置機器在 build time 就把 HTML 產好；速度最快、可直接放 CDN、伺服器成本近乎零，但內容在部署後就固定。適合部落格、文件站、行銷官網。(5) 補一句 ISR 當折衷，並指出 SSR 與 SSG 兩者的瀏覽器端流程一樣都要 Hydration。(6) 加分：指出常見混淆——很多人把「build time 先產好、runtime 直接回傳」講成 SSR，那其實是 SSG。

  2. 為什麼 SSR 架構下不能在元件本體寫 Date.now()？請從「元件執行兩次」推導到 hydration mismatch。

    參考方向：(1) SSR 下元件會執行兩次——伺服器一次產生 HTML 字串，客戶端 hydrateRoot 時再一次。(2) Hydration 的前提是「React 客戶端首次渲染的結果，必須與伺服器送來的 HTML 完全一致」，React 才能安全地認領既有 DOM 節點而不重建。(3) Date.now()、Math.random()、window.xxx 這類值兩次執行必然不同，比對就會不一致，React 會發出 hydration mismatch 警告並可能整棵子樹改用客戶端重繪，SSR 的效能好處就白費了。(4) 正解是把這類副作用放進 useEffect——useEffect 只在客戶端跑，不參與伺服器渲染，自然不會造成兩邊不一致。(5) 這也呼應 React 要求元件本體必須是純函數（StrictMode 會刻意跑兩次來幫你抓這種問題）。

SSR、renderToString 與 Hydration — 伺服器端渲染流程

本篇重點 a–v，共 22 個（l–p 為 2026-09-01 追加；q–v 為 2026-09-06 追加）

(a) SSR（Server-Side Rendering，伺服器端渲染）：在伺服器上先把頁面產生成 HTML 字串再傳給瀏覽器，好處是首屏更快看到內容、對 SEO 友善（爬蟲不必等 JS 執行完才看得到文字）。

Hydration 在完整渲染管線裡是第幾步？——Reflow（重排/Layout）跟 Repaint（重繪/Paint）排在 Hydration 前面，順序是：

  1. 伺服器 renderToString() 產生 HTML 字串（此時沒有 DOM）
  2. 瀏覽器收到 HTML 字串
  3. Parse HTML → 建 DOM Tree
  4. Parse CSS → 建 CSSOM
  5. 合併成 Render Tree
  6. Layout（重排/Reflow）——計算每個元素的位置與大小
  7. Paint（重繪/Repaint）——把像素畫出來 → 此時畫面已經看得到，但完全不能互動
  8. JS bundle 下載完、執行，React 呼叫 hydrateRoot() → Hydration——走訪既有 DOM、掛上事件監聽 → 此時頁面才變成可以互動

SSR 的核心賣點正是把「看得到（Paint 完成）」跟「能互動（Hydration 完成）」拆成兩個時間點，讓使用者先看到內容，互動性稍後才補上（詳細管線見 Critical-Rendering-Path-關鍵渲染路徑-重排vs重繪）。

(b) 伺服器怎麼把元件變成 HTML：靠框架提供的特定函式，React 就是 renderToString（或串流版 renderToPipeableStream）。它把 React 元件樹轉成純字串，不是 DOM 節點。

// 伺服器端（Node.js）
import { renderToString } from 'react-dom/server';
const html = renderToString(<App />);   // 純字串，例如 "<div id=\"root\">…</div>"
res.send(`<!DOCTYPE html><html><body>${html}</body></html>`);

(c) 關鍵釐清（Abby 當時的疑問）：「伺服器產生的 HTML 還會有 DOM Tree 嗎？」伺服器端沒有 DOM Tree，Node.js 環境根本沒有 window 和 document；伺服器產出的只是一段字串。DOM Tree 是「瀏覽器收到 HTML 字串後，自己解析（Parse）建立出來的」。

(d) render 函式做了什麼：React 的 render（函數型元件就是元件函式本身的回傳值）會根據當下的 state 和 props，回傳一段「UI 的描述」——也就是 JSX 編譯後的 React Element 物件樹，而不是直接操作畫面。真正的畫面更新由 React 之後比對再套用。

(e) 函數型元件裡的 JS 操作跑去哪裡（本篇核心問題）：

階段 在哪執行 會執行什麼 不會執行什麼
伺服器端 SSR Node.js 元件函式本體跑一次以產生 HTML 字串 useEffect 不會跑、事件處理器不會綁定
瀏覽器 Hydration 瀏覽器 同一份元件程式碼再跑一次，把事件處理器「接」到既有 DOM 上 —
之後的互動 瀏覽器 state 更新、事件、useEffect 全部正常運作 —

(f) Hydration（水合）：瀏覽器已經有伺服器送來的靜態 HTML，React 在客戶端用 hydrateRoot 不是重畫一次，而是「認領」既有的 DOM 節點並掛上事件監聽，讓死的 HTML 活過來變成可互動的頁面。

// 客戶端
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <App />);

(g) Hydration 陷阱：伺服器渲染結果與客戶端首次渲染結果必須一致，否則會出現 hydration mismatch 警告。最常見的地雷是在元件本體直接用 Date.now()、Math.random()、window.xxx——這類值兩邊必然不同，要改放進 useEffect。

(h) 編譯型 vs 直譯型的效能（對話的起頭問題）：Gemini 的回答是「C++ 通常編譯成機器碼，執行速度通常比直譯型的 JavaScript 快，但實際表現仍取決於演算法與硬體環境」。

(i) ⚠️ 存疑／更正：把 JavaScript 一律說成「直譯型（Interpreted）」已經不精確。現代 V8 引擎採 JIT（Just-In-Time Compilation，即時編譯）——先由 Ignition 直譯器產生位元組碼，熱點程式碼再交給 TurboFan 編譯成最佳化機器碼。所以差距主因並非「有沒有編譯」，而是記憶體管理方式（手動 vs GC）、型別是否靜態已知、以及去最佳化（Deoptimization）風險。

(j) 次要備註：這串對話後半段其實跑題到「LeetCode 找位數乘積」的迴圈起始值問題（該從 n 開始而非 1、要轉字串的是迴圈變數 i 而不是固定的 n），與 SSR 主題無關，已另行歸入雙指標／迴圈相關筆記脈絡，本篇不重複收錄。

(k) CSR / SSR / SSG 的 Hydration 狀態對照（用列表，SSR 與 SSG 幾乎相同）：

  • CSR（純 SPA）：沒有 hydration。伺服器只發空殼 HTML（<div id="root"></div>），瀏覽器端用 createRoot().render() 從零 mount、現場建整棵 DOM（這是「初次渲染」，不是 hydration）。
  • SSR：有 hydration。HTML＝伺服器每次請求現產（runtime 在伺服器跑 renderToString）→ 瀏覽器 hydrateRoot() 認領既有 DOM、掛事件（不重畫）。
  • SSG：有 hydration，跟 SSR 相同。唯一差別在 HTML 的產生時機——SSG 是 build-time 先把每頁 render 成現成的靜態 HTML 檔（不是每請求現產），部署成靜態檔；到瀏覽器端一樣 hydrateRoot() 認領。

一句話：CSR 沒有 hydration（從零建）；SSR/SSG 都有 hydration（認領既有 DOM），差別只在「HTML 是每請求現產（SSR）還是 build-time 先產好（SSG）」。

接效能指標：FP（First Paint）＝第一次畫出任何像素（可能只是背景色）；FCP（First Contentful Paint）＝第一次畫出「內容」（文字/圖片）。SSR/SSG 首屏 HTML 就有內容 → FCP 快；CSR 是空殼 → FP 可能快、但 FCP 要等 JS 建好內容才發生、較慢。這條管線（Parse→DOM→CSSOM→Render Tree→Layout→Paint）跑到「畫出內容」那刻＝FCP。詳見 Critical-Rendering-Path-關鍵渲染路徑-重排vs重繪。

追加 2026-09-01：面試被問「渲染是什麼」該怎麼答

(l) 面試被問到「渲染是什麼」時，只回答 Critical Rendering Path 的流程只答對一半。Critical Rendering Path 指的是瀏覽器把 HTML、CSS 和 JavaScript 轉換成螢幕上像素的過程，那是「瀏覽器內部」的那一層。但在現代網頁開發的語境裡，「渲染」還包含架構層級的 SSR 與 CSR——也就是「這份 HTML 是誰產生的、在哪裡產生的」。

(m) 所以正確的答法是先反問或先分層：「渲染這個詞有兩層意思，一層是瀏覽器把 DOM 畫成像素的關鍵渲染路徑，另一層是架構上的 CSR／SSR／SSG。您想聽哪一層？」——這比直接背 CRP 流程更能顯示你知道詞彙的邊界。

(n) 兩個縮寫的最短定義：CSR（Client-Side Rendering，客戶端渲染）是瀏覽器下載一個很小的 HTML 與 JavaScript 檔案，接著在客戶端的瀏覽器上執行 JavaScript 抓資料並動態產生網頁內容；SSR（Server-Side Rendering，伺服器端渲染）是使用者請求頁面時，伺服器在後端抓資料並把整個 HTML 建立完成，再把完整網頁送給瀏覽器顯示。

(o) CSR 下載的那個「很小的 HTML」就是 index.html，裡面通常只有一個 <div id="root"></div> 的空白骨架。注意不要把它跟 lazy loading 混為一談：lazy loading（延遲載入）是效能手段，把網頁拆成多個區塊或元件、要顯示時才載入那段程式碼；而「JavaScript 動態抓取資料」是資料層的事，兩者是不同概念，CSR 可以用 lazy loading 但不是非用不可。

(p) 同一個 React 元件，在 CSR 執行一次，在 SSR 會執行兩次。

架構 元件執行次數 分別發生在哪
CSR 1 次 只在客戶端瀏覽器執行，直接建立 DOM
SSR 2 次 第一次在伺服器端執行，把結果轉成 HTML 字串傳回；第二次在客戶端載入 JavaScript 時進行 Hydration，元件再次執行、建立虛擬 DOM 並綁定事件，讓畫面恢復互動性

這正是 (g) 那個 hydration mismatch 陷阱的根本成因——「執行兩次」就意味著「兩次結果必須一致」，所以 Date.now()、Math.random()、window.xxx 才會爆炸。

追加 2026-09-06：Build Time 與 Runtime 各做了什麼（CSR／SSR／SSG 分界）

(q) Build Time（建置期）是「你在自己的電腦或 CI 上跑 npm run build 的那一次」，做的是編譯與打包——TypeScript／JSX 轉成瀏覽器看得懂的 JavaScript、Tree Shaking、Minify、切 chunk、產出雜湊檔名。Runtime（執行期）則是「使用者真的送出請求、程式真的在跑」的時候。兩者的分界不是「快或慢」，而是「發生一次」還是「每個使用者都發生一次」。

(r) CSR 的兩個階段：

  • Build Time：打包器（Vite／webpack）只把 React 與你的元件打包成 .js 檔，此時完全沒有任何頁面內容的 HTML，只有一個含 <div id="root"></div> 的空骨架 index.html。
  • Runtime：瀏覽器下載那個空 HTML → 下載並執行大包 JavaScript → JS 在客戶端動態建立 DOM → 畫面才出現。

(s) SSR 的兩個階段：

  • Build Time：一樣只做編譯打包，但會產出兩份 bundle——伺服器端 bundle（給 Node.js 跑 renderToString）與客戶端 bundle（給瀏覽器做 Hydration）。此時同樣沒有任何頁面 HTML。
  • Runtime：每一個請求進來，伺服器才即時抓資料、執行元件、renderToString 產生這一次專屬的 HTML 回傳；瀏覽器 Parse → Layout → Paint（看得到）→ 載入客戶端 bundle → hydrateRoot（能互動）。

(t) ⚠️ 存疑／更正（本次對話最重要的一點）：Gemini 在語音回答中說「SSR 在 Build Time 時，編譯器會預先結合程式碼與後端資料庫請求，將頁面渲染成靜態 HTML；Runtime 時伺服器直接回傳預先準備好的靜態 HTML 檔案」——這段描述的其實是 SSG，不是 SSR。SSR 的 HTML 是「每個請求當下」在伺服器產生的（per-request），不是建置時預先產生好的；正因為每次都重算，SSR 才能呈現即時資料（例如購物車、未讀通知），而 SSG 的頁面內容在部署後就固定了。

(u) 三種架構的「HTML 在哪一刻長出來」一表看完：

架構 HTML 產生的時機 誰產生 資料新鮮度 典型工具
CSR Runtime（瀏覽器端） 使用者的瀏覽器執行 JS 每次開頁都最新（但要等 JS） Vite + React、CRA
SSR Runtime（伺服器端，每個請求一次） Node.js 伺服器 每個請求都最新 Next.js（動態路由）、Remix
SSG Build Time CI／建置機器 部署當下的快照，之後不變 Next.js generateStaticParams、Astro、Hugo
ISR（折衷） Build Time 先產一份，Runtime 到期後背景重產 建置機器 ＋ 伺服器 可設定 revalidate 秒數 Next.js ISR

(v) 一句話記法：問「HTML 是誰、在哪一刻拼出來的」就分得出三者——建置機器拼好的是 SSG，伺服器每次現拼的是 SSR，瀏覽器自己拼的是 CSR。而 Build Time 這一格對三者其實做的事幾乎一樣（編譯＋打包），差別全在 Runtime。

使用者：所以 C++ 一定比 JavaScript 快嗎？
Gemini：C++ 通常編譯成機器碼，執行速度通常比直譯型的 JavaScript 快，但實際表現仍取決於演算法與硬體環境。（⚠️ 見重點 (i) 的更正）

使用者：那 JavaScript 的 SSR 呢？
Gemini：SSR 是伺服器端渲染，把頁面在伺服器上先產生好 HTML 再傳給客戶端，可以讓頁面更快顯示出來，對 SEO 也很有幫助。

使用者：伺服器端要怎麼轉成 HTML？那這樣子 HTML 還會有 DOM Tree 嗎？
Gemini：伺服器端是用特定的函式把 JavaScript 元件轉換成 HTML 字串，例如 React 的 renderToString。傳到瀏覽器後，瀏覽器解析這個 HTML 字串才會重新建立出 DOM 樹，讓網頁可以互動。

使用者：然後 render 函數裡面做了些什麼？
Gemini：渲染函式會根據元件目前的狀態和屬性，回傳一段 UI 的描述，通常就是在 JSX 裡面寫好的畫面結構，用來決定 UI 呈現出來的樣子。
