# 前端建構到執行全景地圖

> **用途**：這份不重寫任何內容，只把 HTML／CSS／JS／React／Vue 各自在 **build-time**（開發者/CI 機器，做一次）跟 **run-time**（使用者瀏覽器，每個訪客各做一次）發生的事串成一張表，回答「這件事到底是什麼時候、被誰做的」。細節一律用 wikilink 指到既有專篇，不做第二次重點整理。
>
> 判斷 build-time 還是 runtime 的最快問法：**「這件事發生時，有沒有瀏覽器／DOM／使用者的 CPU 參與？」有 → runtime；只在建置機器/CI 上、產物還是純文字檔 → build-time。**

---

## 一‧五個主題各自的 build-time → runtime

| 主題 | 🔧 build-time（建置機器/CI，做一次） | 🌐 run-time（使用者瀏覽器，每人一次） |
|---|---|---|
| **HTML** | 輕量文字 parse，只為了把 `<script src>`/`<link href>` 塞進 `index.html`＋minify 去空白；**沒有 DOM、也沒有解析成樹** | HTML Parsing：Blink 逐字元讀字串 → 蓋出 DOM 樹（`<div>` 5 個字元 → `HTMLDivElement` 物件） |
| **CSS** | ⚠️ 待補（PostCSS／Autoprefixer／CSS Modules／Tailwind purge 這類 build-time 處理，vault 裡還沒有專篇） | CSS Parse → CSSOM → 跟 DOM 合併成 Render Tree → Layout（重排）→ Paint（重繪）→ Composite |
| **JS** | 轉譯（TS/JSX→純 JS）→ bundle（tree-shake/code-split/scope-hoist）→ minify → hash 注入，產物**仍是純文字 JS** | V8：Parse→AST→Scope Analysis（編譯期，但這個「編譯期」發生在 runtime）→ Ignition 直譯 Bytecode → 熱點送 TurboFan JIT → 必要時 Deoptimization |
| **React** | JSX → `React.createElement`／`_jsx(...)`（Babel／SWC，跟 V8 完全無關，V8 只看得到轉譯完的標準 JS） | Fiber 排程/reconciliation、（SSR 框架才有）hydration 把伺服器吐的 HTML 骨架接管成可互動頁面 |
| **Vue** | ⚠️ 待補（`.vue` 單檔案元件的 SFC 編譯：`<template>` 怎麼被 `vue-loader`／`@vitejs/plugin-vue` 編成 render function，vault 裡還沒有專篇） | `ref()`/`reactive()` 的響應式追蹤：`ref` 用 getter/setter、`reactive` 用 Proxy（兩者都是原生 JS 機制，跟 Vue 本身無關） |

---

## 二‧HTML

- **build-time**：建置工具只對 `index.html` 做文字層級處理——見 [[script載入方式+前因後果#build-time「打包」五步詳解|script載入方式]] 「HTML 在 build-time 的下場」段落；SSG 例外（`renderToString` 在 build-time 先產好 HTML 字串，但產物仍是**字串**不是 DOM）。
- **run-time**：字串 → DOM 樹的完整過程，見 [[script載入方式+前因後果]] (a)「瀏覽器拿到的 `index.html` 是純文字，必須 Run-time 用 CPU 把它 Parse 成 DOM 樹」、(b)「主執行緒只有一條」。
- **編譯到底躲在哪三處**（HTML 這條線本身**沒有編譯**，只有 Parse）：見 [[script載入方式+前因後果]] (q) 的三處對照表。

## 三‧CSS

- **build-time**：⚠️ **待補**。目前 vault 裡完全沒有 PostCSS／Autoprefixer／CSS Modules 作用域雜湊／Tailwind purge unused class 這類「CSS 在建置階段被怎麼處理」的筆記。`frontend-docs/css/00-CSS觀念複習地圖與資料夾索引.md` 是「觀念複習順序」地圖，不是「build→runtime 管線」，兩者用途不同。
- **run-time**：CSS Parse → CSSOM → Render Tree → Layout/Paint/Composite，完整六大步驟＋重排 vs 重繪的判斷見 [[Critical-Rendering-Path-關鍵渲染路徑-重排vs重繪]] 「六大步驟」「重排 vs 重繪，誰先」兩節；CSSOM 樹狀結構長怎樣，見同篇「追問：CSSOM這棵樹長怎樣」一節。

## 四‧JS

- **build-time**：轉譯／bundle／minify 五步全套（含各打包工具用誰做 transpile/minify 的對照表），見 [[script載入方式+前因後果#build-time「打包」五步詳解|script載入方式]] (k) 整節。
- **run-time**：Parse→Ignition→TurboFan→Deoptimization 完整管線圖＋各階段名詞解釋，見 [[00-V8引擎完整管線-Parse到Deoptimization]]；bytecode／機器碼的通用概念見 [[機器碼與bytecode的差異]]。
- **編譯期 vs 執行期容易搞混的地方**（Parse 雖叫「編譯期」，但仍發生在使用者開頁那一刻，不是 build-time）：見 [[00-V8引擎完整管線-Parse到Deoptimization]] 「編譯期 vs 執行期」節；轉譯 vs 編譯的三處對照表見同篇「Parser 之後如果是 TypeScript／JSX 呢」節。

## 五‧React

- **run-time**：SSR 首屏在伺服器 V8 跑 `renderToString` 產字串（不是 DOM）→ hydration 接管、掛事件監聽器，完整流程見 [[SSR-renderToString與Hydration-伺服器端渲染流程]]；
  CSR vs SSR 的差異表、驗證小技巧見 [[script載入方式+前因後果]] (p)。
- Fiber 有沒有取代 Blink 的排版/繪製功能，見 [[Critical-Rendering-Path-關鍵渲染路徑-重排vs重繪]] 「追問：React的Fiber有完全取代Blink的功能嗎」節。

## 六‧Vue

- **build-time**：⚠️ **待補**。`.vue` 單檔案元件（SFC）的 `<template>` 怎麼被編譯成 render function、`vue-loader`／`@vitejs/plugin-vue` 實際做了什麼，vault 裡目前只在 [[00-前端框架比較-Vue-React-Angular難易度與優缺點]] 提過一句「搭配 SFC 單檔案組件規範」，沒有展開。
- **run-time**：`ref()` 用 getter/setter、`reactive()` 用 Proxy 的完整拆解＋兩者差異，見 [[00-ref與reactive-響應式的兩種實作]]；模板自動解包（unwrap）見同篇「五、模板自動解包」節。
