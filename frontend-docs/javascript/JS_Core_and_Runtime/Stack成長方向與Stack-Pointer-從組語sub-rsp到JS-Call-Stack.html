🧠 自我測驗

是非題

  1. 在 x86-64 上，`push` 指令會讓 rsp（Stack Pointer）的值變大。

    Stack 往低位址成長，push 是減少 rsp、pop 才是增加 rsp。

  2. 反組譯畫面最左邊那一欄的位址，指的是 rsp 目前指到的堆疊位置。

    那是指令自己住的位址（Code Segment），跟 rsp 指的堆疊位址是兩條完全不同的軸。

  3. 0x7FFF0FC0 比 0x7FFF0FD0 小。

    十六進位 C=12、D=13，所以 FC0 < FD0。

  4. JS 裡 Call Stack 的 stack 和存放 primitive 區域變數的 stack 是同一塊記憶體。

    同一塊的兩種用途：既追蹤執行位置，也存當前 frame 的 primitive 值與 Heap 指標。

  5. 被閉包捕捉的變數會留在 Stack Frame 上，等 return 時一起被 pop。

    引擎會把它們搬到 Heap 的 Context 物件，這正是閉包能存活的原因。

  6. Stack 上的記憶體是由 GC（垃圾回收）負責清理的。

    Stack Frame 在 return 時自動 pop，是引擎內建機制；GC 只管 Heap。

填空題

  1. SP 的全名是 Stack ，中文叫堆疊指標，x86-64 上的暫存器名稱是 rsp。

    Stack Pointer，永遠指著堆疊頂端。

  2. BP 的全名是 Pointer，又叫 Frame Pointer，x86-64 上叫 rbp，用來當區域變數偏移量的基準點。

    Base Pointer／基底指標。

  3. 要在堆疊上配置區域變數，組語會下 ` rsp, N`（因為 stack 往低位址成長）。

    配置用 sub、歸還用 add 或 leave。

  4. 反組譯裡 0x0024 的下一行是 0x0028，差的 4 代表這道指令的機器碼長度是 4 。

    是指令長度，跟運算元那個 4 無關。

  5. ISA 的全名是 Instruction Set ，是 CPU 對外公開「有哪些指令與暫存器」的合約。

    指令集架構，x86-64／ARM64／RISC-V 各是一種 ISA。

  6. V8 的 Heap 中，剛建立、生命週期短的物件會先放在 Space（新生代），用 Scavenge 演算法快速回收。

    熬過多次回收才會被搬到 Old Space。

  7. V8 中存放 JIT 編譯器（Ignition／TurboFan）產出的機器碼的區域叫 Space。

    與 New／Old／Large Object Space 並列。

申論題

  1. 用你自己的話解釋：為什麼「sub rsp, 4」明明是減法，反組譯的下一行位址卻從 0x0024 變成 0x0028？請把兩條位址軸講清楚。

    參考方向：(1) 反組譯畫面上同時存在兩條位址軸。左邊那欄是「指令位址」，屬於 Code Segment，程式碼由上往下擺，所以往下讀位址一定遞增，相鄰兩行的差值等於上一道指令的機器碼長度。(2) rsp 指的是「堆疊位址」，屬於 Stack Segment，這條軸往低位址成長，所以配置空間要用 sub。(3) 0x0024 → 0x0028 差 4，是因為 sub 這道指令本身佔 4 bytes，跟運算元的那個 4 沒有任何關係——只是剛好兩個數字都是 4，才特別容易誤會。(4) 一句話：左邊那條軸在回答「下一道指令在哪」，rsp 那條軸在回答「我的區域變數放哪」，是兩件事、兩把尺。

  2. 面試官問：「JavaScript 的記憶體就只有 Call Stack 和 Heap 嗎？」你會怎麼回答？

    參考方向：(1) 先給結論：應用層思考用 Call Stack + Heap 大致夠用，但 V8 底層遠不只兩塊。(2) Call Stack 存執行幀、primitive 區域變數與 Heap 指標，return 時自動 pop，不歸 GC 管。(3) Heap 內部細分：New Space（新生代，Scavenge 快速回收）、Old Space（老生代，Mark-Sweep-Compact）、Large Object Space（大物件獨立配置、GC 不搬動）、Code Space（存 JIT 產出的機器碼）。(4) 補一個反直覺的點加分：被閉包捕捉的變數會被搬到 Heap 的 Context 物件，所以閉包變數其實住在 Heap，不是 Stack。(5) 再補 Event Loop 相關的 Web APIs 與 MacroTask／MicroTask Queue，雖然不算純資料記憶體，但也是執行期存放與排隊的機制。

  3. 為什麼 x86-64 的 Stack 要設計成往低位址成長？這個設計對 Heap 有什麼好處？

    參考方向：(1) 歷史與布局原因：讓 Stack 從記憶體高位址往下長、Heap 從低位址往上長，兩者相向成長。(2) 好處是中間那塊未使用的空白可以被兩邊彈性共用，不必在程式啟動時就把「Stack 佔多少、Heap 佔多少」切死。(3) 連帶的規則：push 減 rsp、pop 加 rsp、配置用 sub、歸還用 add 或 leave——這些全都是同一個成長方向推導出來的，記住方向就不必死背個別指令。(4) 可補充：這是 ISA 與 ABI 共同約定的，不是編譯器可以自由選擇的；ARM64 同樣是 full descending stack。

縮寫先攤開：SP、BP、rsp、rbp 到底是什麼

[!important]+ 縮寫不先講清楚，後面全部會卡住
a. SP＝Stack Pointer（堆疊指標）。一個 CPU 暫存器，永遠指著「堆疊目前的頂端在哪個記憶體位址」。x86-64 上它的名字叫 rsp（r＝register、s＝stack、p＝pointer；32 位元時代叫 esp）。
b. BP＝Base Pointer（基底指標，又叫 Frame Pointer 框架指標）。也是暫存器，指著「目前這個函式的 Stack Frame 從哪裡開始」。x86-64 上叫 rbp。有了固定的 BP，函式內部就能用 [rbp-4]、[rbp-8] 這種固定偏移量去存取自己的區域變數，不必管 SP 這段期間又動了幾次。
c. ISA＝Instruction Set Architecture（指令集架構）。CPU 對外公開的「你可以下哪些指令、有哪些暫存器」這份合約。x86-64（又稱 AMD64）、ARM64、RISC-V 都是不同的 ISA。本篇的 rsp／rbp／sub 都是 x86-64 這個 ISA 的東西，換到 ARM64 名字就不一樣了。
d. ABI＝Application Binary Interface（應用程式二進位介面）。比 ISA 更上一層的約定：參數用哪些暫存器傳、堆疊要怎麼對齊、誰負責清理。Linux／macOS 用的是 System V AMD64 ABI，Windows 用的是另一套。

一、Abby 原本的疑問：「減了 4，位址卻變大？」

這是三段對話裡最核心、也最值得記住的一次卡關。

你以為 實際上
sub rsp, 4 讓位址減 4，所以下一行位址應該變小 你在看的那一欄根本不是 rsp，是指令自己住的位址
0x0024 → 0x0028 是「堆疊往上長」 0x0028 是下一道指令的位址，差 4 是因為 sub 這道指令的機器碼佔 4 bytes

[!warning]+ 關鍵：反組譯畫面上其實有「兩條互不相干的位址軸」
e. 軸一是指令位址（Code Segment）——反組譯最左邊那一欄。程式碼是由上往下擺的，所以往下讀，位址一定遞增。相鄰兩行的差值＝上一道指令的機器碼長度。
f. 軸二是堆疊位址（Stack Segment）——rsp 指的地方。這條軸往低位址成長，所以配置空間要用 sub。
g. 兩條軸都用十六進位、都叫「位址」，但一個在問「下一道指令在哪」，另一個在問「我的區域變數放哪」。用同一把尺去量就必錯。
h. 這次的巧合特別壞心：運算元剛好是 4，指令長度也剛好是 4，兩個 4 一撞在一起就完全分不出誰是誰。

二、為什麼是 sub 而不是 add

[!note]+ 因為 Stack 是「倒著長」的
i. 在 x86／x86-64 上，堆疊從記憶體高位址往低位址成長（grows downward）。這是硬體與 ABI 一起定下的規則，不是編譯器可以自己選的。
j. 所以配置區域變數＝把 SP 往下推＝sub rsp, N；歸還＝把 SP 拉回來＝add rsp, N（或直接一道 leave）。
k. 同理，push 會減少 rsp，pop 會增加 rsp。這跟直覺剛好相反，是初學最常翻車的地方。
l. 為什麼要往下長？歷史原因是讓 Stack 與 Heap 從記憶體的兩端相向成長，中間那塊空白可以被兩邊彈性共用，不必事先切死誰佔多少。

典型的函式開場白（prologue）長這樣：

push rbp            ; 先把呼叫者的 BP 存起來（rsp 減 8）
mov  rbp, rsp       ; 用目前的 SP 當作本函式的 BP 基準點
sub  rsp, 16        ; 往下挖 16 bytes 給區域變數用
; ... 函式本體，用 [rbp-4]、[rbp-8] 存取區域變數 ...
leave               ; 等同 mov rsp, rbp / pop rbp
ret                 ; 跳回呼叫者

[!warning]+ ⚠️ 存疑／更正：對話裡的 sub rsp, 4 在真實 x86-64 幾乎不會出現
m. System V AMD64 ABI 要求 call 之前堆疊必須 16-byte 對齊，所以編譯器實際產生的多半是 sub rsp, 16／sub rsp, 32 這種 16 的倍數，而不是 4。
n. sub esp, 4 這種寫法比較像 32 位元的 x86（esp）或教科書的簡化範例。Gemini 沒有點出這件事，但概念方向（sub 是為了配置、stack 往下長）是對的。

三、十六進位比大小的陷阱

第二段對話卡在這裡：「0x7FFF0FC0 明明數字比較大啊？」

[!danger]+ C 和 D 是數字，不是字母
o. 十六進位裡 A=10、B=11、C=12、D=13、E=14、F=15。
p. 所以 FC0 的中間那位是 12、FD0 的中間那位是 13 → 0x7FFF0FC0 < 0x7FFF0FD0。
q. 對應到 Stack：main() 先被呼叫，住在較高的 0x7FFF0FD0；main() 呼叫 add() 時往下長，add() 的 frame 落在較低的 0x7FFF0FC0。「後呼叫的函式位址比較小」，完全符合往下長的規則，沒有矛盾。

高位址 (High Address)
  ▲
  │   [ main() Stack Frame ]  → 0x7FFF0FD0   （先建立，位址較大）
  │   [ add()  Stack Frame ]  → 0x7FFF0FC0   （後建立，位址較小）
  │   ▼ Stack 成長方向（往低位址）
  ▼
低位址 (Low Address)

四、拉回 JS：Call Stack 的 Stack 跟放 primitive 的 Stack 是同一塊嗎

第三段對話問的是這題，答案是是的，同一塊。

[!note]+ 一個 Stack Frame 裡到底裝了什麼
r. 呼叫函式時，引擎在 Call Stack 上推入一個 Stack Frame，裡面同時裝著三種東西：執行上下文與參數、該函式內宣告的 primitive 變數（直接存值）、物件／參考型別的記憶體位址（指標）——物件本體在 Heap。函式 return 時整個 frame 被 pop，這三樣一起消失。

所以「Call Stack」和「存 primitive 的 Stack」不是兩塊記憶體，是同一塊的兩種用途：既追蹤「程式執行到哪」，也存「當前區塊的區域值與 Heap 指標」。

JS 的記憶體不是只有 Call Stack ＋ Heap

面試層級講 Call Stack ＋ Heap 大致夠用，但 V8 底層還細分：

區域 放什麼 回收方式
Call Stack 執行幀、primitive 區域變數、Heap 指標 return 時自動 pop，不歸 GC 管
New Space（新生代） 剛建立、生命週期短的物件 Scavenger（Minor GC），快速複製式回收
Old Space（老生代） 在新生代熬過多次回收的物件 Mark-Sweep-Compact（Major GC）
Large Object Space 超過尺寸上限的大物件 各自獨立配置，GC 不搬動它
Code Space JIT（Ignition／TurboFan）產出的機器碼 隨程式碼快取失效而回收

[!tip]+ 閉包變數住在哪？答案會顛覆直覺
被閉包捕捉的變數不能隨 Stack Frame 一起被 pop 掉，所以引擎會把它們搬到 Heap 上的 Context 物件裡。也就是說——閉包變數其實住在 Heap，這也正是 12-return-清理記憶體-stack-frame與閉包例外 講的「例外」。

另外 Event Loop 相關的 Web APIs／Node APIs、MacroTask ／ MicroTask Queue 嚴格說不算資料記憶體，但也是執行期會排隊存放東西的地方，細節見 事件循環-Event-Loop-微任務與巨任務。
