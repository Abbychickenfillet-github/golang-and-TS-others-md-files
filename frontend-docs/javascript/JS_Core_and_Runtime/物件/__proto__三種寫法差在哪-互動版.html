結論先講：它們不是同一件事的三種寫法，其中一個根本不設原型｜所有結果都是本頁即時執行出來的｜2026-08-19

a先解決「為什麼要等於 X」

因為 __proto__ 是存取器屬性，它有 getter 也有 setter，所以有「讀」跟「寫」兩種用法。我上次寫 = X 是在示範寫的那一半。

讀 → getter 執行

obj.__proto__          // 沒有等號
// 回傳 obj 的原型是誰

等價於 Object.getPrototypeOf(obj)

寫 → setter 執行

obj.__proto__ = X      // 有等號
// 把 X 設成 obj 的原型

等價於 Object.setPrototypeOf(obj, X)

X 只是我隨手取的變數名，它代表「任何你想拿來當原型的物件」。 寫成 obj.__proto__ = P、obj.__proto__ = animal 都一樣，重點是等號右邊那個東西會變成 obj 的原型。

c為什麼 ["__proto__"] 就不算了？

這是你最卡的地方。關鍵是：引擎是看「你怎麼寫」，不是看「字串長什麼樣」。

在物件字面量裡，__proto__: 這個寫法被規範當成一個特殊的語法形式， 引擎在解析程式碼的當下就認出它，然後走「設定原型」那條路。

但 ["__proto__"] 是計算屬性名 computed property name， 它的意思是「先算出中括號裡的值，再拿那個值當 key」。引擎解析到這裡時只知道「這裡有個要算的 key」， 它走的是「建立一般屬性」那條完全不同的路 —— 這條路根本沒有「設原型」這個選項。

用你熟的東西類比：if 是 JavaScript 的關鍵字，"if" 只是一個剛好長得像關鍵字的字串。
同理：字面量裡的 __proto__: 是「語法」，["__proto__"] 算出來的是「一個剛好叫 __proto__ 的字串 key」。
長得一樣，但**身分完全不同**，因為引擎在解析階段就分道揚鑣了。 
// 路徑一：語法形式 → 設原型
{ __proto__: P }        → 原型變成 P，自有屬性 []
{ "__proto__": P }      → 一樣！字串字面量也算語法形式

// 路徑二：一般屬性 → 不碰原型
{ ["__proto__"]: P }    → 原型還是 Object.prototype，自有屬性 ["__proto__"]
{ __proto__ }           → 簡寫也不算
{ __proto__() {} }      → 方法簡寫也不算
JSON.parse('{"__proto__":...}')  → 也不算，JSON 走的是一般屬性那條路

e所以這三個一樣嗎

不一樣。而且不只「寫法不同」，是「做的事不同」。

寫法有設原型嗎什麼時候發生標準狀態速度
obj.__proto__ = X 有物件建立之後 deprecated慢
{ __proto__: X } 有物件建立的當下 標準，且被引擎最佳化快
{ ["__proto__"]: X } 沒有— 就是普通屬性—

前兩個雖然都設了原型，但時機不同，這正是效能差距的來源，看下一節。

f為什麼 deprecated：理由一「慢」（但要誠實看數字）

V8 會幫每個物件記一張「形狀表」（hidden class 隱藏類別）來加速屬性查找。建立之後才改原型 = 形狀變了 = 之前針對這個形狀做的最佳化全部作廢。

我先講一件老實話：MDN 說改動 __proto__ 是「非常慢的操作」， 但我實測下來，單純建立物件的微型測試根本測不出明顯差距 —— 現代 V8 已經把簡單情境最佳化掉了。
真正的代價出現在「這個物件已經被用過了，你才去改它的原型」的時候： 原本累積的 inline cache 會全部失效，之後每次讀屬性都變慢。

g為什麼 deprecated：理由二「原型污染」

這個比效能嚴重得多，是真實世界的資安漏洞類型。可以按按鈕實際製造一次，再清乾淨。

// 攻擊者送進來的 JSON（看起來人畜無害）
{"__proto__": {"isAdmin": true}}

// 你的後端／前端有一段很常見的「合併設定」函式
for (const k in source) {     // for...in ＋ 直接賦值 = 危險組合
  target[k] = source[k];
}

// 合併之後
({}).isAdmin  // true ← 全世界的物件都變成 admin 了
關鍵細節：JSON.parse 本身是安全的， 它走的是「建立一般屬性」那條路，解析出來只是一個叫 __proto__ 的普通 key。
出事的是後面那個合併動作 —— target[k] = ... 這種賦值會觸發 setter，這才把原型污染掉。
按 ① 開始。這個污染只影響這個分頁，重新整理就沒了。

三種防法：

  • 合併時用 Object.keys(source) 或 Object.hasOwn 過濾掉繼承來的，別用 for...in
  • 明確跳過 __proto__、constructor、prototype 這三個 key
  • 設定物件改用 Object.create(null) —— 它沒繼承那個 setter，攻擊者塞 __proto__ 進來也只會多一個普通屬性

h為什麼 deprecated：理由三「它是遺留特性」

__proto__ 在瀏覽器裡存在很久了，但一直是各家自己實作的非標準功能。 到 ES2015 因為太多網站在用、拿掉會壞掉，才被寫進規範的 Annex B —— 那是專門收「為了網頁相容性不得不承認的遺留特性」的附錄。

換句話說，它進規範不是因為設計得好，是因為移不掉。 真正的正規做法是 ES5 的 Object.getPrototypeOf() 與 ES2015 的 Object.setPrototypeOf()。

i你該記什麼

  • 要讀原型 → Object.getPrototypeOf(o)
  • 建立時就要指定原型 → { __proto__: P } 或 Object.create(P)，這兩個都快
  • 建立之後才要改 → Object.setPrototypeOf(o, P)，但先想想能不能避免，這動作很貴
  • 永遠不要寫 → o.__proto__ = P
  • 合併使用者資料 → 用 Object.keys 過濾，或用 Object.create(null) 當容器
