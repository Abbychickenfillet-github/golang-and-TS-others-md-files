d申論題

先自己講一遍再點開，這幾題都是面試會追問的。

d-1. 為什麼 Object(1) == 1 是 true 但 Object(1) === 1 是 false？
  • 嚴格相等 === 第一步就比型別。左邊是 object 右邊是 number，型別不同直接回傳 false，不做任何轉換。
  • 寬鬆相等 == 遇到「一邊物件一邊原始值」時，會先對物件做 ToPrimitive 抽象操作，把 Number {1} 透過 valueOf() 轉回原始值 1，接著才比較 1 == 1，所以是 true。
  • 順帶一提 Object(1) === Object(1) 也是 false，因為每次呼叫都建立一個新物件，物件比的是參考位址不是內容。
d-2. new Object()、Object()、{} 三者差在哪？實務上該用哪個？
  • 在「不傳參數」這個情境下三者行為完全一樣，原型都是 Object.prototype，但各自是不同的物件，互相 === 是 false。
  • 差別只出現在傳參數的時候。Object(value) 是型別轉換，會依照四條分流做事；{} 永遠只做一件事就是建立空的 plain object。
  • 實務上一律用 {}，MDN 也是這個建議。會用到 Object() 的時機只有兩個：把不確定型別的值強制轉成物件，或刻意要建立包裹物件。
d-3. null-prototype object 有什麼好處與代價？什麼場合會用？
  • 好處是乾淨。它不繼承 Object.prototype，所以不會有 constructor、toString、__proto__ 這些鍵混進來，可以安心當字典使用，也擋掉原型污染 prototype pollution 這類攻擊。
  • 代價是所有繼承來的方法都不見了。np.hasOwnProperty("p") 會 TypeError，連 `${np}` 這種字串轉換都會爆掉，因為沒有 toString 可用。
  • 因應方式是改用靜態方法 Object.keys()、Object.hasOwn()、Object.getOwnPropertyNames()，它們對 null-prototype 物件一樣安全。這也是 MDN 說 modern code 應該優先用靜態方法的理由。
  • 常見場合是拿使用者輸入當 key 的查表結構，例如把 query string 或 JSON 解析結果存成字典。
d-4. 為什麼陣列跟 Map 不算 plain object？拆檔的判準是什麼？
  • 判準就是原型鏈的第一層。Object.getPrototypeOf([]) 是 Array.prototype，Object.getPrototypeOf(new Map()) 是 Map.prototype，都不是 Object.prototype。
  • 它們雖然最終還是接到 Object.prototype 再到 null，但中間多了一層自己的方法集合，所以 API 完全不同：陣列有 map／filter，Map 有 get／set／size，plain object 這些都沒有。
  • 另一個快速檢查是 Object.prototype.toString.call(x)：plain object 得到 [object Object]，陣列得到 [object Array]，包裹物件 Object(1) 得到 [object Number]。
d-5. 物件的 key 到底能是什麼型別？user[1] = "one" 之後 Object.keys() 會看到什麼？
  • 只有兩種：字串與 Symbol。其他任何值當 key 都會被隱式轉成字串。
  • 所以 user[1] = "one" 實際上存的是 user["1"]，Object.keys(user) 會看到字串 "1" 而不是數字 1。
  • 延伸陷阱：obj[{}] 會變成 obj["[object Object]"]，兩個不同的物件當 key 會互相蓋掉，這正是需要 Map 的理由，Map 的 key 可以是任意型別。

e回頭指主軸圖

a. 分流 1 是你 99% 情況會用到的那一條，但你其實應該直接寫 {}。
b. 分流 2 是所有「包裹物件」怪題的來源，它接到 valueOf 與 ToPrimitive 那兩篇。
c. 分流 3 是傳址 pass by reference 的教科書案例。
d. 分流 4 只在 class X extends Object 出現，記得它「參數會被忽略」就夠了。
e. 右側原型鏈那條線，往下延伸就是 null-prototype object 的整個故事。
