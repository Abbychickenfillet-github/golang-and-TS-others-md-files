🧠 自我測驗

是非題

  1. NaN === NaN 的結果是 false。

    NaN 是唯一不等於自己的值，這是 === 的第一個死角。

  2. Object.is(+0, -0) 的結果是 true。

    是 false。Object.is 分得出正負零，=== 分不出。

  3. useState 在更新時會做欄位層級的淺比較。

    useState 只做 Object.is，完全不看物件內部。做淺比較的是 React.memo / PureComponent 用的 shallowEqual。

  4. shallowCompare 是 React 現在推薦的比對工具。

    它是 v15 時代的 add-on，官方早已要求改用 React.memo 或 React.PureComponent。

  5. Vue 3 的 hasChanged 實作就是 !Object.is(value, oldValue)。

    ref 的 setter 只有在 hasChanged 為真時才 triggerRefValue。

  6. 用 items.push(4) 之後再 setItems(items)，React 會重新渲染。

    push 是原地修改，陣列的記憶體位址沒變，Object.is 判定相同 → React 直接 bailout。要寫 setItems([...items, 4])。

  7. 直接改 user.address.city 之後再 setUser(user)，React 偵測不到更新。

    最外層 user 的參照沒變。必須逐層複製：setUser({...user, address:{...user.address, city:'Taipei'}})。

  8. 展開運算子 ... 會產生深拷貝。

    它是淺拷貝（Shallow Copy），只複製第一層；巢狀那一層仍指向同一個物件。

  9. setCount(prev => prev + 1) 連寫三次，count 會加 3。

    函式更新每次都拿排隊時的最新值；寫成 setCount(count+1) 三次則因為批次更新讀到同一個過期值，只加 1。

填空題

  1. Object.is 在規格中的相等演算法名稱叫 Same。

    === 叫 Strict Equality，== 叫 Loose Equality。

  2. React polyfill 用 1 / x === 1 / y 來分辨 +0 與 0。

    1/+0 是 Infinity、1/-0 是 -Infinity。

  3. React polyfill 用 x !== x && y !== y 這個技巧來判斷兩邊都是 。

    只有 NaN 不等於自己。

  4. Markdown 表格若要在同一儲存格內換行，必須使用 <> 標籤而不是按 Enter。

    直接換行會把整張表格拆壞。

  5. 「改到哪一層就從最外層一路複製到那一層」這條規則的正式名稱叫 __ Update（不可變更新）。

    React 官方文件 Updating Objects in State 的核心要求。

  6. setState(prev => ...) 這種寫法叫做「__更新」，它接收先前的狀態。

    英文是 Functional Update / Updater Function。

  7. 巢狀太深不想手寫展開運算子時，實務上常改用 __ 這個套件（useImmer）。

    寫起來像直接改，底層自動產生新參照。

  8. Shallow Copy 講的是「產生資料」，Shallow __ 講的是「比對資料」，兩個 shallow 不同義。

    巢狀 bug 就是這兩個深度對不上造成的。

申論題

  1. 為什麼 React 和 Vue 這兩套架構完全不同的框架，都選擇用 Object.is 當狀態比對的第一道防線？

    參考方向：(1) 共同目標是「最小化無效計算」——只有真的變了才重繪。所以需要一個既不會誤判、成本又極低的比較。(2) 不能用 ==：自動型別轉換會製造不可預期的判斷（0 與 false、null 與 undefined），一個渲染引擎不能容忍這種模糊。(3) 不能只用 ===：NaN === NaN 為 false 會造成無效渲染（值沒變卻重繪），+0/-0 分不出來則在高精度數值場景會漏判。Object.is 剛好只補這兩個洞，其餘行為與 === 相同，成本是 O(1)。(4) 它同時定義了「不做什麼」：Object.is({},{}) 是 false，代表框架擺明不比內容、只比引用，這反過來推導出「不可變更新（immutable update）」這個開發慣例——你想讓框架知道資料變了，就要給它一個新引用。(5) 需要比內容時才往上疊一層 shallowEqual（React.memo）或用 Proxy 做細粒度追蹤（Vue 3），但第一層永遠是最便宜的 Object.is。

  2. 日常寫程式你會用 === 還是 Object.is？請給判準。

    參考方向：(1) 業務邏輯一律用 ===，語法簡潔、涵蓋 99% 情境，而且團隊都看得懂。(2) 只有在寫「會被別人拿去用的通用工具」時才改用 Object.is——例如自訂的 useDeepCompareEffect、狀態管理庫的 diff 函式、快取的 key 比對。理由是這些程式碼面對的是任意輸入，NaN 一定會出現。(3) 反過來說，如果你確定值域裡不可能有 NaN 或 -0（例如比對字串 id），用 Object.is 只是增加閱讀成本，沒有好處。(4) == 只在一種情況值得用：x == null 同時判斷 null 與 undefined，這是社群公認的例外，其餘一律避免。

  3. 狀態是 { name, address: { city } }，只改 city 卻畫面不動。請說明底層原因，並給出兩種正確做法與各自的取捨。

    參考方向：(1) 原因——useState 的 bailout 用 Object.is 比最外層參照；直接改內層時外層 user 仍是同一個位址，Object.is 回傳 true，React 直接跳過重繪。(2) 做法一：逐層展開 setUser({...user, address:{...user.address, city}})，零依賴、語意明確，但層數一多會很難讀也容易漏抄某一層。(3) 做法二：用 Immer 的 useImmer，寫成 draft.address.city = x，可讀性最好，代價是多一個相依套件與一層心智模型。(4) 附帶提醒：structuredClone 雖能深拷貝，但複製不了函式、DOM 節點與 class 原型，且整棵樹都換新參照會讓 React.memo 的優化全部失效，不建議當預設解。(5) 進階：也可以用扁平化 state（把巢狀拆成多個 useState 或用 useReducer）從源頭避開這個問題。

5W1H 速查：讀本篇之前先把座標定好

[!important]+ 最常被搞錯的一件事：以為 useState 會幫你做「淺比較」
a. useState／useReducer 的 bailout 只做一件事：Object.is(oldState, newState)，也就是比引用，完全不看欄位。所以 setState({...oldObj}) 就算每個欄位都一樣，引用是新的就照樣重繪——這正是「保持 Immutable 更新」這個慣例的來源。
b. 做淺比較的是React.memo／PureComponent 內部的 shallowEqual：① 先比引用 → ② 比 key 數量 → ③ 逐一比第一層 value（每一步仍用 is()）。兩者是不同層級的東西，不要混講。本篇「⚠️ 存疑／更正」記的就是這個錯被抓出來的過程。
c. 第三個誤解：以為 Object.is 比較「聰明」所以會看內容。不會——Object.is(空物件, 空物件) 依然是 false，它比的是記憶體位址；它跟 === 的差別只有 NaN 與 ±0 這兩個洞而已。

5W1H 問題 一句話答案
What 是什麼 三兄弟到底差在哪？ 只差兩件事：a. 會不會自動轉型。b. 怎麼處理 NaN 與 ±0。== 會轉型；=== 不轉型但 NaN === NaN 是 false、+0 === -0 是 true；Object.is 不轉型並補上這兩個洞
When 什麼時候 這個比較在哪一格發生？ 執行期，而且每次都重跑。框架端更具體：每次 setState、每次 Vue ref 的 setter 被觸發都完整跑一次判斷
Who 誰在用 誰真的在呼叫它？ a. React 的 useState／useReducer bailout 用自家 polyfill is()（shared/objectIs.js），不是全域 Object.is。b. React.memo／PureComponent 用 shallowEqual。c. Vue 3 的 hasChanged 就是 !Object.is(...)
Where 在哪裡 比的到底是什麼東西？ 對物件而言，比的是記憶體位址，不是內容。這是所有框架比對機制的起點，也是它的限制
Which 哪一種 什麼時候該用哪一個？ a. 日常業務邏輯 → ===。b. 底層封裝、狀態管理、通用工具函式、Custom Hook → Object.is（要面對別人傳進來的任意值，包含 NaN）。c. == → 現代開發基本不用
How 怎麼做到 React 的 polyfill 憑什麼分得出來？ 兩個經典技巧：1 / x === 1 / y 用 Infinity 與 -Infinity 分辨 +0 與 -0；x !== x 抓出唯一不等於自己的 NaN
Why 為什麼 為什麼框架不能只用 ===？ 因為兩個死角都會變成工程問題：NaN 前後相同卻判 false → 無效渲染（沒變卻重繪）；±0 分不出來 → 高精度圖表與數學運算庫會拿到錯的極限方向

重點整理

本篇主軸圖：上半是三兄弟的嚴格度階梯，下半是 React 的兩條判斷路徑。後續追問請直接指回圖上的方框。

一、三者的核心差異（a–d）

(a) 三者的差別只有兩件事：會不會自動轉型，以及怎麼處理 NaN 與 ±0 這兩個特例。

比較方式 語法 型別轉換 特殊案例 主要用途
鬆散比較 a == b 會自動轉換 1 == "1" 為 true；null == undefined 為 true 現代開發極少使用（防禦性程式碼除外）
嚴格比較 a === b 不轉換 NaN === NaN 為 false；+0 === -0 為 true 日常業務邏輯的首選標準
同值比較 Object.is(a, b) 不轉換 Object.is(NaN, NaN) 為 true；Object.is(+0, -0) 為 false 精準判斷兩值是否完全相同

(b) === 的兩個死角：NaN === NaN 是 false（NaN 是唯一不等於自己的值），以及 +0 === -0 是 true（分不出正負零）。

(c) Object.is 就是專門補這兩個洞的，其他情況跟 === 完全一樣。所以它的規格名稱叫 SameValue，=== 叫 Strict Equality。

(d) Object.is({}, {}) 依然是 false——它比的是「是不是同一個記憶體位址」，不會去比內容。這是後面所有框架比對機制的起點與限制。

二、為什麼框架不能只用 ===（e–g）

(e) 現代 UI 框架的核心機制是「資料變更 → 觸發重新渲染」，所以「狀態到底有沒有變」這個判斷必須無副作用而且極度準確。

(f) 不用 == 的理由：自動型別轉換會引發不可預期的渲染 Bug（例如 0 變成 false 卻沒被偵測到）。

(g) 不只用 === 的理由有兩個：
- NaN 死角：state 前後都是 NaN 時 === 判 false，框架誤以為資料改了，做一次無謂的重繪。
- +0 與 -0：在高精度圖表或數學運算庫中兩者代表不同的極限方向，=== 分不出來。

[!tip] 工程上的兩種錯誤
無效渲染（Over-rendering）＝沒變卻重繪，浪費效能；漏渲染（Under-rendering）＝變了卻沒偵測到，UI 不更新。比對機制不夠精準時兩種都會發生。

三、React 的兩條路徑（h–l）

(h) useState / useReducer 的 bailout 機制，底層預設就是 Object.is(oldState, newState)。

(i) useState 本身完全沒有做任何欄位層面的淺比較。你傳入一個全新的物件引用（例如 setState({...oldObj})），即使欄位一模一樣，Object.is 仍回傳 false，就會觸發 re-render。這就是「保持 Immutable 更新」這個慣例的來源。

(j) React 內部的 is() 是 Object.is 的 polyfill（shared/objectIs.js）：

function is(x, y) {
  return (
    (x === y && (x !== 0 || 1 / x === 1 / y)) ||   // 用 1/x 分辨 +0 與 -0
    (x !== x && y !== y)                            // 專門處理 NaN
  );
}
export default typeof Object.is === 'function' ? Object.is : is;

(k) React.memo / React.PureComponent 用的是內部的 shallowEqual，邏輯是三步：

function shallowEqual(objA, objB) {
  if (is(objA, objB)) return true;                 // ① 先比引用

  if (typeof objA !== 'object' || objA === null ||
      typeof objB !== 'object' || objB === null) return false;

  const keysA = Object.keys(objA);
  const keysB = Object.keys(objB);
  if (keysA.length !== keysB.length) return false;  // ② 比 key 數量

  for (let i = 0; i < keysA.length; i++) {          // ③ 逐一比第一層 value
    const key = keysA[i];
    if (!Object.prototype.hasOwnProperty.call(objB, key) ||
        !is(objA[key], objB[key])) return false;
  }
  return true;
}

(l) shallowCompare 是不同的東西而且已經廢棄。它是 React v15 時代 react-addons-shallow-compare 這個 package 裡的附加工具，手動寫在 class component 的 shouldComponentUpdate 裡；官方文件早就要求改用 React.memo（函式元件）或 React.PureComponent（class 元件）。

機制／工具 底層邏輯 現行官方建議
useState / useReducer 直接執行 Object.is(old, new)，不比對內部 key 保持 Immutable 更新，傳入新引用
React.memo / PureComponent 內部呼叫 shallowEqual，先比引用再比第一層屬性（仍用 Object.is） 避免子元件不必要 re-render 的首選
shallowCompare（add-on） 舊版生命週期輔助函式 不要使用

四、Vue 3 的 hasChanged（m–n）

(m) Vue 3 的 ref 在 setter 被觸發時，會先呼叫 hasChanged，而 hasChanged 就是 !Object.is(...)。

// Vue 3 packages/shared/src/index.ts（極簡版）
export const hasChanged = (value: any, oldValue: any): boolean =>
  !Object.is(value, oldValue);

class RefImpl<T> {
  private _value: T;
  set value(newValue) {
    if (hasChanged(newValue, this._value)) {
      this._value = newValue;
      triggerRefValue(this, newValue);   // 只有確定變更才觸發 effect 與畫面更新
    }
  }
}

(n) React 與 Vue 是兩套完全不同的架構，卻不約而同把 Object.is 當成第一道防線——這正是「最小化無效計算」這個共同工程原則的體現。

五、給自己的結論（o–p）

(o) 日常業務邏輯：優先用 ===，語法簡潔且涵蓋絕大多數情境。

(p) 寫底層封裝、狀態管理、通用工具函式或 Custom Hook 時：改用 Object.is，因為那些程式碼要面對別人傳進來的任意值，包含 NaN。

七、承上：不可變更新與巢狀物件的盲點（s–x，2026-09-06 追加）

(s) Abby 自己在語音對話中先講出結論、Gemini 確認完全正確：因為 React 底層是用 Object.is 在比，比的是「兩個陣列／物件是不是同一個記憶體位址」而不是內容，所以要更新陣列裡的某一筆資料時，不能直接改原陣列，必須複製出一個新陣列、建立新的參照，狀態改變才會被偵測到。這條規則的正式名稱叫 Immutable Update（不可變更新）。

const [items, setItems] = useState([1, 2, 3]);

// ❌ 位址沒變 → Object.is(old, new) 為 true → React 直接 bailout，畫面不動
items.push(4);
setItems(items);

// ✅ 展開運算子產生新陣列 → 新位址 → Object.is 為 false → 觸發 re-render
setItems([...items, 4]);

(t) 展開運算子（Spread Operator，...）之所以成為標準做法，是因為它用最短的語法產生一個「內容一樣但位址不同」的新容器，剛好滿足 (i) 那條「傳入全新引用就一定重繪」的規則。但它只複製第一層——這正是下一點的陷阱來源。

(u) 巢狀物件的盲點（本次對話的核心）：淺比較只檢查最外層物件的記憶體位置，所以直接改巢狀內部的屬性時，最外層參照沒變，React 偵測不到，畫面不會更新。正解是「改到哪一層，就從最外層一路複製到那一層」：

const [user, setUser] = useState({
  name: 'Abby',
  address: { city: 'Taoyuan' }
});

// ❌ 直接改內層：user 的參照沒變，React 不會重新渲染
user.address.city = 'Taipei';
setUser(user);

// ✅ 逐層建立新參照（外層 user 換新、內層 address 也換新）
setUser({
  ...user,
  address: { ...user.address, city: 'Taipei' }
});

巢狀太深時的實務替代方案：改用 Immer（useImmer 讓你寫起來像直接改，底層自動幫你產生新參照），或先用 structuredClone(user) 深拷貝再改——但 structuredClone 無法複製函式、DOM 節點與 class 實例的原型，別當萬用解。

(v) 函式更新（Functional Update／Updater Function）：Abby 在對話裡把 prev 誤唸成「韓式蒸氣」，Gemini 給的正解是——setState(prev => ...) 這種寫法叫函式更新，它在更新函式中接收「先前的狀態」，確保這次更新是基於最新的數值。

// ❌ 批次更新（batching）時三行讀到的都是同一個過期的 count，結果只加 1
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);

// ✅ 每一次都拿 React 排隊時的最新值，結果加 3
setCount(prev => prev + 1);
setCount(prev => prev + 1);
setCount(prev => prev + 1);

這一點與 useState底層-Fiber-Tree-memoizedState與過期閉包 是同一個問題的兩面：那篇講「為什麼閉包會抓到過期的 state」，這裡講「用 updater function 繞過它」。

(w) ⚠️ 存疑／更正（用詞精確度）：Gemini 回答「React 確實採用淺比較，也就是檢查記憶體位置是否相同」——這句把兩件事混成一句了。依本篇 (h)(i)(k) 已建立的區分：useState 的 bailout 只做 Object.is，那是「比一層引用」不是「淺比較」；真正逐 key 比第一層的 shallowEqual 是 React.memo / PureComponent 在用的。結論方向沒錯（都是「不換新參照就不重繪」），但面試時把兩者講混會被追問。

(x) 順帶釐清兩個都叫 shallow 的東西：Shallow Copy（淺拷貝）是「... 只複製第一層」，講的是產生資料；Shallow Comparison（淺比較）是「只比第一層」，講的是比對資料。(u) 那個巢狀 bug 之所以出現，正是因為淺拷貝的深度與淺比較的深度剛好對不上你想改的那一層。
