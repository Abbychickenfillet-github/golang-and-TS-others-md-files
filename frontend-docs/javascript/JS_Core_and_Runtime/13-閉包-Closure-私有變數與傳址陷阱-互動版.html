重點整理

一句話定義：閉包是一個內層函式，能「記憶」並存取外層函式的範疇（Scope），即使外層函式已經執行完畢、從 [[事件循環-Event-Loop-微任務與巨任務|Call Stack]] 離開了（機制細節見 [[return-清理記憶體-stack-frame與閉包例外]]；函式參數綁定與 Execution Context 完整整理見 [[函式呼叫核心機制-Execution-Context-與-Parameter-Binding]]）。 在 JS 中閉包不是要特別開啟的功能，而是伴隨函式建立而自然誕生的底層機制。

兩大基石：

  • 詞法範疇 Lexical Scope：變數的存取權限在「程式碼被寫下來的那一刻（宣告位置）」就決定了，而不是函式被執行的那一刻。
  • 垃圾回收 GC：一般函式執行完，局部變數會被釋放；但若該變數還被內層函式引用，瀏覽器就不敢釋放，會繼續留在記憶體（Heap）中。

應用：用閉包做私有變數

function createCounter() {
  let count = 0; // 鎖在 createCounter 範疇內，外部摸不到
  return {
    increment: function() { count++; console.log(count); },
    decrement: function() { count--; console.log(count); }
  };
}
const counter = createCounter();
counter.increment(); // 1
counter.increment(); // 2
// console.log(count); // ReferenceError: count is not defined

createCounter() 執行完回傳物件後，因為回傳的方法仍引用 count，所以 count 活在閉包裡，成為這些方法的專屬私有變數。

經典面試題：var 迴圈 + setTimeout

for (var i = 1; i <= 3; i++) {
  setTimeout(() => { console.log(i); }, 1000);
}

直覺以為 1,2,3；實際是 4, 4, 4。
因為 var 是函式作用域，迴圈裡沒有函式包裹時它幾乎等同全域變數；1 秒後回呼執行時迴圈早跑完，全域 i 已累加到 4，三個閉包指向同一個 i。
修正：把 var 改成 let（區塊作用域），每次迭代建立獨立範疇，三個閉包各自鎖定 1, 2, 3。

魔王題：閉包「漏水」（傳值 vs 傳址）

function createWallet(initialAmount) {
  let money = initialAmount;
  let history = [];
  return {
    checkBalance: () => money,
    getHistory: () => history,         // 直接回傳陣列參照！
    spend: (amount) => { if (amount <= money) { money -= amount; history.push(`Spent ${amount}`); } }
  };
}
const myWallet = createWallet(100);
const record = myWallet.getHistory();  // record 與閉包內 history 指向同一陣列
myWallet.spend(30);                     // money 70, history=['Spent 30']
record.push('Found 100 on the street');// 直接竄改了閉包內部私有狀態！
myWallet.spend(20);                     // money 50
myWallet.checkBalance(); // 50
myWallet.getHistory();   // ['Spent 30','Found 100 on the street','Spent 20']

核心反思：用閉包做私有變數時，若直接回傳物件或陣列，私有性就破功了——外部拿到參照就能繞過你的方法任意改內部資料。
正解：回傳時切斷參照，回傳複本，例如 getHistory: () => [...history]（展開運算子產生新陣列）。

觀念釐清（是非題）

  • return money 會不會讓 money 變成全域變數？ 不會。 money 既不在全域、也沒「回到」函式內部，而是被封裝在專屬 myWallet 的閉包環境裡。return 只是把值複印一份送給外面的變數，口袋裡的本體不會穿透到外面。
  • money 是 checkBalance 的區域變數嗎？ 不是。 money 是 createWallet 函式的區域變數，checkBalance 是透過閉包才能存取到外層 createWallet 裡的 money。（注意：判斷一個變數屬於誰，看的是它宣告在哪個函式，而不是被哪個函式用到。）
  • myWallet 是「函式物件變數」嗎？ 不是。 createWallet 本身才是函式物件（可被呼叫）；myWallet 是 createWallet(100) 回傳的普通物件（Plain Object），myWallet() 會噴 TypeError: myWallet is not a function。物件裡的 spend、checkBalance 因綁在物件上，正名是方法（Method）。

實戰除錯：按鈕計數器（Counter）綁定陷阱

另一個常見的閉包實戰場景，是「每顆按鈕各自獨立計數」的 UI：

function createCounter(buttonId) {
  let count = 0;
  const button = document.getElementById(buttonId);
  button.addEventListener('click', function () {
    count++;
    console.log(count);
  });
}
createCounter('counter1');
createCounter('counter2');

除錯時踩到的幾個真實陷阱：

  • buttonId 抓的是「HTML 元素的 id 屬性」，不是變數名稱——document.getElementById(buttonId) 是拿參數的值（字串）去比對 DOM 上 id="..." 屬性，跟這個參數叫什麼變數名完全無關。容易誤以為傳入的是「變數名稱」本身。
  • 呼叫 createCounter() 時傳入的字串，必須跟 HTML 裡按鈕的實際 id 完全一致（例如 HTML 是 id="counter1"，就不能傳 "buttonId1"），否則 getElementById 拿到 null。
  • 一旦某次 getElementById 綁錯（拿到 null）就對它呼叫 addEventListener，會直接丟出 TypeError 中斷整段程式碼的執行——後面所有按鈕的事件綁定都會被連帶跳過而失效，畫面上看起來像「全部按鈕都壞掉了」，但根因往往只是最前面一個 ID 打錯字。
  • 這裡的閉包核心：count 和 button 都被鎖在 createCounter 的作用域裡，每呼叫一次 createCounter(...)，就會產生一個全新、互不干擾的 count，這就是「各按鈕獨立計數」的原理——與前面 createWallet 私有變數是同一套機制的不同應用。
  • 術語補充：const button = document.getElementById(buttonId) 這種「把 DOM 查詢結果存進變數」的寫法叫做 Caching the DOM elements（快取 DOM 元素）——好處是只查詢一次 DOM、存進變數重複使用，不用每次要操作這顆按鈕時都重新呼叫 getElementById 整份文件重找一次，效能更好。

[!tip] 除錯心法：多顆按鈕同時「全部失效」時，別急著懷疑閉包邏輯本身，先檢查是不是某一個 getElementById 撲空（id 打錯/多了空白字元），導致後續程式碼被整串中斷。

延伸提問：函式參數算不算「宣告」？參數名稱符合 Identifier 定義嗎？名稱真的具備唯一性嗎？

承接上面 createCounter(buttonId) 的例子——直覺是：小括號裡的參數名稱「有點像是在那邊宣告，但又不是真的宣告」，而且「唯一性」好像也沒有真的被保障。這個直覺完全正確，拆成三點講：

(a) 是不是「宣告」？——是，而且是貨真價實的宣告，不是「看起來像」

函式被呼叫的當下（不是定義的當下），JS 引擎會執行規格內部叫 FunctionDeclarationInstantiation 的步驟：先建立一個新的 Function Environment Record，再把每個參數名稱在裡面建立綁定（binding），並用呼叫時傳入的值去初始化它——這一步做完，函式本體才開始執行。
所以參數名稱不是「文件上假裝宣告一下」，它就是在函式作用域內對變數環境做了一次真的宣告與初始化，效果上很接近你在函式體最頂端手寫了一排 let buttonId = 傳入的值——只是這個動作是引擎自動幫你做的，不用你寫關鍵字。

(b) 參數名稱符不符合 Identifier 的文法定義？——符合

照 ECMAScript 文法一路展開：FormalParameter → BindingElement → SingleNameBinding → BindingIdentifier Initializer(opt) → BindingIdentifier → Identifier。
也就是說參數名稱在文法上就是一個 Identifier production，跟你寫 let x、const y 的 x、y 是同一種文法節點，必須遵守一樣的規則（不能是保留字、不能用數字開頭等）。這點跟「宣告位置不符合 Identifier 定義」的猜測相反——參數位置的名稱在文法上是正牌 Identifier，只是它被「誰來初始化、什麼時候初始化」這件事跟一般變數宣告不同（由呼叫時傳入的引數決定，而不是你在等號右邊手寫的值）。

(c) 名稱是不是「具備唯一性」？——規格其實沒有全面保障，這是歷史包袱

這是三點裡最違反直覺的地方：同一個參數列表裡出現重複名稱，不一定會報錯，要看兩個條件——是否為 strict mode、參數列表是不是「simple（簡單）」。

情境 重複參數名稱（例：function f(a, a)）
非 strict mode ＋ 簡單參數列表（沒有 default 值／rest／解構） ✅ 允許，不報錯（舊時代遺留行為，最後一個同名參數的值生效）
strict mode（不論參數列表型態） ❌ SyntaxError: duplicate formal argument
非 simple 參數列表（用了 default 值／rest／解構，即使沒開 strict mode） ❌ SyntaxError: duplicate argument names not allowed in this context 
function add(a, a) { return a; }
add(1, 2); // 2　（沒開 strict、也是簡單參數列表 → 合法，等同覆寫）

"use strict";
function add2(a, a) {} // SyntaxError（strict mode 一律禁止重複）

function add3(a, a = 1) {} // SyntaxError（有 default 值 → 非 simple 參數列表，即使沒宣告 strict）

function add4(name, { name }) {} // SyntaxError（解構參數 → 非 simple 參數列表）

「簡單參數列表」的精確定義（每個參數都是純 Identifier，只要有一個帶 default／rest／解構，整份列表就降級為非簡單）、以及這個判定同時如何影響 arguments 物件是 mapped 還是 unmapped、能不能在函式體內寫 "use strict"，完整展開見 [[函式呼叫核心機制-Execution-Context-與-Parameter-Binding]] 的 (e) 節。

[!tip] 三點合併結論
參數名稱「是」真宣告（引擎在呼叫當下真的建立綁定並初始化），也「是」文法上正牌的 Identifier；但「唯一性」不是被規格無條件保障的東西——只有 strict mode 或用了 default／rest／解構這些「非簡單參數列表」語法時，規格才會在解析階段（Early Error）直接擋掉重複名稱；舊時代 sloppy mode 搭配簡單參數列表則是刻意保留的歷史相容行為，才會讓人感覺「好像沒有真的唯一性」。

(d) Early Error 完整定義：跟「靜態檢查」是什麼關係？

承接上面 duplicate formal argument 這個具體例子，往上一層看：Early Error（早期錯誤）是 ECMAScript 規範裡定義的「引擎內建靜態檢查機制」，而「靜態檢查」是更大的概念，兩者是包含關係，不是同一件事。

  • Early Error：專指程式碼在解析（Parsing）與編譯階段就被 JS 引擎（V8／SpiderMonkey…）捕捉到的錯誤。一旦抓到，整段 Script／Module 完全不會被執行，連第一行都不會跑，try...catch 也攔不到。上面的 function add(a, a) 在 strict mode 下報錯，就是 Early Error 的具體案例。
  • 廣義靜態檢查：泛指「不實際執行程式碼」就分析程式碼結構的過程，除了引擎的 Early Error 之外，還包含 TypeScript 的型別檢查（編譯階段）、ESLint 這類 Linter（潛在邏輯漏洞、風格規範）。
比較維度 Early Error（早期錯誤） 廣義靜態檢查
定義來源 ECMAScript 語言規範本身 開發工具／編譯器（TS／ESLint）或語言規範
執行主體 JS 執行引擎（V8、SpiderMonkey…） IDE、建置工具鏈或引擎 Parser
檢查範圍 語法結構、規範明定的語意約束 型別安全、程式碼品質、潛在 Bug、風格
阻擋機制 引擎直接拒絕執行，程式完全無法啟動 工具拋出 Warning／Error，阻止 Build 或 CI/CD

一句話：Early Error 是語言引擎實作靜態檢查裡最底層、最基礎的一塊；TypeScript／ESLint 則是把檢查再往前推到開發階段（Dev/Build Time），兩者共同的核心價值都是「錯誤越早發現、修復成本越低」。跟本篇主題的關聯：與 [[06-靜態檢查vs動態檢查-TS-vs-JS]] 對照著看——那篇談的是 TypeScript 靜態型別 vs JS TypeError 動態檢查的分界；這裡補上的是「JS 自己内建的 Early Error，本身就是最底層的靜態檢查」這一塊拼圖。

延伸提問：閉包是不是微任務？算不算非同步任務？

都不是。 閉包（Closure）是同步、結構性的語言機制，跟微任務／巨任務（[[事件循環-Event-Loop-微任務與巨任務]] 講的那套 Event Loop 排程）是完全不同層次的東西，只是很容易因為常出現在同一段程式碼裡而被搞混。

閉包 Closure 微任務／巨任務 Microtask／Macrotask
屬於哪個層次 作用域／記憶體機制——這個函式能看到哪些變數、那些變數要活多久 任務排程機制——這段程式碼什麼時候被排進 [[事件循環-Event-Loop-微任務與巨任務|Call Stack]] 執行
何時決定 詞法範疇（Lexical Scope）在程式碼寫下的那一刻就決定了 Event Loop 在執行期依任務種類（Promise.then／setTimeout…）決定執行順序
需要非同步才成立嗎 不需要——100% 同步的程式碼裡照樣有閉包 定義上就是非同步概念，一定跟「等 Call Stack 清空才執行」綁在一起

鐵證：本篇最開頭的 createCounter() 範例（見上面「應用：用閉包做私有變數」），從頭到尾沒有一行 setTimeout 或 Promise，整段都是同步執行，但 count 照樣被閉包鎖住成為私有變數——證明閉包完全不需要非同步就能存在。

為什麼容易搞混：經典面試題（for 迴圈 + setTimeout）裡，那個傳給 setTimeout 的 callback 函式剛好同時身兼兩個身分：① 它是一個閉包（捕獲了外層的 i）；② 它被排進了巨任務佇列，等 Call Stack 清空才執行。這兩件事發生在同一個函式身上，容易誤以為是同一套機制在運作。拆開看就很清楚：

  • 這個 callback 之所以「記得」外層的 i → 這是閉包的功勞（不管它是不是非同步都成立，把 setTimeout 拿掉、直接同步呼叫這個函式，它一樣記得 i）。
  • 這個 callback「什麼時候」真的被丟進 Call Stack 執行 → 由 Event Loop 依照它是巨任務（setTimeout）還是微任務（Promise.then）決定，跟它有沒有捕獲外層變數完全無關。

反過來也成立：一個被 setTimeout 排程的非同步 callback，不一定是閉包——如果它完全沒有引用任何外層變數（例如 setTimeout(() => console.log('hi'), 1000)），就只是個普通函式，談不上「捕獲外部變數」這件事，一般不會特別稱它為閉包。

一句話總結：閉包回答的是「這個函式看得到誰、記得誰」；微任務／巨任務回答的是「這個函式什麼時候被排進去跑」——兩支箭完全不同方向，只是常常同時射在同一個函式身上。

C++ 也有閉包嗎？（對比）

有，C++11 起用 Lambda 表達式引入：[捕捉列表](參數) { 函式本體 }。最大差別：JS 閉包自動發生且靠 GC 保命；C++ 沒有 GC，必須明確寫出要捕捉哪些變數。

特性 JavaScript 閉包 C++ Lambda
觸發方式 自動（內層引用外層即觸發） 必須明寫在捕捉列表 [...]
記憶體管理 靠 GC 自動保留 開發者手動管理，注意 Stack 存活期
底層實現 範疇鏈 + 環境物件 編譯器產生的匿名仿函式（Functor）
  • 傳值捕捉 [count]：建立當下複製數值進閉包，外層銷毀也安全。
  • 引用捕捉 [&money]：像 JS 一樣能改外部變數，但回傳引用捕捉的 Stack 變數會造成懸空引用（Dangling Reference），觸發未定義行為甚至 Crash。
