重點整理

a. JS 變數本質是抽象指標：JS 引擎自動處理記憶體配置與管理，開發者看不到、也不能像 C 語言那樣直接操作實體位址；「指標」在這裡是幫助理解的抽象概念，不是語言規格中可觀察的具體實作細節。

b. ⚠️ 存疑：Gemini 原話「數字變成 5 之後，指標會轉向記憶體中存放 5 的新位置，而非直接覆蓋」，這個說法把物件（object）的傳址概念套用到基本型別（number）上；嚴謹來說 ECMAScript 規格並未定義 primitive 有可觀察的「指標指向新位置」語意，這只是引擎實作細節的簡化比喻，詳見與 [[10-傳值vs傳址-賦值與記憶體空間]] 對照，primitive 的正規理解是「開闢新的獨立記憶體、複製值過去」，不是「指標轉向」。

c. 全域變數 vs 區域變數的回收時機差異：函式內的區域變數（基本型別）會隨著 call stack 的 stack frame pop 而自動釋放；全域變數不屬於任何 stack frame，只要沒被切斷參照，理論上會一直存活到「應用程式生命週期結束」（網頁：分頁或瀏覽器關閉；Node.js：process 結束）。

d. GC 回收的唯一依據是「可達性 Reachability」，不是「有沒有被使用」：瀏覽器環境中 window（全域物件）是 GC Root；只要一個變數能從 GC Root 沿著參照鏈（Reference Chain）找到，就是 Reachable，GC 絕對不會回收它——即使這個變數「很久沒被用到」也一樣，因為「沒被使用」與「不可達」是兩件不同的事。

e. 看似矛盾的兩句話，其實描述兩個不同情境：①「全域變數會在應用程式結束後才被回收」——指一般仍被 window 參照著的全域變數，window -> myGlobal 這條參照鏈只要頁面不關閉就一直存在，GC 永遠不會碰它；②「全域變數會留在 heap 中等待垃圾回收」——指變數被手動切斷參照之後（例如 myGlobal = null），物件與 GC Root 的連結斷開、變成 Unreachable，才會「留在 heap 裡等 GC 下次觸發時被真正掃描回收」（不是切斷的瞬間就立刻釋放）。

f. React 組件 unmount 不會回收全域變數：全域變數掛在 window（全域範圍），不屬於任何特定組件；組件 unmount 只會清理該組件自己的資源（例如 useEffect 的 cleanup），完全不會影響 window 上的全域變數，它會繼續佔用記憶體直到應用程式結束或被手動切斷參照。

g. 全域物件（Global Object）在不同環境的名稱：瀏覽器環境是 window（document 是 window 的屬性，即 window.document，代表整份 HTML 文件/DOM）；Node.js 後端環境是 global；現代 JavaScript 統一提供 globalThis，可以跨瀏覽器/Node.js 環境存取全域物件。

h. ⚠️ 存疑：Gemini 把 GC 演算法簡化描述為單一的「Mark-and-Sweep（標記清除）」，這是主流演算法之一、方向正確，但實務上 V8 等現代引擎採用更複雜的分代式 GC（Generational GC，新生代 Scavenge + 老生代 Mark-Sweep-Compact 等組合），Gemini 的說法是簡化版，理解核心概念（可達性判斷）沒問題，但不宜直接當作 V8 實作的精確描述。
