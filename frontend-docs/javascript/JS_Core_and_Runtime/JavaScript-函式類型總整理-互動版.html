軸①：宣告 vs 表達式

1-1 三個名詞的層級關係

名詞規範裡的對應層級一句話
實例化 instantiationFunctionDeclarationInstantiation整個流程（容器）進入作用域時，把所有名字一次整批安頓好的那個步驟
① 建立綁定 declareCreateMutableBinding流程裡的一個動作在 Environment Record 裡登記名字，還沒有值
② 初始化 initializationInitializeBinding流程裡的一個動作讓某一個綁定拿到第一個值
③ 賦值 assignmentSetMutableBinding已經不在那個流程裡後來改掉已經有值的綁定

instantiation 是「整場開學典禮」，initialization 是「幫某一個學生把課本發下去」。一場典禮會發很多次課本，也可以刻意跳過某幾個——那就是 TDZ。

函式物件還沒被建立，算哪一種

算 沒被初始化，不算沒被實例化。實例化已經做完了，它只是被刻意跳過了 InitializeBinding。
TDZ 的定義就是「實例化做完了、初始化還沒做」的那段空窗。

1-2 每一步在哪一個 Phase

步驟function foo(){}var foo = fnlet／const foo = fn
① 建立綁定CreationCreationCreation
② 初始化Creation，函式物件Creation，undefinedExecution，跑到那一行
①②之間有空窗嗎沒有沒有有，＝TDZ
③ 賦值不需要Execution不需要，②就是拿到函式物件那一刻
  1. 「函式物件在哪個 Phase 被做出來」才是真正的分界。函式宣告在 Creation Phase 就做好（InstantiateFunctionObject）；函式表達式的 = 右邊是表達式，只在 Execution Phase 才被求值。
  2. 賦值不屬於 instantiation。instantiation 在 Creation Phase 就收工了。
  3. 函式宣告只有①②，沒有③。兩步都在 Creation Phase，中間不換格。

設計意圖：let／const 刻意保留 TDZ，就是要把「用在宣告之前」從 var 那種安靜的 undefined 升級成大聲的 ReferenceError。安靜的錯會一路傳到很遠才爆，大聲的錯當場就停。

1-4 所以實務上該怎麼呼叫

// ✅ 函式宣告：兩個位置都可以
processProducts()
function processProducts() { console.log('成功') }
processProducts()

// ❌ 函式表達式：宣告之前不行
processProducts()                                  // ReferenceError
const processProducts = function () { console.log('成功') }

// ✅ 函式表達式：一定要在下面
const processProducts2 = function () { console.log('成功') }
processProducts2()
一條不用背規則的實務準則
不管哪一種，一律寫成「先定義、後呼叫」。這樣兩種寫法行為完全一致，你不需要在腦中維護「這個能提前、那個不行」這張表。

唯一真的需要用到「宣告可以提前呼叫」的場合，是互相遞迴的兩個函式（A 呼叫 B、B 也呼叫 A），那時函式宣告才有不可取代的價值。

軸②：具名 vs 匿名

  • 具名：function foo(){}、const a = function bar(){}
  • 匿名：function(){}（沒名字）。「不具名」＝「匿名」，只是中文翻譯不同。
為什麼沒有「匿名函式宣告」
因為函式宣告語法的 function 一定要有名字，function(){} 單獨寫直接 SyntaxError。所以匿名只能長在函式表達式上。
四種組合：具名宣告 ✅、匿名宣告 ❌、匿名表達式 ✅、具名表達式 ✅。

具名函式表達式（Named Function Expression）const a = function foo(){}：名字 foo 只在函式內部可見，好處是利於自我遞迴與除錯堆疊。

軸③：箭頭 vs 非箭頭（決定 this 與 arguments）

函式類型自己的 arguments自己的 this能 new有 prototype
function foo(){}有有能有
const foo = function(){}有有能有
{ foo(){} } 物件簡寫方法有有不能沒有
const foo = () => {}沒有沒有不能沒有
function* gen(){}有有不能有
箭頭函式那一列全是「沒有」，不是四條各自獨立的規定：它的內部欄位 [[ThisMode]] 是 lexical，而規範裡同一個判斷式同時關掉了 this 綁定與 arguments 物件。它們在規格裡是同一個 if 的兩個結果。

arguments 三個必須講清楚的點

  1. 它不是保留字，是隱式區域變數／識別碼。驗證：非嚴格模式下 var arguments = 99 合法，回傳 99；真保留字 var class = 1 直接 SyntaxError。
  2. 它是類陣列物件：有 length、可索引，但沒有 push／slice／forEach／map，Array.isArray() 回 false。
  3. ES6 之後它可迭代（有 Symbol.iterator），所以 [...arguments] 就能轉成真陣列，不必再寫 Array.prototype.slice.call(arguments)。

實務上應該用 rest 參數 (...args) 取代它——拿到的是真陣列，而且箭頭函式也能用。機制細節見 09-Hoisting-函式宣告vs函式表達式-TDZ。

軸④：一般 vs Generator vs Constructor

  • Generator function* gen(){}：* 只改「怎麼被呼叫、回傳什麼」。gen() 不會執行任何一行函式本體，只回傳一個 iterator；第一次 .next() 才真的跑到第一個 yield。
    yield：產出一個值並「暫停」，下次 .next() 從這裡繼續。return：直接結束（done: true）。
  • Constructor 函式：用 new 呼叫、慣例首字大寫，用來產生物件實例。

這條軸跟軸①、軸③互不干涉——Generator 一樣有宣告與表達式兩種寫法，一樣有自己的 this 與 arguments。

自我測驗：申論題

Q1　同事說「函式表達式不會 hoisting」，你要怎麼更正他，而且說明為什麼 TDZ 反而是提升的證據？
參考答案

更正：三種寫法的綁定全部都會在 Creation Phase 建立，差別在初始化被往後挪多遠。沒被提升的不是名字，是值。

TDZ 是證據的理由：如果 const foo 的名字真的沒被登記，提前碰它應該得到 foo is not defined（名字不存在）。但實際上得到的是 Cannot access 'foo' before initialization——引擎知道有這個名字，才有辦法分辨這兩種情況。更強的證據是 typeof：它對完全不存在的名字會安靜地回 'undefined'，卻擋不住 TDZ。

Q2　為什麼說「宣告 vs 表達式」完全不影響 this？請舉例。
參考答案

因為 this 由軸③（箭頭 vs 非箭頭）決定，軸①只決定綁定何時被初始化。

function foo(){ return this } 與 const foo = function(){ return this } 的 this 行為完全相同——兩者都在每次呼叫時依「誰點它」重新決定。差別只在前者能提前呼叫。

反過來，const foo = () => this 跟 const foo = function(){ return this } 同樣都是「表達式 ＋ const」，軸①一模一樣，this 行為卻天差地遠：箭頭版在求值那一刻把外層 this 定死，call／apply／bind 都改不動它。

Q3　什麼情況下你會刻意選用「函式宣告」而不是 const ＋ 函式表達式？
參考答案

互相遞迴是唯一真的不可取代的場合：A 呼叫 B、B 也呼叫 A，寫成 const 的話一定有一個會落在另一個的 TDZ 裡。函式宣告因為在 Creation Phase 就完整就緒，兩個互相參照沒有先後問題。

其他常見理由是可讀性偏好——把主要流程寫在檔案上方、輔助函式寫在下方，靠宣告的提升讓閱讀順序符合思考順序。但這是團隊風格選擇，不是技術必要。

反方意見也要知道：一律用 const 的好處是所有函式行為一致、不用記例外，而且 const 擋掉了不小心重新賦值。多數現代 style guide 傾向後者。
