一、三個名詞的層級關係

這一節之所以難，是因為「實例化 instantiation」「初始化 initialization」「賦值 assignment」被當成同義詞在用，其實它們是一個容器裝著兩個動作的關係。

實例化 instantiation 規範對應：FunctionDeclarationInstantiation
層級：整個流程（容器）
進入一個作用域時，把這個作用域裡所有名字一次整批安頓好的那個步驟。
① 建立綁定 declare 規範對應：CreateMutableBinding／CreateImmutableBinding
層級：流程裡的一個動作
在 Environment Record 裡登記這個名字，但還沒有值。
② 初始化 initialization 規範對應：InitializeBinding
層級：流程裡的一個動作
讓某一個綁定拿到它的第一個值。
③ 賦值 assignment 規範對應：SetMutableBinding
層級：已經不在那個流程裡了
後來改掉已經有值的綁定。
instantiation 是「整場開學典禮」，initialization 是「幫某一個學生把課本發下去」。 一場典禮會發很多次課本，也可以刻意跳過某幾個學生不發——那就是 TDZ。
所以「函式物件還沒被建立」算哪一種

算 沒被初始化，不算沒被實例化。

實例化已經做完了——進入作用域時那一整批流程早就跑完，foo 這個名字已經被登記進 Environment Record 了。 它只是在那個流程裡被刻意跳過了 InitializeBinding 這一步。

TDZ 的定義就是「實例化做完了、初始化還沒做」的那段空窗。

二、每一步發生在哪一個 Phase

步驟function foo(){}var foo = fnlet／const foo = fn

② 初始化（拿到第一個值）Creation，值＝完整函式物件Creation，值＝undefinedExecution，跑到那一行才做
①②之間有沒有空窗沒有沒有有，這段就是 TDZ
③ 賦值不需要，①②就結束Execution，跑到那一行不需要，②就是拿到函式物件的那一刻

三個必須記住的結論

  1. 「函式物件在哪個 Phase 被做出來」才是宣告與表達式的真正分界
    函式宣告的函式物件在 Creation Phase 就被建立（規範的 InstantiateFunctionObject），所以提前呼叫沒問題。
    函式表達式右邊那個 function(){} 是一個表達式，而表達式只在 Execution Phase 逐行執行時才會被求值。Creation Phase 只建綁定，不求值任何 = 右邊的東西。
  2. 賦值不屬於 instantiation
    instantiation 在 Creation Phase 就整批結束了。var foo = fn 的賦值發生在 Execution Phase，那時 instantiation 早就收工。所以「要到賦值才算完成 instantiation」是錯的。
  3. 函式宣告只有①②，沒有③
    它是一連串行雲流水沒錯，但那串是「①建立綁定 → ②初始化成函式物件」，兩步都在 Creation Phase，中間不換格，也沒有第三步在等。

var 的函式表達式：進入作用域同時就初始化了嗎

會，而且值就是 undefined。規範在 FunctionDeclarationInstantiation 裡對每個 var 名字明確做了 InitializeBinding(名字, undefined)。

所以 var 的綁定在 Creation Phase 結束時是「已宣告、已初始化、還沒賦值」——三個階段走完了兩個。

(function () {
  console.log(typeof foo)   // 'undefined'，不報錯
  console.log(foo)          // undefined，不報錯
  var foo = function () {}
})()

白話講：typeof foo 跟 console.log(foo) 都拿得到值，證明綁定存在而且有值，只是那個值是 undefined。如果它連初始化都沒做，這裡會跟 const 一樣丟 ReferenceError。

用 typeof 一秒分辨三種狀態

typeof 從來沒出現過的名字   // 'undefined'  ← 不報錯
typeof varFoo（提前）       // 'undefined'  ← 不報錯
typeof constFoo（提前）     // ReferenceError: Cannot access 'constFoo' before initialization

白話講：typeof 是 JS 裡唯一一個對「完全不存在的名字」也不報錯的運算子。但它擋不住 TDZ。

這正好反證了 TDZ 不是「不存在」：如果 constFoo 真的不存在，typeof 應該安靜地回 'undefined' 才對。它卻報錯，代表名字是存在的，只是不准碰。

四、arguments：非箭頭函式自帶的隱式綁定

這個知識點放在本篇，是因為 arguments 綁定的建立跟 hoisting 發生在同一格——都在 FunctionDeclarationInstantiation 這一步。它跟 var 一樣是「你沒寫，但引擎幫你建好的綁定」。

(a) 它不是保留字，是隱式區域變數／識別碼

保留字是 parser 層級就禁止拿來當名字的（if、return、class 那些）。arguments 不是。驗證方式：

// 非嚴格模式：合法，可以蓋掉它 —— 證明它只是一個普通識別碼
(function () { var arguments = 99; return arguments })()   // → 99

// 對照組：真保留字連當變數名都不行
var class = 1    // → SyntaxError: Unexpected token 'class'

// 嚴格模式：SyntaxError: Unexpected eval or arguments in strict mode

白話講：非嚴格模式下 var arguments = 99 把引擎建好的那個綁定重新賦值成數字，一點錯都不報。嚴格模式的 SyntaxError 是 ES5 額外加的早期錯誤 Early Error 規則，不是因為它升格成保留字。

(b) 它是類陣列物件，不是真正的 Array

arguments真陣列 Array
length 屬性有有
中括號索引存取可以可以
push／slice／forEach／map沒有有
Array.isArray()falsetrue

(c) 最後一列是多數教材漏掉的：ES6 之後可迭代

function f() {
  const 真陣列 = [...arguments]                       // ✅ 最短
  // Array.from(arguments)                            // ✅ 也可以
  // Array.prototype.slice.call(arguments)            // ES5 時代的老寫法
  return 真陣列.map(x => x * 2)
}

白話講：[...arguments] 透過 Symbol.iterator 把元素一個一個取出來，放進一個新的真陣列，之後才能直接 .map()。

(d) 形式參數與 arguments 會重疊：MDN myConcat

function myConcat(separator) {
  let result = ''
  for (let i = 1; i < arguments.length; i++) {      // ← 注意是從 1 開始
    result += arguments[i] + (i < arguments.length - 1 ? separator : '')
  }
  return result
}
myConcat(', ', 'red', 'orange', 'blue')   // → 'red, orange, blue'
值說明
separator', '具名形式參數，佔用第一個實參當佔位符
arguments[0]', '跟 separator 是同一個實參，不是另一個
arguments[1..3]'red' 'orange' 'blue'
arguments.length4實參個數，不是形參個數（形參只有 1 個）

迴圈從 i = 1 開始，正是因為索引 0 那一格已經被 separator 拿去當分隔符了。

(e) 但現在不該這樣寫

const myConcat = (separator, ...items) => items.join(separator)

白話講：...items 把第一個之後的所有實參收集成一個真陣列，連迴圈都不用寫。arguments 現在的價值只剩「讀得懂舊程式碼」。

(f) 箭頭函式完全沒有這個綁定
它在 FunctionDeclarationInstantiation 那一步就被跳過了，原因是箭頭函式的內部欄位 [[ThisMode]] 是 lexical——同一個判斷同時關掉了 this 與 arguments。它們在規格裡是同一個 if 的兩個結果。

自我測驗：申論題

Q1　用你自己的話說明「實例化」與「初始化」的差別，並回答：const foo = function(){} 在 TDZ 裡時，是哪一個沒做完？
參考答案

實例化（instantiation）是進入作用域時把整個作用域的所有名字一次安頓好的整個流程，規範裡叫 FunctionDeclarationInstantiation。初始化（initialization）是那個流程裡的一個動作（InitializeBinding），讓某一個綁定拿到第一個值。兩者是包含關係，不是同義詞。

所以 const foo 在 TDZ 裡時，實例化已經做完了（名字已經登記進 Environment Record，不然引擎不會知道要丟 TDZ 的錯而是丟 foo is not defined），沒做完的是初始化——那個 InitializeBinding 被刻意延後到執行到宣告那一行才做。

Q2　為什麼函式宣告可以提前呼叫，函式表達式不行？請從「函式物件在哪個 Phase 被建立」回答，不要只說「因為會提升」。
參考答案

兩者的綁定都在 Creation Phase 建立，所以「會不會提升」不是分界線。真正的分界是函式物件在哪一格被做出來。

函式宣告是一個宣告，引擎在 Creation Phase 執行 InstantiateFunctionObject 把函式物件做出來並直接綁上去，所以那一刻它就已經是可呼叫的函式了。

函式表達式的 = 右邊是一個表達式，而表達式只在 Execution Phase 逐行執行時才會被求值。Creation Phase 只建綁定，不求值任何 = 右邊的東西，所以那個函式物件在提前呼叫的當下根本還不存在。

Q3　var foo = function(){} 提前呼叫是 TypeError，const 版本是 ReferenceError。請說明這個差別的根本原因。
參考答案

差在初始化的時機。var 在 Creation Phase 就被 InitializeBinding(foo, undefined) 初始化了，所以綁定有值——讀它拿到 undefined，完全不報錯；只有當你把 undefined 當函式呼叫時，才因為「值的型別不支援呼叫」丟 TypeError。

const／let 的初始化被延後到執行到宣告那一行，在那之前綁定連值都還沒有，所以引擎在識別碼解析時就直接擋下來丟 ReferenceError，讀、typeof、呼叫全部一視同仁。

一句話：ReferenceError 是名字這一關過不了，TypeError 是名字過了、值的型別不對。
