重點整理

一、核心差異：控制對象不同（a–c）

(a)兩者的核心差異是「算位數的起點不同」：toFixed(n) 控制小數點後的位數，起點固定在小數點 . 之後，適合貨幣、金額、百分比這種「一定要顯示到小數後幾位」的場景；toPrecision(n) 控制整體的有效數字，起點是從第一個非 0 的數字開始算，適合科學計算、測量數據這種要求整體精確度的場景。

const num = 123.4567;

// toFixed：規定「小數點後面要留幾位」
num.toFixed(2);      // "123.46"（小數點後留 2 位，四捨五入）
num.toFixed(0);      // "123"（只留整數）

// toPrecision：規定「整串數字一共要留幾位有效數字」
num.toPrecision(2);  // "1.2e+2"（總共只要 2 位，整數放不下就轉科學記號）
num.toPrecision(4);  // "123.5"（從頭數 4 位：1,2,3,5）

(b)「toPrecision 不處理小數點後面的位數」是常見誤解：它一樣會處理小數，只是算盤從最左邊（第一個非 0 數字）開始數，而不是從小數點開始數。

(12.3456).toPrecision(4); // "12.35" —— 4 位有效數字：1,2,3,5，小數點後留了 2 位
(12.3456).toPrecision(2); // "12"    —— 只要 2 位：1,2，小數點後全部捨棄

(c)單字記憶法：toFixed 對應英文 Fixed point（定點數），相對於 Floating point（浮點，小數點位置會「浮動」），Fixed 就是把小數點「釘死」在某個位置，後面只准留 n 位（如 toFixed(2) 固定留 2 位，像 $10.50）。toPrecision 對應英文 Precision（精確度）：不管數字多大多小，只要求前 n 位最有價值的數字。

二、四捨五入為什麼會「跟想像的不一樣」（d–h）

(d)根本原因：JavaScript 用 IEEE 754 雙精度浮點數（64-bit）儲存所有數字。許多十進位小數轉成二進位後會變成無限循環小數，電腦只能在邊界截斷，因而產生微小的精度偏差（Precision Error）。toFixed()／toPrecision() 處理的其實是已經被二進位微幅調整過的近似值，不是你輸入的十進位原始數字。

(e)經典陷阱：(1.005).toFixed(2) 不是 "1.01" 而是 "1.00"：

(1.005).toFixed(2);        // "1.00" —— 不是直覺的 "1.01"！
(1.005).toPrecision(20);   // "1.0049999999999998934" —— 這才是它在記憶體裡的真實值

因為二進位無法精確表達 0.005，實際存的是 1.00499999999999989...。toFixed(2) 四捨五入時看的是小數點後第 3 位——是 4（小於 5），所以被捨去，結果變成 "1.00"。對照組 (1.015).toFixed(2) 因為實際存的是 1.0150000000000001243（比 1.015 微幅偏大），結果就如預期是 "1.02"。

(f)除了二進位表示誤差，規範本身的捨入定義也會影響結果：(1.25).toPrecision(2) 是 "1.3"（正常進位），因為 1.25 剛好能被二進位精確表示；一旦數字無法被精確表示，結果就取決於誤差是微幅偏大還是偏小。

(g)解法：不要在金融／帳務場景直接依賴原生 toFixed()。三種修正方式：

  1. 改用最小單位整數儲存——把金額換算成「分／角」再計算，避開小數點（例如 $1.05 存成整數 105 分）。
  2. 指數修正技巧（Exponential Correction）——利用科學記號把小數點暫時往右移，四捨五入完再移回來：
function safeRound(num, decimalPlaces) {
  const factor = Math.pow(10, decimalPlaces);
  return (Math.round(Number(num + "e" + decimalPlaces)) / factor).toFixed(decimalPlaces);
}
safeRound(1.005, 2); // "1.01" —— 正確修正
  1. 改用任意精度（Arbitrary-precision）套件——big.js（輕量，適合金融金額）、decimal.js（功能更完整）、bignumber.js。

(h)toPrecision(20) 是很好用的偵錯技巧：把精度拉到 20 位，直接看某個小數在記憶體裡「真正」被存成什麼樣子，可以用來驗證浮點數誤差是否是結果不如預期的原因。

三、科學記號 vs. 一般小數：toPrecision 怎麼決定要不要展開（i–l）

(i)toPrecision() 的設計目標是「優先給人類閱讀」，不是每種情況都硬輸出科學記號。引擎算出標準科學記號後，會依規則二選一：直接展開成一般小數，或維持科學記號。

(j)判斷條件 1：展開成一般小數會不會「失真」。123.4567.toPrecision(2) 的科學記號是 1.2×10²，展開成一般數字是 120——但 120 看起來像 3 位有效數字，跟要求的「2 位」語意不符，不允許展開，強制用 "1.2e+2"。toPrecision(4) 的科學記號是 1.235×10²，展開是 123.5，剛好 4 位有效數字（1,2,3,5）完全不失真，允許展開為 "123.5"。

(k)判斷條件 2：指數 e 是否落在 −6 ≤ e < n 的可讀範圍內。只要指數在這個舒適區內、且展開不失真，就優先展開成一般小數（123.5 比 1.235e+2 直覺）。

123.4567.toPrecision(2)
└─► 標準科學記號：1.2 × 10²
   ├─► 嘗試展開：120（無法精準表達 2 位有效數字 ❌）
   └─► 最終輸出："1.2e+2"

123.4567.toPrecision(4)
└─► 標準科學記號：1.235 × 10²
   ├─► 嘗試展開：123.5（剛好完美符合 4 位有效數字 ✔️）
   └─► 最終輸出："123.5"

(l)小數點的位置不是固定在「倒數第一位」，純粹取決於原數字的數量級與要求的有效位數 n。舉例（皆要求 4 位有效數字）：(0.123456).toPrecision(4) → "0.1235"（4 位全在小數點後）；(1234.56).toPrecision(4) → "1235"（展開後剛好是整數，連小數點都不用寫）。規則就是：先數出前 n 個有效數字，再把小數點「放回原本的數量級位置」。
