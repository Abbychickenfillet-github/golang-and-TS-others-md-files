1. Set.prototype 到底是什麼（a–e）

一句話Set.prototype 是一個普通物件，它是所有 new Set() 產出的實例共用的那一份「母版」。

↓ 黃色色塊點一下顯示答案

  • (a) Set 是建構函式，Set.prototype 是掛在它身上的一個屬性，值是一個物件。
    typeof Set 得到 "function"，typeof Set.prototype 得到 "object"。
  • (b) 每次執行 new Set()，引擎會建一個新實例，並把它的 [[Prototype]] 指向 Set.prototype。
    所以 Object.getPrototypeOf(new Set()) === Set.prototype 是 true。
  • (c) .add()、.has()、.size 這些都不在實例身上，它們住在 Set.prototype 上。
    呼叫 mySet.add(1) 時，引擎在 mySet 身上找不到 add，沿 [[Prototype]] 往上一階找到 Set.prototype.add，再以 this = mySet 呼叫它。
  • (d) ★ MDN 那句 Allows the addition of properties to all Set objects 的意思是：往 Set.prototype 上塞屬性，所有已建好的、以及未來才建的 Set 實例都立刻拿得到。
    關鍵是查找是動態的，不是建立實例時把方法複製一份給它，所以「先建實例、後補方法」也照樣生效。
  • (e) Set.prototype 自己也是物件，所以它自己也有原型：Object.getPrototypeOf(Set.prototype) === Object.prototype，完整鏈是 mySet → Set.prototype → Object.prototype → null，共 三 階。
const mySet = new Set([1, 2, 3]);

Object.getPrototypeOf(mySet) === Set.prototype;             // true
Object.getPrototypeOf(Set.prototype) === Object.prototype;  // true
Object.getPrototypeOf(Object.prototype);                    // null

// 「後補的方法」舊實例也吃得到 —— 這就是 (d) 那句話的意思
Set.prototype.isEmpty = function () { return this.size === 0; };
mySet.isEmpty();     // false（mySet 比這個方法早出生）

2. JavaScript 沒有 Set 字面量（f–i）

  • (f) Abby 的判斷是對的：JavaScript 確實沒有 set literal。
  • (g) JS 只保留兩種集合類字面量：{} 是物件字面量，[] 是陣列字面量。
    {1, 2, 3} 在 JS 裡是 SyntaxError，因為 { 開頭會被當成物件字面量或區塊，裡面必須是 key: value。
  • (h) Python 才有 set literal（{1, 2, 3}），所以從 Python 過來的人最容易卡在這裡。
  • (i) 建立 Set 的唯一途徑是 new Set(iterable)，而且 new 不能省略，省略會丟 TypeError: Constructor Set requires 'new'。

3. Symbol.toStringTag：為什麼講它要扯到 Object.prototype.toString()（j–n）

Abby 的原問題：「這邊為何要提及 Set 的原型是物件？」 因為這個機制同時用到原型鏈的兩端：toString 這個方法是從 Object.prototype 繼承下來的，而標籤 "Set" 是掛在 Set.prototype 上的。少講任何一端，這句 MDN 都讀不通。
  • (j) typeof 對所有物件一律回傳 "object"，它分不出 Set、Map、Array、Date 的差別。
  • (k) 要精準辨型時，老派做法是呼叫 Object.prototype.toString.call(x)，拿到 "[object Xxx]" 這種字串。
  • (l) 內部流程是：先做特例判斷（null、undefined、array、function 等）→ 沿原型鏈讀 x[Symbol.toStringTag] → 讀到字串就當標籤，讀不到就退回 "Object"（對照主軸圖右欄）。
  • (m) ★ Set.prototype[Symbol.toStringTag] 的初始值被規格訂為字串 "Set"，屬性特性是 writable: false, enumerable: false, configurable: true。
    所以 Object.prototype.toString.call(new Set()) 會回 "[object Set]"。標籤是掛在 Set.prototype 上，實例是繼承到它的。
  • (n) 自己寫的 class 也能設這個標籤，Object.prototype.toString 一樣會讀到。
const s = new Set([1, 2]);

typeof s;                                    // "object"  ← 分不出來
Object.prototype.toString.call(s);           // "[object Set]"

Object.hasOwn(s, Symbol.toStringTag);              // false ← 實例身上沒有
Object.hasOwn(Set.prototype, Symbol.toStringTag);  // true  ← 住在原型上
Set.prototype[Symbol.toStringTag];                 // "Set"

class Wallet { get [Symbol.toStringTag]() { return "Wallet"; } }
Object.prototype.toString.call(new Wallet());      // "[object Wallet]"
兩次原型鏈查找，停的樓層不同 第一次往上：s 沒有 toString → Set.prototype 也沒有 → 走到 Object.prototype.toString，找到方法。
第二次往上：進到方法內部後讀 this[Symbol.toStringTag]，s 沒有 → Set.prototype 有，值是 "Set"，找到標籤。

5. ⚠️ 為什麼「擴充內建原型」是紅色警告（s–v）

語法上做得到，工程上不要做這個行為有個專有名詞叫 monkey patching。
  • (s) 直接賦值加上去的屬性是可列舉的，for...in 會把它一起撈出來。若真的非加不可，一定要用 Object.defineProperty(..., { enumerable: false })。
  • (t) ★ 撞名會讓別人的網站整個掛掉，而且歷史上真的發生過：
    TC39 原本要把陣列攤平的方法命名為 Array.prototype.flatten，但 MooTools 早就自己 patch 了同名方法，瀏覽器一上線就讓一票網站爆掉。最後規格改名成 Array.prototype.flat 閃開，這件事被叫做 SmooshGate（2018）。
  • (u) 引擎最佳化會失效：V8 為「沒被動過的內建原型」走快速路徑，一旦你改了 Set.prototype，相關的 Inline Cache 與 ValidityCell 會被作廢。
  • (v) 現代替代方案：寫成普通函式 first(arr)、寫成工具模組、或用 class MySet extends Set 繼承出子類別，都不會動到全域。
順帶一提：現在 Set 已經有原生集合運算了，不用自己 patch union()、intersection()、difference()、symmetricDifference()、isSubsetOf()、isSupersetOf()、isDisjointFrom() 七個方法自 2024 年 6 月起成為 Baseline 2024。
它們接受任何 set-like 物件當參數（只要有 size 屬性、has() 方法、keys() 方法），但 this 必須是真正的 Set 實例。
const evens = new Set([2, 4, 6, 8]);
const squares = new Set([1, 4, 9]);
evens.union(squares);          // Set(6) { 2, 4, 6, 8, 1, 9 }
evens.intersection(squares);   // Set(1) { 4 }

自己考自己 ①　是非題

1. Set.prototype 是一個函式。
✗ 錯。typeof Set 才是 "function"，typeof Set.prototype 是 "object"。它是一個普通物件。
2. 先建好的 Set 實例，也吃得到之後才補到 Set.prototype 上的方法。
✓ 對。原型查找是執行當下才往上走的動態行為，不是建立實例時複製一份方法給它。
3. {1, 2, 3} 在 JavaScript 裡會建出一個 Set。
✗ 錯。那是 Python 的語法。JS 沒有 set literal，{1, 2, 3} 會丟 SyntaxError，只能寫 new Set([1, 2, 3])。
4. Symbol.toStringTag 這個屬性是掛在每個 Set 實例身上的。
✗ 錯。它掛在 Set.prototype 上，實例是繼承到它的。驗證：Object.hasOwn(new Set(), Symbol.toStringTag) 是 false。
5. Object.prototype.toString 這個方法，跟 "Set" 這個標籤，住在原型鏈的不同樓層。
✓ 對。方法住 Object.prototype，標籤住 Set.prototype。這正是「為何要提及 Set 的原型是物件」的答案。
6. 用 Array.prototype.xxx = fn 擴充內建原型是標準且推薦的做法。
✗ 錯。那叫 monkey patching：會被 for...in 撈到、會撞名（SmooshGate）、會讓 V8 最佳化失效。要擴充就 class MySet extends Set。
7. evens.union(squares) 的參數可以不是真正的 Set，但 evens 本身必須是。
✓ 對。參數只要是 set-like（有 size、has()、keys()）就行，但 this 必須是真正的 Set 實例，因為它直接讀底層資料而不呼叫使用者程式碼。

自己考自己 ②　申論題

Q1. 用原型鏈解釋：為什麼 typeof new Set() 得到 "object"，但 Object.prototype.toString.call(new Set()) 得到 "[object Set]"？
參考答案： typeof 是語言層級的運算子，它只看值的內部型別分類，所有非函式的物件一律回 "object"，它根本不看原型鏈。
Object.prototype.toString.call(x) 則走了兩次原型鏈查找：第一次從實例往上找 toString 這個方法，一路走到 Object.prototype 才找到；第二次在方法內部讀 this[Symbol.toStringTag] 這個標籤，在 Set.prototype 這一層就讀到字串 "Set"，於是拼成 "[object Set]"。
所以差別是：typeof 不查原型鏈，toString 查了兩趟且停在不同樓層。
Q2. 同事想加一個 Set.prototype.isEmpty()，說「很方便啊，全專案都能用」。請寫出你會提出的三個反對理由，以及一個替代方案。
參考答案： 理由一（列舉汙染）：直接賦值的屬性 enumerable 預設為 true，任何 for...in 都會多撈到它，遍歷行為被悄悄改掉。
理由二（撞名）：未來 TC39 若把同名方法標準化，語意不一致就會炸；SmooshGate 就是真實案例，最後是規格被迫改名成 flat。
理由三（效能）：V8 對未被修改的內建原型有快速路徑，patch 之後相關 Inline Cache 的 ValidityCell 被作廢，全專案的 Set 操作都變慢。
替代方案：寫成普通工具函式 isEmpty(set)，或 class MySet extends Set { isEmpty() { return this.size === 0; } }，作用域只限自己的型別，不動全域。
Q3. 為什麼 JavaScript 沒有 Set 字面量？如果今天 TC39 想補一個，會遇到什麼困難？
參考答案： 歷史原因是 {} 在 JS 誕生時就被物件字面量佔走了，而 Set 遲至 ES2015 才進語言，沒有可用的括號符號可以配。
困難在於 JS 的語法必須向後相容：{ 開頭在陳述式位置會被 parse 成 block、在表達式位置會被 parse 成物件字面量，任何新的 {1, 2, 3} 語意都得跟這兩者共存而不產生歧義。要嘛借用新符號（成本高、可讀性差），要嘛靠複雜的 lookahead（讓 parser 難寫、也讓人難讀）。
現況的折衷是保持 new Set(iterable)，並在 2024 年補上原生集合運算方法，讓「用起來方便」而不動語法。
