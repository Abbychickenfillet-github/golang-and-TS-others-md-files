  1. callback 的三種常見形態（逐元素處理、非同步完成通知、成功失敗分支）各自把「什麼決定權」交給了呼叫端？請各舉一個 API 為例。

    逐元素處理（map／filter／forEach）：外層負責走訪陣列與決定呼叫幾次，把「每個元素要變成什麼／留不留」交給呼叫端。非同步完成通知（setTimeout／fs.readFile／舊式 AJAX）：外層負責等待 I/O 或計時，把「拿到結果之後做什麼」交給呼叫端。成功失敗分支（onSuccess／onError、Promise 的 then／catch）：外層負責判斷條件選一條路，把「成功要幹嘛、失敗要幹嘛」交給呼叫端。三者共同點是外層只保留流程控制權，業務邏輯全部外包。

filter() 方法與 Callback 函式定義

本篇重點 a–j，共 10 個（2026-09-21 由 Gemini 對話補入 (g)～(j)：callback 的三種形態與小括號陷阱）

重點整理

(a) filter() 一定會用到一個 callback function：filter() 遍歷陣列每個元素時都會呼叫這個 callback，callback 回傳 true 該元素就保留進新陣列、回傳 false 就被濾掉——callback 就像篩網，決定誰能通過。

(b) MDN 對 Callback 的定義：「回呼函式（Callback function）是指被作為引數（Argument）傳入另一個函式的函式，並在該外部函式內部被呼叫，以完成某些任務或流程。」

(c) Callback 既是寫法風格，也涉及記憶體機制，可從兩個角度理解：
　　① 語法/設計角度：JS 函式是「一等公民（First-Class Functions）」，可賦值給變數、當引數傳遞、當回傳值——fnA(fnB) 時 fnB 就是 callback，意思是「這是我的邏輯，交給你（fnA），你在適當時機再呼叫回（call back）我」。
　　② 記憶體角度：不只是文字寫法，底層涉及三個核心機制（見 d、e、f）。

(d) 記憶體位址傳遞（Reference Pass）：寫 data.filter(checkId) 時，傳的不是函式「執行後的結果」，而是該函式在記憶體堆積（Heap）中的記憶體位址（指標 Reference）；外部函式（如 filter）拿到這個位址後，在自己的執行過程中透過位址找到並執行該函式。

(e) 閉包（Closure）與變數生存週期：若 callback 存取了外層變數（例如 data.filter(item => item.id !== targetId) 用到外層的 targetId），callback 會保留對其詞法範疇（Lexical Scope）中變數的引用；即使 filter 正在自己的作用域運作，callback 依然能存取外部的 targetId，這就是閉包保留記憶體上下文的特性。

(f) Call Stack 與 Event Loop 的分野：callback 可分同步／非同步。同步 callback（如 Array.filter）直接在當前執行上下文（Call Stack）中被呼叫、推入釋放記憶體；非同步 callback（如 setTimeout／API 請求）會先擺在記憶體空間中，等非同步任務完成後，經 Web APIs → Task Queue → Event Loop 才重新被推回 Call Stack 執行。

(g) 一句話定義：callback 是「被當成引數傳進另一個函式、並在適當時機被那個函式回頭呼叫」的函式
　　拆成三個動作就不會忘：你定義它（寫好 greeting）→ 你傳遞它（processUserInput(greeting)，注意不加小括號）→ 別人呼叫它（processUserInput 內部回頭執行 greeting()）
　　　　「回呼（call back）」的 back 就是指這個「控制權先交出去、時候到了再回頭叫你」的方向

(h) 三種最常見的 callback 形態，對照著看就知道它在解什麼問題：

形態 外層函式負責什麼 callback 負責什麼 典型 API
逐元素處理 走訪陣列、決定呼叫幾次 決定「每個元素要變成什麼」 map、filter、forEach
非同步完成通知 等待 I/O、計時器、網路回應 決定「拿到結果之後做什麼」 setTimeout、fs.readFile、舊式 AJAX
分支解耦（成功／失敗） 判斷條件，選一條路呼叫 決定「成功要幹嘛、失敗要幹嘛」 onSuccess / onError、Promise 的 then / catch 
// 形態一：逐元素處理——把「怎麼變」抽出來交給呼叫端決定
function processArray(arr, callback) {
  const result = [];
  for (let i = 0; i < arr.length; i++) {
    result.push(callback(arr[i]));   // 外層只負責走訪，變形邏輯是 callback 的事
  }
  return result;
}
const double = num => num * 2;
console.log(processArray([1, 2, 3], double));   // [2, 4, 6]

// 形態二：非同步完成通知——資料到手才回呼
function fetchData(callback) {
  setTimeout(() => {
    const data = { id: 101, name: "Alice" };
    callback(data);                  // 等 2 秒拿到資料，才回頭呼叫
  }, 2000);
}
fetchData(userData => console.log("收到使用者資料：", userData.name));

// 形態三：分支解耦——成功與失敗各給一個 callback
function checkNumber(num, onSuccess, onError) {
  if (num > 0) onSuccess(num + " 是正數");
  else onError(num + " 不是正數");
}
checkNumber(5, msg => console.log("成功：", msg), msg => console.log("錯誤：", msg));

(j) 形態二是「回呼地獄（Callback Hell）」的起點：巢狀的非同步 callback 一層包一層會讓錯誤處理與流程閱讀變得很痛苦，這正是 Promise 與 async/await 被發明出來要解決的問題——它們沒有取消 callback，只是把「等結果之後做什麼」從參數位置搬到 .then() 或 await 的下一行。
