那支程式的三個 bug

bug 1 — 兩組數字在 HTML 裡相鄰，視覺上黏成一串

msg += '<p>X:<span id="mouseX"></span>' + window.screenX + '</p>';
// 渲染後：<p>X:<span>1100</span>319</p>  →  畫面上看成 1100319
// Y 那行：<p>Y:<span>2</span>-861</p>      →  畫面上看成 2-861

不是「X 跟 Y 的精度不同」，是兩個不相干的數字被串在一起：span 裡是 e.clientX，緊接著的是 window.screenX。

bug 2 — 抓不存在的 id，listener 從那一行起全部停擺

document.getElementById('clientX')            // HTML 裡沒有這個 id → 回傳 null
                       .textContent = e.clientX;
// TypeError: Cannot set properties of null (setting 'textContent')

JS 例外會中斷整個 listener 的剩餘程式，所以就算前兩行寫對了也看不到效果。

bug 3（核心）— innerHTML 重建子樹，順序不是存在

⚠️ 存疑／更正：Gemini 這裡答錯了
Gemini 說「問題出在 msg 是在監聽器外設定的，把 el.innerHTML = msg 移除看看」以及「必須註解掉它才能更新數值」。
兩句都不對：msg 明明宣告在 listener 內部；把 el.innerHTML = msg 註解掉，<span id="mouseX"> 根本不會被建出來，getElementById 只會回 null，畫面反而空白。
真正原因是「順序」不是「存在」：innerHTML 賦值 ＝ 丟掉舊子樹、parse 字串、建新子樹。只要保證「先重建、再抓、再寫」就會正常。Abby 原本的順序其實是對的，真正擋住它的是 bug 2 的 TypeError。 
var el = document.getElementById('info');
el.innerHTML = '<h2>滑鼠座標</h2>'
             + '<p>Client X: <span id="cx"></span> | Client Y: <span id="cy"></span></p>';

var cx = document.getElementById('cx');   // 骨架已存在，這個參照可以一直重用
var cy = document.getElementById('cy');

document.addEventListener('mousemove', function (e) {
  cx.textContent = e.clientX;             // 只改文字節點，不重建任何元素
  cy.textContent = e.clientY;
});

完整可執行版本在同層的 mouse-coords-demo.html，另外加了 requestAnimationFrame 節流。

✅ 重點 l–o
l. innerHTML 賦值 ＝ 丟舊子樹 → parse 字串 → 建新子樹，所有指向舊節點的變數賦值後都變成孤兒參照。
m. 所以「先抓節點 → innerHTML → 寫值」必敗；順序要嘛「先 innerHTML → 再抓 → 再寫」，要嘛讓骨架只建一次。
n. getElementById 找不到回的是 null（不是 undefined、也不丟錯），錯是錯在下一步對 null 取屬性。用 n?.textContent 或先 if (n)。
o. mousemove 這種高頻事件每次重建 DOM 容易掉幀；用骨架法或把更新包進 requestAnimationFrame。

innerHTML／textContent／createElement

寫法怎麼處理字串這個範例能用嗎XSS 風險效能
el.innerHTML = msg當 HTML parse，<h2> 變成真的標題元素能，這正是範例要的有，含使用者輸入時必須先 sanitize差，整棵子樹重建
el.textContent = msg當純文字，標籤原樣印出不能，畫面會印出 <h2>browser window</h2>無，自動 escape好
createElement + textContent逐個建節點能，最安全但最囉唆無好
⚠️ 重點 p–r：innerHTML 的 XSS 邊界
p. 危險的前提是「字串裡混入了使用者可控的內容」。本範例 msg 全由 window.innerWidth、e.clientX 這類數值組成，沒有使用者輸入，所以用 innerHTML 本身沒有資安問題，只有效能問題。
q. 真正危險長這樣：把留言板內容塞進 innerHTML，攻擊者送 <img src="x" onerror="…">。注意 innerHTML 插入的 <script> 不會被執行（HTML 規格如此），所以攻擊者改走事件處理屬性（onerror／onload）。
r. 現代作法：安全優先用 textContent／createElement；一定要插 HTML 就先過 DOMPurify 或走 Trusted Types。React／Vue 預設會 escape，除非你用了 dangerouslySetInnerHTML。
🗒 重點 s–t
s. 原範例最後那行 alert('Current page: ' + window.location) 會在載入時跳窗並擋住後面的程式，示範時記得拿掉；window.location 被字串串接時會隱式呼叫 toString()。
t. window.history.length 讀的是這個分頁的歷史筆數，不是瀏覽器全部歷史；基於隱私，實際 URL 清單讀不到。

申論題

1. 用「動詞—受詞—拋接關係」的寫法，完整敘述 el.innerHTML = msg 這一行從賦值到畫面更新之間，瀏覽器做了哪幾件事，以及為什麼它會讓先前抓到的節點參照失效。
JS 引擎把 msg 這個字串交給 Blink 的 HTML parser → parser 把字串 tokenize 再 tree-construct 成一棵新的節點子樹 → Blink 先把 el 底下的舊子節點全部從文件樹上卸下（detach）→ 再把新子樹掛（append）到 el 底下 → 排入 style／layout／paint。 因為第三步把舊節點卸下了，先前 getElementById 拿到的那個參照仍然指著已被卸下的舊節點物件，它還活在記憶體裡（變數抓著它，GC 不會收），只是不在文件樹上，所以對它寫 textContent 畫面不會有任何反應。
2. 若要在 1920×1080 的螢幕上，把一個提示框精準貼在滑鼠右下角 12px 處，你會用哪一組座標？若頁面可以捲動，答案會不會變？請說明理由。
若提示框用 position: fixed（相對 viewport 定位），就用 e.clientX + 12 / e.clientY + 12，因為 fixed 的座標系跟 clientX 的原點同樣釘在 viewport 左上角，捲動也不必改。 若提示框用 position: absolute 掛在 <body> 底下（相對文件定位），就要用 e.pageX + 12 / e.pageY + 12，因為 absolute 的座標系是文件座標系。 screenX 兩種都不適用——它含了瀏覽器視窗在螢幕上的偏移，網頁內部根本不知道那段偏移是多少。
3. Gemini 在這組對話裡把「innerHTML 會重建子樹」這個正確的觀察，接上了「所以要把它註解掉」這個錯誤的結論。請說明：正確的觀察配上錯誤的結論，錯在推論的哪一步？你會怎麼設計一個一分鐘內能驗證對錯的實驗？
錯在把「A 會覆蓋 B」誤讀成「A 與 B 不能共存」，但實際上兩者只是有先後順序要求：A 必須先發生，B 才有對象可抓。移除 A 等於同時移除了 B 的前提，是把因果鏈整條砍斷而不是修好它。
驗證實驗：在 listener 裡連寫三行 console.log(document.getElementById('mouseX'))——一行放在 innerHTML 賦值之前、一行放之後、一行放在寫值之後。註解掉 innerHTML 時三行全印 null，保留時第一行 null、後兩行是節點，一眼就能證明是順序問題。
