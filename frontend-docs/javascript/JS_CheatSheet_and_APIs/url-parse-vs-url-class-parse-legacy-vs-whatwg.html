c. 實測：同一個字串兩個 parser 看到什麼

Node v24.14.0，2026-10-26 重跑。表中 host 欄是 parser 認定的主機，path 欄是路徑與查詢字串。

輸入字串url.parsenew URLURL.parse有差異嗎
/a/b?x=1接受。host null，path /a/b?x=1丟 ERR_INVALID_URLnull有，寬鬆 vs 嚴格
//a.com/xhost null，path //a.com/x丟 ERR_INVALID_URLnull有
http:a.com/x（少 //）host null，path a.com/xhost a.com，path /xhttp://a.com/x有，主機不同
反斜線 http:\\a.com\xhost a.com，path /xhost a.com，path /xhttp://a.com/x沒有
http://a.com\@evil.com/xhost a.com，path /@evil.com/xhost a.com，path /@evil.com/x同 new URL沒有
HTTP://A.COM/X（大小寫）host a.com，path /Xhost a.com，path /Xhttp://a.com/X沒有
前後有空白host a.com，path /xhost a.com，path /xhttp://a.com/x沒有
http://a.com@evil.com/xhost evil.com，auth a.comhost evil.com，username a.com同 new URL沒有
重要：不要把反斜線、大小寫、前後空白寫成兩者有差這三項實測結果兩個 parser 相同。真正會讓兩者「認出不同主機」的是少一個斜線的 http:a.com/x。

d. Parser differential：檢查與發請求用不同 parser

對 http:a.com/x，url.parse 認為沒有主機，new URL 認為主機是 a.com。這種「兩個 parser 對同一字串解讀不同」就是 parser differential。

// 危險：檢查用一個 parser，發請求用另一個
const allowed = new URL(input).host === 'a.com'      // WHATWG：host 是 a.com，通過
if (allowed) {
  const target = url.parse(input)                    // Legacy：host 是 null，path 是 a.com/x
  // 後面若用 target 去發請求，請求端看到的目標可能不是 a.com
}

差異本身已實測。實際能不能被利用要看請求端怎麼處理 host 為 null 的物件，這部分沒有實測，不要當成已證實的漏洞。處理原則：檢查與使用同一個 parser，並且用標準的那一個。

f. 怎麼找出誰在呼叫 url.parse

npx cross-env NODE_OPTIONS=--trace-deprecation npm run build
要點說明驗證
為什麼用 NODE_OPTIONS它是環境變數，子行程都繼承，所以 next build 的 worker 也吃得到。直接寫 node --trace-deprecation 只作用在第一個行程已實測：父行程用旗標時子行程只印一行警告沒有堆疊，用 NODE_OPTIONS 則子行程印出完整堆疊
為什麼可能找不到DEP0169 是 Application 類型，只有非 node_modules 的程式碼呼叫才會印警告。依賴套件內的呼叫是靜默的，加 --pending-deprecation 也一樣已實測 Node v24.14.0：app 程式碼有警告，node_modules 內呼叫兩種情況都沒有
所以看到警告代表什麼呼叫點在非 node_modules 路徑。可能是專案檔、設定檔，或被 Next.js 打包進 .next/server 的依賴程式碼後半是推論，未驗證
build 後再搜grep -rn "url.parse" .next/server，找被打包進去的呼叫指令未執行
你的專案現況專案自己的程式碼沒有 url.parse，依賴掃描也沒找到，呼叫者未知依來源 session 的掃描結果，本次未重掃

這個警告在 npm run build 出現，和 預渲染時元件在 Node 裡真的執行一遍 是同一個原因：建置期程式碼跑在 Node，所以 Node 的棄用警告會出現在 build 輸出。
