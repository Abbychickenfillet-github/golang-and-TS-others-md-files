申論題

  1. 你不小心把 .env 連同 AWS 金鑰 commit 並 push 到公司的 GitHub repo 了。請寫出完整處理流程，說明每一步的理由，並解釋 git rev-parse 在這整件事裡扮演什麼角色（或為什麼它幫不上忙）。

git rev-parse 與 git filter-repo｜唯讀查詢 vs 破壞性歷史改寫

[!info] 本篇重點 a–k，共 11 個
這兩個指令唯一的共通點是名字裡都有「處理 commit」的味道，其他地方完全不同。一個絕對不會改到你的東西，一個會把整個 repo 的歷史重寫一遍。會放在一起問，通常是因為在清理誤推的金鑰時同時遇到這兩個名詞。
關聯筆記：git-filter-repo 是實際操作步驟與踩坑紀錄，這篇補上「它跟查詢類指令的分界在哪」；Git-Graph-Outgoing-Changes與rev-parse-status-sb 講 rev-parse 在讀取分支狀態上的實際應用；git-ref-vs-branch-vs-head 講 rev-parse 要解析的那些「引用」到底是什麼。

重點整理

一. 先定義兩個 Git 世界的專有名詞

(a) Plumbing（水管）指令：Git 的低階內部工具，輸出格式穩定、適合寫進腳本，但不好給人看。rev-parse、cat-file、hash-object、ls-tree 都屬於這一類。

(b) Porcelain（瓷器）指令：包給人用的高階指令，輸出漂亮但格式可能隨版本變動。status、log、commit、checkout 屬於這一類。

[!note] 這個命名的由來
Git 官方把自己比喻成馬桶：Porcelain 是你看得到的白瓷外殼，Plumbing 是牆裡面那堆水管。寫 CI script 時要用 plumbing，因為 porcelain 的輸出格式官方明講「隨時可能改」。

(c) rev-parse 是 plumbing，filter-repo 兩者都不是——它根本不是 Git 內建指令，是一支獨立的 Python 套件。

二. 核心差異對照

(d)

比較項目 git rev-parse git filter-repo
主要功能 解析 SHA-1 雜湊值、查詢 Git 內部狀態 重寫專案 Git 歷史紀錄（History Rewriting）
資料修改 唯讀，完全不修改資料 破壞性修改，所有 commit SHA 都會變
典型用途 取得當前 commit ID、取得 .git 目錄路徑 刪除誤推的金鑰／密碼、批次清理大檔
工具類型 Git 內建核心低階指令 官方推薦的 Python 擴充套件，需額外安裝
執行速度 毫秒級 視 repo 大小，數秒到數十分鐘
可逆嗎 沒有東西可逆，它什麼都沒動 不可逆，做之前一定要另外備份一份 clone

三. git rev-parse 常用場景

(e)

# 取得目前 HEAD 的完整 40 字元 commit SHA
git rev-parse HEAD

# 只要前 7 碼（寫 log 或 tag 常用）
git rev-parse --short HEAD

# 檢查當前目錄是否在 Git 專案內（寫 script 的護欄）
git rev-parse --is-inside-work-tree

# 取得 repo 根目錄的絕對路徑（不管你 cd 到多深的子資料夾）
git rev-parse --show-toplevel

# 取得目前分支名稱
git rev-parse --abbrev-ref HEAD

(f) 逐行拆解第一個：HEAD 是一個引用（reference），指向「你現在在哪個 commit」。rev-parse 的工作就是把這種人類看得懂的名字（HEAD、main、v1.0、HEAD~3、main@{yesterday}）翻譯成那個唯一的 40 字元雜湊值。rev = revision（版本），parse = 解析，合起來就是「版本名稱解析器」。

(g) 實務用法：--show-toplevel 在寫專案腳本時特別好用，可以讓腳本不管從哪個子資料夾執行都找得到專案根目錄。

四. git filter-repo 常用場景

(h)

# 從整個 commit 歷史中徹底刪除 passwords.txt
git filter-repo --path passwords.txt --invert-paths

# 清除歷史中所有超過 50MB 的大型檔案
git filter-repo --strip-blobs-bigger-than 50M

(i) 拆解第一個：--path passwords.txt 是「我關心這個路徑」，--invert-paths 把選取反轉成「留下其他全部，把這個丟掉」。少了 --invert-paths 意思會變成「只留這個檔案，其他全刪」，方向完全相反。

(j) 三個一定要知道的陷阱：

  • 它是官方推薦用來取代 git filter-branch 的。filter-branch 官方文件現在開頭就寫著不建議使用，因為慢且容易做錯。
  • filter-repo 預設會拒絕在有未推送變更或非新鮮 clone 的 repo 上跑，要加 --force 才會硬做。這個限制是保護你的，不要習慣性加 --force。
  • 跑完之後 remote 會被移除，這是刻意設計，逼你重新確認要推去哪。之後要 git push --force 覆蓋遠端，並且通知所有協作者重新 clone，因為他們本機的歷史已經對不上了。

(k) 最重要的一點：把金鑰從 Git 歷史刪掉，不等於那把金鑰安全了。只要曾經 push 到遠端，就要當作已外洩，正確流程是先去服務商後台把那把金鑰作廢並換新，再回來清歷史。順序反了就沒有意義。
