Next.js：src/ 目錄之爭與檔案系統路由的雙軸制

建立日期：2026-09-06　｜　對應版本：Next.js 16.3.4　｜　分類：react / nextjs
主題：為何 create-next-app 預設不含 src/、資料夾路由與檔名路由的差異、route.ts 與 proxy.ts 的定位、專案邊界的三層強制力

一、先修正一個我先前講錯的地方

更正 先前說法「用 src 要設定很多」是誇大的。實際上用 create-next-app 勾選 src，額外設定是 零，CLI 會自動把 tsconfig.json 的 paths 寫成 "@/*": ["./src/*"]。

另外，官方 src Folder 文件中「Tailwind 要在 content 加 /src 前綴」那條，是 Tailwind v3 時代的敘述。Next.js 16 預設安裝的是 Tailwind v4，v4 改為 CSS-first（@import "tailwindcss"）並自動偵測來源檔，沒有 content 欄位要改。引用文件時要看該段落是不是跟著版本更新。

a　「零設定就能跑」真正的意思

defaults 的判準不是「哪個架構比較好」，而是這三件事：

  1. 減少決策點——新手第一次跑 CLI 時，每多一個選項就多一次卡住的機會
  2. 跟官方文件與教學截圖一致——90% 的 Next.js 教學是根目錄 app/，多一層會讓學習者一直要在腦中做路徑轉換
  3. 避免靜默失效——官方文件明列：若根目錄同時存在 app/，則 src/app 會被完全忽略。這是不報錯的失敗，最難 debug

b　真正會痛的只有「事後手動搬」

專案跑到一半才決定加 src，要同步改的東西：

  1. tsconfig.json 的 paths（否則 @/ 全部解析失敗）
  2. CI 與 lint／test 的 glob 設定
  3. proxy.ts 要一起搬進 src/
  4. 確認根目錄的舊 app/ 真的刪乾淨，否則 src/app 靜默失效

而 public/、package.json、next.config.ts、tsconfig.json、.env.* 這些 一律留在根目錄，不能搬進 src/。

二、動畫：src/ 到底幫你解決了什麼

下面模擬一個專案從「剛建立」長到「上線兩年」的過程。左邊沒有 src/，右邊有。請注意看每個階段底下的兩個數字，以及最下面那行 lint／test 的 glob 要怎麼寫。

✗ 沒有 src/（Next.js 預設）
    根目錄項目數：0　｜　其中「應用程式碼」：0
    ✓ 有 src/
      根目錄項目數：0　｜　其中「應用程式碼」：1
      動畫要你看見的重點
      1. 右邊的根目錄項目數幾乎不成長，成長全部發生在 src/ 裡面——根目錄永遠只是「這個專案怎麼被建置」的設定層
      2. 左邊的根目錄裡，next.config.ts（設定）跟 components/（業務邏輯）平輩並排，兩種完全不同性質的東西混在同一層
      3. glob 那一行是最實際的差異：右邊永遠是 src/**，左邊要一條一條列舉，而且每新增一個業務資料夾就要回頭改一次設定（漏改就是 lint 沒掃到、coverage 算錯）

      a　所以 src/ 的價值準確地說是什麼

      1. 把「應用程式碼」與「專案設定」分成兩個不同的層——這是概念上的分層，不是資料夾潔癖
      2. 讓工具的掃描範圍變成一個穩定的常數——ESLint、Vitest、coverage、CODEOWNERS、Docker 的 COPY 都寫 src/ 就好，不會因為新增業務資料夾而失效
      3. 降低「新資料夾放哪」的決策成本——只要不是設定檔，一律進 src/
      誠實的評估 以上三點都是真的，但它們是工具便利性，不是架構嚴謹度。src/ 不會讓任何一條 import 變得不合法。下一節示範這件事。

      三、為什麼「有 src 比較嚴謹」是錯覺

      關鍵前提：JavaScript／TypeScript 沒有 package-private 這種存取控制。

      語言模組私有機制
      Javaprivate／protected／package-private（不寫修飾字＝同 package 才看得到）
      Go識別字小寫開頭＝套件私有，大寫開頭才匯出
      Rustpub 才公開，預設模組私有
      JS / TS沒有。只要路徑打得出來，任何檔案都能 import 任何檔案

      沒有 src/

      features/

import { calcPrice } from
  '@/features/cart/internal/priceCalc'
// ✅ 編譯通過，執行正常，零警告

      有 src/

      src/

      a　邊界強制力的三個層級

      層級手段強制力怎麼繞過
      1src/ 資料夾分層零——純視覺不用繞，本來就沒擋
      2eslint-plugin-boundaries軟——lint 報錯、CI 擋 PR// eslint-disable-next-line
      3monorepo workspaces硬——模組解析失敗繞不過，除非改 package.json

      b　monorepo 為什麼是「硬強制」

      my-app/
  package.json          # workspaces: ["apps/*", "packages/*"]
  apps/
    web/package.json    # dependencies: { "@acme/ui": "workspace:*" }  ← 有宣告
    admin/package.json  # dependencies: { }                            ← 沒宣告
  packages/
    ui/package.json     # name: "@acme/ui"
    db/package.json

      apps/admin 想 import '@acme/ui'？Node 的模組解析在 admin/node_modules 和它的父層都找不到那個套件名，直接執行期爆錯。這不是有人在旁邊提醒你不要這樣寫，是物理上跑不起來。

      修正一個常見誤解 monorepo 不是「比 src 更強的版本」，它們解決不同層級的問題：
      1. src/＝一個 npm package 內部的視覺整理
      2. monorepo＝多個可獨立建置、獨立版本化的 package，靠 package.json 的 dependencies 形成真實邊界
      真正大型的專案走 monorepo 之後，分隔應用程式碼的是 apps/ 那一層，src/ 這一層的價值就被取代掉了。

      四、檔案系統路由是「雙軸制」，不是單軸

      先釐清一個撞名 1. routes.ts（複數）——這是 React Router／Vue Router 社群習慣的路由表檔名，屬於 config-based routing，是純前端的「網址對應到哪個元件」設定
      2. route.ts（單數）——這是 Next.js 的 Route Handler，是一個真正的 後端 HTTP endpoint
      兩者只是名字像，沒有任何關係。

      a　軸一：資料夾決定「網址路徑」

      資料夾寫法名稱產生的網址
      app/dashboard/一般路徑段/dashboard
      app/blog/[slug]/Dynamic Segment（動態段）/blog/hello → params.slug = 'hello'
      app/shop/[...slug]/Catch-all（全捕捉，一層以上）/shop/a/b → params.slug = ['a','b']
      app/shop/[[...slug]]/Optional Catch-all（可選全捕捉）連 /shop 本身也會命中
      app/(marketing)/Route Group（路由群組）不產生網址，只用來分組與套 layout
      app/_lib/Private Folder（私有資料夾）完全不參與路由掃描
      app/@modal/Parallel Route（平行路由）不產生網址，同時渲染多個 slot

      b　軸二：檔名決定「這個路徑段扮演什麼角色」

      檔名不會出現在網址裡。它是在告訴 Next.js 這層資料夾要做什麼：

      1. page.tsx——這一段是可訪問的頁面。沒有它，這層資料夾就不是一個網址
      2. route.ts——這一段是後端 endpoint，回傳 JSON／XML／檔案
      3. layout.tsx——外框，切換子路由時不會重新掛載（狀態保留）
      4. template.tsx——外框，但每次導航都重新掛載（狀態重置）
      5. loading.tsx——自動包成 React Suspense 的 fallback
      6. error.tsx——自動包成 Error Boundary
      7. not-found.tsx——404 畫面
      8. default.tsx——Parallel Route 的預設 slot
      這就是 colocation（就近放置）的基礎 你可以在 app/dashboard/ 裡直接放 DashboardChart.tsx、useDashboard.ts、utils.ts。它們既不叫 page 也不叫 route，所以永遠不會意外變成一個公開網址。這是 App Router 相對舊制最大的架構解放。

      c　對比：Pages Router（舊制）才是純檔名路由

      pages/about.tsx        → /about          # 檔名直接就是網址
pages/blog/[slug].tsx  → /blog/:slug
pages/api/users.ts     → /api/users

      舊制是「檔名＝網址」，所以 pages/ 裡不能放非頁面檔案（會變成路由）。新制改成「資料夾＝路徑，檔名＝角色」，就是為了解開這個限制。

      五、route.ts 的定位與正確路徑

      a　它跟 SSR 不在同一個分類軸上

      分類軸在講什麼對象
      SSG / ISR / SSR / PPR這個畫面的 HTML 在哪個時間點產生page.tsx
      Route Handler這是一個 伺服器端的 HTTP endpointroute.ts

      route.ts 本身就是伺服器程式，它產生的是 JSON 不是 HTML，所以沒有「HTML 在哪產生」的問題。

      「SSR 才有」這個印象可能的來源 Next.js v15.0.0-RC 起，GET handler 的預設快取由 static 改為 dynamic。以前 GET 會在 build 時被靜態化成一個 JSON 檔，現在預設每次請求都執行——所以看起來很像 SSR，但那是快取策略的改變，不是渲染模式。

      b　app/(api)/api/ 能動，但那一層是多餘的

      app/(api)/api/users/route.ts   →  /api/users
app/api/users/route.ts         →  /api/users     # 完全一樣的網址

      因為 (api) 是 Route Group，小括號資料夾不會出現在網址裡。多包這一層沒有帶來任何東西，卻多了一層目錄深度。

      Route Group 的正確用途是「我要分組並套不同 layout，但不想讓分組出現在網址裡」：

      app/(marketing)/layout.tsx        # 行銷版外框：有導覽列、footer
app/(marketing)/about/page.tsx    → /about
app/(marketing)/pricing/page.tsx  → /pricing

app/(app)/layout.tsx              # 登入後外框：有側邊欄
app/(app)/dashboard/page.tsx      → /dashboard

      c　建議的路徑寫法

      1. 一般情況——app/api/<資源名>/route.ts 
        app/api/users/route.ts          → GET/POST         /api/users
app/api/users/[id]/route.ts     → GET/PUT/DELETE   /api/users/123
      2. 需要版本化——app/api/v1/users/route.ts → /api/v1/users
      3. 需要按權限分組又不想動網址——這時 Route Group 才派上用場 
        app/api/(public)/health/route.ts   → /api/health
app/api/(admin)/users/route.ts     → /api/users
      4. 硬規則——同一個資料夾不能同時有 page.tsx 和 route.ts，同一個網址不能有兩個 handler，會直接衝突
      5. 更重要的建議：你可能根本不需要 route.ts——「自家前端呼叫自家後端」現在推薦用 Server Actions（'use server'），不用寫 endpoint、不用手動 fetch、型別自動打通。route.ts 應該留給：
        • 第三方要打的 webhook（Stripe、GitHub）
        • 需要開放 CORS 給外部的公開 API
        • 非 JSON 的回應（app/rss.xml/route.ts、OG image）

      六、proxy.ts：跟 Vue 的 proxy 是兩回事

      a　檔名與寫法

      檔名就是 proxy.ts（或 proxy.js），放在專案根目錄，有 src 就放 src/proxy.ts，規則是「跟 app 或 pages 同一層」。

      // proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

// 必須是 default export，或者具名 export 且名字就叫 proxy
export function proxy(request: NextRequest) {
  return NextResponse.redirect(new URL('/home', request.url))
}

// 沒有 matcher 的話會對「每一個請求」執行，連 CSS、圖片、public/ 的檔案都會被攔
export const config = {
  matcher: '/about/:path*',
}
      舊名 middleware，Next.js 16 起改名 舊檔名是 middleware.ts，函式叫 middleware，在 v16.0.0 被 deprecated。官方 codemod：
      npx @next/codemod@canary middleware-to-proxy .

      Vercel 給的改名理由：「middleware」這個詞常被誤會成 Express.js 的 middleware，導致大家過度使用；「proxy」暗示「在你的 app 前面的一道網路邊界」，更貼近它真正的行為——它可能被部署到 CDN 邊緣節點，跟你的 app 主程式是分開跑的。官方甚至直說：建議把 Proxy 當最後手段，能不用就不用。

      b　跟 Vue / Vite 的 proxy 對照

      Vue / Vite 的 server.proxyNext.js 的 proxy.ts
      執行時機只在 dev serverdev 與 production 都在跑
      目的本機開發時把 /api 轉給後端，解 CORS請求進入路由前攔截：驗證、redirect、rewrite、加 header
      build 之後完全消失（真實環境靠 Nginx 做）照樣執行

      c　那 Next.js 裡真正對應 Vue proxy 的是什麼？

      是 next.config.js 的 rewrites，而且它 dev 與 prod 都有效：

      // next.config.js
module.exports = {
  async rewrites() {
    return [
      { source: '/api/:path*', destination: 'http://localhost:8080/api/:path*' },
    ]
  },
}
      我想做的事Vue / ViteNext.js
      開發時把 /api 轉給後端解 CORSserver.proxynext.config.js 的 rewrites
      每個請求先驗證登入Vue Router 的 beforeEach（瀏覽器端，可被繞過）proxy.ts（伺服器端，繞不過）
      資安提醒（官方文件明列） Server Actions 不算獨立路由——它們是對「使用它的那個路由」發出的 POST 請求。所以 Proxy 的 matcher 排除掉某路徑時，也會一併跳過那裡的 Server Action。驗證與授權要在每個 Server Action 內部自己再做一次，不要只靠 Proxy。

      七、Next.js 不能用在 Vue 或 Angular

      不是「他們懶得支援」，是綁在骨頭裡：

      1. "use client" ／ "use server" 這些 directive 是 React 的語言層機制，不是 Next.js 發明的
      2. RSC（React Server Components） 的序列化格式、Suspense、renderToPipeableStream 全部是 React 內部 API
      3. layout.tsx ／ page.tsx 回傳的是 JSX，由 React 的 reconciler 渲染

      Next.js 是「React 的框架」，不是「JS 的框架」。

      UI 函式庫對應的全端框架
      ReactNext.js、Remix / React Router v7、TanStack Start
      VueNuxt
      Angular官方 @angular/ssr、社群的 Analog
      SvelteSvelteKit
      SolidSolidStart
      要混用Astro（同一專案可同時放 React、Vue、Svelte 元件）

      八、互動測驗

      a　填空題

      1. 若根目錄同時存在 app/ 與 src/app/，Next.js 會忽略 這一份。
      答案：src/app。這是靜默失效，不會有任何錯誤訊息，是遷移到 src 時最常見的坑。
      2. Next.js 16 中，請求進入路由前的攔截檔案叫 ，它的舊名是 。
      答案：proxy.ts ／ middleware.ts。函式名也一起改了（middleware → proxy），可用 npx @next/codemod@canary middleware-to-proxy . 自動遷移。
      3. 在 App Router 中，決定一個資料夾「是不是一個可訪問頁面」的檔名是 ；決定它是「後端 endpoint」的檔名是 。
      答案：page.tsx ／ route.ts。兩者不能放在同一個資料夾，會造成同一網址兩個 handler 的衝突。
      4. 想「分組並套不同 layout，但不要讓分組出現在網址裡」，資料夾要用 包起來。
      答案：小括號 ( )，稱為 Route Group。例如 app/(marketing)/about/page.tsx 的網址是 /about，(marketing) 不會出現。
      5. 在 Next.js 中，真正對應「Vue 的 server.proxy（開發時把 /api 轉給後端）」的功能，是 next.config.js 的 而不是 proxy.ts。
      答案：rewrites。而且它 dev 與 production 都有效，比 Vue 的 devServer proxy 更完整。

      b　是非題

      1. 加上 src/ 之後，features/user 就不能再 import features/cart/internal 的檔案了。
      JS/TS 沒有 package-private 機制，src/ 只是把整棵樹往下移一層，誰能 import 誰完全沒變。要擋要靠 eslint-plugin-boundaries（軟強制）或 monorepo workspaces（硬強制）。
      2. public/ 資料夾在使用 src/ 時，應該一起搬進 src/public/。
      官方明列 public/、package.json、next.config.js、tsconfig.json、.env.* 一律留在根目錄。只有 app／pages 與其他應用程式資料夾（components、lib）搬進去。
      3. route.ts 是「SSR 專用」的檔案，靜態網站不會用到它。
      分類軸不同。SSG/ISR/SSR/PPR 講的是 page.tsx 的 HTML 何時產生；route.ts 本來就是伺服器端 endpoint，產生的是 JSON。（不過 output: 'export' 純靜態輸出時，只有 GET 能被靜態產出，且 Proxy 完全不支援。）
      4. proxy.ts 若不寫 matcher，連 _next/static 的 CSS、JS 與 public/ 的圖片請求都會經過它。
      官方文件明確警告這點。沒有 matcher 時 Proxy 對每個請求執行，auth 邏輯會意外擋掉 CSS/JS/圖片載入，畫面會整個裸奔。要用 negative lookahead 排除：'/((?!api|_next/static|_next/image|favicon.ico).*)'
      5. Next.js 可以搭配 Vue 使用，只要換掉渲染層即可。
      不行。RSC 序列化、"use client"／"use server" directive、Suspense 都是 React 內部機制。Vue 的對應品是 Nuxt，Angular 是 @angular/ssr 或 Analog。

      c　申論題

      1. 有人在 code review 說「我們專案要改用 src/，這樣架構才夠嚴謹，才撐得住規模」。請寫出你的回覆，並提出真正能達成他目的的做法。
      回覆架構：
      1. 先肯定他真正想解決的問題——他想要的是「模組之間不要亂 import、重構時不會炸」，這個目標是對的
      2. 指出手段對不上目標——src/ 只是把整棵樹往下移一層，不改變任何 import 的合法性。改完之後 features/user 一樣能直接摸進 features/cart/internal
      3. 給出真正有效的三個手段，並說明強制力層級：
      　a. eslint-plugin-boundaries——宣告資料夾分類與允許的依賴方向，違規 lint 報錯、CI 擋 PR（軟強制）
      　b. 每個 feature 只透過 index.ts 對外，配合 lint 規則禁止深層路徑 import
      　c. 真的大到需要獨立建置時走 monorepo workspaces——沒宣告 dependency 就模組解析失敗（硬強制）
      4. 對 src/ 本身給出誠實評價——它有真實但有限的好處（設定與程式碼分層、lint/test/coverage 的 glob 變成穩定常數 src/**），值得做，但要用「工具便利性」的理由去說服，不要用「架構嚴謹度」的理由
      5. 提醒遷移成本——事後搬要同步改 tsconfig.json 的 paths、CI glob、proxy.ts 位置，且根目錄舊 app/ 沒刪乾淨會讓 src/app 靜默失效
      2. 請說明 App Router 的「雙軸制」，並解釋為什麼這個設計讓 colocation（就近放置）成為可能，而 Pages Router 做不到。
      雙軸制：
      1. 軸一——資料夾決定網址路徑：app/dashboard/settings/ → /dashboard/settings；特殊語法有 [slug] 動態段、[...slug] 全捕捉、[[...slug]] 可選全捕捉、(group) 不入網址、_folder 完全不參與路由、@slot 平行路由
      2. 軸二——檔名決定該路徑段的角色，且檔名不會出現在網址裡：page.tsx（頁面）、route.ts（endpoint）、layout.tsx（不重掛的外框）、template.tsx（每次重掛的外框）、loading.tsx、error.tsx、not-found.tsx、default.tsx

      為什麼 colocation 因此成立：
      只有叫 page 或 route 的檔案才會變成可訪問的網址。所以 app/dashboard/DashboardChart.tsx、useDashboard.ts、schema.ts 可以直接放在功能旁邊，不會意外對外公開。相關程式碼的物理距離縮短，改一個功能只要動一個資料夾。

      Pages Router 為什麼做不到：
      舊制是純單軸「檔名＝網址」——pages/about.tsx → /about。任何放進 pages/ 的檔案都會變成一條路由，所以元件、hook、工具函式必須被趕到 pages/ 之外（典型是根目錄的 components/、lib/），造成「同一個功能的檔案散落在三個不相鄰的資料夾」。這也是為什麼舊制專案的根目錄特別容易膨脹，src/ 在舊制時代的需求也因此比較高。
      3. 你要設計一個電商站的 API 層。請規劃 route.ts 的路徑結構，並說明哪些情境「不該」用 route.ts。
      該用 route.ts 的路徑規劃：
      app/api/webhooks/stripe/route.ts     # 第三方打進來的 webhook
app/api/webhooks/shipping/route.ts   # 物流商回報
app/api/(public)/products/route.ts   # 開放給外部/App 的公開 API
app/api/(public)/products/[id]/route.ts
app/rss.xml/route.ts                 # 非 JSON 回應
app/sitemap.xml/route.ts
      規劃原則：
      1. 用 (public)／(internal) 這類 Route Group 分權限，網址仍然乾淨
      2. 需要對外長期相容時才加版本段 app/api/v1/...
      3. 動態資源用 [id]，記得 v15 起 params 是 Promise，要 await
      4. 絕不在同一資料夾同時放 page.tsx 與 route.ts

      不該用 route.ts 的情境：
      1. 自家前端呼叫自家後端——加入購物車、更新數量、送出訂單，這些用 Server Actions（'use server'）。不用寫 endpoint、不用手動 fetch、型別自動打通，也少一層可被外部直接呼叫的攻擊面
      2. 只是為了在 Server Component 取資料——Server Component 可以直接 await db.query()，繞一圈打自己的 API 是多餘的網路往返
      3. 包在 (api) 這種對網址沒有影響的多餘群組裡——app/(api)/api/x/route.ts 與 app/api/x/route.ts 網址相同，前者只是多一層深度

      安全補充：改用 Server Actions 之後，別忘了它不算獨立路由，Proxy 的 matcher 可能不覆蓋它，授權檢查要寫在每個 Server Action 內部。

      九、關聯筆記與關聯原因

      [[圖解_CSR-SSR-SSG的HTML在哪一刻長出來]]
      關聯原因：本篇第五節指出「route.ts 跟 SSR 不在同一個分類軸上」。那份筆記處理的是渲染時機軸（HTML 何時產生），本篇處理的是路由角色軸（檔名決定這是頁面還是 endpoint）。兩份合看才不會把「route.ts 是不是 SSR」這種跨軸問題問錯。
      [[學習前端工程_圖解_NodeJS執行環境與打包工具的層級關係]]
      關聯原因：本篇第二節談 src/ 讓 lint／test／coverage 的 glob 變成穩定常數。那份筆記講的是打包工具在哪一層運作——glob 是打包與檢查工具的輸入，理解工具層級才知道為什麼「掃描範圍穩定」在大專案是實際的成本差異，而不是潔癖。
      [[學習資安_圖解_CSRF流程-Cookie自動夾帶vs-Bearer手動夾帶]]
      關聯原因：本篇第六節的資安提醒——Vue Router 的 beforeEach 在瀏覽器端可被繞過，proxy.ts 在伺服器端才擋得住；以及 Server Actions 是 POST 到當前路由、不算獨立路由。這兩點都直接涉及「憑證怎麼被夾帶、誰在哪一層驗證」，跟那份 CSRF 筆記是同一組心智模型。
      [[TS]]（tsconfig.json 的 paths 設定）
      關聯原因：src/ 遷移最容易漏掉的一步就是 paths 的 "@/*": ["./src/*"]。改了資料夾沒改 paths，所有 @/ import 會全數解析失敗。
