三、為什麼 ESLint 有錯誤會擋建置

不是 ESLint 自己有權力擋，而是 build 腳本把 lint 串在打包前面，shell 遇到非零 exit code 就中斷整條鏈。

{ "scripts": { "build": "vue-tsc && eslint . && vite build" } }
  1. b&& 的意義是：前一個指令 exit code 為 0 才執行下一個。
  2. c只有 error 等級會擋，把規則改成 "warn" 就不會中斷建置。
  3. d設計初衷是把未使用變數、未處理的非同步例外擋在 production 之外，避免上線白屏。

prebuild 為什麼會自動跑

{
  "prebuild": "npm run lint",
  "build": "next build",
  "lint": "npx eslint ."
}
  1. e原因不是 next 這個字，而是 npm 的 lifecycle scripts：定義了 pre<NAME>，執行 npm run <NAME> 時就會先自動跑它；post<NAME> 則在成功後跑。
  2. fprebuild 裡一定要寫完整的 npm run lint，因為 scripts 的值只是一串丟給 shell 的字串，shell 不認識你自訂的 key lint，只會去找 lint.exe。

四、npx eslint . --fix 是怎麼改檔案的

g ESLint 用 espree（預設 parser）把原始碼 parse 成 AST（Abstract Syntax Tree，抽象語法樹） → 規則走訪 AST 找到違規節點 → --fix 依規則重新產生標準化字串 → 直接覆寫原始檔。

h 安全，因為 --fix 只動格式與無歧義的風格，不會改業務邏輯。
i 保險做法：先 commit，跑完用 git diff 檢查，不滿意就 git restore .。

五、import/no-unresolved 這個否定句

結構原字意思
import/Importeslint-plugin-import 的命名空間
no-No否定詞，「出現這情況就報錯」
unresolvedUnresolved未被 resolve 的（un- ＋ resolved）

j 完整直譯：Do not allow import statements to reference modules that cannot be resolved to a real file.

k 什麼叫 resolve：bundler／Node 拿到 import eve from 'eve' 的 specifier 'eve' → 先判斷是不是相對路徑 → 不是就去 node_modules/eve 找 → 讀該套件 package.json 的 exports 或 main 找進入點 → 找不到就回報 unresolved。

l 同款否定句：no-unused-vars、no-undef、no-console。

六、Oxlint 與 ESLint 的分工

oxlint（Rust 高速 linter）先跑完絕大多數基礎規則 → eslint-plugin-oxlint 把 ESLint 設定中「Oxlint 已檢查過」的同名規則 disable → eslint（JS 通用 linter）只剩高階／自訂／外掛規則要跑。

m 理由一：不要重跑，否則 Rust 的速度優勢被浪費。
n 理由二：避免兩邊對同一件事的修法不一致而互相打架。

七、ESLint 的作用域分析

o parser 產出 AST 之後，eslint-scope 走訪 AST 建立 Scope Tree（global → module → function → block），並把每個變數的 definition 與 references 綁在一起。

p 這是兩條經典規則的基礎：no-unused-vars ＝ 有 definition 但 references 長度為 0；no-undef ＝ 有 reference 但整條 scope chain 上找不到 definition。

八、Dev Inspector 是給誰用的

是開發者在用，只活在 npm run dev 階段，production build 會被完全剔除。

vite-plugin-vue-inspector 在開發期於每個 DOM 元素注入 data-*（檔案路徑＋行號）並注入監聽腳本 → 你點擊元件，腳本發 GET /__open-in-editor?file=src/App.vue:10 給本機的 Vite Dev Server → Vite 呼叫 Node 的 child_process 啟動你本機 VS Code 並跳到該行。

q 關鍵在於「瀏覽器連的是你自己電腦上的 dev server」，才有權力叫起本機編輯器；線上使用者連的是 CDN 靜態檔，既沒這段腳本也沒那台 server。

九、ES 代表什麼

ESLint 與 esbuild 的 ES ＝ ECMAScript，JavaScript 的官方標準名稱。ESLint ＝ ECMAScript ＋ lint（源自 C 時代的 lint，挑出程式碼裡的「棉絮」）；esbuild ＝ ECMAScript ＋ build。

⚠️ 更正
對話中提到「Oxlint 的 Ox 代表公牛」，Gemini 順著接話沒更正。依 oxc 官方，Ox 取自 Oxidation（氧化），是 Rust 社群對「用 Rust 重寫既有 JS 工具」的慣用說法（oxidize），不是公牛。

十、自己考自己

是非題

1. prebuild 會自動執行，是因為 build 指令裡有 next 這個字。
2. ESLint 的 warning 等級不會擋住 npm run build。

申論題

Q：請用「誰 用什麼 做什麼、產物是什麼、再拋給誰」的句式，完整描述從 npm run build 到 vite build 之間發生的事。


使用者在終端機下 npm run build → npm 先檢查 scripts 有沒有 prebuild，有就先把 npm run lint 這串字丟給 shell → shell 執行 npx eslint . → ESLint 用 espree 把原始碼 parse 成 AST，交給 eslint-scope 建 Scope Tree，再讓各規則走訪節點 → 產物是一份 error／warning 清單與一個 exit code → 若有任一 error，exit code 為 1，shell 中斷，next build／vite build 根本沒被呼叫；若全部只有 warning，exit code 為 0，npm 才接著把 next build 丟給 shell 去打包。

Q2：為什麼 vite-plugin-vue-inspector 能叫起你本機的 VS Code，但線上的使用者不行？


因為開發期你的瀏覽器連的是「跑在你自己這台電腦上的 Vite Dev Server（一支 Node 程式）」，它與 VS Code 在同一台機器上，所以能用 child_process 啟動編輯器。打包後這些插件與注入的監聽腳本會被完全剔除，線上使用者拿到的只是 CDN 上的靜態 HTML／JS，既沒有 /__open-in-editor 這個端點，也沒有任何一台屬於他的 Node 程式可以呼叫。
