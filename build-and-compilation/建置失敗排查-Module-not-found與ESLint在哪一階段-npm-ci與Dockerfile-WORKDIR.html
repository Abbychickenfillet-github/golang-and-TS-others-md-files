申論題

  1. CI 上建置失敗但本機一切正常，你會怎麼查？

    參考方向：(1) 先看失敗訊息落在哪一格：Linting（ESLint 規則或 --max-warnings 0）、Transpiling（Babel／tsc 型別或語法）、還是 Bundling（模組解析找不到檔）。(2) 模組解析失敗最常見的兩個原因是路徑寫錯，以及 _backup 之類的備份檔留在 src/ 底下被一起掃到——後者直接刪掉或搬出 src/。(3) 「本機好、CI 壞」的經典成因是依賴版本不一致：本機用 npm install 裝到了較新的版本，CI 用 npm ci 嚴格照 lock 檔。對策是把 lock 檔納入版控並在本機也跑一次 npm ci 復現。(4) 另一個常見差異是大小寫：本機 Windows/macOS 檔名不分大小寫，CI 的 Linux 分，import 路徑大小寫錯了只有 CI 會爆。(5) Docker build 時再確認 WORKDIR 與 COPY 的相對路徑是否一致。

重點整理

一、Module not found：路徑解析失敗（a–b）

(a) 錯誤訊息類似 「can't resolve ./intro.module.scss in intro-page_backup.js」，意思是打包工具在做「模組解析（module resolution）」時找不到那個檔。

(b) 兩個處置方向：修正 import 路徑，或者——如果那是像 _backup 這種備份檔——直接刪掉它。備份檔留在 src/ 底下會被打包工具一起掃到，是很常見的建置失敗來源；要留就搬到 src/ 外面或加進忽略設定。

二、ESLint 落在建置流程的哪一格（c–d）

(c) 現代前端建置流程大致是這幾步，ESLint 屬於 linting 這一格：

階段 做的事 代表工具
Linting 檢查程式碼品質與潛在錯誤 ESLint
Formatting 統一排版 Prettier
Transpiling 把新語法降級成目標環境看得懂的 Babel、SWC、tsc
Bundling 解析模組相依、打成少數幾包 Vite／Rollup、webpack

(d) ESLint 報的是 warning 還是 error 決定會不會擋建置。warning 通常不擋，error 才擋；但 CI 常設 --max-warnings 0，那時候 warning 也會讓建置失敗，看到一堆 warning 就掛掉先去確認這個設定。

三、npm ci 為什麼能取代 npm install（e–g）

(e) npm ci 嚴格照著 package-lock.json 安裝，而且不會去更新它；npm install 會在必要時改寫 lock 檔。

(f) 差別整理：

面向 npm install npm ci
依據 package.json（必要時改 lock） 只認 package-lock.json
會不會改 lock 檔 會 不會
node_modules 增量更新 先整個刪掉再重裝
速度（CI 環境） 較慢 較快
沒有 lock 檔時 照樣裝 直接報錯
適用 本機開發、加新套件 CI／CD、Docker build

(g) 「可重現的建置（reproducible build）」是 npm ci 存在的理由：同一份 lock 檔在任何機器上裝出完全一樣的版本，才不會出現「我本機好好的，CI 就掛」這種事。

四、Dockerfile 的 WORKDIR（h–i）

(h) WORKDIR /app 是把容器內的工作目錄設成 /app，之後的 COPY、RUN、CMD 都以這個目錄為基準。它還有一個常被忽略的好處：目錄不存在時會自動建立，不用先 RUN mkdir。

(i) /app 不是 Docker 規定的名稱，只是社群慣例。叫 /project、/code、/usr/src/app 都可以，重點是整份 Dockerfile 前後一致。
