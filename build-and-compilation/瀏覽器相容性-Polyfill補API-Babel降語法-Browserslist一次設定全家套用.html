🧠 自我測驗

是非題

  1. Babel 可以把舊瀏覽器缺少的 Promise 補回來。

    Babel 管語法，Promise 是執行期的 API，要靠 core-js 這類 Polyfill 補。

  2. Browserslist 是一個瀏覽器外掛（Extension）。

    它是一個設定規格加上一個 npm 套件，被 Babel、Autoprefixer、Vite、Webpack 共用。

  3. .browserslistrc 裡的多行條件之間是 OR（聯集）關係。

    所以 > 0.5% 一行就涵蓋所有市佔達標的瀏覽器，不必逐一列舉。

  4. 把事件處理包成 el.addEventListener('blur', function(){ checkUsername(5) }) 這件事，核心概念是閉包。

    詞法作用域是規則，閉包是「函式連同定義時的環境一起被保存下來等待觸發」這個現象。

填空題

  1. 自動補上舊瀏覽器缺少的 API，這種墊片庫叫做 ，代表套件是 core-js。

    跟 Transpiler 分工：一個補 API、一個降語法。

  2. Browserslist 條件 not 用來排除官方已停止維護的廢棄瀏覽器。

    超過 24 個月沒更新且沒市佔的會被排掉。

  3. 寫在 package.json 時，欄位名稱是 ""，值是字串陣列或分環境的物件。

    好處是少維護一個獨立設定檔。

申論題

  1. 同事說「我們專案有裝 Babel，所以不用管舊瀏覽器了」。你會怎麼補充？

    參考方向：(1) 先肯定一半——Babel 確實會把 ES6+ 語法降級成 ES5，箭頭函式、class、async/await 都能處理。(2) 但 Babel 只翻語法，翻不出「執行期才存在的東西」：Promise、Array.prototype.includes、Object.assign、fetch 這些是 API，舊瀏覽器根本沒有這些物件與方法，必須靠 core-js 之類的 Polyfill 在執行時掛上去。(3) 兩者要一起設定，而且都應該讀同一份 Browserslist 目標，否則會出現「語法降到 ES5 但用了 IE 沒有的 API」這種只在正式環境炸掉的狀況。(4) 另外要提醒定期跑 npx update-browserslist-db@latest，否則 caniuse-lite 資料過期會讓 > 0.5% 的判斷失準，建置時也會一直跳警告。

重點整理

一、事件監聽為什麼要包一層匿名函式（a–c）

(a) 不能寫 el.addEventListener('blur', checkUsername(5))。這樣寫會在執行到這一行時「立刻執行」checkUsername(5)，再把它的回傳值交給監聽器，達不到「等 blur 發生才執行」的目的。

// ✅ 包一層匿名函式，事件發生時才執行內部呼叫
el.addEventListener('blur', function () {
  checkUsername(5);
}, false);

(b) 詞法作用域（Lexical Scope）是規則：這個匿名函式在「定義的位置」就決定了它能存取外層的 checkUsername 與數字 5。

(c) 閉包（Closure）是現象與機制：匿名函式被註冊給 DOM 元素之後，主程式跑完它仍留在記憶體裡等待觸發；blur 發生時它在全新的執行環境中被呼叫，卻依然能存取當初定義時捕獲的環境。所以這題的核心答案是「閉包」，詞法作用域只是它成立的前提。

二、相容性程式碼不用手寫（d–g）

(d) 全部手寫 if...else 檢查瀏覽器能力，程式碼會很髒且難以維護。現代前端早就交給自動化編譯工具處理。

(e) Polyfill（墊片庫）＝補「缺失的 API」，代表套件是 core-js。你正常寫 el.addEventListener(...)，Polyfill 會在載入時偵測環境，發現舊瀏覽器不支援就自動掛上模擬的 API。

(f) Transpiler（語法轉譯器）＝把「新語法」翻成「舊語法」，代表工具是 Babel（現代專案大多已整合在 Vite、Next.js、Webpack 底層）。箭頭函式、async/await、const/let 都會被翻成 ES5 的 var 與 function。

(g) 兩者的分工一句話記：Babel 管「語法（syntax）」，Polyfill 管「內建物件與方法（API）」。Promise、Array.prototype.includes 這些是 API，Babel 翻不出來，只能靠 Polyfill 補。

工具 補的東西 代表套件 例子
Transpiler 語法 Babel / SWC / esbuild () => {} 轉成 function(){}
Polyfill 執行期的 API core-js / regenerator-runtime 舊瀏覽器沒有的 Promise、Object.assign
後處理器 CSS 前綴與新語法 PostCSS / Autoprefixer 自動補 -webkit-

三、Browserslist 是什麼（h–k）

(h) Browserslist 不是瀏覽器外掛（Extension），而是前端工具生態系的「共用設定規格＋一個 npm 套件」。

(i) 它的核心工作是把「人類語言的條件」轉成「確切的瀏覽器與版本號清單」。

你寫的條件：
> 0.5%, last 2 versions, not dead

Browserslist 解析出來的結果：
chrome 124, chrome 123, safari 17.4, safari 17.3, edge 124, firefox 125...

(j) 它是前端建置流程的「中央指令中心」：一次設定，Babel、Autoprefixer、PostCSS、SWC 全家套用，不必在每個工具的設定檔各寫一次相容目標。

                   ┌──> Babel        （決定語法要降到哪個 ES 版本）
                   │
.browserslistrc ───┼──> Autoprefixer （決定 CSS 要加哪些 -webkit- / -moz- 前綴）
                   │
                   └──> PostCSS / SWC（決定要打包哪些 Polyfill）

(k) 不需要把每個瀏覽器都列出來，這些條件之間是 OR（聯集）關係：

條件 意思
> 0.5% 全球市佔率超過 0.5% 的所有瀏覽器版本，一行就涵蓋 Chrome、Safari、Edge、Firefox、Samsung Internet、Opera
last 2 versions 所有主流瀏覽器的最新 2 個版本
Firefox ESR Firefox 企業長期支援版，更新慢、市佔常不到 0.5%，但企業還在用，所以單獨列出
not dead 排除官方停止維護、或超過 24 個月沒更新的廢棄瀏覽器

[!tip] 要指定特定瀏覽器才需要寫死
Chrome >= 80、iOS >= 12、ie 11、last 2 Chrome versions。大部分現代專案只要 > 0.5% / last 2 versions / not dead 三行。

四、寫在 package.json 的兩種格式（l–n）

(l) 陣列格式（一般專案）：在根層級加一個 "browserslist" 欄位，值是字串陣列，元素之間同樣是 OR 關係。

{
  "name": "my-project",
  "version": "1.0.0",
  "scripts": { "build": "vite build" },
  "browserslist": [
    "> 0.5%",
    "last 2 versions",
    "Firefox ESR",
    "not dead"
  ]
}

(m) 物件格式（分環境）：開發環境只支援最新瀏覽器以換取編譯速度，正式環境才追求相容性。

{
  "browserslist": {
    "production": ["> 0.5%", "last 2 versions", "not dead"],
    "development": [
      "last 1 chrome version",
      "last 1 firefox version",
      "last 1 safari version"
    ]
  }
}

(n) 寫在 package.json 的好處是少維護一個 .browserslistrc 檔案，中小型專案更乾淨；大型專案或需要註解時才拆成獨立檔（.browserslistrc 支援 # 註解，JSON 不支援）。

⚠️ 存疑／更正

  • Gemini 說 Browserslist 的資料「來自 Can I Use」。更精確的說法是：版本與支援度資料來自 caniuse-lite，但市佔率統計來自 StatCounter GlobalStats，兩者是不同來源。這也代表 > 0.5% 的結果會隨 caniuse-lite 版本更新而變動，所以官方建議定期執行 npx update-browserslist-db@latest——這點 Gemini 完全沒提，卻是實務上最常出現的建置警告。
  • Gemini 舉的解析結果（chrome 124 / safari 17.4）是 2024 年前後的版本號，當作示意即可，不要當成現在的實際輸出。
  • Gemini 提到「Vue CLI」。Vue CLI 已於 2024 年進入維護模式，新專案官方建議改用 create-vue + Vite。

使用者： 在我剛剛給你的這個例子，第二個參數是一個 function 裡面呼叫 checkUsername 傳入參數是 5，你覺得這是跟詞法作用域有關係而已，還是跟閉包有關係？可是開發者會需要寫很多的相容性的程式碼，這樣不會變得很混亂嗎？有沒有什麼套件可以一次轉換？

Gemini： 第一是「閉包」，第二是「現代前端開發早就不用手寫這些相容性程式碼了」。不能直接寫 el.addEventListener('blur', checkUsername(5))，因為那樣會立即執行並把回傳值傳給監聽器。詞法作用域是規則（決定匿名函式在定義時能存取哪些外層變數），閉包是現象與機制（函式被註冊給 DOM 後仍留在記憶體，觸發時仍能存取當初捕獲的環境），所以核心本質是閉包。相容性方面有三層工具：Polyfill（core-js，自動補缺失 API）、Transpiler（Babel，把 ES6+ 語法降級成 ES5）、以及 Babel + Polyfill + Browserslist 的專案自動化整合。

使用者： > 0.5% / last 2 versions / Firefox ESR / not dead，那如果不是 Firefox 也要一一寫出來嗎？

Gemini： 不用。Browserslist 是查詢語法、是篩選條件組合，條件之間是 OR（聯集）關係。> 0.5% 一行就涵蓋所有市佔超過 0.5% 的瀏覽器；last 2 versions 涵蓋主流瀏覽器最新兩版；Firefox ESR 單獨列出是因為企業長期支援版更新慢、市佔常不到 0.5%；not dead 排除已停止維護的廢棄瀏覽器。要針對特定瀏覽器才需要寫 Chrome >= 80、iOS >= 12、ie 11 這種。現代專案大多只要三行 > 0.5% / last 2 versions / not dead。

使用者： Browserslist 是一個插件嗎？

Gemini： 不是獨立執行的瀏覽器外掛，而是前端工具生態系的共用設定規格與庫。它同時是一個放在專案根目錄的設定檔（.browserslistrc 或 package.json 的 browserslist 欄位），也是一個 Node.js 的 npm 套件；Babel、Autoprefixer、ESBuild、SWC、Vite、Webpack 底層都引入了它。核心功能是把人類語言條件轉成確切的瀏覽器版本清單，扮演建置流程的「中央指令中心」，一次設定全家套用。

使用者： 「或直接寫在 package.json 裡的 browserslist 欄位」這邊怎麼寫？

Gemini： 在根層級新增 "browserslist" 欄位，值用字串陣列（條件之間同樣是 OR）。也可以改寫成物件格式做分環境設定，production 注重相容性、development 只支援最新瀏覽器以追求編譯速度。寫在 package.json 的優點是少維護一個獨立的 .browserslistrc 檔案。
