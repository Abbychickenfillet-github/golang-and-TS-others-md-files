Docker Socket 與 Client-Daemon 通訊—順便解剖 /var/lib/docker 路徑

🔖 本篇重點索引：a–r，共 18 個。

重點整理

一、Socket 是什麼

(a) Socket（插座／通訊端點）定義：在電腦網路與行程間通訊（IPC，Inter-Process Communication）中，Socket 是應用程式之間進行雙向資料傳輸的「端點」。它是一個抽象的收發窗口，不是一段資料。

(b) 兩個好記的類比：

  • 硬體類比：牆上的插座與插頭——插上去，電力（資料）就能流動。
  • 軟體類比：一個檔案路徑，或一組 IP＋Port。程式 A 往這裡寫，程式 B 就能從這裡讀。

(c) Unix Domain Socket（UDS，Unix 網域通訊端）：Docker 在 Linux 上的預設通訊方式，路徑是 /var/run/docker.sock。三個關鍵特性——

  • 它不是網路協定，而是一個特殊的檔案（用 ls -l 看，檔案類型是 s）。
  • 僅限同一台機器上的不同行程（Process）互通。
  • 效能極高，因為不需要經過 TCP/IP 協定堆疊的封裝與解封裝。

(d) UDS 的安全模型＝檔案權限：因為它就是一個檔案，誰能存取 Docker 完全由這個檔案的擁有者與群組決定。這就是為什麼你要嘛加 sudo，要嘛把自己加進 docker 群組。

(e) ⚠️ 把 docker.sock 掛進容器＝把 root 權限送出去：常見寫法 -v /var/run/docker.sock:/var/run/docker.sock（例如 Portainer、CI runner）等於讓容器內的程式可以任意操控主機的 Docker Daemon，包含起一個掛載主機根目錄的特權容器。這在安全上等同交出主機 root，只在完全信任的映像檔上才這樣做。

(f) TCP Socket（Remote API）：需要遠端操控另一台伺服器的 Docker 時使用，形式是 tcp://<IP>:2375（未加密）或 tcp://<IP>:2376（TLS 加密）。資料會封裝進 TCP 封包經網路卡送出。2375 未加密埠絕對不可以曝露在公網，等於開放無密碼的 root shell。

二、Docker 到底是 Client 還是 Server

(g) 答案：Docker 是一個完整的 C/S（Client-Server，主從式）系統，兩部分都包含。

元件 角色 主要職責
Docker Client（docker CLI） 發令者 我們在終端機打的 docker build／pull／run。它不負責執行容器，只把指令打包成 API 請求送給後端
Docker Daemon（dockerd） 執行者（Server） 長駐後台的服務，管理映像檔、容器、網路與磁碟卷軸（Volume）。真正幹活的就是它

(h) 「Server 部分只有 Daemon 嗎？」嚴格來說是的：真正處理運算、存取資源、執行管理邏輯的伺服器端就是 dockerd，它對外提供一套 REST API。

(i) 即使同機也要走 Socket：Client 與 Daemon 就算在同一台電腦上，Client 仍然得透過 Socket 送請求，邏輯跟瀏覽器連到網頁伺服器一模一樣。這解釋了為什麼 Docker Desktop 沒開時 docker ps 會報「Cannot connect to the Docker daemon」——不是指令壞了，是電話那頭沒人接。

(j) docker run 的完整流向（六步）：

  1. 使用者在終端機輸入 docker run hello-world。
  2. Docker Client 收到指令，轉換成一個 REST API 請求。
  3. 請求被寫入 /var/run/docker.sock。
  4. Docker Daemon 監聽該 Socket，收到請求。
  5. Daemon 檢查本機有無映像檔、分配記憶體與 CPU、啟動容器。
  6. Daemon 把結果沿原路傳回 Client，顯示在終端機上。

三、路徑解剖—為什麼是 /var/run 與 /var/lib

(k) Linux 路徑不是隨便取的：遵循 FHS（Filesystem Hierarchy Standard，檔案系統階層標準）。懂了 var 與 lib，就懂 Docker 為什麼把東西放那裡。

(l) /var ＝ Variable（會變動的）：專門存放系統運作過程中內容會不斷改變的檔案——日誌（Logs）、快取（Cache）、暫存檔，以及各種服務的執行資料。Docker 在這裡，是因為容器的狀態、日誌、暫存資料一直在變。

(m) /lib ＝ Library（函式庫／資料庫）：存放程式執行時需要的核心資料、共用函式庫或應用程式的內部資料。Docker 把最核心的「資產」（映像檔層、容器層資料）都放這。

(n) /var/lib/docker ＝ Docker 的倉庫總部（進去通常需要 root 權限）：

子目錄 存放內容
image/ 映像檔（Images）的元資料與層級資訊
containers/ 所有容器的組態與日誌
volumes/ 你建立的 Docker Volumes（持久化資料）
overlay2/ 實際的磁碟層資料，佔硬碟空間最大的地方

(o) /var/run 與 /var/lib 的分工，一句話記住：

  • /var/run/docker.sock＝通訊窗口，像電話線。存放「系統啟動後到現在」的資訊，特別是行程 ID（PID）與 Socket 檔案；Docker 沒跑就不存在，重開機後重建。
  • /var/lib/docker＝資料倉庫，像倉庫。重開機後還在，刪掉等於刪光所有映像檔與容器。

四、匿名卷（Anonymous Volume）能不能持久化

(p) 答案：可以持久化，但管理起來非常麻煩。只要是 Volume，不論具名或匿名，資料在實體上都存在主機的 /var/lib/docker/volumes/，只要不主動刪除那個卷，資料就不會消失。匿名卷的產生方式是 docker run -v /data（只給容器內路徑，沒給名稱或主機路徑），Docker 會自動配一串雜湊碼當名字。

(q) 匿名卷 vs 具名卷：

特性 匿名卷（Anonymous） 具名卷（Named）
建立方式 -v /container/path -v my_data:/container/path
資料持久化 會（重啟容器資料仍在） 會
容器刪除後 卷變成「孤兒（dangling）」殘留在硬碟 保留，名稱清晰好找
可重複利用性 極低，你記不住那串亂碼 極高，隨時掛給新容器

(r) 匿名卷的兩大痛點與實務建議：

  • 難以識別：跑十個容器就有十個亂碼資料夾，根本分不出誰是誰。
  • 生命週期陷阱：刪容器時若下 docker rm -v，Docker 會連匿名卷一起刪掉；具名卷通常會被保留。
  • 建議：開發測試圖方便可以用匿名卷；正式環境與重要資料一律用具名卷或 Bind Mount，這樣升級容器版本時才能把舊資料輕鬆掛到新容器。
# 查看所有「孤兒」卷（沒被任何容器使用）
docker volume ls -f dangling=true

# 看某個卷實際落在主機哪個路徑
docker volume inspect <volume_name>

# ⚠️ 清掉所有孤兒卷（不可復原，執行前先 inspect 確認）
docker volume prune

補充—docker pull 的「完整句子」

對話最後 Abby 問 docker pull 的完整寫法。整理如下（本段依 Docker 官方文件補齊，原始回覆內容未完整擷取到）：

# 一般人打的簡寫
docker pull nginx

# 管理指令的完整形式（docker pull 是它的別名）
docker image pull nginx

# Docker 實際幫你補齊之後的完整座標
docker pull docker.io/library/nginx:latest
#            └─ registry ─┘└ namespace ┘└name┘└ tag ┘

# 完整語法
docker pull [OPTIONS] NAME[:TAG|@DIGEST]

三個被省略的東西：registry（登錄機構）預設補 docker.io、namespace（命名空間）對官方映像檔預設補 library、tag（標籤）預設補 latest。latest 不代表「最新版」，它只是一個普通標籤名，正式環境請釘死版本號或用 @sha256: digest。
