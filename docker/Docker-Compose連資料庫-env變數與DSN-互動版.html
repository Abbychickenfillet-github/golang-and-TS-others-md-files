1. 一句話結論

Docker 連資料庫沒有 tokenization。

compose 在建立容器時把 environment: 的變數注入 Go 程序 → Go 用 os.Getenv 讀出 host、帳號、密碼 → 拼成一條 DSN（Data Source Name，資料來源名稱）連線字串 → 交給 GORM（Go 的 ORM）和 go-sql-driver/mysql（MySQL driver）開 TCP 連線 → 用 MySQL 自己的帳號密碼握手完成認證。

主機名稱寫 mysql 就能連到，是因為 compose 把每個 service 名稱註冊成內部網路的 DNS 名稱。

3. 指令一行一行拆

docker compose -f backend-go/docker-compose.dev.yml up --build
片段做什麼
dockerDocker CLI（client）把請求透過 named pipe 傳給 dockerd（daemon，背景服務）。真正建容器的是 daemon。
composecompose 外掛讀 YAML 檔，把「多個容器＋網路＋volume」一次排好。
-f backend-go/…yml指定要讀哪一份 compose 檔。不寫的話預設讀目前資料夾的 compose.yaml 或 docker-compose.yml。檔案所在資料夾就是 project 目錄，所以 build.context: . 指的是 backend-go/。
up建立網路、volume、容器，然後啟動，並把所有容器的 log 印在終端機（前景模式，加 -d 才會丟到背景）。
--build啟動前先重新 build 有 build: 的服務（這裡是 backend-go）。每 build 一次就會留下舊的 layer 和 build cache，這才是 vhdx 變大的主因。
你這份 backend-go/docker-compose.dev.yml 檔頭寫著「這份是備用」，主要檔案在 deploy/docker/docker-compose.dev.yml。兩份要一起改，不然會出現「改了沒反應」。

4. 為什麼 host 寫 mysql 就連得到

compose 啟動時會建立一個預設網路 <專案名>_default，每個 service 都加入這個網路，而且 service 名稱（mysql、redis）會變成可以被解析的主機名稱。

誰在連host 要寫port原因
backend-go 容器mysql3306走 compose 內部網路，用 service 名稱解析
你在 Windows 上的 DBeaver、或直接 go runlocalhost3306靠 ports: "3306:3306" 把容器的 port 開到主機
容器裡寫 localhost✗ 連不到—容器裡的 localhost 是容器自己，不是 MySQL

ports: 是給主機用的，容器和容器之間互連根本不需要 ports:。

所以 Redis 的 REDIS_HOST=redis 也是同樣道理。

5. env 變數怎麼一路走到 Go

5-1 compose 宣告變數

backend-go:
  environment:
    - MYSQL_HOST=mysql
    - MYSQL_PORT=3306
    - MYSQL_USER=root
    - MYSQL_PASSWORD=password
    - MYSQL_DATABASE=ticketing_dev

在 backend-go 容器建立時，compose 把這 5 個 KEY=VALUE 放進容器裡程序的環境變數，跟你在終端機打 export MYSQL_HOST=mysql 效果一樣。

5-2 Go 讀出來（internal/config/config.go:174）

Host: getEnv("MYSQL_HOST", "localhost"),

去環境變數找 MYSQL_HOST，有就用它的值（mysql），找不到就用預設值 localhost。這就是為什麼不用 Docker 直接 go run 時也能連本機 MySQL。

5-3 拼成 DSN（config.go:296）

fmt.Sprintf("%s:%s@tcp(%s:%d)/%s?charset=utf8mb4&parseTime=True&loc=Local",
    user, password, host, port, dbName)

把帳號、密碼、主機、port、資料庫名稱依序填進格式字串，產出像 root:password@tcp(mysql:3306)/ticketing_dev?charset=utf8mb4&parseTime=True&loc=Local 的一條字串。

DSN 片段意思
root:password@MySQL 帳號：密碼
tcp(mysql:3306)用 TCP 連到主機 mysql 的 3306 port
/ticketing_dev預設使用的資料庫
charset=utf8mb4用完整 UTF-8（包含 emoji）
parseTime=True把 DATETIME 欄位轉成 Go 的 time.Time，不然會拿到 []byte
loc=Local時間用容器的本地時區解讀

5-4 開連線（internal/database/database.go:60）

db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{ ... })

mysql.Open(dsn) 把 DSN 包成 GORM 看得懂的 dialector（方言設定），gorm.Open 再用它建立一個帶連線池的 *gorm.DB，之後所有查詢都從池子裡借連線。

6. 你說的「tokenization」其實是 MySQL 認證握手

連資料庫用的是帳號密碼，不是 token。driver 開 TCP 連線之後的流程：

  1. MySQL server 先送出問候封包，裡面有一段隨機 salt（亂數）。
  2. driver 用密碼和 salt 算出雜湊（MySQL 8 預設外掛是 caching_sha2_password），只送雜湊，不送明文密碼。
  3. server 驗證通過回 OK，這條連線就放進連線池重複使用。

同一份 compose 裡真正跟 token 有關的是 JWT_SECRET：

那是「使用者 ↔ 你的 Go 後端」的登入憑證，Go 用 JWT_SECRET 簽 token 給前端。後端 ↔ 資料庫這一段完全不用 JWT。

7. build 時 vs 執行時：dev 和 build 差在哪

設定方式什麼時候生效改了要怎樣才生效你的例子
compose environment:容器建立時（執行時）docker compose up -d 重建容器即可，不用 rebuildMYSQL_HOST、JWT_SECRET
Dockerfile ENV寫進映像檔，執行時讀要 rebuildDockerfile.dev 沒用到
compose build.args＋Dockerfile ARG只在 build 時要 rebuild被註解掉的前端 VITE_API_URL

Go 後端是執行時才讀 env，所以同一個映像檔換 env 就能連不同資料庫（本機 MySQL 或 Zeabur staging）。

Vite 前端剛好相反：VITE_* 在 build 時就被寫死進 JS 檔，所以要用 build args，改了一定要重 build。

docker compose restart 只是重開同一個容器，不會套用新的 env。改了 environment 要用 docker compose up -d，compose 發現設定變了會重建容器。

dev 模式的熱重載是另一件事：

volumes: - .:/app 把你的原始碼掛進容器，air（Go 熱重載工具）偵測到 .go 檔變動就重新編譯，env 不受影響。

8. compose 裡 env 的 4 種寫法與優先順序

# a. environment 清單（你現在的寫法）
environment:
  - MYSQL_HOST=mysql

# b. environment map 寫法，效果一樣
environment:
  MYSQL_HOST: mysql

# c. env_file：把整個檔案的 KEY=VALUE 都注入容器
env_file:
  - .env.dev

# d. ${} 插值：值從主機的 shell 或 project 目錄的 .env 讀
environment:
  - MYSQL_PASSWORD=${MYSQL_PASSWORD}

a 和 b 只是 YAML 的兩種寫法。c 是把一整份檔案搬進容器。d 是在 compose 解析 YAML 時，先把 ${MYSQL_PASSWORD} 換成主機上的值再交給容器。

常見誤會：project 目錄的 .env 預設只拿來做 ${} 插值，不會自動整包進容器。要整包注入要用 env_file:。

同一個變數寫在多個地方時，誰贏（官方文件順序，1 最優先）

  1. docker compose run -e KEY=VALUE
  2. environment: 或 env_file:，而且值是從 shell 或 .env 插值進來的
  3. 只寫在 environment:
  4. env_file:
  5. Dockerfile 的 ENV

檢查最後實際值的方法：

docker compose -f backend-go/docker-compose.dev.yml config
docker compose -f backend-go/docker-compose.dev.yml exec backend-go env | grep MYSQL

第一行印出插值完成後的完整 compose 設定。第二行進到執行中的 backend-go 容器，列出它真正拿到的 MYSQL 開頭變數。

9. ⚠️ 你這份 compose 檔的安全問題

backend-go/docker-compose.dev.yml 有被 git 追蹤，remote 指向 GitHub。檔案裡直接寫了真的金鑰：

  • Zeabur staging 資料庫密碼（雖然被註解，還是在檔案裡）
  • Google OAuth client secret
  • AWS access key 和 secret key
  • Mailgun API key

（這篇筆記刻意不抄任何金鑰的值。）

建議處理順序：

  1. 到 GitHub 確認 repo 是 private，以及有誰有權限看。
  2. 如果 repo 曾經公開或分享給別人，到 AWS、Google Cloud Console、Mailgun、Zeabur 重新產生（rotate）這些金鑰，因為 git 歷史裡還留著舊值。
  3. 把金鑰搬到 backend-go/.env.dev，加進 .gitignore，compose 改成 env_file: .env.dev 或 ${} 插值。
  4. 另外提交一份 .env.example，只放 key 不放值，讓別人知道要設定哪些變數。

小細節：compose 幫 MySQL 建了 devuser 帳號，但 backend-go 其實用 root 連線。開發環境沒關係，正式環境要用權限較小的帳號。

10. 自我測驗

是非題

申論題

Q1. 為什麼同一份 Go 映像檔可以連本機 MySQL 也可以連 Zeabur staging，但 Vite 前端換 API 網址就得重 build？

Go 是在程式啟動時用 os.Getenv 讀 MYSQL_HOST，所以只要換 compose 的 environment 再重建容器就好。Vite 的 VITE_* 是在 build 時被字串替換寫進打包好的 JS，瀏覽器裡根本沒有 process.env，所以改值一定要重新 build。

Q2. backend-go 容器報錯 dial tcp 127.0.0.1:3306: connect: connection refused，可能是哪裡設錯？怎麼查？

127.0.0.1 代表 Go 讀到的 host 是 localhost，最可能是 MYSQL_HOST 沒傳進容器，getEnv 用了預設值 localhost。用 docker compose exec backend-go env | grep MYSQL 檢查，確認改的是正在用的那份 compose 檔（備用檔和 deploy/docker 主檔），改完用 up -d 重建容器而不是 restart。
