# GoF 23 種設計模式總覽

> [!info] 這篇跟其他筆記的關聯，以及為什麼要一起看
> - a. [[高階函式與函數式範式-取代OOP三大設計模式]]：那篇是**特寫**，示範怎麼用高階函式取代 Strategy、Decorator、Factory 三個模式的 OOP 寫法。這篇是**母集合**，先給你 23 個模式的全景，才知道那三個在地圖上的位置，以及為什麼偏偏是那三個最容易被函式取代。
> - b. [[00-前端框架比較-Vue-React-Angular難易度與優缺點]] 的第 (i) 點：那裡的 Vue `Proxy` 響應式是本篇 **Proxy 代理模式**的真實產品級實例。模式是抽象的，那篇是它長在框架裡的樣子。
> - c. [[程序編程-Procedural-Programming-與控制反轉IoC對比]]：設計模式的存在理由幾乎都是「把控制權從呼叫端搬走」，跟控制反轉是同一個母題的不同尺度。

---

## 一、GoF 是什麼

<mark style="background: #FFF3A3A6;">GoF ＝ Gang of Four（四人幫），指 Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides 四位作者。</mark>

他們在 1994 年出版《Design Patterns: Elements of Reusable Object-Oriented Software》（中譯《設計模式：可復用物件導向軟體的基礎》），整理出 23 個模式。因為作者剛好四個人，社群戲稱這本書為 GoF，久了變成標準簡稱，講「GoF 模式」就是指這 23 個。

> [!warning] 三個常見誤解
> - a. <mark style="background: #FF5582A6;">設計模式不是語法也不是函式庫</mark>，它是「某類問題反覆出現時，社群收斂出來的解法骨架」。你不會 import 一個 Proxy 模式，你是照它的結構寫。
> - b. <mark style="background: #FF5582A6;">23 個不需要都背</mark>。前端日常真正會遇到的大約 6 到 8 個，其餘多半出現在後端或框架原始碼裡。
> - c. <mark style="background: #FF5582A6;">很多模式在 JavaScript 裡會「消失」</mark>。因為 JS 的函式是一等公民，OOP 需要用一整個類別解決的事，JS 用一個函式就做完了——這正是 [[高階函式與函數式範式-取代OOP三大設計模式]] 那篇的主題。

## 二、為什麼分成三類

分類依據是<mark style="background: #FFF3A3A6;">「這個模式在管什麼」</mark>：

| 類別 | 數量 | 管什麼 | 一句話 |
|---|---|---|---|
| <mark style="background: #ADCCFFA6;">創建型 Creational</mark> | 5 | 物件**怎麼被生出來** | 把「new 什麼」這件事跟「用它」解耦 |
| <mark style="background: #ADCCFFA6;">結構型 Structural</mark> | 7 | 物件**怎麼被組裝在一起** | 用組合的方式擴充功能，而不是繼承 |
| <mark style="background: #ADCCFFA6;">行為型 Behavioral</mark> | 11 | 物件**之間怎麼溝通與分工** | 把「誰在什麼時候做什麼」變成可抽換的 |

## 三、23 個模式完整清單（依原書順序）

### 創建型 Creational（5 個）

| # | 模式 | 一句話 | 前端有沒有遇過 |
|---|---|---|---|
| 1 | Abstract Factory 抽象工廠 | 生產「一整組相關的物件」，不指定具體類別 | 少，多見於跨平台 UI 套件 |
| 2 | Builder 建造者 | 分步驟組裝複雜物件，同樣步驟可產出不同結果 | <mark style="background: #BBFABBA6;">有</mark>：鏈式 API 如查詢建構器 |
| 3 | Factory Method 工廠方法 | 由子類別決定要生出哪一種物件 | <mark style="background: #BBFABBA6;">有</mark>：`createStore()`、`createRouter()` |
| 4 | Prototype 原型 | 複製既有物件來產生新物件 | <mark style="background: #BBFABBA6;">有，而且是語言內建</mark>：JS 的原型鏈 |
| 5 | Singleton 單例 | 保證一個類別只有一個實例，並提供全域存取點 | <mark style="background: #BBFABBA6;">有</mark>：Pinia／Redux store、資料庫連線池 |

### 結構型 Structural（7 個）

| # | 模式 | 一句話 | 前端有沒有遇過 |
|---|---|---|---|
| 6 | Adapter 轉接器 | 把 A 的介面轉成 B 期待的樣子，讓不相容的兩邊能合作 | <mark style="background: #BBFABBA6;">有</mark>：把第三方 API 回傳格式轉成前端要的形狀 |
| 7 | Bridge 橋接 | 把抽象與實作拆成兩條可獨立變化的軸 | 少 |
| 8 | Composite 組合 | 讓「單一物件」與「物件樹」用同一套介面操作 | <mark style="background: #BBFABBA6;">有</mark>：DOM 樹、React 元件樹 |
| 9 | <mark style="background: #FFF3A3A6;">Decorator 裝飾器</mark> | 包一層，動態加上新功能，不改原本的東西 | <mark style="background: #BBFABBA6;">有，而且很常用</mark>：React 的 HOC、中介層 middleware |
| 10 | Facade 外觀 | 給一堆複雜子系統一個簡單的統一入口 | <mark style="background: #BBFABBA6;">有</mark>：把 fetch 包成 `api.getUser()` |
| 11 | Flyweight 享元 | 大量相似物件共用同一份內部狀態，省記憶體 | <mark style="background: #BBFABBA6;">有</mark>：長列表虛擬滾動的節點回收 |
| 12 | <mark style="background: #FFF3A3A6;">Proxy 代理</mark> | 放一個替身控制對真實物件的存取 | <mark style="background: #BBFABBA6;">有，語言內建</mark>：JS 的 `Proxy`、Vue 3 響應式 |

### 行為型 Behavioral（11 個）

| # | 模式 | 一句話 | 前端有沒有遇過 |
|---|---|---|---|
| 13 | Chain of Responsibility 責任鏈 | 請求沿著一條鏈傳，誰能處理誰接手 | <mark style="background: #BBFABBA6;">有</mark>：Express／Koa 的 middleware、事件冒泡 |
| 14 | Command 命令 | 把「一個操作」包成物件，可以排隊、記錄、復原 | <mark style="background: #BBFABBA6;">有</mark>：Redux 的 action、undo／redo |
| 15 | Interpreter 直譯器 | 為一種語言定義文法並寫出解讀器 | 少，見於模板編譯器、正規表達式引擎 |
| 16 | <mark style="background: #FFF3A3A6;">Iterator 迭代器</mark> | 提供統一走訪集合的方式，不暴露內部結構 | <mark style="background: #BBFABBA6;">有，語言內建</mark>：`Symbol.iterator`、`for...of` |
| 17 | Mediator 中介者 | 讓物件不直接互相引用，全部透過中介溝通 | <mark style="background: #BBFABBA6;">有</mark>：事件匯流排 event bus |
| 18 | Memento 備忘錄 | 存下物件的快照，之後能還原 | <mark style="background: #BBFABBA6;">有</mark>：表單草稿、時光旅行除錯 |
| 19 | <mark style="background: #FFF3A3A6;">Observer 觀察者</mark> | 一個物件變了，自動通知所有訂閱它的人 | <mark style="background: #BBFABBA6;">有，到處都是</mark>：`addEventListener`、RxJS、Vue 的依賴收集 |
| 20 | State 狀態 | 物件內部狀態改變時，行為跟著整組換掉 | <mark style="background: #BBFABBA6;">有</mark>：狀態機、XState |
| 21 | <mark style="background: #FFF3A3A6;">Strategy 策略</mark> | 把可替換的演算法各自封裝，執行期挑一個用 | <mark style="background: #BBFABBA6;">有</mark>：排序比較函式、驗證規則 |
| 22 | Template Method 樣板方法 | 父類別定好流程骨架，細節留給子類別填 | <mark style="background: #BBFABBA6;">有</mark>：框架生命週期鉤子 |
| 23 | Visitor 訪問者 | 把操作從資料結構裡抽出來，可以對同一棵樹做不同事 | <mark style="background: #BBFABBA6;">有</mark>：Babel／ESLint 走訪 AST |

> [!note] 為什麼有些網站說只有 22 個
> Refactoring.Guru 等資源會省略 <mark style="background: #FFB86CA6;">Interpreter 直譯器</mark>，因為它在應用開發中極少用到，只有寫語言工具的人會碰。<mark style="background: #BBFABBA6;">原書是 23 個，記 23 這個數字才不會在面試被問倒。</mark>

## 四、Proxy、Decorator、Adapter 是三兄弟：結構幾乎一樣，差在意圖

<mark style="background: #FF5582A6;">這是面試最愛考的辨異題，因為三個模式的 UML 圖長得幾乎一模一樣——都是「包一層」。</mark>區分它們的唯一依據是**你為什麼要包這一層**：

| 模式 | 介面有沒有變 | 功能有沒有變 | 意圖（為什麼包） |
|---|---|---|---|
| <mark style="background: #ADCCFFA6;">Proxy 代理</mark> | 不變 | 不變 | <mark style="background: #FFF3A3A6;">控制存取</mark>：延遲載入、權限檢查、記錄、快取。你以為在跟本人講話，其實中間有人在記帳。 |
| <mark style="background: #ADCCFFA6;">Decorator 裝飾器</mark> | 不變 | <mark style="background: #BBFABBA6;">變多了</mark> | <mark style="background: #FFF3A3A6;">附加功能</mark>：原本的能力都在，額外多長出新的。可以層層疊。 |
| <mark style="background: #ADCCFFA6;">Adapter 轉接器</mark> | <mark style="background: #BBFABBA6;">變了</mark> | 不變 | <mark style="background: #FFF3A3A6;">相容轉換</mark>：能力沒增減，只是把插頭換成對方插得進去的形狀。 |

> [!tip] 一句話記法
> **Proxy 是保鑣，Decorator 是外掛，Adapter 是轉接頭。**保鑣不改變你的能力只管誰能找你；外掛讓你多會一招；轉接頭讓你插得進不同的孔。

### Vue 的 Proxy 為什麼是 Proxy 而不是 Decorator

`reactive(obj)` 回傳的替身，<mark style="background: #FFF3A3A6;">介面完全一樣（你還是寫 `state.count`）、功能完全一樣（讀到的還是那個值）</mark>，多出來的只有「在背後記錄誰讀了誰寫了」。這符合 Proxy 的定義：控制存取，不改變契約。

如果它讓你多出一個原本沒有的方法，那才會變成 Decorator。細節見 [[00-前端框架比較-Vue-React-Angular難易度與優缺點]] 第 (i) 點。

## 五、HOC 是 Decorator 模式在 React 的實現

> [!warning] 先把兩個縮寫分清楚，它們常被混用
> - a. <mark style="background: #FF5582A6;">HOF ＝ Higher-Order Function（高階函式）</mark>：接收函式當參數，或回傳一個函式的**函式**。例如 `map`、`filter`、`debounce`。
> - b. <mark style="background: #FF5582A6;">HOC ＝ Higher-Order Component（高階元件）</mark>：接收一個**元件**、回傳一個新元件的函式。例如 `withRouter(MyPage)`、`connect(mapState)(MyPage)`。
>
> HOC 是 HOF 的一個特例——它剛好處理的是 React 元件。<mark style="background: #FFF3A3A6;">HOC 的 C 是 Component 不是 Function</mark>，這一個字母在面試講錯會被聽出來。

HOC 完全符合 Decorator 的三個特徵：

- a. **介面不變**：`withAuth(Profile)` 回傳的東西還是一個元件，用起來跟 `Profile` 一樣。
- b. **功能變多**：多了登入檢查、多了注入的 props。
- c. **可以層層疊**：`withRouter(withAuth(withTheme(Page)))`，這正是 Decorator 模式的招牌用法。

```javascript
// Decorator 模式的 React 版本
function withLogger(WrappedComponent) {
  return function Enhanced(props) {
    console.log('[render]', WrappedComponent.name, props);
    return <WrappedComponent {...props} />;   // 原本的能力原封不動傳下去
  };
}

const LoggedButton = withLogger(Button);       // Button 什麼都沒改，但多了 log
```

> [!info] 為什麼這一格要跟 [[高階函式與函數式範式-取代OOP三大設計模式]] 一起看
> 那篇的核心論點是「JS 有一等公民函式，所以 OOP 需要一整個類別階層才能做到的 Strategy、Decorator、Factory，在 JS 裡一個函式就解決了」。<mark style="background: #BBFABBA6;">HOC 就是這句話最漂亮的證據</mark>：Java 的 Decorator 要定義抽象元件、具體元件、抽象裝飾器、具體裝飾器四個類別，React 只要一個接收元件回傳元件的函式。兩篇合起來看，才會理解「設計模式不是消失了，是被語言特性吸收了」。
>
> 補充：React 現在多半改用 <mark style="background: #FFB86CA6;">自訂 Hook</mark> 取代 HOC，因為 HOC 會疊出很深的元件樹（wrapper hell）且 props 來源難追。<mark style="background: #FFF3A3A6;">但 Hook 不是 Decorator，它比較接近 Strategy——把可替換的行為抽出來，由呼叫端決定用哪個。</mark>模式換了，因為問題換了。
