先定義：這個檔案裡的 Buffer 到底是什麼

就是一條 Uint32Array —— 一塊連續記憶體，每格固定 4 bytes，專門存 CSS tokenizer 掃描過程中產生的「純數字中繼資料」。

它不是檔案內容，也不是字串。原始 CSS 文字另外存在 source 裡；buffer 只存「第幾個字元到第幾個字元是一個 token、它是什麼型別、在第幾行第幾欄」這類座標與編號。

⬛ 退一步：這條 Uint32Array 底下是什麼 —— ArrayBuffer

// ① 開一塊原始記憶體
var buffer = new ArrayBuffer(8);
//                          └─ 單位永遠是 byte，不是 bit
//                             8 bytes = 64 bits
//   做的事：請 V8 幫你跟作業系統要一塊「連續的、固定長度的 8 bytes 原始記憶體」
//   注意：這塊記憶體不在 V8 的 JS heap 裡面，是 heap 外（off-heap）另外配置的，
//         JS 這邊只拿到一個持有指標的包裝物件

// ② ArrayBuffer 本身什麼都不能做
buffer[0] = 5;
console.log(buffer[0]);              // 5          ← 看起來有寫進去
console.log(new Uint8Array(buffer)); // [0,0,0,0,0,0,0,0]
//   真相：buffer[0] = 5 只是在「物件」上掛了一個叫 "0" 的普通屬性，
//         底層那 8 個 bytes 一個都沒動。ArrayBuffer 沒有索引讀寫能力。

// ③ 所以必須套一個「視圖 view」才能讀寫
var z = new Uint8Array(buffer, 1, 4);
//                     └──┬─┘  │  └─ length：要 4 個元素
//                        │    └──── byteOffset：從第 1 個 byte 開始
//                        └───────── 掛在這塊 buffer 上（借用，不是複製）

z.length      // 4   幾個元素
z.byteOffset  // 1   從第幾個 byte 起算
z.byteLength  // 4   共佔幾個 byte（Uint8 每格 1 byte，所以 4x1=4）
z.buffer === buffer   // true  ← 指向同一塊，沒有任何複製

// ④ 證明共用同一塊記憶體
var all = new Uint8Array(buffer);   // 看整塊 8 bytes 的視圖
z[0] = 255;
z[3] = 7;
console.log(Array.from(all));
// [0, 255, 0, 0, 7, 0, 0, 0]
//  ↑            ↑
//  byte 0 不在 z 範圍內，所以還是 0
//               z 寫的東西全部落在 byte 1~4
buffer（8 bytes）
 byte:  0    1    2    3    4    5    6    7
      ┌────┬────┬────┬────┬────┬────┬────┬────┐
      │ 0  │255 │ 0  │ 0  │ 7  │ 0  │ 0  │ 0  │
      └────┴────┴────┴────┴────┴────┴────┴────┘
            └──────── z ────────┘
            z[0] z[1] z[2] z[3]

⚠️ byteOffset 有對齊限制：必須是元素寬度的倍數。Uint8 每格 1 byte 所以 offset 給 1 沒問題；new Uint32Array(buffer, 1) 會噴 RangeError: start offset of Uint32Array should be a multiple of 4，Uint32 的 offset 只能是 0、4、8…

🔁 那 TypedArray 自己有沒有記憶體？沒有，它永遠只是視圖。

var u32 = new Uint32Array(8);        // 沒有傳 buffer 進去
u32.buffer instanceof ArrayBuffer    // true  ← 但它還是有一個
u32.buffer.byteLength                // 32    ← 8 元素 x 4 bytes，V8 偷偷幫你開的
u32.BYTES_PER_ELEMENT                // 4
//   白話：沒有「不是視圖的 TypedArray」這種東西。
//         你沒給 buffer，引擎就自己 new 一個再把視圖架上去。

同一塊 bytes，換個視圖就是完全不同的數字：

var b     = new ArrayBuffer(8);
var asU8  = new Uint8Array(b);       // 一格 1 byte
var asU32 = new Uint32Array(b);      // 一格 4 bytes，兩者看的是同一塊

asU8[0]=1; asU8[1]=0; asU8[2]=0; asU8[3]=0;
asU32[0]   // 1
asU8[0]=0; asU8[3]=1;
asU32[0]   // 16777216
//   白話：底層都是同樣 4 個 bytes，只是「1 放在哪一端」不同，
//         用 Uint32 讀出來就差了一千六百多萬倍。
//         這是 little-endian 小端序 —— 低位 byte 放在前面。

三層關係：ArrayBuffer（有記憶體、不能讀寫）→ 套上 TypedArray 視圖（沒記憶體、決定幾個 byte 算一個數字）→ 才有 u32[0] 這個可以讀寫的數字。
回到本篇：offsetAndType 能把 (type << 24) | end 塞進一格，正是因為它選了 Uint32 這個視圖 —— 換成 Uint8Array 視圖，同樣的記憶體會被切成 4 個互不相干的小數字，打包就失效了。

📌 補充（ES2024 起）：「固定長度」已經不是絕對。new ArrayBuffer(8, { maxByteLength: 16 }) 可以建立 resizable buffer，之後用 .resize(16) 改大小；一般寫法 new ArrayBuffer(8) 的 .resizable 是 false，仍然是固定的。另外 .transfer() 會把所有權轉走並讓原本那個 .detached === true，這就是 Worker 之間零複製傳遞（Transferable）的基礎。

css-tree v3.2.1 實際只有四個地方呼叫 adoptBuffer，就是這四條 buffer：

呼叫處buffer長度一格存什麼

TokenStream.js:57balancesource.length + 1括號／大括號的配對位置（哪個 index 跟哪個 index 成對）

為什麼長度用 source.length？因為 token 數事先不知道，所以拿「最壞情況 ＝ 每個字元都自成一個 token」當上界先開好，寧可開大也不要中途擴容。

🔑 這才是非用 32-bit 不可的真正原因（補強下面的 (k)）

const OFFSET_MASK = 0x00FFFFFF;   // 低 24 bits
const TYPE_SHIFT  = 24;
offsetAndType[index] = (type << TYPE_SHIFT) | end;   // 型別與 offset 打包進同一個數字

白話：它把兩個資訊塞進同一個 32-bit 整數 —— 左移 24 位把 token 型別推到高 8 bits，再用 | 把結束 offset 填進低 24 bits。一格就同時回答「這是什麼 token」和「它到哪裡結束」，不必開兩條陣列。所以不是「32-bit 比較夠用」，是結構上需要 24+8 這個切法，Uint8Array 根本塞不下。

副作用：offset 只有 24 bits，上限 16,777,215 —— 也就是 css-tree 能處理的 CSS 原始碼最大約 16 MB。

那「buffer」這個詞本身呢

通用定義是「一塊事先配置好、大小固定的連續記憶體，用來暫存正在流動中的資料」，存在的理由是兩端速度對不上（例如讀檔、網路封包）。但 css-tree 用的是另一種意思：它不是接資料流的桶子，而是可重複使用的工作區（scratch space）。同一個詞，這裡的重點在「重用」而不是「緩衝」—— 這也是 adoptBuffer 的 adopt（領養、沿用）這個字的由來。

⚠️ 別跟 cache 搞混：buffer 解決「速度／時機對不上」或「避免重複配置」，cache 解決「不想重算或重抓」。兩者都是中間層，目的不同。

重點整理

  • (a) adopt-buffer 是 css-tree（CSS parser 套件）內部的小工具函式：呼叫端傳入「既存的 Buffer（上一輪已配置好的 TypedArray）」與需要的 size，容量夠就原樣回傳重用，不夠才配置新的。
  • (b) 目的是減少記憶體配置與 GC（垃圾回收）壓力：若每次解析都 new Uint32Array(size)，會頻繁配置並觸發 V8 垃圾回收，造成卡頓。
  • (c) 這裡的 Buffer 就是「放資料的容器」：連續記憶體，裡面存 token 的起訖 offset、字元碼、換行位置等數字。
  • (d) 可信的實作形狀（依我所知 css-tree 原始碼）：const MIN_SIZE = 16 * 1024;，容量不足時 return new Uint32Array(Math.max(size + 1024, MIN_SIZE))，足夠時 return buffer。
  • (e) MIN_SIZE = 16 * 1024 是 16384 個「元素」，不是 16 KB；Uint32Array 每元素 4 Bytes，所以實際是 16384 × 4 = 65536 Bytes = 64 KB。
  • (f) Math.max(size + 1024, MIN_SIZE)：需求小（例如 100）時取保底 16384；需求大（例如 20000）時取 size + 1024 = 21024，多預留 1024 個元素當緩衝。
  • (g) new Uint8Array(2) 的 2 是「長度（元素個數）」，不是數值上限，總記憶體 = 2 × 1 Byte。
  • (h) uint8 = [1,2,3,...] 沒有報錯，是因為這句是把變數 uint8 重新賦值成一個普通 Array，原本的 Uint8Array 被丟棄，並不是改了 Uint8Array 的長度。
  • (i) TypedArray 長度固定：uint8[2] = 3 寫入越界索引會被忽略，uint8[2] 仍是 undefined，length 仍為 2。
  • (j) 8-bit 的限制在「元素值」：Uint8 範圍 0–255，存入 256 會 wrap（模 256）變 0，257 變 1。
  • (k) Uint32Array 範圍 0–4,294,967,295，適合存索引與偏移量（offset），所以 css-tree 用 32-bit 而不是 8-bit。
  • (l) 另一則對話順帶說明 Vue 的 v-model：它是 :value + @input 的語法糖，實現表單元素的雙向綁定；修飾符 .lazy（改在 change 事件同步）、.number（轉數字）、.trim（去頭尾空白）。
var uint8 = new Uint8Array(2);
uint8[0] = 256; uint8[1] = 257;
console.log(uint8[0], uint8[1]);   // 0 1（wrap）
uint8[2] = 3;                      // 越界寫入被忽略
console.log(uint8.length, uint8[2]); // 2 undefined

<!-- 等同於 -->
<input :value="message" @input="message = $event.target.value">

✅ 已查證結案（2026-10-10，實際下載 npm 套件 css-tree@3.2.1 讀原始碼 lib/tokenizer/adopt-buffer.js）：真實實作就是下面這五行，整段沒有任何複製舊資料的程式碼，所以筆記原本懷疑的「第一版說法（buffer.length * 2 或 2048、會把舊資料複製過去）不可採信」判斷正確。另外也確認 buffer.length < size 比的是元素個數而不是 bytes，(e) 的說法成立。

const MIN_SIZE = 16 * 1024;

export function adoptBuffer(buffer = null, size) {
    if (buffer === null || buffer.length < size) {
        return new Uint32Array(Math.max(size + 1024, MIN_SIZE));
    }

    return buffer;
};

白話逐行：預設參數 buffer = null 代表第一次呼叫時根本還沒有 buffer；buffer === null || buffer.length < size 是「沒有、或現有的裝不下」兩種情況合在一起判斷；成立就配一條新的 Uint32Array，長度取「需求 +1024 緩衝」與「保底 16384」之中較大者；都不成立就 return buffer 把原本那條原封不動還回去。
