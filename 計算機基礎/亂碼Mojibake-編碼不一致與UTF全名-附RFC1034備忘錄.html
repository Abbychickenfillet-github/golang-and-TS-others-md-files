重點整理

  • (a) 看到像 Sðpc-20 g*NØk> 的符號，是Mojibake（亂碼，日文「文字化け」）：檔案實際儲存的編碼與讀取時使用的編碼不一致。
  • (b) 最常見組合：檔案以 Big5（繁中）或 GBK（簡中）儲存，卻被當成 UTF-8 或 Windows-1252／ISO-8859-1（Latin-1，西歐編碼）讀取；ð、û、› 這類字元是多位元組中文被拆成單位元組後的典型殘影。
  • (c) 台灣環境中，Excel 匯出的 CSV 極大機率是 Big5；建議開發環境與資料庫統一用 UTF-8，匯入時再轉碼。
  • (d) Node.js 修復：用 fs.readFileSync 讀成 Buffer（不要直接讀字串），再用 iconv-lite 的 iconv.decode(buffer, 'big5') 轉成 UTF-8 字串。
  • (e) 瀏覽器修復：FileReader.readAsText(file, 'big5') 的第二個參數指定編碼。
  • (f) UTF = Unicode Transformation Format（Unicode 轉換格式），UTF-8 / UTF-16 / UTF-32 是把 Unicode 碼位（code point）編成位元組序列的不同方案。
  • (g) RFC（Request for Comments）文件標頭的「Memo」是歷史沿用稱呼，RFC 1034（Domain Names – Concepts and Facilities，DNS 核心觀念）是 Internet Standard（STD 13）。
  • (h) 「Distribution of this memo is unlimited」意思是本文件散佈不受限制，任何人可自由閱讀、複製、轉載；不是指「發行數量無限」。
  • (i) 診斷小技巧：先猜來源編碼（Big5 / GBK / UTF-8），用 iconv 或編輯器「以編碼重新開啟」逐一試，通常 1–2 次就能還原。
const fs = require('fs');
const iconv = require('iconv-lite');
const buffer = fs.readFileSync('data.txt');   // Buffer，不是字串
console.log(iconv.decode(buffer, 'big5'));    // 以 Big5 解碼成 UTF-8 字串

⚠️ 存疑/更正：Gemini 把 Mojibake 寫成「加持（Mojibake）」，這是錯誤翻譯，Mojibake 源自日文「文字化け」，中文就是「亂碼」。另外它從貼上的亂碼推測原內容是「電器規格或出貨清單」純屬猜測，無法由亂碼證實（500W、110V 只是殘留的 ASCII 字元）。

相關筆記：ASCII-美國資訊交換標準碼（ASCII 範圍的字元不會亂，這就是為何 500W 110V 還看得到）、Epoch時間起點-閏秒與UTC-GMT差別（同為標準文件的「規範背景」類筆記）。
