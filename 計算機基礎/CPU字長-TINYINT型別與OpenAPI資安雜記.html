重點整理

CPU 字長（Word Size）

(a) CPU 字長＝CPU「一次能思考的寬度」／內部管道寬度。當說電腦是「64 位元」，這個 64 就是字長，決定三件事：暫存器容量（64 位元字長 → 每個暫存器可裝 8 Bytes）、資料匯流排寬度（一次能搬運的資料量）、記憶體定址能力（最大支援多少 RAM）。

(b) 若 CPU 是 64 位元（字長 8 Bytes），即使程式只想讀 1 Byte 的 TINYINT，硬體管道通常還是會整組 8 Bytes 一起抓進來，再由內部邏輯把需要的那個 Byte 挑出來——這與另一篇 CPU 筆記中「Byte 是定址最小單位」的原則一脈相承，字長則是「一次搬運/處理的最大單位」。

TINYINT vs SMALLINT

(c) TINYINT＝1 Byte，範圍 -128~127（有號）或 0~255（無號），適合狀態碼、布林值、百分比。SMALLINT＝2 Bytes，範圍 -32768~32767（有號）或 0~65535（無號），適合數量、年齡、計數器。兩者是完全獨立的型別，同一張表可以混用，不會「打架」；只有寫入超出範圍的值才會出錯。設計原則：盡量選用能滿足需求的最小整數型別省空間，預期數字可能超過 65535 則該直接用 MEDIUMINT 或 INT。

sed 指令

(d) sed = Stream Editor（串流編輯器），命令列工具，逐行讀取輸入、對每行執行指定編輯操作後輸出，屬於非互動式、用於自動化/腳本化文字轉換的工具，最常見用途是查找替換：sed 's/old_host/new_host/g' config.txt（s=替換、g=全域替換一行中所有匹配）。

React useFormState 的 disabled 屬性

(e) useFormState 是一個「訂閱（Subscribe）」Hook，負責監聽表單狀態變化並在變化時觸發重新渲染。disabled: true 會讓 Hook 停止訂閱表單狀態更新，適合用在組件被隱藏、使用者尚未開始操作等不需要即時渲染的情境，目的是效能優化、減少不必要的 re-render。

OpenAPI 定位與資安價值

(f) OpenAPI（前身 Swagger）是與語言無關的 API 規格描述格式，定位是前端與後端之間的「契約（Contract）」，不屬於前端也不屬於後端；表單（Form）是 UI 組件，OpenAPI 定義的是表單送出後、伺服器期望收到的資料結構（Schema），而非表單 UI 本身。TanStack Router 這類前端路由工具透過 OpenAPI 生成的 TypeScript 型別，讓 Loaders 抓取的資料具備類型安全。

(g) 資料庫欄位限制（如 VARCHAR(50)）不會被 OpenAPI 自動實踐——必須在規格中明確寫入 maxLength: 50，且這個限制要靠前端表單驗證、後端 Middleware/Schema 驗證、資料庫層三道防線共同落實，資料庫的欄位型別限制永遠是最後一道防線。

(h) OpenAPI 對資安的核心價值：不是取代密碼加密或防 SQL 注入，而是透過標準化＋自動化大幅降低人為疏漏（漏檢查輸入長度、意外洩漏敏感欄位）。關鍵資安觀念：絕不能只信任前端驗證（Never Trust the Client）——前端驗證只是提升 UX，攻擊者可用 Postman/curl/Burp Suite 等工具完全繞過前端 JS 邏輯直接打後端 API；真正的安全防線在後端伺服器對每個請求依 OpenAPI 規格（maxLength、required、型別）做強制驗證，不合規請求直接回 400 拒絕，不讓資料碰到業務邏輯或資料庫。

攤位號碼（如 h10）資料表欄位設計

(i) 儲存像 h10 這種「字母區域+數字編號」格式的攤位代碼，建議拆成兩個欄位：stall_area（CHAR(1) 或 VARCHAR，存字母部分）+ stall_number（SMALLINT UNSIGNED，存數字部分），而非只用單一 VARCHAR 存整串。拆分的好處：可用 ORDER BY stall_area, stall_number 做精確排序（避免字串排序把 h10 排在 h2 前面的問題）、數字欄位有型別安全。

(j) 若要讓 stall_display（如 h10）自動等於兩欄位合併結果，最推薦用資料庫的 Generated Column（MySQL 5.7+/PostgreSQL 12+）：stall_display VARCHAR(10) AS (CONCAT(stall_area, stall_number)) STORED，插入/更新基礎欄位時自動算好並實際落地儲存，查詢速度最快；不支援的舊資料庫版本則退而求其次用 VIEW，但寫入仍須對底層基礎表操作。

追加：為何 1 bit 就夠、TINYINT 仍要佔 1 Byte（2026-07-21）

(k) 記憶體以 Byte 為最小可定址單位，CPU 無法對單一 bit 定址（無法要求記憶體「只給我這一個 bit」）；因此即使數值只需 2 位數二進位（如 01），系統仍必須配置最小可定址單位、也就是整個 1 Byte 空間給它，不存在「半個 Byte」的定址方式。這與 (b) 的「Byte 是定址最小單位、字長是一次搬運的最大單位」是同一原理的不同切角，Abby 前後兩次都問到同一個核心疑惑，值得留意這是她容易卡關的觀念。

(l) 「最小基本單位」vs「基本最小單位」：中文語意上前者強調「在一群基本單位裡，挑出規模最小的那個」；後者強調「那個被定義為系統基石的、本身就是最小尺度的單位」。落到 CPU/記憶體脈絡：Byte 是記憶體定址的「基本最小單位」（系統設計上就以它為定址基石，不可再切分定址），而在字長、快取行等不同「單位家族」裡各自的最小者則屬於「最小基本單位」的用法。⚠️ 存疑：Gemini 兩次針對這組詞義的回答用詞略有出入且偏抽象，本質上是中文構詞的語感辨析、非嚴謹計算機科學術語，Abby 若要在面試中引用建議直接用英文原詞（byte-addressable / word size）取代這組容易各自表述的中文措辭。
