1. 重點整理

  • (a) 看到像 Sðpc-20 g*NØk> 的符號，是Mojibake（亂碼，日文「文字化け」）：檔案實際儲存的編碼與讀取時使用的編碼不一致。 例：最常見的組合是，檔案以 Big5（繁中）或 GBK（簡中）儲存，卻被當成 UTF-8 或 Windows-1252／ISO-8859-1（Latin-1，西歐編碼）讀取。 ð、û、› 這類字元，是多位元組中文被拆成單位元組後的典型殘影。
  • (b) 台灣環境中，Excel 匯出的 CSV 極大機率是 Big5。開發環境與資料庫統一用 UTF-8，匯入時再轉碼。 票務系統專案實際踩過的是「檔名」而不是「內容」：2025-12-31 匯出「廠商支付_亞洲香水節.xlsx」時，中文檔名放進 HTTP 標頭觸發 UnicodeEncodeError: 'latin-1'，改用 RFC 5987 的 filename*=UTF-8'' 加上 URL 編碼解決。詳見 2025-12-31-http-header-chinese-encoding。 Excel 內容本身不會亂：專案用 excelize 產生 .xlsx，.xlsx 是壓縮過的 XML，固定用 UTF-8，沒有 CSV 那種 Big5／UTF-8 猜錯的問題。
  • (c) Node.js 修復：用 fs.readFileSync 讀成 Buffer（不要直接讀字串），再用 iconv-lite 的 iconv.decode(buffer, 'big5') 轉成 UTF-8 字串。 狀態：觀念筆記，尚未在票務系統專案實際使用（2026-11-15 查 git，iconv-lite 只以套件相依性出現在 package-lock.json，程式碼裡沒有呼叫）。
  • (d) 瀏覽器修復：FileReader.readAsText(file, 'big5') 的第二個參數指定編碼。
  • (e) UTF = Unicode Transformation Format（Unicode 轉換格式），UTF-8／UTF-16／UTF-32 是把 Unicode 碼位（code point）編成位元組序列的不同方案。 四者關係見 2. 主軸圖。
  • (f) Unicode 是字元集，負責定編號：像一本大字典，給全世界每個字元一個碼位，例如 a 是 U+0061，「中」是 U+4E2D。 它只定編號，不規定怎麼存成位元組，所以嚴格說 Unicode 不是編碼。日常說的「Unicode 編碼」，指的是 UTF-8、UTF-16 這類以 Unicode 為字典的編碼。
  • (g) UTF-8 是編碼，負責把碼位轉成位元組：英文 1 個位元組，中文通常 3 個位元組（「中」＝E4 B8 AD）。 「編碼（encoding）」的定義就是「把字元轉成位元組的規則」，所以稱 UTF-8 為編碼、或稱它為轉換規則，指的是同一件事。 反方向叫解碼：瀏覽器用 UTF-8 規則把 E4 B8 AD 還原成 U+4E2D，也就是「中」。用哪套規則解碼，由 charset 決定（見 3. charset 機制）。
  • (h) ASCII 同時是字元集也是編碼，只有 128 個字元，每個 1 個位元組。它是早期的小規模版本，現在被 UTF-8 吸收成前 128 個碼位，仍在使用（例如 HTTP 標頭）。 兩個刻意設計讓它跟 UTF-8 完全相容：Unicode 的 U+0000–U+007F 直接沿用 ASCII 編號，UTF-8 又規定這 128 個碼位用 1 個位元組、直接存編號本身。 所以 a 在兩種編碼裡都是 01100001，只有英文的檔案，用 ASCII 或 UTF-8 存，位元組完全相同。
  • (i) Base64 方向相反：把任意位元組轉成安全文字，只用 A–Z、a–z、0–9、+、/（加上補位的 =），方便把圖片等二進位資料塞進只接受文字的地方，例如 email、data URL。 64 個字元＝A–Z（26）＋a–z（26）＋0–9（10）＋+ 和 /（2）。網址用的 Base64URL 把 +、/ 換成 -、_，因為前兩個在網址裡有特殊意義。 「任意位元組」就是任何一串位元組：圖片、壓縮檔，甚至 UTF-8 文字本身都可以。做法是每 3 個位元組（24 位元）切成 4 段 6 位元，每段對應一個字元，所以資料約變大三分之一。 Base64 解碼＝安全字元 → 原本的位元組，跟 UTF-8 解碼（位元組 → 字元）方向相反。兩者常串接，例如 data URL：PNG 位元組 → Base64 字元 → 寫進 HTML 檔 → 再用 UTF-8 存成位元組。
  • (j) 傳輸時的 0 和 1 代表「文字」，不是「指令」：JS 檔用 UTF-8 編成位元組 → gzip／Brotli 壓縮 → 網路送出 → 瀏覽器解壓縮、用 UTF-8 解碼還原成 JS 文字。 要等 V8 把 JS parse、編譯之後，才產生 CPU 能執行的機器碼。 gzip／Brotli 不屬於 UTF-8，是另一個選用的無損壓縮步驟。HTTP 用兩個不同標頭分開宣告：Content-Type: text/javascript; charset=utf-8 管「位元組怎麼變回文字」，Content-Encoding: br 管「壓縮過的位元組怎麼還原」。
  • (k) RFC（Request for Comments）文件標頭的「Memo」是歷史沿用稱呼，RFC 1034（Domain Names – Concepts and Facilities，DNS 核心觀念）是 Internet Standard（STD 13）。
  • (l) 「Distribution of this memo is unlimited」意思是本文件散佈不受限制，任何人可自由閱讀、複製、轉載。
  • (m) 診斷小技巧：先猜來源編碼（Big5／GBK／UTF-8），用 iconv 或編輯器「以編碼重新開啟」逐一試，通常 1–2 次就能還原。
const fs = require('fs');
const iconv = require('iconv-lite');
const buffer = fs.readFileSync('data.txt');   // 讀成 Buffer（原始位元組），不要直接讀成字串
console.log(iconv.decode(buffer, 'big5'));    // 用 Big5 規則把位元組解碼成 JS 字串

白話：先拿到檔案的原始位元組，再告訴程式「這些位元組是用 Big5 編的」，它就能還原成正確的中文。

⚠️ 更正：Gemini 原回答把 Mojibake 寫成「加持（Mojibake）」，正確中文是「亂碼」。它從亂碼推測原內容是「電器規格或出貨清單」，無法由亂碼證實（500W、110V 只是殘留的 ASCII 字元）。

2. 主軸圖：Unicode、ASCII、Base64、UTF-8 的關係

2-1 文氏圖：左邊是字元，右邊是位元組，箭頭是編碼與解碼

讀法：外圈包內圈＝包含關係。粉紅實線＝編碼（往右、往位元組），藍色實線＝解碼（往左、回到字元），紫色曲線＝Base64（方向相反）。

  • (a) 左邊是字元的包含關係：Base64 的 64 個字元 ⊂ ASCII 128 個 ⊂ Unicode。 Base64 產出的字元全部在 ASCII 裡，ASCII 又全部在 Unicode 裡。
  • (b) 右邊是位元組的包含關係：ASCII 位元組 ⊂ UTF-8 合法序列 ⊂ 所有位元組序列。 不是每串位元組都是合法 UTF-8，例如 FF 在 UTF-8 裡永遠不會出現。
  • (c) UTF-8 不是一個圈，而是左右之間的箭頭：編碼把左邊的字元搬到右邊的綠圈，解碼反過來。順序固定是 ① 字元集 → ② 編碼規則 → ③ 位元組。
  • (d) ASCII 在左右兩邊各有一圈，而且一一對應：在這個範圍內，編號就是位元組的值，這就是 ASCII 檔案不用轉換就是合法 UTF-8 的原因。
  • (e) Base64 把右邊最外圈的任意位元組，搬進左邊最內圈的安全字元。 圖片位元組不是合法 UTF-8，無法直接當文字放進 HTML 或 email，所以先用 Base64 變成安全字元。 這些安全字元又在 ASCII 裡，再用 UTF-8 存檔時走的是甜蜜點那條線，形成 data URL 的完整循環。

2-3 UTF-8 與 UTF-16：以 1 位元組或 2 位元組為單位怎麼包裝

「單位」（code unit，碼元）是編碼一次讀寫的最小格子，每個字元都由整數個格子組成。同一個 Unicode 編號，兩種編碼用不同大小的格子去裝。

讀法：每個方框是一個碼元。灰色位元＝標頭（告訴解碼器「這格是開頭還是接續」），黑色位元＝真正裝編號的內容。

  • (a) UTF-8 用「標頭位元」說明長度：第一格開頭有幾個 1，這個字元就佔幾格，後續格一律以 10 開頭。 0xxxxxxx＝1 格，110xxxxx＝2 格，1110xxxx＝3 格，11110xxx＝4 格。 標頭佔掉一些位元，所以「中」的 16 位元編號要切成 4＋6＋6，分進 3 格。
  • (b) UTF-16 編號在 U+FFFF 以內就直接放進一格，沒有標頭位元，「中」的 4E2D 就是編號本身。 超過 U+FFFF 才拆成兩格的代理對：前半以 110110 開頭（D8–DB），後半以 110111 開頭（DC–DF）。
  • (c) 體積比較：英文 UTF-8 較小（1 對 2 位元組），中文 UTF-16 較小（2 對 3 位元組），emoji 兩者都是 4 位元組。 網頁有大量 HTML 標籤和英文程式碼，整體仍是 UTF-8 較省。
  • (d) UTF-16 有位元組順序（endianness，位元組序）問題，需要 BOM 或標明 BE／LE。UTF-8 沒有這個問題。
  • (e) JS 字串內部用 UTF-16 碼元，所以 '😀'.length 是 2，charCodeAt(0) 拿到 55357（0xD83D，代理對前半），codePointAt(0) 才拿到完整編號 128512（0x1F600）。 詳見 JS字串-UTF-16碼元與代理對。
'😀'.length          // 2，😀 佔 2 個 UTF-16 碼元
'😀'.charCodeAt(0)   // 55357（0xD83D），只拿到代理對前半
'😀'.codePointAt(0)  // 128512（0x1F600），完整的 Unicode 編號

白話：length 和 charCodeAt 都是以 UTF-16 碼元為單位在數，碰到 emoji 會算成兩個，要拿完整編號就用 codePointAt。

3. charset 機制：瀏覽器怎麼選解碼規則

伺服器送出的只是位元組，瀏覽器必須先決定「用哪套規則解碼」，才能還原成字元。charset 字面是「字元集」，實際填的是編碼名稱，是歷史沿用的叫法。

  • (a) 伺服器在 HTTP 標頭寫 Content-Type: text/html; charset=utf-8，HTML 裡寫 <meta charset="utf-8">，兩者都是告訴瀏覽器「用 UTF-8 解碼」。
  • (b) 優先順序：BOM → HTTP 標頭的 charset → 前 1024 位元組內的 meta charset → 瀏覽器猜測。<meta charset> 要放在 <head> 最前面，才會落在前 1024 位元組內。
  • (c) 選錯規則就是重點 (a) 的 Mojibake，例如 Big5 檔案被當成 UTF-8 解碼。

4. UTF-8 的普及程度

  • (a) 在已知編碼的網站中，UTF-8 佔 99%（W3Techs，2026-08-31）。
  • (b) 成長軌跡：2015 年初 82.3% → 2026 年初 98.9%，剩下的多半是 ISO-8859-1 這類舊的單一語系編碼。
  • (c) ASCII 在統計裡幾乎看不到，原因是它被 UTF-8 吸收：純英文檔案標成 UTF-8 即可，位元組不變，所以不需要另外宣告 ASCII。

標準現況：UTF-8 的現行規格是 RFC 3629（2003-11，STD 63），Base64 的現行規格是 RFC 4648（2006-10）。兩份至 2026 年都仍是現行標準，值得學。

5. 自我測驗

填空（點底線顯示答案）

1. Unicode 給「中」的碼位是 U+4E2D，UTF-8 把它編成 3 個位元組。

2. UTF-8 的前 128 個碼位，跟 ASCII 的位元組完全相同。

3. Base64 每 3 個位元組變成 4 個字元，體積約增加 三分之一。

4. 瀏覽器決定解碼規則的優先順序：BOM → HTTP 標頭的 charset → 前 1024 位元組內的 meta charset。

是非題（點題目顯示答案）

1. UTF-8 只是在描述「用幾個位元組」，本身不是編碼。
✗ 錯。UTF-8 就是編碼本身，是把碼位轉成位元組的完整規則。
2. JS chunk 在網路上傳送時，已經是 CPU 能直接執行的機器碼。
✗ 錯。傳送的 0／1 代表 UTF-8 文字，要等 V8 編譯後才變成機器碼。
3. Base64 的用途是把二進位資料轉成只含安全字元的文字。
✓ 對。
4. Unicode 是一種編碼。
✗ 錯。Unicode 是字元集，只定編號，UTF-8、UTF-16 才是編碼。
5. gzip／Brotli 壓縮是 UTF-8 編碼的一部分。
✗ 錯。壓縮是另一個選用步驟，用 Content-Encoding 標頭宣告，UTF-8 用 Content-Type 的 charset 宣告。
6. 「中」用 UTF-16 存比用 UTF-8 存更省空間。
✓ 對。UTF-16 是 2 位元組，UTF-8 是 3 位元組。

申論題（點題目顯示參考答案）

為什麼 UTF-8 能幾乎無痛取代 ASCII？
參考答案：Unicode 的前 128 個碼位沿用 ASCII 編號，UTF-8 又規定這 128 個用 1 個位元組直接存編號本身，所以所有舊的 ASCII 檔案不用轉換就是合法的 UTF-8。程式碼大多是英文，因此切換到 UTF-8 幾乎沒有成本。
