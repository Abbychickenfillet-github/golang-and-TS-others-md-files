## (a) 範例程式對照（C原始碼 vs 反組譯清單）

```c
int result = 0;

void main()
{
      result = add(3, 4);
}

int add(int a, int b)
{
      int sum = a + b;
      return sum;
}
```

> [!info]- 1.為什麼是main()先宣告、add()後宣告
> 這是照妳截圖裡實際寫的順序抄的——`result`先宣告成全域變數、接著是`void main()`呼叫`add(3,4)`，`int add(int a, int b)`定義反而寫在最後面。C語言允許這樣寫，是因為編譯器在編譯`main()`看到`add(3,4)`這一行時，只要之後`add`確實有定義（或至少有事先宣告過），就不會報錯；宣告順序不影響反組譯出來的機器碼、也不影響下面表格列的位址，跟main先或add先無關。

> [!info]- 2：main()是不是C語言的固定寫法、不是自己定義的？它跟其他函式的宣告順序調換真的完全不影響嗎？
> <mark style="background: #ADCCFFA6;">這句話要拆成兩層來看，不能只用「對」或「不對」一句話回答。</mark>
>
> a. **固定的部分**：C語言標準（C standard，規範這個語言合法寫法的官方文件）規定，每一個可執行程式都必須剛好有一個叫做`main`的函式，作為整個程式的進入點（entry point）；它的回傳型別（return type，函式執行完傳回去的值的種類）必須是`int`，參數列也只能是標準允許的幾種寫法（例如`int main(void)`或`int main(int argc, char *argv[])`）。名字、回傳型別、參數列的形式、「整個程式只能有一個main()」這幾件事，是C語言規定死的，不是妳自己發明的，也不能隨便改寫成`float main()`或叫別的名字。
>
> b. **不固定的部分**：main()大括號`{}`裡面實際要執行什麼程式邏輯，完全是妳自己寫的，跟寫其他函式沒有兩樣，這一點才是「自訂的」。也就是main()是「外殼規格固定、內容自訂」，不是整個函式從頭到尾都被規定好。
>
> c. **關於順序調換**：對已經編譯成功、產生出來的執行檔來說，main()和add()誰的原始碼寫在檔案前面、誰寫後面，完全不影響最後產生出來的機器碼或執行時的行為，這也是前面幾題回答的重點。但編譯**當下**這一關，其實有一個常被忽略的規則：C語言要求呼叫一個函式之前，編譯器必須已經知道它的存在，透過事先的宣告（prototype）或者它的完整定義已經出現在呼叫的地方之前。像這支影片的範例，main()呼叫`add(3, 4)`的時候，`add()`的定義還沒出現在前面，理論上在比較嚴格、遵守現代C標準（C99以後）的編譯器底下，這樣寫應該會被當成錯誤（implicit宣告錯誤）擋下來，除非編譯器用的是比較寬鬆的模式，或者這支影片的範例本來就只是教學用的簡化示意，沒有真的照嚴格的編譯規則跑過一次。所以誠實地說，「執行結果不受影響」是對的，但「編譯階段的順序完全沒有限制」這句話並不完全正確，我要幫妳更正一下。

> [!info]- 追問一：main()確實是第一個被呼叫、執行的，為什麼原始碼裡沒有寫`main();`去呼叫它？
> <mark style="background: #ADCCFFA6;">對，main()確實是整支程式第一個開始執行的函式——這正是它被稱為entry point（程式進入點）的原因。但妳不會在C原始碼裡自己寫一行`main();`去呼叫它，因為main()不是被「妳自己寫的程式碼」呼叫的。</mark>
>
> 真正呼叫main()的，是編譯器／連結器自動附加進最終執行檔裡的一段**啟動程式（runtime startup code）**，常見的名字有`crt0`、CRT startup、Linux上glibc的`__libc_start_main`。作業系統載入程式後，第一個真正開始跑的不是main()，而是這段啟動碼；它負責做一些準備工作（設定Stack、初始化全域變數等），準備好之後才會執行一行`call main`，把控制權交給main()——這一行`call main`跟本篇表格裡main()呼叫`call add`是同一種機制，只是呼叫者換成了妳看不到、也不是妳自己寫的啟動碼。
>
> 所以「main()是第一個被呼叫、執行的」這句話完全正確，只是呼叫它的那一行`call main`，寫在妳原始碼**之外**（編譯器自動加的啟動碼裡），不會出現在妳自己的`.c`檔案裡，這支影片的反組譯畫面也只截了main()開始之後的部分，沒有往前捲到啟動碼那一段。

> [!info]- 追問二：main()確實是先被呼叫、先執行的，那main()自己的程式碼為什麼不是從`0x0004`開始？
> <mark style="background: #ADCCFFA6;">這一題問到重點了：表格裡最早出現的位址是`0x0004`（`mov edi,3`），但這不代表main()的程式碼是從`0x0004`開始的，也不代表main()自己完全沒有更早的指令。比較合理的推測是：main()自己也會有一段開場白（prologue，就是`push rbp`、`mov rbp,rsp`這類固定的準備動作，跟`add()`開頭那三行的作用一樣），這段開場白很可能就佔掉了`0x0000`到`0x0003`這幾個位址，只是妳4:28的截圖範圍剛好從`0x0004`開始截，沒有把更早的部分拍進去。</mark>
>
> 老實說這裡要跟妳說清楚：這是**推測，不是妳截圖裡實際確認過的數字**，原因有兩個：第一，妳目前給我的所有截圖都是從`0x0004`開始，沒有任何一張拍到`0x0000`到`0x0003`；第二，這支影片本身的位址（像`0x1234`那一格，上面已經註明是「示意位址」）看起來是教學用的簡化範例，不一定是真實編譯器／連結器（linker，負責把編譯好的各個部分組合、分配實際記憶體位址的工具）跑出來的位址，所以main()真正的起始位址也可能根本不是`0x0000`，而是連結器決定的任何一個數字。等妳之後補上更早的截圖，我再回來確認這一格。

> [!info]- 追問三：為什麼是main()（在`0x0004`那裡）先把3放進edi，而不是add()自己處理它的第一個參數？
> <mark style="background: #ADCCFFA6;">這個問題問到了呼叫慣例（ABI，Application Binary Interface，前面提過、規定「用哪個暫存器放第幾個參數」的那一套約定）最核心的分工方式：**準備參數是呼叫者（caller，也就是main()）的責任，不是被呼叫者（callee，也就是add()）的責任**。</mark>
>
> 具體來說，`call add`這個指令執行的當下，CPU（中央處理器）只會做兩件事：把返回位址push進Stack、然後跳到add()的位址，它完全不會幫妳把參數準備好。所以按照ABI的規定，main()必須在自己還在執行、還沒跳到add()之前，就先把`a=3`放進edi、`b=4`放進esi，準備好一切，才能安心執行`call add`；等到CPU跳進add()以後，add()一開始執行的第一件事（`push rbp`）已經是`0x0020`，這時候edi、esi裡面已經是main()事先準備好的3和4了，add()只需要「相信」呼叫者已經照規矩把參數放好，直接去讀edi、esi就好，完全不用自己動手處理「怎麼把3跟4弄進來」這件事。
>
> 換句話說：`0x0004`、`0x0009`這兩行雖然位址上看起來跟main()綁在一起、屬於main()的程式碼，但它們做的事其實是「代表add()先把家裡打掃好」，這是呼叫慣例規定好的分工，跟main()和add()誰先宣告、誰的程式碼寫在前面完全無關。

> [!info]- 追問四：呼叫慣例ABI的全部（完整正式）名稱是什麼？
> <mark style="background: #ADCCFFA6;">ABI本身是「Application Binary Interface（應用二進位介面）」的縮寫，這是一個統稱，底下依照作業系統／處理器架構的不同，會有各自具體的規格文件跟名字。</mark>
>
> 這篇筆記、還有前面回答裡提到「edi放第1個參數、esi放第2個參數」，屬於的是Linux／macOS這一系的規格，正式全名叫**System V AMD64 ABI**（System V是這份規格文件所屬的作業系統家族名稱、AMD64是x86-64這個架構的另一個常見稱呼、ABI就是應用二進位介面），完整的官方文件標題是《[System V Application Binary Interface AMD64 Architecture Processor Supplement](https://refspecs.linuxbase.org/elf/x86_64-abi-0.99.pdf)》。
>
> 這裡有一個很重要的補充：**這一套「第1個參數放edi、第2個放esi」的規定，只在System V AMD64 ABI底下成立，不是所有x86-64系統通用的規則**。同一段C程式碼如果拿去Windows底下用微軟自己的編譯器編譯，會遵循另一套叫做**[Microsoft x64 calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention)**的規格，第1、2、3、4個整數參數放的是RCX、RDX、R8、R9這幾個暫存器，完全是不同的分配方式。所以之後如果妳看到別的教學影片或文件，暫存器用法跟這篇筆記不一樣，很可能只是因為對方在講 Windows的呼叫慣例，不代表誰對誰錯。

> [!info]- 追問五：表格裡`0x0004`到`0x0036`這樣由上到下列出來，順序是照什麼排的？跟CPU實際執行的順序一樣嗎？
> <mark style="background: #ADCCFFA6;">表格由上到下排的是**記憶體位址由小到大的順序**（`0x0004`→`0x0009`→……→`0x0036`），這是[反組譯](https://zh.wikipedia.org/zh-tw/反汇编)工具常見的呈現方式：把整段程式碼依照它被放在記憶體裡的先後位置，由上到下印出來，方便閱讀。</mark>
>
> 但這個順序**不完全等於CPU實際執行的順序**：CPU大部分時間確實是照位址由小到大一路往下執行（`0x0004`→`0x0009`→`0x000E`），可是`0x000E`這一行是`call add`，執行到這裡CPU會直接跳到`0x0020`（add()的開頭），中間`0x0013`那一行（main()原本排在call add後面那一行）會先被跳過、暫時不執行，一直等到add()最後的`ret`把返回位址從Stack裡pop出來，CPU才會跳回`0x0013`繼續往下執行。所以真正的執行順序是：`0x0004`→`0x0009`→`0x000E`→（跳到）`0x0020`→`0x0021`→`0x0024`→`0x0028`→`0x002A`→`0x002C`→`0x002F`→`0x0032`→`0x0036`→`ret`→（跳回）`0x0013`，不是表格由上到下那樣一路念下去的。

> [!info]- 追問六：那這邊指令的順序（表格順序）跟call stack的順序（(a-1)節a到f那個順序）其實不一樣？
> <mark style="background: #ADCCFFA6;">對，這裡其實涉及三種不同的「順序」，很容易混在一起。</mark>
>
> a. **表格由上到下的順序**：純粹是記憶體位址由小到大排的，跟指令實際有沒有被執行、什麼時候執行完全無關，只是反組譯工具排版的方式。
>
> b. **CPU實際執行的順序**：上面追問五已經整理過，因為`call add`跟`ret`會讓CPU跳來跳去，所以是`0x0004`→`0x0009`→`0x000E`→（跳到）`0x0020`→……→`0x0036`→`ret`→（跳回）`0x0013`，跟表格的順序不同。
>
> c. **call stack（Stack上push／pop事件）的順序**：也就是(a-1)節a到f那個列表，這是從b.的執行順序裡，只挑出「會影響Stack內容」的那幾個動作（`call`的push、`push rbp`、`sub rsp,4`、`add rsp,4`、`pop rbp`、`ret`的pop），其他不影響Stack的指令（像`mov edi,3`、`mov eax,edi`這些單純搬資料的動作）都被跳過不列進去。
>
> 所以妳的直覺是對的：表格順序、CPU執行順序、Stack的push／pop順序，是三件事，只是後兩者（b.和c.）有重疊的部分，c.其實是從b.裡面篩選出來的一個子集合。

> [!info]- 追問七：所以add()裡面的`return sum;`，最後真的會把值給main()的`result`嗎？
> <mark style="background: #ADCCFFA6;">會，但中間要經過eax這個暫存器接力，不是`return sum;`這一行直接寫進`result`的記憶體位置。</mark>
>
> 對照回表格：`return sum;`這一句C原始碼，實際上被翻譯成`0x002F`那一行`mov eax,[rbp-4]`，先把`sum`的值從它在Stack上的位置（`[rbp-4]`）讀出來、複製進eax；之後`0x0032`到`0x0036`是epilogue收尾（釋放Stack空間、還原main()的BP），再來`ret`把返回位址pop出來、跳回main()的`0x0013`。這時候main()執行`0x0013`那一行`mov [0x1234],eax`，才是真正把值寫進`result`的地方——它讀的正是add()剛剛透過`return sum;`放進eax、而且一路帶著沒被改動過的那個值。
>
> 也就是說，`return sum;`跟`result = add(3, 4);`這兩句C原始碼，中間是靠**eax這個暫存器**接力完成的：add()負責把`sum`放進eax（這是ABI規定好的，eax／rax是回傳值固定要放的暫存器，前面筆記也提過），main()負責把eax裡的值搬進`result`。兩邊各自完成自己那一半，合起來才是`result = add(3, 4);`這句話真正的效果。

> [!info]- 追問八：前面計算的結果是不是存在`0x0020`這個記憶體位置，然後被複製成`0x0013`的計算結果，再放進main()裡面？
> <mark style="background: #ADCCFFA6;">方向直覺是對的（最後確實是把一個已經算好的值放進main()裡面），但`0x0020`跟`0x0013`這兩個數字的角色跟妳想的不一樣，要幫妳更正兩個地方。</mark>
>
> a. `0x0020`**不是記憶體位置，而是指令位址**：它是`push rbp`這條指令自己被存放在記憶體裡的位置（就像一本書第幾頁），不是存放`sum`這個計算結果的地方。`sum`真正存放的位置是`[rbp-4]`，這是一個**資料位址**（data address，實際裝著數值的地方），跟`0x0020`這種**程式碼位址**（code address，裝著指令本身的地方）是兩種完全不同的位址，雖然都用同一套十六進位數字寫法，但代表的東西完全不一樣，這也是很多初學者會混淆的地方。
>
> b. `0x0013`**也不是自己在計算什麼**，它是main()程式碼裡`mov [0x1234], eax`這條指令所在的位址。真正的計算（`a+b`）早在`0x002A`的`ADD`指令就算完了，`0x0013`這行只是把這時eax裡面已經存在的值（經過`ret`完整帶回main()）**複製到**`result`所在的記憶體位置，這一步是「存放」不是「計算」。
>
> 所以整理一次正確的流程：`a+b`在`0x002A`算好→存進`sum`（`[rbp-4]`，在`0x002C`）→`0x002F`把`sum`讀回eax→`ret`跟返回，回到main()→main()執行`0x0013`，把這時eax裡的值複製進`result`。妳說「把它放進main()裡面」這句話完全正確，只是真正把值放進去的那一行是`0x0013`，不是`0x0020`。

> [!info]- 追問九：我是學JS的，我應該了解的是反編譯器（decompiler）而不是反組譯器（disassembler），對吧？
> <mark style="background: #ADCCFFA6;">這句話要拆開來看：對這篇筆記系列想弄懂的東西（呼叫堆疊、push/pop/call/ret這些CPU層級的機制）來說，妳需要的其實是反組譯（disassembly）的概念，不是反編譯（decompilation）；但如果換成JS的世界，這兩個詞對應到的東西又不太一樣，要分開講。</mark>
>
> a. **反組譯跟反編譯不是同一件事**：反組譯是把machine code（機器碼，CPU真正執行的二進位指令）一條一條、幾乎一對一地翻回助憶符（mnemonic，例如`push`、`mov`、`call`），過程是機械式的，不會猜測或重組原始邏輯，妳在這篇筆記裡看到的整份`0x0004`到`0x0036`對照表，就是反組譯的結果。反編譯則是更進一步，試圖把機器碼或反組譯結果重新組合、猜測回接近高階語言（像C）的原始碼樣貌（例如把一串`cmp`／`jmp`猜回`if`／`for`這種結構），過程需要大量推測、常常不準確，而且刻意把底層細節（像Stack Frame怎麼建立、暫存器怎麼搬動）包起來、隱藏掉，讓輸出看起來更像人寫的原始碼（見[Hex-Rays文件](https://docs.hex-rays.com/core/decompiler/overview/introduction-to-decompilation-vs-disassembly)、[Daniel Miessler的說明](https://danielmiessler.com/blog/programming-decompiler-vs-disassembler)）。
>
> b. **對妳這篇筆記的學習目標來說，反組譯才是對的方向**：妳想搞懂的正是`push rbp`、`call add`、`ret`這些機制怎麼一步步操作Stack，反編譯的整個目的恰好相反——它是要把這些細節藏起來、重組成看不到Stack操作的高階程式碼。如果一開始就去看反編譯器的輸出，反而會看不到妳想學的東西，等於選了一個目的跟妳想學的內容互相矛盾的工具。
>
> c. **JS的世界要分開看**：JS這種語言本身不像C那樣先整個編譯成原生機器碼再執行，而是由像V8（Chrome跟Node.js底層用的JavaScript引擎，engine，負責執行JS程式碼的軟體）這樣的直譯器／即時編譯器（interpreter／JIT compiler）邊執行邊處理。所以JS原始碼沒有一份對應的「反組譯清單」可以直接看；最接近這篇筆記裡「反組譯」概念的，是V8內部一個叫Ignition的位元組碼（bytecode，介於原始碼跟機器碼之間的一種中間表示法）產生器，可以透過`node --print-bytecode`這個旗標（flag，指令列參數）印出來看（見[nodejs/node GitHub issue #38158](https://github.com/nodejs/node/issues/38158)、[Understanding V8's Bytecode](https://medium.com/dailyjs/understanding-v8s-bytecode-317d46c94775)），這是VM（虛擬機器，Virtual Machine）層級，不是CPU層級，但精神上一樣是「機械式地把執行單位攤開來看」，跟反組譯是同一類東西。
>
> d. 至於JS世界裡常聽到的「反編譯」，通常指的是另外兩件事，都跟這篇筆記講的反編譯不太一樣：把已經被壓縮、改過變數名稱的JS原始碼（minified／obfuscated code，最小化／混淆過的程式碼）想辦法還原成比較好讀的樣子（de-minify／de-obfuscate），或者是把WebAssembly（wasm，一種可以在瀏覽器裡跑、效能接近原生的位元組碼格式）的二進位檔反編譯回類似C或wat的原始碼——這兩者處理的都是JS或wasm特有的轉換，跟這篇筆記在講的、C編譯成x86機器碼再反組譯回來，是不同層次的問題。
>
> 所以簡短回答：以妳現在想搞懂「呼叫堆疊到底怎麼運作」這個目標來說，反組譯才是妳該弄懂的概念，不是反編譯；等妳之後想連結回JS本身，比較對應的入口是V8的Ignition bytecode，而不是一般意義上的反編譯器。

> [!info]- 追問十：組合語言就是助憶符、機器語言就是機器碼、編譯是高階到低階、反編譯是編譯完再組裝回高階、那為什麼說反編譯是猜測、V8是不是用直譯／JIT取代了反組譯、反組譯為什麼還有反組譯清單？
> <mark style="background: #ADCCFFA6;">這一串問題把好幾個名詞放在一起釐清，一個一個拆開回答。</mark>
>
> a. **組合語言就是助憶符喔？** 不完全是。組合語言（assembly language）是一整套「用文字寫CPU指令」的語言，助憶符（mnemonic）只是組合語言裡的一個成分——是每一行指令最前面那個代表「做什麼動作」的字（像`mov`、`push`、`add`）。一行完整的組合語言敘述通常是「助憶符＋運算元（operand，動作要用在哪些暫存器／數值上，例如`mov edi, 3`裡的`edi`跟`3`）」，另外組合語言裡還有標籤（label，用來標記位址或跳躍目標的名字）、組譯器指示（assembler directive，像`.data`、`.text`這種給組譯器看、不是CPU指令本身的指示）這些助憶符以外的成分。所以助憶符是組合語言的其中一個零件，不是組合語言的全部。
>
> b. **機器語言就是機器碼喔？** 這兩個詞在日常使用上幾乎可以當同義詞，但嚴格分的話：機器語言（machine language）指的是「CPU看得懂的二進位指令規則」本身（一種語言規格），機器碼（machine code）則是照著這套規則實際寫出來的一串二進位數字（這套規則的具體實例）。類似「中文」跟「一篇用中文寫的文章」的關係。不過這個區分在日常對話裡通常不太計較，兩個詞混用是常態，不用太糾結。
>
> c. **編譯是高階程式碼去低階程式碼？** 方向大致正確，但「編譯」這個詞本身的定義比這個更廣：編譯（compilation）是把某一種程式語言寫的原始碼，轉換成「另一種」程式語言的對等程式碼，最常見、也是這篇筆記在講的情境，確實是高階語言（像C）轉成低階語言（組合語言／機器碼）。但也存在原始碼轉原始碼的編譯器（source-to-source compiler，常被叫做transpiler／轉譯器，見[Wikipedia – Source-to-source compiler](https://en.wikipedia.org/wiki/Source-to-source_compiler)），例如把TypeScript轉成JavaScript，這兩者其實都是高階語言、只是層級不同，這種也算編譯的一種。所以在這篇筆記C→組合語言的脈絡下，妳說的沒錯；但「編譯」這個詞本身不是嚴格規定死「一定要高到低」。
>
> d. **反編譯是：編譯過後的檔案再組裝回高階程式碼？** 方向是對的，但「組裝」這個字要小心，容易跟「組譯（assembly，把組合語言翻成機器碼的動作）」搞混。反編譯（decompilation）比較精確的說法是：拿已經編譯完成的低階輸出（機器碼，或先反組譯出來的組合語言），試圖逆向推導、重建出接近高階語言的原始碼樣貌——是「逆向推導、重建」，不是「組裝」。
>
> e. **那你為什麼要說"反編譯是猜測重組回高階原始碼"？** 這題問到重點了。核心原因是：編譯（compilation）這個過程本身是「多對一」、會遺失資訊的，不是「一對一」可逆的過程，具體有兩層：第一，變數名稱、註解、原始的程式碼排版跟寫法，這些東西編譯完全部消失，機器碼裡完全不會留下`sum`這個名字，只會留下`[rbp-4]`這種位址；反編譯器面對這種情況，只能自己發明一個看起來合理的名字（像`var_4`、`local_1`），不是真的「找回」原來的名字，因為原來的名字根本沒被存起來過（見[CMU – Meaningful Variable Names for Decompiled Code](https://www.cs.cmu.edu/~clegoues/docs/jaffe-icpc18.pdf)）。第二，不同寫法的高階原始碼，常常會被編譯器編譯成一模一樣、或非常接近的機器碼——例如同樣邏輯的`for`迴圈跟`while`迴圈，經過編譯器優化後很可能產生幾乎相同的組合語言，這表示反編譯器拿到一份機器碼的時候，理論上可能對應到好幾種不同、但一樣合理的高階原始碼寫法，沒有唯一正確答案，只能挑一個最可能、最常見的樣式印出來，這就是為什麼要說是「猜測」——不是編譯器做壞事，是編譯這個方向的轉換本來就會丟掉資訊，回頭走不可能無損還原。反過來看，反組譯（disassembly）之所以是機械式、不用猜的，是因為機器碼跟助憶符之間幾乎是嚴格一對一對應，這個方向沒有資訊遺失的問題，所以才不需要猜。
>
> f. **所以V8引擎直譯／即時編譯執行會代替反組譯？** 不是「取代」的概念，比較精確的說法是：JS的執行模式讓一般學習者少了一個「像C那樣先編譯出一個檔案、再拿去跑反組譯工具」的固定步驟可以照做。其實V8（Chrome跟Node.js底層的JavaScript引擎）內部真的有即時編譯器（JIT compiler，這裡特別指V8裡叫TurboFan的最佳化編譯器）會把JS程式碼編譯成真正的原生機器碼，這個機器碼理論上也可以被反組譯來看，V8甚至有專門的旗標`--print-code`／`--print-opt-code`可以印出這個階段的組合語言（見[v8-print-code-filter](https://github.com/eush77/v8-print-code-filter)），只是這個機器碼是執行時期暫時產生在記憶體裡的（不會像C程式那樣變成一個固定的執行檔讓妳事後慢慢反組譯），而且要看懂TurboFan印出來的東西，需要先懂V8內部的中間表示法，門檻比看Ignition位元組碼高很多。所以對妳現在的學習階段來說，比較實際的入口還是Ignition的位元組碼（透過`node --print-bytecode`），真正的原生機器碼反組譯是進階、但確實存在的下一步，不是完全看不到，只是通常不會是第一站。
>
> g. **為何反組譯還有反組譯清單？** 「反組譯清單」不是另一個獨立的概念，只是反組譯這個動作「印出來的那份文件」的名字。反組譯（disassembly）是動作本身（把機器碼翻回助憶符這件事），反組譯清單（disassembly listing）指的是做完這個動作以後、實際印出來妳看得到的那一份文字表格——就是這篇筆記裡從`0x0004`到`0x0036`那份「位址／助憶符／說明」的表格本身。這跟「計算」跟「計算結果的報表」的關係一樣：反組譯是動作，反組譯清單是這個動作產生出來的輸出文件，不是兩種不同的東西。

> [!info]- 追問十一：妳這次補拍的截圖裡有完整的機器碼（hex bytes）欄位，把表格加上這一欄，順便說說怎麼核對這些位元組
> <mark style="background: #ADCCFFA6;">已經把機器碼欄位加進上面(a)節的表格了，這裡說明怎麼核對每一列的位元組數，順便誠實標出一個目前還沒解開的落差。</mark>
>
> a. **核對方法**：每一條指令佔幾個byte，剛好等於「下一條指令的位址」減去「這一條指令自己的位址」，兩者理論上要對得起來。例如`0x0020`（`push rbp`）到`0x0021`（`mov rbp, rsp`）只差1，`push rbp`的機器碼`55`剛好也只有1個byte，對上了；`0x0021`到`0x0024`差3，`mov rbp, rsp`的機器碼`48 89 e5`剛好是3個byte，也對上了。用這個方法把`0x0020`到`0x0036`整段add()自己的部分（`push rbp`／`mov rbp,rsp`／`sub rsp,4`／`mov eax,edi`／`add eax,esi`／`mov [rbp-4],eax`／`mov eax,[rbp-4]`／`add rsp,4`／`pop rbp`）逐條核對過，**每一條的byte數都跟位址差完全吻合**，這部分的機器碼可以放心確認。
>
> b. **一個順便驗證到的巧合**：`call add`（`0x000E`）的機器碼是`e8 0d 00 00 00`，其中`e8`是`call`指令的opcode（操作碼，指令裡代表「做什麼動作」的那一段位元組，跟助憶符是一體兩面——助憶符`call`是給人看的文字，`e8`是給CPU看的實際位元組），後面`0d 00 00 00`是一個**相對位移**（relative offset，這裡`0d`是16進位，換算十進位是13）。這個13不是隨便湊的：`call`指令的相對位移，定義上就是「跳躍目標位址」減去「`call`指令結束後下一行的位址」，這裡是`0x0020`（目標）減`0x0013`（下一行）＝`0x0D`（十進位13），跟機器碼裡的`0d`完全吻合——這是本篇追問三提到「`call`指令執行時CPU怎麼算出要跳去哪裡」這個抽象說法，第一次有具體位元組可以驗算。
>
> c. **已核對：`0x0013`完整機器碼**：妳後來補傳的全螢幕截圖（`3:11 / 15:35`）把筆尖擋住的部分露出來了，`0x0013`這一行`mov [0x1234], eax`完整機器碼是`a3 34 12 00 00`——開頭`a3`是這種「直接寫入絕對位址」的mov指令的opcode，後面`34 12 00 00`正是`0x1234`用little-endian小端序寫法的4-byte位址，跟先前推算的完全吻合，這一格現在是**已核對**，不再是推測。
>
> d. **仍然誠實標出的落差**：`0x0013`加上完整5個byte，應該落在`0x0018`，但下一個確認過的位址是`0x0020`，中間`0x0018`到`0x0020`這8個byte，即使有了(c)的新截圖，這一段本身**還是沒有截圖可以核對**（新截圖露出的是`0x0013`那一列被筆尖擋住的部分，不是`0x0018`到`0x0020`這一段）——比較合理的推測仍然是編譯器常把函式的進入點對齊到16-byte邊界（function alignment，一種常見的編譯器最佳化，讓函式開頭的位址是16的倍數，方便CPU一次抓取指令時效率更好；`0x0020`換算十進位是32，剛好是16的兩倍，符合這個對齊慣例），中間可能塞了幾個不影響邏輯的填充指令（padding，常見的填法是`NOP`「什麼都不做」指令或系統保留的`INT3`），但這只是根據對齊慣例做的推測，不是妳截圖裡逐byte確認過的（見[Hex-Rays – Alignment items](https://hex-rays.com/blog/igors-tip-of-the-week-133-alignment-items)），等之後補上這一段的截圖，我再回來確認。

> [!info]- 追問十二：與剛剛我問你的問題相關，變數的長度一定要用2的倍數嗎
> <mark style="background: #ADCCFFA6;">沒有強制規定，但「基本數值型別」幾乎都約定成2的次方，這裡把「變數」拆成兩層來看，順便解釋為什麼跟追問十一(c)節那個16-byte對齊的落差，本質上是同一種設計哲學。</mark>
>
> a. **先分清楚「變數」這個詞涵蓋的範圍**：變數可以是一個基本數值型別（像`int`、`char`），也可以是陣列、字串、結構（struct）這類複合型別。複合型別的長度完全由內容決定，沒有一定要是2的倍數——例如一個字串變數存`"abc"`是3個字元、存`"台北"`可能是6個byte（依編碼而定），一個結構體的大小是裡面所有欄位加起來，也不保證剛好是2的倍數。
>
> b. **但這篇筆記表格裡看到的都是固定大小的基本數值型別**：`char`＝1 byte、`short`＝2 bytes、`int`＝4 bytes（就是表格裡`mov edi, 3`這種操作用的大小）、`long long`＝8 bytes，這些大小幾乎都是1、2、4、8這樣2的次方——這不是C語言語法規定死的，而是幾乎所有編譯器跟硬體設計上共同遵守的慣例。
>
> c. **為什麼這些基本型別偏好2的次方大小，三個理由**：
>   1. **記憶體對齊（data alignment）效率**：CPU從記憶體讀取資料時，如果一個4-byte的`int`剛好放在4的倍數的位址上（例如`0x0024`、`0x0028`這種，跟表格裡`sub rsp,4`留出的空間對齊方式一樣），一次記憶體存取就能完整讀到；如果沒對齊（例如硬要塞在`0x0025`），有些CPU架構要拆成兩次讀取再拼起來，速度變慢，甚至某些架構（像早期ARM）會直接觸發硬體例外、程式當掉（見[Microsoft Learn – Alignment (C11)](https://learn.microsoft.com/en-us/cpp/c-language/alignment-c)）。
>   2. **位元運算（bit shift）效率**：2的次方大小可以用「位移」（左移／右移，像`<<`、`>>`這種直接搬動二進位位元的運算）快速算出陣列裡第n個元素的位址（位址＝起始位址＋n左移log2(大小)位），比用一般的乘法／除法快，這是編譯器最佳化陣列存取常用的技巧。
>   3. **跟CPU暫存器寬度、cache line（快取行，CPU從主記憶體一次搬進快取的資料區塊大小）相容**：這些硬體邊界通常也設計成2的次方（例如常見cache line是64 bytes），資料大小配合2的次方，比較容易剛好塞滿或對齊這些硬體邊界，不會讓一個變數尷尬地跨在兩個cache line中間、需要多讀一次。
>
> d. **複合型別（struct）反而會被「湊」成2的倍數**：結構體本身的大小規則不是「所有欄位大小相加」這麼單純，編譯器通常會在欄位之間插入看不到的填充位元組（padding），一來讓每個欄位自己對齊到它該對齊的位址，二來讓整個結構體的總大小變成「結構體裡最大成員的對齊值」的倍數，方便這個結構體被放進陣列時，每一個元素都還是對齊的。所以妳有時候會看到`sizeof(struct)`算出來的數字比欄位大小總和還大，多出來的就是padding（見[GeeksforGeeks – Structure Member Alignment, Padding and Data Packing](https://www.geeksforgeeks.org/c/structure-member-alignment-padding-and-data-packing/)）。
>
> e. **跟追問十一(c)節那個8-byte落差有什麼關係**：兩者其實是同一種現象的兩種展現方式——追問十一(c)節討論的是**函式對齊**（function alignment，讓一段指令／code的開頭位址對齊16-byte邊界），這裡討論的是**資料對齊**（data alignment，讓一個變數／資料的大小跟位址對齊）。一個作用在CPU要執行的指令上，一個作用在CPU要讀寫的資料上，但背後想解決的問題是同一個：讓CPU存取記憶體時，盡量一次就對齊、一次就讀完，不要跨界、不要多讀一次，這也是為什麼[[計算機基礎/CPU字長-TINYINT型別與OpenAPI資安雜記|CPU字長筆記]]裡會提到「即使TINYINT只需要1 bit，仍要用整個1 byte」——那篇談的是「定址最小單位是byte」，這篇談的是「型別大小為什麼常常是2的次方」，兩者是同一個對齊哲學的上下游關係，所以互相連結。

## (a-1) 直覺類比：洋芋片罐頭（LIFO）

![[計算機基礎_x86組合語言助憶符字典_Stack洋芋片罐頭LIFO類比_2026-07-31.svg]]

Stack最基本的行為規則叫LIFO（Last In First Out，後進先出），把它想像成一罐洋芋片最直覺：新的洋芋片只能從罐口放進去、疊在最上面，這個動作對應到`push`指令；要拿的時候也只能先拿最上面那一片、不能從中間抽走，這個動作對應到`pop`指令。SP（Stack Pointer，堆疊指標）永遠指向最上面那一格，就像妳的手指永遠停在最上面那片洋芋片的位置。

圖中用一個虛線方塊把`push rbp`到`pop rbp`這三片真正屬於add()的洋芋片圍起來，當作是add()的Stack Frame（add function）；罐底下那大塊則標註成main主函數，代表呼叫add()之前就已經存在的Stack內容（這部分沒有截圖可以逐一確認，所以圖裡只籠統畫成一塊，不逐項列出）。

對照回這支影片的範例，整段程式從main()呼叫add()到add()結束返回，實際疊進罐子、又拿出罐子的完整順序依序是：

a. main()執行到`call add`（`0x000E`）：把返回位址`0x0013`這片洋芋片放進罐子，這是CPU執行`call`指令自動做的push，不是妳自己寫的指令。<<CPU執行call指令會push函式的返回位址進去記憶體嗎？

b. add()開頭`push rbp`（`0x0020`）：把main()的BP（Base Pointer，基底指標）這片洋芋片疊在返回位址上面，備份起來準備之後歸還。

c. add()的`sub rsp,4`（`0x0024`）：在罐子裡多留出一格空間，準備放區域變數`sum`，這一步嚴格說不是push一個新值，而是先把空間留出來，之後`mov [rbp-4],eax`才是真正把`sum`的值寫進這一格。>>>
sub rsp,4是空出4個bytes operands的空間出來還是把stack pointer往高/低位址走？4個bytes?

d. add()收尾`add rsp,4`（`0x0032`）：把`sum`那一格空間釋放掉，等於把最上面那片洋芋片的位置讓出來，因為裡面的值已經不需要了。（這裡的「上面」指的是本段原圖——罐口朝上——的方向；如果拿下面追問十三(d)點的倒放版圖當參考畫面，這句要換成「最下面」才對得起來，詳見追問二十八）

e. add()的`pop rbp`（`0x0036`）：把b.備份的main() BP這片洋芋片從罐口拿出來、還給main()的BP暫存器。

f. add()最後的`ret`：把a.放進去的返回位址這片洋芋片從罐口拿出來，CPU就跳回`0x0013`繼續執行main()剩下的程式碼。

這正是LIFO的具體展現：最後放進去的c.（`sum`的空間）最先被拿出來（d.），再來是b.放的BP（e.），最後才輪到最早放進去的a.（返回位址，在f.才被拿出來），跟洋芋片罐頭一模一樣，永遠是後放的先拿、先放的後拿。

> [!info]- 追問十三：可是為什麼現在洋芋片的底部是ADD()，而上層才是main()？
> <mark style="background: #ADCCFFA6;">先確認一下妳現在看到的畫面：目前存在硬碟裡這張圖，底部（罐底，藍色方塊）畫的是**main()**、上層（紫色虛線框）畫的才是**add()的Stack Frame**——如果妳現在Obsidian裡看到的是相反過來（底部add()、上層main()），很可能是Obsidian還在顯示**舊版快取圖片**，沒有跟著重新整理，建議把這篇筆記關掉再重新打開，或是對著圖片按右鍵選「重新載入」看看會不會換成新的。不論妳現在看到的是哪一種，這裡把「為什麼一定要是main()在底、add()在上」的原因說清楚。</mark>
>
> a. **main()的既有內容一定要畫在底部**：main()呼叫`add()`之前，Stack裡本來就已經有main()自己的內容（雖然這篇筆記沒有逐一列出細節，但這些內容確實存在，是main()開始執行後就陸續累積起來的），這些內容在時間上比add()的任何一片洋芋片都**更早**被放進罐子裡，所以依照LIFO（後進先出）的規則，越早放進去的東西，物理位置上一定越靠近罐底，這不是美術排版的選擇，是push這個動作本身的機制決定的：push只能往罐口塞新的一片，不能從中間或罐底插隊，所以main()的舊內容注定只能待在下面。
>
> b. **add()的三片洋芋片一定要疊在main()上面，不能疊在下面**：main()執行`call add`（`0x000E`）之後，CPU跟add()自己的程式碼依序push了三樣東西（返回位址0x0013、main() BP備份、`sum`的空間），這三個動作全部發生在main()的內容已經在罐子裡**之後**，push的定義就是「加到最上面」，物理上完全不可能把新東西塞進已經疊好的洋芋片下面——如果畫成add()在底、main()在上，等於是說add()的Stack Frame比main()的內容更早存在，這會直接違反「main()先呼叫add()、add()才開始執行」這個事實順序，也違反LIFO push只能往上疊的規則。
>
> c. **一句話總結**：底部＝時間上更早存在的東西（main()既有內容），上層＝時間上更晚被push進去的東西（add()的Stack Frame）——誰在下、誰在上，不是任意畫的，是by design跟着「push只能疊在最上面」這個LIFO鐵律走的，跟(a-1)節a到f那個push／pop順序列表是同一套邏輯。
>
> d. **追問延伸：「底部一定是高位址（main()）」沒錯，但底部要畫在上面還是下面，有硬性規定嗎？** 沒有——這一點要幫妳分清楚兩層，一層是「鐵律」、一層是「畫圖習慣」。**位址方向是鐵律**：main()的內容位址一定比較高、add()新push進去的東西位址一定比較低，這是push指令讓Stack Pointer遞減決定的，沒有例外，跟怎麼畫圖無關。但**紙上／螢幕上要把「高位址」畫在上面還是下面，純粹是排版習慣，本身沒有物理上的強制規定**，因為記憶體本身沒有「上下」這種方向，那是人類畫圖時自己加上去的視覺輔助。只是實務上，課本、教材、除錯器（debugger）畫Stack時，**比較常見的習慣**是把高位址畫在上面、低位址畫在下面、SP畫在最下面、新push的東西往頁面下方增加——這篇筆記(a-1)節原本畫成「罐口朝上」剛好是相反方向（低位址在上、高位址在下），下面這張倒放版特地把它轉過來，改成「封底（main()，高位址）朝上、開口（低位址）朝下」，就是為了對齊這個比較常見的畫法習慣，方便妳以後看課本或除錯器畫的Stack圖時不會因為方向相反而感到陌生。

> [!info]- 追問十四：把這篇筆記拿去讀書會問朋友，發現我原本卡住的地方是「記憶體位置分Code Segment（指令位址）跟Stack記憶體Runtime」這兩層搞混了，是這樣嗎？
> <mark style="background: #ADCCFFA6;">完全正確，這正是妳從頭卡到現在的根源——而且這個誤會很合理，因為這篇筆記從頭到尾都用同一種16進位寫法（`0x0004`這種格式）在標地址，很容易讓人以為它們是同一套位址系統，其實完全不是。</mark>
>
> a. **表格裡`0x0004`到`0x0036`全部是Code Segment（指令位址），不是Stack位址**：這篇筆記(a)節那份對照表，每一列的「位址」欄位，指的都是**這條指令本身被放在記憶體哪個位置**（程式碼區，Code Segment），是編譯器排版決定的、**靜態、固定不變**的位置——main()的原始碼寫在add()前面，所以main()的指令排在比較前面、位址比較小（`0x0004`~`0x0013`）；add()寫在後面，指令位址自然比較大（`0x0020`起）。這跟main()、add()誰先被呼叫、誰在Stack上疊得比較高完全無關，純粹是「誰的原始碼寫在前面」決定的。
>
> b. **Stack記憶體Runtime是完全不同的另一套位址，這篇筆記其實沒有標出實際數字**：Stack上的位址（main()既有內容、返回位址`0x0013`這個值本身、main() BP備份、`sum`的空間，各自實際存在Stack上的哪個記憶體位址）是程式**執行的時候**才動態決定的，取決於**誰先被呼叫**——main()先執行，它的Stack Frame先建立，佔住比較高的Stack位址；main()呼叫add()後，add()的Stack Frame才建立，因為push會讓Stack Pointer往低位址方向長，所以疊在main()下面、佔比較低的Stack位址。這篇筆記到目前為止只用「洋芋片罐頭」跟「倒放版」兩張圖示意這個高低關係，沒有另外編造一組假的Stack位址數字去對照，避免製造出「Stack位址」和「指令位址」是同一套數字的錯覺。
>
> c. **兩層位址的關鍵差異，整理成一句話**：Code Segment位址回答的是「這條指令躺在記憶體的哪裡」，由**原始碼寫的先後順序**決定，執行前就固定了；Stack位址回答的是「這個Stack Frame疊在記憶體的哪裡」，由**呼叫的先後順序**決定，執行到那一刻才動態決定。妳原本的直覺「main()先進去、應該在較高位置」其實是對的，只是這條規則要套用在**Stack Frame**上，不能拿去套用在**指令位址**上——這兩者剛好用同一種16進位寫法呈現，才會讓人誤以為是同一回事。
>

> [!info]- 追問十五：0x000E是不是add()釋放的判斷依據、Gemini舉的Stack位址範例對不對、洋芋片罐頭圖到底是Code Segment還是Stack Segment、compiler是不是code segment的主人、完整的兩個segment順序來源、還有你矛盾的地方在哪
> <mark style="background: #ADCCFFA6;">這一次的問題其實是把追問十四打開的「Code Segment vs Stack Segment」這個大哉問一次拆成七小題問到底，這裡逐項回答，並且清楚交代每一點是「已核對」還是「推論／示意」。</mark>
>
> a. **`0x000E`跟add()釋放沒有關係，判斷高低要看整段位址範圍、不能看單一指令位址；跨segment比數值大小也沒有意義**：`0x000E`（`call add`）本身是main()自己的一行Code Segment指令，它的角色只是「main()執行到這裡、去呼叫add()」，跟add()什麼時候執行完、Stack Frame什麼時候被釋放完全無關——`0x000E`不會因為add()釋放而改變，它從編譯完成那一刻就固定在那裡，直到程式結束都不會動。判斷Code Segment裡main()跟add()誰高誰低，正確的做法是看**整段函式指令實際佔用的位址範圍**：main()是`0x0004`~`0x0013`、add()是`0x0020`~`0x0036`（見(a)節表格），不是挑某一行指令位址、賦予它「代表某個runtime事件發生的時刻」這種意義——這是本題最核心的誤解，先幫妳更正過來。至於妳發現「AI講的位址高低跟16進位數值大小好像不成正比」：在**同一個位址空間內部**，數值大小跟高低是完全成正比、沒有例外的（`0x0004` < `0x0037`，數字小的就是低位址，這是鐵律），不成正比的感覺，來自於不小心拿Code Segment的位址（像`0x000E`這種前面沒幾位數的小數字）去跟Stack Segment的位址（像`0x7FFF0FC0`這種一開頭就是7位數的大數字）互相比大小——這兩組數字**根本不屬於同一個位址空間**，中間隔著整段heap、data、bss、text等區域（見下面e點的完整順序），拿兩邊的數值直接比大小，就像拿台北市的門牌號碼跟東京都的門牌號碼比大小一樣，數字上比得出誰大誰小，但這個「大小」在真實世界裡沒有任何意義——這正是為什麼會覺得「不成正比」，因為它們本來就不該被放在同一把尺上量。
>
> b. **Gemini舉的Stack位址範例，逐句核對過，是正確的**：妳貼的這段話（`main()`的Code Segment指令在`0x0004`~`0x0013`低位址、`add()`在`0x0020`~`0x0037`高位址，是因為原始碼main()寫在前面；Stack記憶體位址是執行時動態決定、通常在`0x7FFF...`這種很高的區段、往低位址成長；main()先執行建立Frame在較高Stack位址例如`0x7FFF1000`、呼叫add()後它的Frame在較低Stack位址例如`0x7FFF0FC0`）跟這篇筆記(a)、(a-1)、追問十四已經確認過的規則完全吻合，沒有錯誤，可以放心採信。這段話也剛好是追問十四d點姜姜那張「行程記憶體配置全貌圖」的具體數字版本——那張圖只畫出「stack在上、text在下」這種相對位置，Gemini這段話補上了一組示意用的實際數字，讓妳看到main()跟add()的Frame在Stack上具體差了多少。

> c. **鋼筆截圖那份反組譯表格，100%是Code Segment；洋芋片罐頭圖畫的是Stack Segment的LIFO結構，但不是真正的Stack數字位址**：這兩件事要分開確認。鋼筆截圖裡的每一列（`0x0004`、`0x0013`、`0x0020`……）都是指令自己被放在記憶體哪裡，屬於Code Segment，這點在追問十四a點已經確認過，這裡再次明確答覆：對，就是Code Segment，不是Stack Segment。至於(a-1)節跟追問十三的洋芋片罐頭圖／倒放版圖，它們畫的是**Stack Segment的相對結構跟LIFO順序**（誰先push、誰後push、誰先pop、誰後pop、main()的內容一定在add()下面這些關係），但圖裡寫的「返回位址`0x0013`」「push rbp／`0x0020`」這些標籤，**用的仍然是Code Segment的位址**，它們的作用只是「註記這一片洋芋片裡實際存的值是什麼（例如存的是`0x0013`這個返回位址的值）、或是哪一行指令觸發了這次push」，並不是這一片洋芋片自己在Stack上真正的儲存位址（那應該是`0x7FFF....`這種數字）。這篇筆記在b點以前，從來沒有替洋芋片罐頭圖編造過一組假的Stack位址數字，就是為了避免製造「圖上寫的數字就是Stack位址」這種錯覺——直到這次b點才第一次用示意數字，具體對照到潛在的Stack位址長什麼樣子。
>
> d. **compiler不是Code Segment唯一的「主人」，要拆三層來看，這裡也補上ASLR（位址空間佈局隨機化）這個安全機制**：
>   1. **編譯器（compiler）**：把C原始碼翻譯成組合語言／機器碼，決定指令的實際內容，也因為main()寫在add()前面，順帶決定了兩者在同一個編譯單元裡的相對排列順序——但編譯器產生的通常還不是最終、真正拿去執行的絕對位址，而是帶著一份「哪些位址之後還需要調整」的**重定位表**（relocation table）。
>   2. **連結器（linker）**：把一個或多個編譯器產生的目的檔（object file）合併起來，將同類型的區段（segment）合併成一個，並且分配彼此不重疊的執行期位址跟符號（symbol）位址——這一步才把來自不同檔案的程式碼真正排定相對順序。
>   3. **作業系統載入器（OS loader）**：程式真正被執行的那一刻，載入器負責把連結器排好的這份執行檔，實際放進這個行程（process）的虛擬記憶體空間裡；如果作業系統開啟了**ASLR（Address Space Layout Randomization，位址空間佈局隨機化）**這個安全機制，載入器每次執行同一支程式，實際放置的起始位址都會不一樣（隨機跳動），這樣即使有心人事先知道某個舊版本的固定位址，也沒辦法直接拿來攻擊——這也是為什麼現代作業系統底下，重定位表即使對執行檔（不只是動態連結庫）也變成必要的，因為程式可能不會被放在原本預期的位址。
>   所以「compiler是不是Code Segment的主人」這句話沒有單一正確答案：**編譯器決定內容跟相對順序、連結器決定合併後的排列、載入器（可能搭配ASLR）決定執行當下實際落在記憶體哪裡**，三者分工合作，沒有誰是唯一的主人。
>
> e. **完整的Code Segment vs Stack Segment順序，參考的公信力來源**：整個行程（process）的虛擬記憶體位址，由低到高大致是：**text／code segment（程式碼本身，唯讀，最低位址）→ data（已經有初始值的static／global變數）→ bss（沒有初始值的static／global變數）→ heap（動態配置變數，往高位址方向成長）→〔中間一段尚未使用的間隙〕→ stack（區域變數／函式呼叫的Frame，往低位址方向成長，是使用者位址空間裡最高的區段）**——這個順序已經用GeeksforGeeks跟Gustavo Duarte（manybutfinite.com）兩份文件互相印證過，其中Duarte的文件明確寫出「stack是行程位址空間裡最頂端的區段」。姜姜那張圖多畫了一層**system**（命令列參數argv、環境變數envp）在stack的更上方，這是很常見的畫法慣例，我額外查了kernel.org上Mel Gorman的《Understanding the Linux Virtual Memory Manager》第4章，裡面確認Linux核心的`mm_struct`資料結構確實會追蹤`arg_start`／`arg_end`、`env_start`／`env_end`這兩組區域的存在，等於間接證實argv／envp在核心眼裡確實是獨立追蹤的一塊區域；但誠實說明一點：這份文件本身沒有給出一張把system畫在stack上方、完整標出全部區段順序的圖，所以「system在stack正上方」這一格，是業界常見畫法（也是姜姜那張圖畫的方式），跟kernel.org的追蹤機制互相吻合，但不是我從kernel.org這份文件裡直接讀到一張現成的順序圖——這一點誠實保留，避免講得比來源實際證實的還要肯定。

## (b) 助憶符字典（依常見出現順序）

a. **`mov`**（move，移動）——實際行為是**複製**，把一個數值從來源（暫存器／記憶體／立即值）複製一份到目的地，來源本身不會被清空。例：`mov edi, 3`＝把立即值3複製進edi。

b. **`push`**（推入）——把一個值放進Stack最上面新增的一格，同時讓Stack Pointer往「數字變小」的方向移動。例：`push rbp`＝把rbp目前的值存進Stack新的一格。

c. **`pop`**（取出）——跟`push`相反，把Stack最上面那一格的值讀出來，同時讓Stack Pointer往「數字變大」的方向移回去。通常用在函式收尾（epilogue）把備份的值還原。

d. **`sub`**（subtract，減法）——把兩個數值相減，結果寫回目的暫存器。例：`sub rsp, 4`＝把Stack Pointer的值減掉4，效果是往Stack成長方向多移動4個byte、預留區域變數空間。

e. **`add`**（addition，加法）——把兩個數值相加，結果寫回目的暫存器。

> [!danger]- ⚠️ 命名陷阱：函式`add()` ≠ 加法指令`ADD`
> <mark style="background: #FF5582A6;">這支影片範例剛好把函式取名叫`add()`，跟x86指令集裡真正的加法指令`ADD`撞名——兩者是完全不同的東西：函式`add()`是C原始碼裡妳自己寫的函式名稱，編譯後變成一整串指令（prologue、加總、epilogue、`ret`）；`ADD`才是那一串指令裡，實際做「兩數相加」這個動作的其中一條組合語言指令。看到反組譯清單裡同時出現`add`這個字，要分清楚是在講「呼叫`add()`這個函式」還是「執行`ADD`這條加法指令」。</mark>

> [!info]- 追問十六：你之前提醒我函式`add()`跟指令`ADD`會撞名不要搞混，那影片裡哪一行才是真正的`ADD`指令？它是不是只是助憶符的寫法？是看到加法運算子`+`才會用到它嗎？
> <mark style="background: #ADCCFFA6;">表格裡真正的`ADD`指令，就是`0x002A`那一行：`add eax, esi`，這是唯一一行CPU實際執行「兩數相加」動作的指令；其他寫著`add`字樣但其實是函式呼叫或函式名稱的地方（例如函式`add()`本身、`call add`裡的`add`），指的都是妳C原始碼裡那個函式，不是這條加法指令。</mark>
>
> 妳問「是不是只是助憶符的寫法」，沒錯，`add`這個小寫的英文字，只是給人類看的**助憶符（mnemonic，(b)節已經介紹過，是機器碼的文字化代稱）**，CPU實際執行的時候，看到的不是這幾個英文字母，而是對應的一串二進位機器碼；`add`只是為了讓妳我這種人類寫組合語言、看反組譯結果的時候方便記憶跟閱讀，不用直接背二進位數字才生出來的文字寫法。
>
> 妳問「是看到加法運算子才會使用嗎」，這個問題問到了**編譯器（compiler，把C原始碼翻譯成組合語言／機器碼的工具）跟CPU分工的關鍵**：`int sum = a + b;`這一行C原始碼裡的`+`，是編譯器在把C原始碼翻譯成組合語言的階段（compile time，編譯的當下）看到這個加法運算子之後，自己決定挑選`ADD`這條指令來實現它，這個決定是編譯器做的，不是CPU做的。CPU本身完全不認識、也不會去看C原始碼裡的`+`符號，CPU只會照著編譯器已經翻譯好、排在記憶體裡的指令，一條一條執行下去；等CPU真正執行到`0x002A`這一行的時候，它看到的只是「把eax和esi這兩個暫存器的值相加、結果寫回eax」這個動作本身，完全不知道、也不需要知道這個動作最初是從C原始碼裡的哪一個`+`號翻譯過來的。

> [!info]- 追問十七：CPU要去哪抓指令是什麼意思，這些指令在暫存器了還是在memory
> <mark style="background: #ADCCFFA6;">直接講重點：指令本身躺在memory裡（就是這篇筆記(a)節那份表格裡`0x0004`、`0x0020`這些位址實際代表的地方，屬於Code Segment），**不是事先存在暫存器裡**——暫存器只是CPU每次執行指令時，暫時借來搬運／加工用的極小空間，完全裝不下整支程式。</mark>
>
> a. **直接回答問題本身**：對，這些指令確實都放在memory（主記憶體，RAM）裡，更精確地說是放在行程虛擬記憶體空間裡的**Code Segment（text segment）**這一區——這點追問一、追問二、追問十四都已經確認過：表格裡`0x0004`到`0x0036`這些位址，指的就是每一行指令實際被放在記憶體裡的位置。CPU自己內部的暫存器，完全裝不下整支程式的所有指令，也從來不會事先把一整支程式搬進去——CPU是**一次只拿一條**，拿進來、執行完，再去拿下一條，這個動作就叫做fetch（提取）。
>
> b. **暫存器在fetch這一刻真正扮演的角色**：CPU內部的暫存器只有幾十個Byte大小，一次只裝得下極少量的東西——它們的作用是「這一刻CPU正在處理的資料或位址」，不是「存放所有指令的地方」。其中有四個專門負責fetch這個動作的暫存器：
>   1. **PC（Program Counter，程式計數器）**：存的不是指令本身，而是「下一條指令在記憶體裡的位址」——這正是追問二那句「CPU要去哪裡抓指令來執行」講的就是PC裡面那個數字。
>   2. **MAR（Memory Address Register，記憶體位址暫存器）**：把PC裡的位址複製過來，準備發給記憶體。
>   3. **MDR（Memory Data Register，記憶體資料暫存器）**：記憶體真正把那個位址存的內容（也就是指令的機器碼，像`e8 0d 00 00 00`這種hex bytes）送回來，先暫時放這裡。
>   4. **IR（Instruction Register，指令暫存器）**：把MDR拿到的內容正式搬進來，準備給Control Unit解碼、執行。
>
> c. **完整的fetch五個步驟**（套用(a)節`0x000E`（`call add`）這一行實際驗算）：
>   1. PC裡的`0x000E`複製到MAR
>   2. Control Unit對記憶體發出讀取訊號，要求拿`0x000E`這個位址的內容
>   3. 記憶體把`0x000E`存的機器碼`e8 0d 00 00 00`送進MDR
>   4. MDR的內容再搬進IR
>   5. PC自動更新——一般情況是PC+指令長度（指向下一條），但`call add`這次特殊，PC會被改成跳躍目標的`0x0020`，不是單純+1——這就是追問五、追問六講過的「表格順序≠CPU執行順序」在暫存器層次的具體機制。
>
> d. **跟這篇筆記已經確認過的內容連結**：這五個步驟不是一次性把整支程式搬進來，而是**每一條指令都重複一次**——fetch完`0x000E`、解碼、執行（跳到add()），下一次fetch就變成拿`0x0020`，一條接一條，這正是追問五「表格由上到下排的是位址順序，不是CPU實際執行順序」、追問六「表格順序、執行順序、call stack順序三種順序」這兩題背後更底層的運作方式。
>
> e. **效率補充：cache並不是每次都真的去慢速RAM跑一趟**：上面c點講的是概念上的fetch流程，實務上CPU速度遠比RAM快很多，現代CPU會先確認要抓的那個位址，是不是已經在更快的Cache（尤其是L1指令快取）裡，有的話直接從Cache拿、不用真的跑一趟RAM，這部分已經在[[CPU五大單元-ALU-CU-暫存器-快取與微指令]]筆記(d)(k)(l)點談過。
>
> f. **跟[[CPU五大單元-ALU-CU-暫存器-快取與微指令]]的關聯，寫出關聯原因**：那篇筆記(c)點講的是CU為了執行比較／運算，去抓「變數值」進暫存器的流程（CU發出讀取指令→值搬進暫存器→ALU拿暫存器的值做比較），這篇要講的是更前面一步——CU怎麼把「指令本身」從記憶體抓進來的fetch cycle。兩篇一個講「抓資料」、一個講「抓指令」，都會經過暫存器，但處理的東西不同，是同一個CPU執行主題下互補的兩個環節，所以互相連結。
>

> [!info]- 追問十八：為什麼Code Segment、Stack Segment的位址都用像記憶體位址的0x標記開頭
> <mark style="background: #ADCCFFA6;">這一題延伸自上面(e)節的完整位址順序，同時也是回頭修正追問十五(a)點一個講得不夠精確的地方——上一輪聊天已經先口頭回答過，這裡補上完整的書面版本。</mark>
>
> a. **`0x`只是「進位制」的寫法慣例，跟位址屬於哪個segment完全無關**：`0x`開頭表示「後面接的是16進位（hexadecimal）數字」，這只是一種記法，就像10進位數字前面不用加任何符號一樣。不管是Code Segment的`0x0004`，還是Stack Segment的`0x7FFF0FC0`，本質上都是「同一種東西」——一個記憶體位址，只是用同一套16進位記法寫出來，跟這個位址實際落在哪個segment、代表什麼內容，沒有任何關係。
>
> b. **為什麼位址普遍都用16進位寫，而不是10進位或2進位**：因為16＝2^4，1個16進位數字剛好可以對應4個bit，1個byte（8 bit）就正好可以用2位16進位數字完整表示（例如二進位`11111111`＝16進位`FF`＝10進位255），既不像2進位那樣落落長（一個位址可能要寫32或64個0跟1），又比10進位更貼合電腦內部以2的次方運算的方式，所以16進位是「寫機器碼／位址」最常見、最精簡的記法。來源：[uo-cis211.github.io – What the Hex?](https://uo-cis211.github.io/chapters/06_3_Hex.html)，驗證於2026-08-03。
>
> c. **更深一層的原因：Code Segment跟Stack Segment其實屬於同一個process的同一塊虛擬位址空間，只是距離非常遙遠**：這是要回頭修正的地方——並不是像追問十五(a)講的「這兩組數字根本不屬於同一個位址空間」，精確來說，它們是**同一個process的同一塊虛擬位址空間**裡，兩段相隔非常遙遠、彼此不重疊的區域（中間隔著Data、BSS、Heap，見(e)節來源），Code Segment在這塊空間裡位址比較小的那一端，Stack Segment在位址比較大的那一端。正因為本質上是「同一塊位址空間」，所以自然會用同一套16進位記法去寫，不會因為區域不同就換一套記法。
>
> d. **修正比喻**：追問十五(a)用「台北市門牌號碼跟東京都門牌號碼比大小」來比喻兩段位址不能直接比較，這個比喻容易讓人誤會成「兩個完全不同的系統」，其實更精確的畫面是——想像同一條非常非常長的路，門牌號碼從很小的數字（1號、2號……）一路編到天文數字，Code Segment就是這條路最前面幾號門牌，Stack Segment是這條路最後面幾號門牌，用的是同一套編號規則（16進位），只是數值差得非常遠。「不能直接拿數值比大小去判斷有意義的關聯」這個結論本身仍然成立，只是原因不是「不同系統」，而是「同一條路上隔太遠，比較沒有意義」，這裡幫妳把原因講得更精確一點。

> [!info]- 追問二十：Code Segment都放在memory裡面，但表格右邊對照的是機器碼跟組語、還混著暫存器名稱，這樣不會矛盾嗎？為什麼Code Segment跟Stack Segment總共會出現兩次記憶體位址？CPU一次只fetch一條，是不是就是fetch表格裡`mov edi, 3`這一整列？
> <mark style="background: #ADCCFFA6;">這三個問題環環相扣，核心都在區分「這條指令本身躺在哪裡」跟「這條指令執行後要動哪個對象」是兩件不同的事，這裡逐項拆開回答，也把妳這次補傳的影片截圖放進來當作最直接的證據。</mark>
>
> a. **表格裡出現暫存器名稱，不代表指令被存在暫存器裡，完全不矛盾**：`0x0004  mov edi, 3  bf 03 00 00 00`這一整列，不管是助憶符寫法`mov edi, 3`，還是機器碼`bf 03 00 00 00`，整條指令從頭到尾都**原封不動躺在Code Segment裡的`0x0004`這個記憶體位址**，沒有任何一部分被搬進暫存器——指令內容裡提到的`edi`，只是這條指令的**操作對象說明**，意思是「等這條指令被CPU抓進來、解碼、執行的那一刻，把立即值3寫進edi這個暫存器」，不是說這條指令現在就已經放在edi裡面。可以想像成一張寫在紙條上的留言「把100元放進錢包」，紙條本身放在抽屜裡（對應Code Segment／記憶體），紙條上寫的「錢包」只是指示的對象，不代表這張紙條自己被放進錢包裡——同樣道理，機器碼`bf 03 00 00 00`裡的`bf`這個byte本身就已經編碼了「目的地是edi」這項資訊（這部分[[x86通用暫存器與Register-in-Opcode編碼]]已經詳細講過opcode怎麼把暫存器編進機器碼裡，可以互相對照），但這個編碼結果本身仍然是靜靜躺在記憶體裡的一串byte，要等CPU執行到這一列才會真正發生「值被寫進edi」這件事。
>

> b. **「總共出現兩次記憶體位址」，這裡分兩種情況幫妳確認**：
>
>   1. **Code Segment跟Stack Segment分別各有一套自己的位址，所以位址概念會出現兩次**：這正是追問十八(c)點剛講過的——Code Segment有自己一套位址（`0x0004`~`0x0036`，標記指令躺在哪裡），Stack Segment也有自己一套位址（像`0x7FFF0FC0`這種，標記Stack Frame的內容躺在哪裡），兩者都只是**同一個process虛擬位址空間**裡的不同區域；只要是記憶體，不管裡面放的是指令還是資料，就一定需要位址去定位它，所以「位址」這個概念自然會在Code Segment、Stack Segment裡各出現一次，這不是重複或衝突，而是每一塊記憶體區域都需要有自己的座標系統。
>
>   2. **同一列指令裡，也可能同時出現兩個角色不同的位址**：例如表格裡`0x0013  mov [0x1234], eax`這一列——`0x0013`是這條指令自己躺在Code Segment的位置（**程式碼位址**），`0x1234`是這條指令執行後要寫入的目標（存放全域變數`result`的**資料位址**）——這兩個位址一個講「指令住哪」、一個講「指令要動哪一塊資料」，是追問八(a)點已經區分過的「程式碼位址 vs 資料位址」，這裡剛好是這兩種位址同時出現在同一列的實際例子，不是新的規則，只是妳這次親眼在同一列裡看到了。
>
> c. **CPU一次fetch，確實剛好對應表格上一整列，但精確地說，fetch搬的是機器碼位元組，不是助憶符文字**：對，妳的理解方向完全正確——CPU執行到`0x0004`這一步時，一次fetch進來的份量，剛好就是這一整列指令的機器碼`bf 03 00 00 00`（5個byte），透過追問十七(c)點講過的五個步驟（PC→MAR→發出讀取訊號→記憶體回傳到MDR→搬進IR）整條搬進來。但要幫妳補上一個精確的地方：CPU電路真正認得、真正fetch進來處理的，是`bf 03 00 00 00`這一串二進位／16進位數字本身，不是「mov edi, 3」這幾個英文字——「`mov edi, 3`」是給人類讀反組譯清單方便用的助憶符寫法，等這5個byte被搬進IR、Control Unit解碼（decode）之後，才會「翻譯」出這其實是「把立即值3放進edi」這個動作，進而指揮把值寫進edi暫存器。所以「CPU去fetch表格裡`mov edi, 3`這一列」這句話，當成一種方便溝通的講法完全沒問題，只是精確來說，fetch搬的是這一列的機器碼位元組，助憶符文字只是這串位元組的人類可讀翻譯，兩者是同一件事的兩種呈現方式。
>

> [!info]- 追問二十一：「每個thread各自擁有一份」到底是什麼、這個區分「所以呢」、BSS是什麼、以及main()跟add()在Stack Segment跟Code Segment裡各自對應的具體組合語言與機器碼完整對照
> <mark style="background: #ADCCFFA6;">上一輪回答得不夠完整，這裡重新整理——原本的a點（process跟thread分層「所以呢」）跟c點（「每個thread各自擁有一份」到底是什麼）其實是同一件事的兩個角度，合併成一點回答，不重複講兩次；BSS跟最後的對照表是兩個完全獨立的問題，保持分開。</mark>
>
> a. **「每個thread各自擁有一份」的是Stack，不是process；這個區分「所以呢」——實際會造成什麼差別**：先精確一次這句話本身——Code Segment、Data、BSS(Block-Started by Symbol)、Heap這幾塊，同一個process底下的所有thread都共用「同一份」；只有Stack，是每一個thread各自擁有自己「獨立的一份」（不是「各自擁有一份process」——thread不會擁有process，process是容器、thread是活在容器裡面的東西，一個thread本身就活在某一個process裡，不會反過來擁有自己的process）。如果一個process有3個thread，Code Segment／Data／BSS／Heap各自只存在1份、大家共用，但Stack會存在3份，一個thread一份，彼此獨立、互不影響。那這個區分「所以呢」——如果一個process只有一個thread（就是main()／add()這支影片的情況），不會造成任何實際差別，可以先放著不管。但如果同一個process開了「第二個」thread，差別就出現了：兩個thread會共用同一份Code Segment（也就是同一份`0x0004`~`0x0036`的機器碼，記憶體裡只有一份，不會複製兩份），如果這兩個thread「同時」都呼叫了add()，它們執行的其實是同一份指令，但因為每個thread各自擁有獨立的Stack，這兩次呼叫產生的Stack Frame會落在不同的Stack位址上，`sum`這個區域變數會各自有各自的一份、不會互相覆蓋踩到——這正是多執行緒（multithreading）可以讓好幾個thread「同時」呼叫同一個函式、卻不會讓彼此的區域變數互相干擾的底層原因：程式碼只有一份、大家共用，但每個thread「執行中的資料」（Stack）是各自獨立的。
>
> b. **BSS是什麼**：BSS全名是Block Started by Symbol，這個名字是歷史留下來的（源自早期一台IBM組譯器裡一個組譯指示的名稱），現在已經跟原始全名沒有直接關聯，單純變成一個固定的專有名詞，指的是<mark style="background: #FFF3A3A6;">存放「已經宣告、但沒有給初始值」</mark>的<mark style="background: #D2B3FFA6;">全域／靜態變數的</mark>那塊記憶體區域。例如C語言裡`static int count;`（沒有寫`= 0`或其他初始值）就會被放進BSS。它跟Data Segment（存放`static int count = 5;`這種「已經給初始值」的全域／靜態變數）的關鍵差異在於：Data Segment的初始值必須真的被寫進執行檔案本身（因為載入時要能真的把這個值寫進記憶體），而BSS完全不需要——反正沒有初始值，作業系統只要在程式載入時把這塊區域直接清成全部是0就好，所以BSS只需要在執行檔案裡記錄「這裡需要多大的空間」，不需要真的存一堆0進去，可以讓執行檔案的體積變小。
>
> c. **完整對照：main()跟add()兩個函式，在Code Segment跟Stack Segment裡實際對應的內容**：這裡要先更正一個重要前提——Stack Segment裡面放的從來就不是「組合語言／機器碼」，Stack Segment裡放的是程式執行時的**資料**（一個返回位址的數值、一個備份的暫存器數值、一個區域變數的數值），不是指令本身。真正的組合語言／機器碼，兩個segment裡只有Code Segment這一份——Code Segment回答的是「指令長什麼樣子、放在哪裡」，Stack Segment回答的是「執行到這裡的時候，資料長什麼樣子、放在哪裡」，兩者性質完全不同，沒有「Stack Segment版本的組合語言」這種東西。所以下面把妳要的對照整理成表格：Code Segment欄位是真正的組合語言／機器碼（全部已從截圖核對過，見(a)節），Stack Segment欄位標的是「這一格Stack內容，是被Code Segment哪一行指令、在執行的當下寫進去或釋放掉的」，Stack位址沿用追問十五(b)已核對過的Gemini示意數字（非截圖逐byte確認的真實數值）。

> [!info]- 追問二十二：為什麼談記憶體時又穿插CPU指標名稱、Stack位址由高到低的排列容易搞混、寫入與釋放具體指的是什麼，以及核對妳自己重新整理的add()五步驟

>
> a. **CPU暫存器名稱出現在Stack討論裡，不代表矛盾**：追問二十一(d)表格裡「main() BP備份的值」這一格，標籤裡提到「BP」，容易讓人誤以為這格記憶體本身變成了CPU的暫存器——其實不是。這一格100%仍然是Stack Segment裡一塊普通的記憶體（住在`0x7FFF0FE0`），提到「BP」只是在說明「這格記憶體存放的內容，來源是main()的rbp暫存器當下的值」，就像一份備份檔案取名叫「BP備份」，檔案本身仍然放在硬碟裡，取這個名字只是為了讓人知道它備份的是誰，不代表這個檔案跑進CPU裡面去了——這跟追問二十(a)點「表格出現暫存器名稱不代表指令住在暫存器裡」是同一種「標籤說明來源，不等於物理位置改變」的邏輯，可以互相對照。
>
> b. **Stack位址由高到低排列，先訂正一個筆誤**：妳核對時提到「下一個是`0x7FFF0F10`」，這個數字跟追問二十一(d)表格裡實際寫的`0x7FFF0FE0`不一樣（差在後兩碼），這裡先幫妳訂正——表格由上到下依序是`0x7FFF1000`→`0x7FFF0FF0`→`0x7FFF0FE0`→`0x7FFF0FC0`，確實是越往下數字越小，妳「底下變得比較小」這個結論完全正確，只是引用數字時打錯了一碼。至於「能不能統一成上面永遠是高的」——這正是表格本來的排法，`0x7FFF1000`（最高）在最上面、`0x7FFF0FC0`（最低）在最下面，妳的閱讀方向沒有問題，只是中途數字抄錯了一格，才會覺得對不起來。
>
> c. **「寫入」「釋放」具體指的是什麼——用`0x7FFF0FF0`這一格逐字拆開**：這一格「寫入」，指的是`0x000E call add`這一行指令執行的當下，CPU把返回位址`0x0013`這個值放進這一格（`call`指令的固定動作之一，見(b)節f項）；這一格「釋放」，指的是`ret`指令執行的時候，把這一格的內容讀出來（讀到的正是`0x0013`）、然後讓Stack Pointer往回移動，讓這一格從此被視為「不再使用」，CPU接著跳回`0x0013`繼續執行——妳自己重新整理的這句「`0x7FFF0FF0`是被`0x000E call add`寫入的，然後它釋放的時候是因為return，然後跳回`0x0013`」完全正確。「寫入」＝某一行指令把值放進這一格；「釋放」＝某一行指令（通常是`pop`或`ret`）把這一格讀出來後、讓這一格的空間讓出來，不代表這格記憶體本身被清空或消失，只是「不再被視為目前有效的資料」。
>
> d. **核對妳自己重新整理的add()五步驟**：
>   1. push base pointer——對，對應`0x0020 push rbp`，把main()的BP備份進Stack。
>   2. 複製stack pointer給base pointer——對，對應`0x0021 mov rbp, rsp`，把新的一層BP設成目前的SP。
>   3. stack pointer又減了4——對，對應`0x0024 sub rsp, 4`，預留`sum`的空間。
>   4. 這一步妳合併成一句，實際上是**兩行**指令，要幫妳拆開：`0x0028 mov eax, edi`（把第1個參數a複製進eax）跟`0x002A add eax, esi`（eax再加上第2個參數b，變成`a+b`）是分開的兩條指令，不是同一行做完兩件事。
>   5. 把EAX複製到base pointer減少4個bytes的位置——對，對應`0x002C mov [rbp-4], eax`，把算好的`a+b`寫進`sum`的空間。
>   整體來說，妳的五步驟重述除了第4步應該拆成兩條指令之外，其餘完全正確。

> a. **模擬延伸main()自己完整的Stack Frame（全部是邏輯推演，不是截圖核對過的事實）**：追問二十一(d)表格裡`0x7FFF1000`那一格，原本只寫「SP停在這裡，沒有已知的具體變數」；如果假設main()也遵守跟add()一樣的標準prologue寫法（`push rbp`／`mov rbp, rsp`），可以邏輯上推演出main()自己完整的Stack Frame，由高到低大致會是：最上面一格是main()自己的返回位址（回到呼叫main()的那段執行期啟動碼，見追問一，這格比`0x7FFF1000`更高，目前完全沒有截圖範圍拍到）；再往下一格，也就是`0x7FFF1000`這個位置，推論起來應該裝的是main()自己的BP備份——main()執行`push rbp`的時候，把呼叫main()之前CPU裡rbp原本的值（極可能是啟動碼自己的BP，或一個初始值）備份進這一格；再往下，main()自己如果有區域變數，會接著往下排，但這支範例main()沒有宣告任何區域變數（`result`是全域變數，追問二十一(d)已確認過），所以main()的Frame理論上到BP備份這一格就結束，緊接著往下就是`0x7FFF0FF0`（add()呼叫時push進去的返回位址）。**再次強調：這整段是根據add()已核對過的prologue寫法邏輯推演出來的合理延伸，不是截圖裡實際拍到的數字，跟追問二十一(d)表格裡「已核對」的三格性質不同，這裡全部算是推論。**
>
> b. **「bp是做備份用的嗎？」——不完全是，備份只是附帶的副作用，BP真正的設計目的是「穩定的定位錨點」**：BP（Base Pointer，基底指標）的核心用途，是**在一個函式執行期間，提供一個固定不變的參考點**，讓函式裡所有存取區域變數、參數的指令，都可以用「BP加減一個固定的位移量」來定位（例如`[rbp-4]`固定指向`sum`），不會因為Stack Pointer在函式執行過程中不斷變動（`sub rsp,4`、`push`、`pop`都會讓SP的值改變）而跟著跑掉——這是BP存在的**主要原因**：給整個函式一個穩定的座標原點。至於「備份」（`push rbp`把舊值存起來、`pop rbp`把它還原回去）之所以會發生，是因為**整台CPU實際上只有一個實體的rbp暫存器**，main()在用、add()被呼叫的時候也要用，兩個函式沒辦法同時各自擁有一份rbp，所以每次呼叫新函式，都必須先把目前這個唯一的rbp暫存器裡「上一個函式還需要用到的值」暫存到Stack上，等這個函式執行完，再把它讀回來還給上一個函式——這個「備份、歸還」的動作，是rbp暫存器只有一份、必須被所有函式輪流共用而產生的**必要副作用**，不是BP這個機制被設計出來的初衷。可以類比成：辦公室只有一張辦公桌（rbp），下一個人要用之前，必須先把前一個人桌上的東西收進抽屜（push），等他自己用完，再把東西放回原位（pop）——桌子本身的設計目的是給人辦公用的（定位錨點），「收進抽屜暫存」只是因為桌子只有一張、必須共用才需要做的動作。
>

> [!info]- 追問二十四：姜姜那張經典32位元Stack Frame圖裡「Return Address」被畫成Stack Segment的一格，但它裝的值`0x0013`明明是Code Segment的位址，這樣算不算矛盾
> <mark style="background: #ADCCFFA6;">不矛盾，這裡用信箱跟紙條的比喻，把「盒子住在哪裡」跟「盒子裡寫的內容指向哪裡」拆成兩件事說清楚。</mark>
>
> Return Address這個「盒子」本身，物理位置100%屬於Stack Segment（追問二十一(d)表格裡的`0x7FFF0FF0`那一格）；但這個盒子裡裝的「內容」，也就是`0x0013`這個數值，它的意義是指向Code Segment裡的一個位置。姜姜追問十四(d)點那張經典圖，把Return Address畫在Stack Frame那一側，是因為那張圖在講「這個值住在Stack Frame裡的哪個相對位置」，不是在講「這個值代表哪個segment的內容」——同一件事可以同時回答「它住在哪」（Stack）跟「它指向哪」（Code），這兩個問題的答案本來就可以不一樣，這正是追問二十(b)點2.已經拆過的「程式碼位址 vs 資料位址」，只是這次換成「儲存位置 vs 內容意義」的角度再問一次。

> [!info]- 追問二十五：Stack不是只放實際數值嗎，那`0x0013`到底算是裡面的值還是Code Segment主責的東西；main()跟add()都是函式，為什麼Frame放在Stack不是Heap，Stack是不是只存位址
> <mark style="background: #ADCCFFA6;">兩個問題分開回答：第一個問題其實跟追問二十四是同一件事換句話問；第二個問題要先訂正一個前提——函式本身從來不會被放進Stack或Heap。</mark>
>
> a. **這一格（`0x7FFF0FF0`）的「物理歸屬」跟「裡面存的數值的意義」要分開看**：這一格100%屬於Stack Segment，這點不變；它裡面存的實際數值就是`0x0013`——這個數值本身沒有分裂成兩份或搬到別的地方，從頭到尾只有一份，只是這個數值恰好等於Code Segment裡一個合法的位置，所以「Code Segment主責」指的是「這個數值所指向的意義／用途」，不是說這格記憶體被Code Segment搬走或共同持有，跟追問二十四是同一個結論。
>
> b. **Stack跟Heap的取捨關鍵，不是「是不是函式」，而是資料的生命週期由誰決定、什麼時候結束**：Stack上放的是「跟著函式呼叫自動誕生、自動消滅」的資料——返回位址、備份的BP值、區域變數，這些東西的存在時間完全綁定在這次函式呼叫上，函式一返回，這些資料就自動失效，不需要程式設計師自己動手管理；Heap放的是程式設計師自己明確要求配置（`malloc`／`new`）、也要自己明確決定何時釋放的資料，存在時間不跟任何一次函式呼叫綁定，可以活得比呼叫它的函式還久。main()跟add()這兩個函式的**程式碼本身**永遠只會放在Code Segment，不會出現在Stack或Heap裡；Stack上放的從來不是函式的程式碼，而是函式被呼叫這件事所產生的、暫時性的執行期資料——這也是為什麼Stack不會因為main()和add()是函式就把它們放進Heap，函式本身根本不會被放進Stack或Heap，只有「呼叫函式所產生的資料」才會放進Stack。至於「Stack是不是只存位址」——不是，Stack上混合著位址類型的值（像返回位址、BP備份，本質上是位址）跟純資料類型的值（像`sum`這個計算結果，是一個普通的整數，不是位址），兩種都存在，不是只存位址。

> [!info]- 追問二十六：`0x0013`這個數字，是裡面的數字還是地址數字
> <mark style="background: #ADCCFFA6;">這兩個問題問的其實是同一個數字，只是它同時扮演兩種角色，不是兩個不同的數字。</mark>
>
> a. 從「這一格裡面裝的是什麼」這個角度看，`0x0013`是**裡面的數字**——它是Stack Segment位址`0x7FFF0FF0`這一格實際存放的內容（已核對，對應(a)節表格`call add`那一行push進去的返回位址）。
>
> b. 從「這個數字被拿去做什麼用」這個角度看，`0x0013`同時也是**地址數字**——因為它剛好等於Code Segment裡`mov [0x1234], eax`這一行指令的位置，所以當`ret`把它從Stack pop出來的時候，CPU會把它當成一個要跳過去的位址來用。
>
> c. 所以正確的理解是：這是同一個數字，**它被存放的位置屬於Stack Segment**（住在`0x7FFF0FF0`這個Stack格子裡），**但它的意義（拿出來要做什麼用）指向Code Segment**（跳回`0x0013`這個Code位址）——跟信箱裡的紙條比喻是同一件事：紙條本身放在信箱裡（Stack），但紙條上寫的內容是另一個地址（Code Segment），紙條的「位置」跟紙條「寫的內容」是兩件事，但紙條和紙條上的數字，從頭到尾都只有一份，沒有變成兩個數字。
>

> [!info]- 追問二十七：main()自己的返回位址回到的那段執行期啟動碼，指的是組合語言嗎；Code Segment到底存的是不是全部的原始碼
> <mark style="background: #ADCCFFA6;">兩個問題分開回答，都是釐清「一段程式的角色名稱」跟「這段程式編譯完之後的呈現形式」不是同一件事。</mark>
>
> a. **啟動碼指的不是「組合語言」這個語言本身**：啟動碼（runtime startup code，crt0／`__libc_start_main`這類，見追問一）本身不是「組合語言」這個語言類別的代稱，而是一段真正的程式（負責初始化Stack、處理argv／envp等準備工作），最初可能用C語言或組合語言寫成原始碼，跟main()、add()一樣，一樣要經過編譯／組譯，變成機器碼，放進Code Segment。所以精確地說：啟動碼是這段程式的功能角色名稱，它「編譯完的結果」確實跟main()一樣，會以組合語言／機器碼的形式呈現在Code Segment裡，但「啟動碼」這個詞本身指的是這段程式的功能（初始化工作），不是在指「組合語言」這個語言本身——這跟main()不是組合語言、但main()編譯完的結果會用組合語言表示，是同樣的道理。
>
> b. **Code Segment存的不是原始碼，是原始碼編譯後的結果**：Code Segment存的不是原始碼（妳寫的那份.c檔案裡的文字），而是原始碼經過編譯器翻譯之後產生的機器碼／指令。原始碼只是拿去餵給編譯器的輸入，編譯完成後，變數名稱、註解、排版這些東西全部消失（追問九(e)點已經講過這件事），Code Segment裡剩下的只有轉譯後的指令，例如`0x0004 mov edi, 3`這種形式，不是`int result = 0;`這種C語言文字。至於「全部」——Code Segment確實會包含這個可執行檔用到的所有已編譯指令：main()、add()這些自己寫的函式、前面提過的執行期啟動碼（crt0等），如果有靜態連結進來的函式庫函式，那些函式編譯後的機器碼也會在裡面——但這些統統是「編譯後的指令」，不是「原始碼文字」本身。

> [!info]- 追問二十八：(a-1)節a到f那份順序列表裡「最上面那片洋芋片」，指的是原圖（罐口朝上）還是追問十三的倒放版（罐口朝下）
> <mark style="background: #ADCCFFA6;">這正是追問十三(d)點最後一段講過的「排版習慣」問題，這次妳自己親身遇到了，這裡把兩張圖分開來對照清楚。</mark>
>
> (a-1)節a到f那份「疊放順序」文字列表，包括這次問到的d點「add()收尾`add rsp,4`……等於把最上面那片洋芋片的位置讓出來」，是寫在追問十三、也就是倒放版圖出現**之前**，描述的是(a-1)節最原始那張圖——罐口朝上，push／pop都發生在畫面上方（開口那一端），所以a到f文字裡的「上面」，指的是「開口這一端」，也就是Stack Pointer所在、最近一次push／pop發生的位置。追問十三後來加的「倒放版」圖，是把同一張圖上下顛倒過來畫，開口（push／pop發生的地方）改畫在畫面下方，main()既有內容（罐底）改畫在畫面上方，目的是配合課本、除錯器常見的「高位址畫在上面」習慣——但a到f這份文字列表當初沒有跟著倒放版重新改寫，所以文字裡仍然沿用原圖的說法。
>
> 所以：如果妳現在腦中想的是**倒放版**，d點這句話要換成「等於把**最下面**那片洋芋片的位置讓出來」才對得起來，因為倒放版裡開口在下面；如果腦中想的是**原圖**（罐口朝上），原本寫的「最上面」就是對的。兩者講的是完全同一件事——被釋放的都是SP旁邊那格`sum`的空間——只是「上面」「下面」這兩個字，會隨著妳心裡用哪一張圖當參考畫面而互換，這正是追問十三(d)點「紙上要把高位址畫在上還是下，純粹是排版習慣，記憶體本身沒有上下」這個結論的具體example。

f. **`call`**（呼叫）——同時做兩件事：把返回位址（`call`指令結束後下一行的位址）push進Stack，然後跳到目標函式的位址開始執行。

g. **`ret`**（return，返回）——函式執行完的收尾指令：把Stack最上面那一格（也就是`call`當初push進去的返回位址）pop出來，然後跳回那個位址繼續執行呼叫者的程式碼。

h. **`lea`**（load effective address，載入有效位址）——影片裡雖然這個範例目前還沒出現，但屬於同一組常見助憶符，先列在這裡備查：把「一個位址計算的結果」（不是該位址裡的內容）放進目的暫存器，常被拿來做位址運算，不實際存取記憶體。

## (c) 一句話收尾

`mov`複製、`push`/`pop`負責Stack一進一出、`sub`/`add`做算術（也負責移動Stack Pointer）、`call`/`ret`負責跳轉與返回——這幾個助憶符幾乎涵蓋了這支影片範例從呼叫到返回的完整流程；`add()`函式名稱與`ADD`加法指令撞名是這份範例裡最容易搞混的地方，見上面(b)節e項的提醒。
