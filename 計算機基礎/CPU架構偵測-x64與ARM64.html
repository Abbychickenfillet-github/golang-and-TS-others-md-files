🧠 自我測驗

是非題

  1. AMD64、x86-64、x64、Intel 64 講的是同一個指令集架構。

    四個名字一件事。叫 AMD64 是因為這套 64 位元延伸是 AMD 在 2000 年提出的，Intel 後來才跟進。

  2. Intel 的 CPU 在 Windows 上查 PROCESSOR_ARCHITECTURE 會顯示 Intel64。

    會顯示 AMD64。Windows 沿用 AMD 的原始名稱，不管你的 CPU 是誰家的。

  3. 在 PowerShell 打 echo %PROCESSOR_ARCHITECTURE% 可以正確查到架構。

    %VAR% 是 CMD 語法，PowerShell 會原樣吐回字串。PowerShell 要用 $env:PROCESSOR_ARCHITECTURE。

  4. PROCESSOR_ARCHITECTURE 回報的是這台機器的架構，跟目前行程是幾位元無關。

    它回報的是「目前這個行程」的架構。32 位元 shell 會回 x86，ARM64 上的 x64 模擬行程會回 AMD64，都會騙你。

  5. PROCESSOR_ARCHITEW6432 只有在「32 位元行程跑在 64 位元系統上」時才存在。

    這是 WOW64 子系統替被建立的行程重寫環境變數的結果，內容是機器的真實架構。

  6. x86-64 編譯出來的執行檔可以直接在 ARM64 的 CPU 上原生執行。

    兩個 ISA 的機器指令完全不相容。要嘛重編譯，要嘛靠模擬層（Windows on ARM 的 x64 模擬、macOS 的 Rosetta 2）。

  7. Linux 的 uname -m 顯示 aarch64 代表這是 ARM 的 64 位元架構。

    AArch64 是 ARM 官方名稱，macOS 與 Windows 習慣顯示 arm64。

填空題

  1. ISA 的全名是 Instruction Set ，中文叫指令集架構。

    CPU 對外公開的合約：認得哪些指令、有哪些暫存器、怎麼定址。

  2. ARM 架構 64 位元執行狀態的官方名稱是 （ARMv8-A 起引入）。

    Linux 的 uname -m 就顯示這個。

  3. PowerShell 讀環境變數要用 $:PROCESSOR_ARCHITECTURE 這個 provider 前綴。

    PowerShell 把環境變數當成像檔案系統的磁碟機，所以也可以 Get-ChildItem Env: 列全部。

  4. 讓 64 位元 Windows 能跑 32 位元程式的子系統，縮寫是 ，全名 Windows 32-bit On Windows 64-bit。

    它會替 32 位元行程重寫 PROCESSOR_ARCHITECTURE。

  5. 在程式裡最可靠的架構偵測 Win32 API 是 IsWow64Process，它會分別回傳行程架構與機器原生架構。

    IsWow64Process2 比舊版的 IsWow64Process 多回一個 nativeMachine。

  6. Apple Silicon 上讓 x86-64 程式能執行的轉譯層叫 Rosetta 。

    效能會打折，所以能裝原生 arm64 版就裝。

申論題

  1. 你要幫同事的 Windows 筆電下載一個開發工具，官網同時提供 x64 與 ARM64 版。請完整說明：ISA 是什麼、為什麼選錯版本程式會完全打不開、你會用哪些指令去查、以及為什麼「查到 AMD64 就一定是 Intel/AMD 機器」這個推論其實有漏洞、該怎麼補。

    參考方向：(1) ISA（Instruction Set Architecture，指令集架構）是 CPU 對外公開的合約——認得哪些機器指令、有哪些暫存器、怎麼定址、位元組順序。同一 ISA 的二進位可互通，不同 ISA 完全不相容。(2) 選錯會怎樣——x86-64 與 ARM64 的機器碼互不相容，Windows 會直接彈「此應用程式無法在您的電腦上執行」。(3) 怎麼查——CMD 用 echo %PROCESSOR_ARCHITECTURE%；PowerShell 用 $env:PROCESSOR_ARCHITECTURE（%VAR% 在 PowerShell 會被當普通字串原樣吐回）；WSL 或 Git Bash 用 uname -m；Node 程式內用 os.arch()。(4) 漏洞——這些變數回報的是「目前這個行程」的架構而非機器。開到 SysWOW64 底下的 32 位元 PowerShell 會回 x86；更麻煩的是 Windows 11 on ARM 能模擬執行 x64 程式，所以一個 x64 行程在 ARM64 機器上會回 AMD64，讓你誤判成 Intel 機。(5) 怎麼補——同時檢查 PROCESSOR_ARCHITEW6432（只有 32 位元行程跑在 64 位元系統時才存在，內容是機器真實架構）；程式裡最可靠的是呼叫 IsWow64Process2，它分別回傳行程架構與機器原生架構。(6) 補充 AMD64 這個名字的由來：這套 64 位元延伸是 AMD 在 2000 年提出、2003 年隨 Opteron 出貨，Intel 後來跟進（官方叫 Intel 64），Windows 沿用 AMD 的原始名稱，所以 Intel 機器也顯示 AMD64。

名詞先攤開（f–h）

[!info] 縮寫全名
f. ISA（Instruction Set Architecture，指令集架構）——CPU 對外公開的「合約」：它認得哪些機器指令、有哪些暫存器、記憶體怎麼定址、位元組順序是大端還小端。同一個 ISA 的程式碼可以在任何實作該 ISA 的 CPU 上跑，不同 ISA 之間的二進位檔完全不相容。x86-64 與 ARM64 就是兩個不同的 ISA。

g. x86-64 / x64 / AMD64 / Intel 64——這四個是同一件事的四個名字。它是 x86 這個 32 位元 ISA 的 64 位元延伸。之所以叫 AMD64，是因為這套 64 位元延伸是 AMD 在 2000 年提出、2003 年隨 Opteron 出貨的，Intel 後來才跟進實作（Intel 官方叫它 Intel 64）。Windows 沿用了 AMD 的原始名稱，所以你在 Windows 上查出來會看到 AMD64，即使你的 CPU 是 Intel 的也一樣。

h. ARM64 / AArch64——ARM 架構的 64 位元執行狀態，官方正式名稱是 AArch64（ARMv8-A 起引入）。Linux 的 uname -m 顯示 aarch64，macOS 與 Windows 習慣顯示 arm64。代表產品是 Apple M 系列與高通 Snapdragon X。

關鍵：x86-64 與 ARM64 的機器指令二進位完全不相容。下載錯版本，Windows 會直接彈「此應用程式無法在您的電腦上執行」。就像插頭型號不對，硬插不會通電。

重點整理

一、怎麼問出來（i–k）

i. 各系統的指令對照：

環境 指令 輸出範例與判讀
Windows CMD（命令提示字元） echo %PROCESSOR_ARCHITECTURE% AMD64 代表 x64；ARM64 代表 ARM；x86 代表 32 位元
Windows PowerShell $env:PROCESSOR_ARCHITECTURE 同上
Windows PowerShell（另一招） [System.Environment]::Is64BitOperatingSystem 回傳 True 代表作業系統是 64 位元
macOS / Linux / WSL / Git Bash uname -m x86_64 代表 x64；arm64 或 aarch64 代表 ARM
Node.js 程式內 require('os').arch() 回傳 'x64' 或 'arm64'

j. Node.js 那招一行一行拆：

const os = require('os');
console.log('當前架構為:', os.arch());
// 在 AMD64 的機器上會輸出 'x64'
片段 意思
require('os') CommonJS 的模組載入語法，把 Node 內建的 os 模組抓進來。ESM 寫法是 import os from 'node:os'
os.arch() 回傳「Node 這個行程被編譯成哪個架構」的字串。注意它回的是行程的架構，不見得等於作業系統的架構

k. 為什麼要區分架構：不同 ISA 決定軟體怎麼編譯。x86-64（Intel／AMD）是桌機與筆電的傳統主流；ARM64（Apple M 系列、Snapdragon X）以省電與效能比著稱。安裝 Node.js、Docker、VS Code 這類開發工具時選對版本，才不會被轉譯層（例如 Apple 的 Rosetta 2、Windows 的 x86 模擬層）吃掉效能。

二、實際踩到的坑：PowerShell 不吃 %VAR%（l–n）

l. 對話裡發生的實況：

PS C:\Users\User> echo %PROCESSOR_ARCHITECTURE%
%PROCESSOR_ARCHITECTURE%
PS C:\Users\User>

輸入什麼就吐回什麼，因為 PowerShell 根本沒把它當變數。

m. 原因：%變數名% 是 CMD（cmd.exe，命令提示字元）的變數展開語法，PowerShell 不認得。在 PowerShell 眼裡，%PROCESSOR_ARCHITECTURE% 只是一串普通字元（% 在 PowerShell 裡是 ForEach-Object 的別名，但沒有跟著 script block 時就只是符號），echo（即 Write-Output 的別名）就照原樣印出來。

n. 正解：PowerShell 用 $env: 這個 provider 前綴讀環境變數。

$env:PROCESSOR_ARCHITECTURE
片段 意思
$ PowerShell 的變數符號
env: PowerShell 的 Environment Provider（環境變數提供者）。PowerShell 把環境變數當成一個像檔案系統的「磁碟機」來存取，所以你也可以打 Get-ChildItem Env: 列出全部
PROCESSOR_ARCHITECTURE 變數名稱

三種 shell 的速查：

Shell 讀環境變數的寫法
CMD echo %PROCESSOR_ARCHITECTURE%
PowerShell $env:PROCESSOR_ARCHITECTURE
Bash / WSL / Git Bash echo $PROCESSOR_ARCHITECTURE 或直接 uname -m

三、⚠️ 陷阱：32 位元行程會騙你（o–p）

o. PROCESSOR_ARCHITECTURE 回報的是「目前這個行程」的架構，不是「這台機器」的架構。如果你在 64 位元 Windows 上開了一個 32 位元的 PowerShell（C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe），它會回 x86，而不是 AMD64。

這是 WOW64（Windows 32-bit On Windows 64-bit） 子系統造成的：當 64 位元系統建立 32 位元行程時，WOW64 會替它重寫環境變數。

p. 正確的做法是同時看 PROCESSOR_ARCHITEW6432：

# 只有在「32 位元行程跑在 64 位元系統上」時，這個變數才存在，內容是機器的真實架構
$env:PROCESSOR_ARCHITEW6432

判讀邏輯：

PROCESSOR_ARCHITEW6432 PROCESSOR_ARCHITECTURE 結論
不存在（空值） AMD64 原生 64 位元行程，機器是 x64
不存在（空值） ARM64 原生 ARM64 行程，機器是 ARM64
AMD64 x86 機器是 x64，但你開的是 32 位元 shell
ARM64 x86 或 AMD64 機器是 ARM64，你的行程跑在模擬層裡

最後那一列是 Windows on ARM 最容易踩的坑：Windows 11 on ARM 可以模擬執行 x64 程式，所以一個 x64 行程在 ARM64 機器上問 PROCESSOR_ARCHITECTURE 會得到 AMD64，讓你誤以為機器是 Intel。

在程式裡最可靠的是呼叫 Win32 API IsWow64Process2，它會分別回傳「行程的架構」與「機器的原生架構」。

四、決策：該下載 x64 還是 ARM64（q–r）

q. 對話當下的結論：既然 $env:PROCESSOR_ARCHITECTURE 輸出 AMD64，一律選標示為 x64、x86_64 或 64-bit 的安裝檔，避開 arm64 與 aarch64。

r. 一般性的下載決策表：

你查到的值 該下載的版本 備註
AMD64 或 x86_64 x64 不需要任何轉譯層，原生執行效能最佳
ARM64 或 aarch64 ARM64 若某軟體沒出 ARM64 版，Windows 11 on ARM 與 macOS 的 Rosetta 2 通常可模擬 x64，但會損失效能
x86 先確認是不是 WOW64 造成的假象 真的是 32 位元機器的話，很多現代開發工具已不再提供 32 位元版
