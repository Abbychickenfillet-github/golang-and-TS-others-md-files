# ASCII — 美國資訊交換標準碼

> **ASCII = American Standard Code for Information Interchange**
> 直譯：**美國資訊交換標準碼**。念作「阿斯基」(/ˈæskiː/)。

相關筆記：[[記憶體最小定址單位 (Byte Addressability)]]、[[進位制-二進制-十六進制-Bytes與RGB]]、[[JavaScript-字串方法]]、[[typography]]

---

## 1. 一句話：它是「字元 ↔ 數字」的對照表

電腦裡**只有數字**，沒有文字。所以要存一個字母 `A`，必須先約定「`A` 用哪個數字代表」。

`ASCII 就是那份約定（1963 年制定）：`

```
'A'  →  65
'B'  →  66
'a'  →  97
'0'  →  48   ← 注意！字元 '0' 的編號是 48，不是 0
' '  →  32   ← 空格也有編號
```

沒有這份對照表，你打的 `A` 存進檔案、傳到別台電腦，對方根本不知道那個 byte 該顯示成什麼。

---

## 2. 為什麼只用 0～127？（明明 1 byte 可以到 255）

**因為 ASCII 只用了 7 個 bit**，不是 8 個。

```
2⁷ = 128  →  編號 0 ~ 127
2⁸ = 256  →  編號 0 ~ 255（1 byte 的完整容量）
```

1963 年時，英文字母（大小寫 52 個）+ 數字（10 個）+ 標點 + 控制字元，**128 格就綽綽有餘**，而且當時每個 bit 都很貴，能省則省。第 8 個 bit 原本留作**校驗位（parity bit）**用來偵測傳輸錯誤。

> 📌 **所以 ASCII 字元存進電腦時佔 1 byte（8 bits），但最高位那個 bit 永遠是 0。**
> 這就是為什麼常看到「ASCII 是 0-127」和「一個 ASCII 字元佔 1 byte」同時成立——**不矛盾，是「用不滿」。**

---

## 2.5 ⁉️ 為什麼「最高位永遠是 0」？

**因為那個 bit 的「權重」是 128。一旦它是 1，數值就必定 ≥ 128——而 ASCII 最大只到 127。**

這**不是誰規定的，是數學上的必然。**

### 回想 8 個 bit 的權重

```
 位置：   7    6    5    4    3    2    1    0
 權重： 128   64   32   16    8    4    2    1
        ↑
     最高位（MSB, Most Significant Bit，最高有效位元）
```

**最高位那一格的「面額」是 128。** 所以：

| 最高位 | 數值範圍 | 是不是 ASCII |
|---|---|---|
| **0** | 0 ~ 127 | ✅ **ASCII 全部住在這裡** |
| **1** | 128 ~ 255 | ❌ ASCII 根本沒有這些編號 |

### 實際看幾個

```
'A' = 65   →   0 1 0 0 0 0 0 1
               ↑
               0（65 < 128，用不到那個「128 的格子」）

'z' = 122  →   0 1 1 1 1 0 1 0
               ↑
               0（122 還是 < 128）

DEL = 127  →   0 1 1 1 1 1 1 1   ← ASCII 的最大值！
               ↑
               0（127 = 64+32+16+8+4+2+1，把「128 以外」的格子全湊滿了）

      128  →   1 0 0 0 0 0 0 0
               ↑
               一旦這裡是 1，值就跳到 128 —— 已經不是 ASCII 了
```

> 🔑 **「ASCII 只用 7 bits」和「最高位永遠是 0」是同一句話的兩種說法。**

### 那為什麼不乾脆「只用 7 個 bit」來存？

**因為記憶體給不出「7 bit」這種空間**——門牌（地址）是配給 **byte** 的，最小單位就是 8 bit。
見 [[記憶體最小定址單位 (Byte Addressability)]]

所以實際發生的事是：

```
'A' 只需要 7 個 bit：        1 0 0 0 0 0 1
但記憶體只能給你 8 bit 的格子
        ↓ 前面補一個 0 湊滿
實際存進去：              0 1 0 0 0 0 0 1
                          ↑
                    這個 0 是「湊數」補上去的
```

**那個永遠是 0 的最高位，就是「用不滿一個 byte」留下的空位。**

---

## 2.6 那個閒置的最高位，後來怎麼了？

### 😵 第一階段：各國亂搶 → 大混亂

那個閒置的 bit 一旦拿來用，就多出 **128~255** 共 128 個空格。於是各國搶著把自己的字母塞進去：

| 標準 | 128–255 放了什麼 |
|---|---|
| Latin-1 (ISO-8859-1) | 西歐字母 `é` `ü` `ñ` `ç` |
| ISO-8859-5 | 俄文西里爾字母 |
| Big5 | 繁體中文（要用**兩個** byte） |
| GBK | 簡體中文 |
| Shift-JIS | 日文 |

**問題來了：同一個 byte `0xE9`，在 Latin-1 是 `é`，在俄文標準裡是別的字。**
👉 **檔案傳到別台電腦就變亂碼**——這就是「**萬國碼問題**」，也是你看過的所有亂碼（`ä½ å¥½`、`�`）的根源。

### ✅ 第二階段：UTF-8 出來收拾殘局

**UTF-8 的天才設計：用「最高位是不是 0」來判斷這個 byte 是什麼。**

```
byte 的最高位 = 0  →  「我是一個獨立的 ASCII 字元」  ← 直接照 ASCII 表讀
byte 的最高位 = 1  →  「我是多 byte 字元的一部分」    ← 要跟後面的 byte 一起看
```

實際編碼規則：

```
0xxxxxxx                             ← 1 byte：ASCII（0-127）
                ↑ 最高位是 0

110xxxxx 10xxxxxx                    ← 2 bytes：拉丁字母、希臘文…
1110xxxx 10xxxxxx 10xxxxxx           ← 3 bytes：中文、日文、韓文 ★
11110xxx 10xxxxxx 10xxxxxx 10xxxxxx  ← 4 bytes：emoji 😂
  ↑
最高位是 1，而且「開頭有幾個 1」就代表「這個字元共佔幾個 byte」
```

實例對照：

```
'A'  →  0100 0001                              （1 byte，最高位 0）
        ↑ 跟純 ASCII 一模一樣！

'中' →  11100100 10111000 10101101             （3 bytes = 0xE4 0xB8 0xAD）
        ↑↑↑                                     開頭 1110 → 「我共佔 3 個 byte」
             ↑↑        ↑↑                       後續 byte 都以 10 開頭 → 「我是接續的」
```

### 🎯 這個設計的三大好處

1. **完全向下相容 ASCII**——一份純英文的舊檔案，直接當 UTF-8 讀**完全正確，一個 byte 都不用改**。這是 UTF-8 能席捲全世界的關鍵。
2. **自帶長度資訊**——看第一個 byte 的開頭有幾個 `1`，就知道這個字元佔幾個 byte，不用查表。
3. **可以「自我同步」**——就算從檔案中間隨便切一刀，看到 `10xxxxxx` 就知道「我切在字元中間了」，往前退幾格就能找回字元邊界。

> 💡 **所以「ASCII 最高位永遠是 0」這個看似浪費的空位，反而成了 UTF-8 設計的地基。**
> 當年省下來的那個 bit，40 年後變成了全世界文字統一的關鍵。

## 3. 對照表（重點區段）


| 十進位        | 十六進位          | 字元                | 說明                                                       |
| ---------- | ------------- | ----------------- | -------------------------------------------------------- |
| 0–31       | `0x00`–`0x1F` | （看不見）             | **控制字元**：`\n` 換行(10)、`\r` 歸位(13)、`\t` tab(9)、`\0` 空字元(0) |
| 32         | `0x20`        | ``                | **空格**                                                   |
| 33–47      | `0x21`–`0x2F` | `!"#$%&'()*+,-./` | 標點符號                                                     |
| **48–57**  | `0x30`–`0x39` | `0`**–**`9`       | **數字**（`'0'` = 48）                                       |
| 58–64      | `0x3A`–`0x40` | `:;<=>?@`         | 標點符號                                                     |
| **65–90**  | `0x41`–`0x5A` | `A`**–**`Z`       | **大寫字母**（`'A'` = 65）                                     |
| 91–96      | `0x5B`–`0x60` | `[\]^_``          | 標點符號                                                     |
| **97–122** | `0x61`–`0x7A` | `a`**–**`z`       | **小寫字母**（`'a'` = 97）                                     |
| 123–126    | `0x7B`–`0x7E` | `{                | }~`                                                      |
| 127        | `0x7F`        | DEL               | 刪除                                                       |




### 🎯 值得背的三個數字

```
'0' = 48
'A' = 65
'a' = 97
```

**大小寫剛好差 32**（65 + 32 = 97）。而 32 = 2⁵，也就是**只差第 6 個 bit**：

```
'A' = 0100 0001  = 65
'a' = 0110 0001  = 97
        ↑
      只有這個 bit 不同！
```

> 💡 這就是為什麼「大小寫轉換」在底層只是**翻轉一個 bit**（`c ^ 32`），超級快。

## 4. 實務上你在哪裡踩過它



### JavaScript

```js
'A'.charCodeAt(0)      // 65   字元 → 數字
String.fromCharCode(65) // 'A'  數字 → 字元

// 「字元 '5' 轉成數字 5」的經典坑
'5'.charCodeAt(0)          // 53  ← 不是 5！
'5'.charCodeAt(0) - 48     // 5   ← 減掉 '0' 的 48 才對
Number('5')                // 5   ← 實務上直接用這個
```

見 [[JavaScript-字串方法]]

### Go

```go
strconv.Atoi("123")   // Atoi = ASCII to Integer ← 名字就來自 ASCII！
```

見 [[strconv-atoi]]

### 排序為什麼「大寫排在小寫前面」

因為 `'Z'` (90) < `'a'` (97)，字串比大小其實是在比 ASCII 編號：

```js
['banana', 'Apple', 'cherry'].sort()
// → ['Apple', 'banana', 'cherry']   ← 'A'(65) 贏過 'b'(98)
```



### CSS `unicode-range: U+0020-007F`

`0x20`–`0x7F` = 32–127，**就是整個 ASCII 可見字元範圍**。字型檔用它來標示「我只包含英文字元」。見 [[typography]]

## 5. ASCII 裝不下中文——所以有了 Unicode / UTF-8

128 格連英文都只是剛好，**中文有幾萬個字，根本塞不進去**。


| 編碼        | 能表示什麼               | 一個字佔幾 byte       |
| --------- | ------------------- | ---------------- |
| **ASCII** | 英文、數字、標點（128 個）     | 1 byte           |
| **UTF-8** | **全世界的文字**（Unicode） | **1～4 bytes 變動** |


**UTF-8 最聰明的設計：它「向下相容」ASCII。**

```
英文字元 'A'  → UTF-8 編成 1 byte：0x41   ← 跟 ASCII 一模一樣！
中文字 '中'   → UTF-8 編成 3 bytes：0xE4 0xB8 0xAD
```

> **一份純英文的 ASCII 檔案，直接當成 UTF-8 讀也完全正確**——這就是 UTF-8 能席捲全世界的原因（舊檔案不用改）。

這也解釋了 Go 的字串長度陷阱：

```go
s := "Hi中文"
len(s)          // 8  ← 2(英文) + 3 + 3 = byte 數！
len([]rune(s))  // 4  ← 這才是「字元數」
```

見 [[[]rune]]

**踩過的坑**：[[2025-12-31-http-header-chinese-encoding]]（HTTP Header 只允許 ASCII，中文檔名必須用 RFC 5987 編碼）

## TL;DR

1. **ASCII = American Standard Code for Information Interchange**（美國資訊交換標準碼），1963 年制定。
2. 它是一份**「字元 ↔ 數字」對照表**——電腦裡只有數字，文字得靠約定來翻譯。
3. **只用 7 bits → 0～127**（1 byte 存得下，但**最高位永遠是 0**，用不滿）。
   - **為什麼永遠是 0？** 因為最高位的「面額」是 **128**——它一旦是 1，數值就 ≥128，超出 ASCII 範圍了。這是數學必然，不是規定。
   - 記憶體只能配 byte（8 bit），配不出 7 bit，所以前面**補一個 0 湊數**。
   - **UTF-8 就是靠「最高位是不是 0」來判斷**：`0xxxxxxx` = 單獨的 ASCII 字元；`1xxxxxxx` = 多 byte 字元的一部分。**這讓 UTF-8 完全向下相容 ASCII。**
4. 三個關鍵數字：`'0'`**=48、**`'A'`**=65、**`'a'`**=97**；大小寫只差第 6 個 bit（32）。
5. **裝不下中文** → 才有 Unicode / **UTF-8**（1-4 bytes 變動長度，且**向下相容 ASCII**）。
