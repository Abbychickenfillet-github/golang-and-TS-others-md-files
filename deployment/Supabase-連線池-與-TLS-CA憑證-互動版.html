Supabase 連線池字串能不能取代 CA 憑證

主軸圖：下方「TLS 驗證伺服器身分」流程。連線池與 CA 是這張圖上兩個不同位置的事。
建立日期：2026-10-02 │ 實測對象：本專案的 Supabase 專案（Session pooler，ap-southeast-1）

一、結論：不能取代，而且實測證實了

  1. 連線池（Pooler）解決的問題是「同時有很多連線，資料庫的連線數不夠」。CA 憑證解決的問題是「我連到的真的是 Supabase 嗎」。兩者是不同層的事。
  2. 連線池字串（port 5432 或 6543 的 pooler.supabase.com）本身也走 TLS。要驗證它的身分，仍然需要 Supabase 的 CA 憑證。
  3. 我用 node-postgres 對本專案的 Session pooler 做了實測（2026-10-02）：
    設定結果
    ssl: { rejectUnauthorized: true } 且不給 CA失敗，SELF_SIGNED_CERT_IN_CHAIN
    ssl: { rejectUnauthorized: false }成功（但不驗證身分）
    原因：Supabase 的憑證鏈是 Supabase 自己的 CA 簽發，Node.js 內建的信任清單裡沒有它。
  4. 所以要嚴格驗證，只有「補上 CA 憑證」這條路。要省事就用 rejectUnauthorized: false，但那等於只加密、不驗證，無法防中間人攻擊。

二、主軸圖：TLS 驗證伺服器身分

連線池（Pooler）只影響圖中右上角「Supabase 連線池」那個方框的位置與行為（用哪個 port、是否共用連線）。菱形 C 與 D 是 TLS 的事，換任何連線池字串都不會改變。

三、連線池到底是什麼，Vercel 該選哪一種

資料庫能同時接受的連線數有上限。Serverless 函式（像 Vercel）每個實例都會自己開連線，流量一高就會超過上限。連線池就是在資料庫前面放一個代理，讓很多客戶端連線共用少數幾條真正的資料庫連線。

更正我先前的說法：我之前建議你用 Session pooler（port 5432），並說 Transaction pooler 不建議。查了 Supabase 官方文件後，對 Vercel 這類 serverless，官方建議的是 Transaction pooler（port 6543），而且 Prisma 要加 ?pgbouncer=true。Session pooler 每個客戶端佔一條持久連線，serverless 實例一多容易把池子用滿。目前專案流量小，Session pooler 可以運作，但正式上線建議換成 Transaction pooler。

換成 Transaction pooler 要改什麼

  1. DATABASE_URL 的 port 從 5432 改成 6543，後面加上 ?pgbouncer=true（給 Prisma，讓它關閉 prepared statements）。
  2. pg（node-postgres）預設只用未命名的查詢，不會用具名 prepared statements，所以 config/server.postgresql.js 不用改。
  3. prisma migrate 與 prisma db push 需要 session 狀態，要改用 Session pooler 的字串（port 5432）。這時 schema.prisma 的 datasource 要補一個 directUrl 指向 5432 的字串。

四、三種設定方式比較

方式程式碼加密驗證伺服器身分適合
a. 補 CA 並嚴格驗證ssl: { ca, rejectUnauthorized: true }是是正式環境（目前專案採用）
b. 只加密不驗證ssl: { rejectUnauthorized: false }是否快速測試
c. 不用 SSL不設 ssl否否本機 localhost 資料庫。Supabase 開了 Enforce SSL 會被拒絕
Supabase 後台的 Enforce SSL 只規定「一定要用 SSL」，相當於 PostgreSQL 的 sslmode=require，不驗證身分。官方文件的建議是開啟 Enforce SSL 時搭配 verify-full，也就是方式 a。

五、自我測驗

填空（點黃底框顯示答案）

  1. 連線池解決的是 點我，CA 憑證解決的是 點我。
  2. 對 Node.js 設 rejectUnauthorized: true 卻不給 CA，Supabase 會回錯誤碼 點我。
  3. 官方建議給 Vercel 用的連線池模式是 點我，Prisma 要加 點我。

是非題

a. 改用 Pooler 連線字串之後，就不需要 CA 憑證了。

b. rejectUnauthorized 設成 false 代表連線沒有加密。

申論題

用主軸圖的菱形 C 與 D 解釋：為什麼只換連線池字串，不補 CA 也不改設定，連線仍然會失敗？

連線池字串只改變連線的目的地（主機與 port）。連上之後 TLS 流程不變：伺服器出示憑證，客戶端在 C 檢查憑證鏈能不能追到信任的 CA。Supabase 的 CA 不在 Node.js 內建信任清單，所以 C 的答案是「不能」，接著到 D。rejectUnauthorized 為 true 就拒絕連線。要讓 C 變成「能」，必須把 Supabase 的 CA 憑證交給 pg 的 ssl.ca 選項。
