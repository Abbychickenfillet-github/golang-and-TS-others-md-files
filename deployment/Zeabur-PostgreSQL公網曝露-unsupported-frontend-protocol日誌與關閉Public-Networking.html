重點整理

一、先看對地方：Runtime Logs 不是 Deployment 歷史（a–c）

(a) 查「有沒有人偷偷部署過」要看的是 Deployments 分頁，不是 Runtime Logs。Runtime Logs 是服務執行期間的運行日誌，裡面不會有部署紀錄。

(b) 在 Zeabur 查部署歷史的步驟：點左上角 ← Back 回到該服務主頁 → 點 Deployments 分頁 → 在清單中檢查有沒有非你發起的 commit、不認識的 Git Hash、或標記為 Redeploy／Triggered manually 的時間點。

(c) 判斷「帳號是否被入侵」的關鍵證據是「有沒有你不認識的部署」，不是「有沒有奇怪的連線日誌」。連線日誌天天都有奇怪的東西，那是網際網路的常態。

二、那兩行 FATAL 到底是什麼（d–f）

(d) 看到的日誌長這樣：

FATAL: unsupported frontend protocol 27265.28208: server supports 3.0 to 3.0
FATAL: invalid length of startup packet

(e) 這是「攻擊被擋下」的紀錄，不是你程式的錯誤。PostgreSQL 前端通訊協定只支援 3.0，當外部自動化掃描器（Bot）拿隨機位元組、HTTP 請求或 TLS 握手封包來戳你的資料庫 Port，PostgreSQL 解讀出來的「協定版本」就會是 27265.28208 這種亂數，於是直接拋 FATAL 拒絕連線並關閉 session。

(f) 關鍵判讀：FATAL ＋ 連線被關閉 ＝ 對方沒進來。真正該擔心的是成功登入的紀錄（例如 connection authorized），而不是這種被拒絕的雜訊。

三、根治方法（g–i）

(g) 最有效的處置是「不要讓資料庫出現在公網上」：到 Zeabur 的資料庫設定關閉 Public Networking（對外公開的 Port 綁定），改成只用專案內網連線。沒有公網 Port 就沒有掃描流量，這比事後封鎖 IP 有效太多。

(h) 只有在你真的需要從本機用 DBeaver／HeidiSQL 連線時才需要公網 Port。這種需求應該用臨時開啟或 SSH／VPN 通道處理，不要為了方便就長期讓 5432 對全世界開著。

(i) 附帶好處：關掉公網後日誌會乾淨很多，之後再出現異常連線就真的值得查，不會淹沒在每天幾千筆的掃描雜訊裡。
